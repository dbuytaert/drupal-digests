## Summary

Drupal CMS now ships with an opt-in telemetry system that reports anonymous usage data to the Drupal CMS team via Amplitude (hosted in the EU). Admins with the "administer site configuration" permission see a small, non-intrusive corner dialog asking them to consent the first time they visit an admin page after the setting is introduced. If enabled, the site periodically reports things like: which site template or recipe was applied, which modules were installed or uninstalled after setup, a 30-day "still alive" ping, visits to a handful of specific admin pages (module updates, SEO/language checklists, webform list, recommended add-ons), creation of Canvas code components, and a one-way-hashed ID whenever a user logs in (to count unique users without identifying them). No site content, user data, or visitor data is collected. The choice can be changed at any time from Configuration > System > Site information, and documentation of exactly what is collected is published alongside the module.

## Impact

Affects site owners.

- **Config change:** New 'Send anonymous usage data' checkbox on the 'Basic site settings' form (/admin/config/system/site-information), plus a one-time opt-in dialog shown to admins, controls whether Drupal CMS sends anonymous telemetry to Amplitude. The on/off choice is stored in State, not exported configuration.

## Technical details

The feature lives entirely in the `drupal_cms_helper` module. `TelemetryManager` is the central service: `log()` queues an event (keyed by the `Telemetry` enum, e.g. `ModuleInstall`, `RecipeApplied`, `AdminPage`, `Login`) into a `drupal_cms_telemetry` queue when telemetry is enabled, and `sendAll()`, invoked from `TelemetryHooks::cron()`, drains up to 500 queued items and POSTs them to `https://api.eu.amplitude.com/2/httpapi` via Guzzle. Each batch is tagged with a device ID computed as `Crypt::hmacBase64()` of the site's UUID and hash salt, so events are correlated per-site without being personally identifiable. The opt-in/out flag is stored in `State` under the key `drupal_cms_telemetry` (not exported config); disabling it also deletes the pending queue.

`TelemetryHooks` wires up the event sources: `hook_modules_installed()`/`hook_modules_uninstalled()` (suppressed during config sync, site installation, or while a recipe is running), `hook_cron()` (the 30-day ping, which is skipped under test, preview, or CI environments as detected by the new `davereid/drupal-environment` dependency), `hook_component_presave()` for Canvas components, and `hook_user_login()` (logs an HMACed user ID using the site's private key). `RecipeSubscriber::onApply()` was extended to log `SiteTemplateInstall` versus `RecipeApplied` depending on whether a monolithic site template or an ordinary recipe was applied. The new `TelemetrySubscriber` listens on `KernelEvents::CONTROLLER` to detect visits to specific admin routes (module updates form, SEO/language checklists, webform collection, and Project Browser's "recommended" source).

The consent UI is a non-modal `<dialog>` injected via `hook_page_bottom()` using `TelemetryOptInForm`, shown only on admin routes to users with the `administer site configuration` permission who have not yet made a choice; it's styled by `telemetry.css` and opened by `telemetry.js`. The same checkbox is also exposed directly on the "Basic site settings" form via `hook_form_system_site_information_settings_alter()`. All new classes are marked `@internal`, so there is no new public API.</technical>
