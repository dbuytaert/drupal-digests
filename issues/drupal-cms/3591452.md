# #3591452: Site template with multilingual demo content only works if its intended default language is chosen by the user beforehand, otherwise breaks Canvas

- **Project:** Drupal CMS
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3591452](https://git.drupalcode.org/project/drupal_cms/-/work_items/3591452) · 1 contributor · 10 comments

## Summary

Drupal CMS site templates that ship demo content in more than one language (for example English content with Spanish translations) could silently break Canvas, because the installer lets people pick any language before they pick a template. Depending on which language was chosen during install, the original English content could be discarded instead of kept as a translation, and in some cases none of the shipped content matched the site's configured default language at all, leaving Canvas broken. Site templates can now declare which languages their demo content is shipped in and which of those is the intended default. If the language chosen during install is one the template supports, the installer imports as before but keeps the original values as a translation instead of throwing them away. If the chosen language is not one the template supports, the installer installs the site in the template's own default language so the demo content imports correctly, then adds the user's originally chosen language to the site afterwards. Templates that don't declare any languages behave exactly as before.

## Impact

Affects module maintainers.

- **New API:** New optional `languages` key (`default`, `available`) under `extra.drupal_cms_installer` in a site template's `recipe.yml`, letting it declare which languages its demo content ships in.

## Technical details

Site templates can now declare a `languages` key under `extra.drupal_cms_installer` in `recipe.yml`, with `default` (the template's own default content language) and `available` (all languages it ships translations for). The Drupal CMS installer tracks this as a `LanguagePlan` value object and exposes it via a `languages` property on `SiteTemplate`, re-applying it on every installer request since core re-derives the runtime default language from the `langcode` URL parameter each time.

When the user's chosen installer language is in the template's `available` list, the install proceeds in that language as before, but the installer now asks core to keep English (`keep_english`) when needed and an event subscriber preserves the original shipped values as a translation whenever core's `DefaultContent\Importer` swaps content into the chosen default language, so nothing shipped by the template is lost. This addresses a gap in core's own `Importer::verifyNormalizedLanguage()` behavior, described in the issue as a polyfill pending a core fix. When the chosen language isn't one the template supports, the installer instead sets the site default language to the template's declared default before recipes run, so demo content imports exactly as shipped, and adds the user's originally chosen language to the site afterwards. The configuration language lock follows the site default language (the template's default in this case), while the administrator account still gets the user's originally chosen language as its preferred language.

## Upgrade

Site templates that ship demo content in multiple languages should declare this in `recipe.yml`:

```yaml
extra:
  drupal_cms_installer:
    languages:
      default: en
      available:
        - en
        - es
```

A template must ship a `language.entity.*` config entity for every language listed in `available`, including the declared `default`. Templates that don't add this key are unaffected and keep working exactly as before.
