## Summary

An AI-assisted review of Drupal CMS's telemetry feature found the design sound: events are queued, nothing is sent until the site opts in, cron sends batches, and opting out clears the queue. A first commit fixed small problems. The opt-in event is now logged only when telemetry changes to on, not on every save of the Site information form. The queue is cleared only on opt-out. A stray `console.log()` is gone. Most other findings are still open. Telemetry is still described as "anonymous" though the review calls it pseudonymous. There is no `settings.php` switch to disable it. Amplitude batch rejections are still retried forever. Events carry no timestamp of their own. The `DRUPAL_CMS_TELEMETRY` environment variable still accepts only `0` or `1` reliably, because values like "false" are cast to true and turn telemetry on.

## Impact

No upgrade or configuration changes required.

## Technical details

The commit on the `telemetry-fixes` branch touches three places. `TelemetryManager::status()` now reads the previous state value first. Passing `FALSE` deletes the queue. Passing `TRUE` logs `Telemetry::OptIn` only when the previous value was empty, so re-saving the form with the box ticked no longer queues repeated opt-in events. In `TelemetryHooks::onModuleInstall()`, the XOR (`$is_syncing ^= RecipeRunner::isApplying()`) became `if (RecipeRunner::isApplying()) { $is_syncing = FALSE; }`. In `RecipeSubscriber`, a comment now notes that only `0` and `1` are valid for `DRUPAL_CMS_TELEMETRY`. The `(bool) $value` cast is unchanged. The `console.log(context)` was removed from the opt-in behavior in the telemetry JavaScript.

Still open per the issue body: parsing the variable with `FILTER_VALIDATE_BOOL` and checking `$_SERVER`, `$_ENV` and `getenv()`. Handling Amplitude errors by status (400: drop the listed bad events and resend the rest. 413: use a smaller batch. 401, 403, 404, 429, 5xx and network errors: keep and retry). Dropping events older than 30 days. Sending more than one batch per cron run. Recording a timestamp per event. Correcting the `sendAll()` comment. Sending custom module and recipe names as "custom" without a name. Deciding precedence between state, a possible setting and the environment variable. The login event's hashed user IDs may need a different legal basis than admin consent. The issue lists these as decisions for the product owner.

## Upgrade

Not applicable beyond the following operational note from the issue. `drush sset drupal_cms_telemetry 0` turns telemetry off but leaves queued events behind, and they are sent if telemetry is later turned back on. Any admin can also turn it back on, since state can't be deployed.
