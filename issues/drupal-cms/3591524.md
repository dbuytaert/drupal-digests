## Summary

The search form in Drupal CMS's search feature submitted to a relative `search` URL. From any page below the top level, such as `/recipes/borscht-with-pork-ribs`, it went to `/recipes/search`, which is a 404. The form now submits to the correct search page from any page, including on sites with language prefixes or installed in a subdirectory.

## Impact

No upgrade or configuration changes required.

## Technical details

The search view had been changed from a page display to a block display ([#3591455](https://www.drupal.org/node/3591455)), with `link_display: custom_url` and `link_url: search`. A block display has no route, so `ViewExecutable::hasUrl()` returns FALSE and `ViewsExposedForm::buildForm()` falls back to `getPath()` on the display handler. That returns the `link_url` value unchanged, so it becomes the form action without a base path or language prefix.

The shipped fix changes the view config to `link_url: /search`. It also adds a `form_views_exposed_form_alter` hook, `FormHooks::alterViewsExposedForm()`, which rewrites a `#action` that starts with `/` using `Url::fromUri('base:' . $form['#action'])->toString()`. This adds the base path and language handling that Views skips. It is a workaround, marked with a `@todo` to remove it once the upstream fix in https://www.drupal.org/i/3638040 is released. `ComponentValidationTest` now enables `drupal_cms_helper` so the test environment includes the polyfill.
