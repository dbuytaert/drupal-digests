# #3585933: Authorization denials surface as -32603 Internal server error, because the SDK dispatch loop swallows the exception

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Version:** 2.x-dev
- **Status:** Fixed
- **Discussion:** [#3585933](https://git.drupalcode.org/project/mcp_server/-/work_items/3585933) · 1 contributor · 18 comments

## Summary

Per-call authorization denials thrown from an SDK `RequestEvent` subscriber never produced a 401 or 403. The SDK's per-message guard turned them into an HTTP 200 with JSON-RPC `-32603 Internal server error` and an error-level log entry. The fix does not make that path work. It removes the handling that could never run and states the supported route: authorization belongs in a PSR-15 transport middleware, which answers a denial with its own 401 or 403 response before the SDK dispatches. Custom authorization code, and `mcp_server_oauth` 1.0.0-alpha1 (which still throws the exception), cannot deny calls this way. That code needs to move to middleware.

## Impact

Affects module maintainers.

- **API change:** `McpServerController`, `McpExceptionSubscriber` and the `drush mcp:server` command no longer catch or translate `McpAuthorizationDeniedException`; `McpExceptionSubscriber` drops its logger constructor argument.
- **Deprecation:** `Drupal\mcp_server\Exception\McpAuthorizationDeniedException` is deprecated in mcp_server:2.0.0-beta6 and removed in 3.0.0.

## Technical details

The exception is thrown inside `Protocol::doProcessInput()`'s `catch (\Throwable)` guard, so the controller `catch` and `McpExceptionSubscriber` could not be reached. Of the three options in the issue, the merged change picks neither out-of-band signalling nor an SDK change. It deletes the dead code and points to the existing `mcp_server.transport_middleware` tag, where a middleware returns its own PSR-7 response without entering SDK dispatch or the kernel exception path.

Removed: the `McpAuthorizationDeniedException` catch in `McpServerController::handle()`, the matching catch and JSON-RPC error writing in `McpServerCommands`, and the exception branch in `McpExceptionSubscriber::onException()`. That subscriber now only rewrites the route-level `AccessDeniedHttpException` (`access mcp server`) into `-32001`/`-32002` with 401/403, and its `@logger.channel.mcp_server` argument was dropped from `mcp_server.exception_subscriber` in `mcp_server.services.yml`. The exception class stays, marked `@deprecated`, only because `mcp_server_oauth` 1.0.0-alpha1 still throws it.

The change adds a test fixture, `StateArmedDenyingMiddleware` in `mcp_server_test`, which denies `tools/call` with 401 or 403 when armed through State. It also adds `TransportMiddlewareDenialTest`, and the README authorization section and the `.ai/kenkeep` notes now describe the middleware route. The kenkeep note also records that on SDK releases with php-sdk#528 the throw would escape to core as a 500 rather than `-32603`, so throwing from a subscriber cannot deny a call either way.

## Upgrade

Replace a `RequestEvent` subscriber that throws `McpAuthorizationDeniedException` with a PSR-15 middleware registered under the existing tag, which returns the denial itself:

```yaml
services:
  mcp_server_test.middleware.denying:
    class: Drupal\mcp_server_test\Middleware\StateArmedDenyingMiddleware
    tags:
      - { name: mcp_server.transport_middleware, priority: 50 }
```

In `process()`, return a PSR-7 response with status 401 or 403, JSON-RPC error code `-32001` or `-32002`, and a `WWW-Authenticate` header, instead of calling `$handler->handle($request)`. The test fixture `StateArmedDenyingMiddleware` shows the full pattern.
