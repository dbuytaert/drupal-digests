## Summary

The MCP Server module's tool administration UI is being reworked: instead of manually creating a config entity for every tool you want to expose, all discovered Tool plugins and their individual tools are listed automatically under Configuration > Services > MCP Server > Tools. Admins browse plugins, open a plugin's tool list, and simply check "Enabled" per tool (optionally overriding its exposed name/description and setting per-tool authentication/OAuth scopes); the underlying configuration entity is created, updated, or removed for you on save. The separate "Add tool" form and its autocomplete lookup are gone. Alongside the UI change, the MR also migrates three concrete Tool plugins onto this plugin-based system: a general site-info tool, a content search tool, and a Drush-command-runner tool, all previously part of the older `mcp` module.

## Impact

Affects module maintainers.

- **API change:** The `entity.mcp_tool_config.add_form`, `edit_form`, `delete_form` routes and the `mcp_server.tool_autocomplete` route/controller are removed; tool management now goes through the new `mcp_server.tool_plugins` and `mcp_server.plugin_tools` routes.

## Technical details

The old entity-form based workflow (`McpToolConfigForm` with add/edit/delete routes plus `ToolAutocompleteController` for picking a `plugin_id:tool_name`) is replaced by `ToolPluginListController::list()`, which renders a table of every `ToolPluginManager::getDefinitions()` entry with an "N of M enabled" count and a link into `mcp_server.plugin_tools`. That route is backed by `PluginToolsForm`, which lays out every tool from one plugin in vertical tabs: an `enabled` checkbox, an editable MCP name (validated for global uniqueness across plugins), a custom description, `authentication_mode` (`required`/`optional`/`disabled`), and OAuth `scopes`. `PluginToolsForm::submitForm()` creates or updates the matching `McpToolConfig` entity (machine id generated via `generateUniqueMachineId()`) when a tool is enabled, or deletes it when disabled, so the config entity's structure and storage are unchanged (per the issue, "data model changes: none"); only how entities get created changes. `McpToolConfig`'s annotation drops its `form` handlers and `links` block accordingly, and `mcp_server.links.task.yml`/`links.action.yml` point the "Tools" local task at the new `mcp_server.tool_plugins` route instead of the entity collection.

The MR also adds three `#[Tool]`-attributed plugins under `src/Plugin/Tool/`: `General`, `Content` (a `search_content` tool that builds a `node` entity query from arbitrary field filters/operators, enforcing `accessCheck(TRUE)` and restricting filterable/returned fields via `isSupportedField()`), and `DrushCaller` (discovers available Drush commands via `drush list --format=json` and executes them through Symfony `Process`, building each command's `inputSchema` from Drush's own argument/option metadata). These are plugins only; a tool is still not exposed over MCP until an admin explicitly enables it through the new UI, which also governs its authentication mode and scopes. A new `mcp_server/admin` library/CSS file supplies the table, pill, and badge styling used by both the plugin list and per-plugin tool forms.

## Upgrade

This issue's merge request has not landed yet; once merged, existing `mcp_tool_config` entities keep working without migration. Any custom code or links pointing at the removed routes needs to change:

```yaml
# Before
entity.mcp_tool_config.add_form
entity.mcp_tool_config.edit_form
entity.mcp_tool_config.delete_form
mcp_server.tool_autocomplete

# After
mcp_server.tool_plugins        # /admin/config/services/mcp-server/tools
mcp_server.plugin_tools        # /admin/config/services/mcp-server/tools/{plugin_id}
```
