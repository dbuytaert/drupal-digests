# #3585879: Use a lock for sessions to handle concurrency issue with session data

## Summary

The MCP Server module's HTTP controller now serializes concurrent requests that belong to the same MCP session, preventing session data corruption. Previously, if two requests for the same `Mcp-Session-Id` arrived at once (for example, two tool calls in flight at the same time), each worker could read stale session state and overwrite the other's changes when saving, silently corrupting the session's protocol state. Sites using the MCP Server module with concurrent clients will now see occasional brief waits, or in the worst case a `503 Service Unavailable` response with a `Retry-After` header, instead of silent data corruption.

## Impact

No upgrade or configuration changes required.

## Technical details

The underlying issue traces to the PHP MCP SDK (see modelcontextprotocol/php-sdk#275), which stores protocol state (outgoing queue, request counter, pending requests) in a shared session blob using an unlocked read-modify-write pattern. `McpServerController::handle()` now derives a lock name from the request's `Mcp-Session-Id` header, hashed with `hash('sha256', ...)` to keep the lock key bounded and safe regardless of client-supplied header content, and stored under the `mcp_session:` prefix.

Before invoking `$server->run($transport)`, the controller attempts `$this->lock->acquire($lock_name)`; on failure it calls `$this->lock->wait($lock_name)` and retries once, throwing a `ServiceUnavailableHttpException` (with `retryAfter: 1`) if the lock still cannot be obtained. The lock is released in a `finally` block via `$this->lock->release($lock_name)`. Requests without a session ID (such as `initialize`) skip locking entirely since there is no shared state yet to protect. The lock is injected via the new `LockBackendInterface $lock` constructor parameter, wired to Drupal's core `lock` service in `create()`.

Note that this initial implementation released the lock as soon as `$server->run()` returned, which was not correct for streamed (SSE) responses that continue writing after that point; this was addressed separately in [#3585923](https://www.drupal.org/node/3585923).
