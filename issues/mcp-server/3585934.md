# #3585934: Resource access denials return -32603 because the SDK's ReadResourceHandler swallows the exception

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3585934](https://git.drupalcode.org/project/mcp_server/-/work_items/3585934) · 1 contributor · 9 comments

## Summary

Before this fix, when an MCP client called `resources/read` for a resource it wasn't allowed to access, the site answered with HTTP 200 and a generic JSON-RPC `-32603` internal error saying "Error while reading resource," giving the client no indication that access was actually denied, and logging a spurious error for what is really a routine permission check. Now a denied read answers the same way a request for a nonexistent resource does: a `-32002` (or `-32602` on newer protocol versions) "resource not found" error. This intentionally doesn't reveal that the resource exists at all, matching how the rest of MCP handles resources a client can't see.

## Impact

Affects module maintainers.

- **API change:** `ResourceContentCache::generate()` now throws `Mcp\Exception\ResourceNotFoundException` instead of `Drupal\mcp_server\Exception\McpAuthorizationDeniedException` for a denied resource access check, and for the same exception (previously a plain `\RuntimeException`) when the content callback returns `NULL`.

## Technical details

The root cause is that the php-sdk's `ReadResourceHandler` catches any `\Throwable` it doesn't specifically recognize and converts it into a generic `-32603` internal error, logging it at error level. `ResourceContentCache::generate()`, which both `ResourceProviderHandler` and `ResourceTemplateProviderHandler` delegate to for the access check plus cache lookup, was throwing `Drupal\mcp_server\Exception\McpAuthorizationDeniedException` on a denied `checkAccess()`, which the SDK doesn't know how to map, so it fell into that generic path.

The fix changes `ResourceContentCache::generate()` to throw `Mcp\Exception\ResourceNotFoundException` in that case instead, which the SDK does recognize and maps to a proper resource-not-found JSON-RPC error. The same exception is now also thrown when the content callback returns `NULL` (previously a plain `\RuntimeException`), so a denied read and a missing resource are indistinguishable to the client by design, avoiding disclosure that a forbidden resource exists. `McpAuthorizationDeniedException` itself is untouched and still used for OAuth-scope related failures elsewhere (`McpServerController`, `McpExceptionSubscriber`, Drush commands); only the resource-read path stopped using it. A new kernel test, `ResourceReadErrorTest`, exercises this through the actual `/mcp` endpoint and asserts a denied read and a missing read produce identical error payloads. `ResourceProviderRegistrationTest` was updated to expect `ResourceNotFoundException` for both the forbidden and missing cases. The SDK still logs both cases at error level; a quieter log level needs an upstream fix, tracked at https://github.com/modelcontextprotocol/php-sdk/issues/513.

## Upgrade

If custom code catches the exception thrown by `ResourceContentCache::generate()` for a denied resource read, update it:

```php
// Before
catch (\Drupal\mcp_server\Exception\McpAuthorizationDeniedException $e) {
  // ...
}

// After
catch (\Mcp\Exception\ResourceNotFoundException $e) {
  // $e->uri holds the requested URI.
}
```

A `NULL` return from a resource plugin's content callback now also throws `Mcp\Exception\ResourceNotFoundException` instead of a plain `\RuntimeException`.
