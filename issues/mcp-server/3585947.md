# #3585947: Multi-round elicitation fails on protocol 2026-07-28 without a request state signing key

- **Project:** Drupal AI
- **Type:** Major bug report
- **Version:** 2.x-dev
- **Status:** Fixed
- **Discussion:** [#3585947](https://git.drupalcode.org/project/mcp_server/-/work_items/3585947) · 1 contributor · 10 comments

## Summary

On MCP protocol `2026-07-28`, a tool that asks the client more than one question in a single `tools/call` used to fail on the second question with a "could not carry its own state" internal error. The module now signs the state that carries earlier answers between rounds, so multi-round elicitation works. No new setting is needed. Tools that elicit only once were not affected.

## Impact

No upgrade or configuration changes required.

## Technical details

Under `2026-07-28` there are no server-to-client requests. `ClientGateway::elicit()` ends the call with an `InputRequiredResult`, the client resends the whole call, and the tool reruns from the top. Earlier answers travel in a signed `requestState`. The SDK needs an HMAC key from `Builder::setRequestState()`, which `McpServerFactory` never called.

`McpServerFactory` now takes `@private_key` as a new last constructor argument (`mcp_server.services.yml` is updated). It calls `$builder->setRequestState()` with `Crypt::hmacBase64('mcp_server.request_state', $this->privateKey->get() . Settings::getHashSalt())`. This is the same derivation style as core's `CsrfTokenGenerator`. The key comes from secrets shared across web heads, so a retry can land on any of them. The call is wrapped in `method_exists($builder, 'setRequestState')`, because `mcp/sdk` 0.7 predates this protocol version and has no such method.

Rotating the private key or hash salt only invalidates multi-round calls in progress. The issue cites the SDK's 10-minute TTL for this state. The commit adds a fixture tool, `ElicitingTwiceTool`, and a `2026-07-28` `tools/call` test in `McpServerFunctionalTest` that answers both rounds.
