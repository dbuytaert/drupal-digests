# #3585940: The answer to an elicitation waits 30 seconds for the session lock over HTTP

- **Project:** Drupal AI
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3585940](https://git.drupalcode.org/project/mcp_server/-/work_items/3585940) · 1 contributor · 3 comments

## Summary

Sites running the MCP Server module's HTTP transport could see a tool that asks the connecting AI client a question (via elicitation) take 30 seconds longer than necessary to resume, even when the client answered within a couple of seconds. The delay came from an internal session lock, not from the client or network, so nothing a site owner configured could work around it. The fix removes this artificial wait so elicitation answers are picked up as soon as they arrive.

## Impact

No upgrade or configuration changes required.

## Technical details

`McpServerController::handle()` takes a `mcp_session:`-prefixed lock for the duration of the request and, for streamed (SSE) responses, only releases it once the stream ends, as established by the earlier fix for [#3585923](https://www.drupal.org/node/3585923). When a tool calls `ClientGateway::elicit()`, the SDK suspends the handler's fiber and keeps that first request's SSE connection open while it polls the session store for the client's reply, which arrives as a second POST on the same `Mcp-Session-Id`. That second request calls into `LockBackendInterface::wait()` and blocks until the first request's lock lease expires, 30 seconds by default, so an answer submitted in two seconds is not read until the 30 second mark, and once the lease does expire both requests can end up writing the session at the same time.

The issue lays out two candidate fixes: skip acquiring the lock at all for a POST whose body contains only JSON-RPC responses (as opposed to a request that can itself trigger new elicitation), or release the lock while the handling fiber is suspended waiting on an elicitation answer and reacquire it when the handler resumes. No merge request or commit was available to confirm which approach was ultimately implemented, so the end-state mechanics above reflect the proposed resolution from the issue rather than a verified diff.
