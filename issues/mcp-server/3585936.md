# #3585936: ProtocolVersionMiddleware registered as a custom transport middleware rejects clients on protocol 2026-07-28

- **Project:** Drupal AI
- **Type:** Major bug report
- **Version:** 2.x-dev
- **Status:** Fixed
- **Discussion:** [#3585936](https://git.drupalcode.org/project/mcp_server/-/work_items/3585936) · 1 contributor · 5 comments

## Summary

On mcp_server 2.x with mcp/sdk 0.8 or later, any MCP client request carrying the `MCP-Protocol-Version: 2026-07-28` header was rejected with HTTP 400 (error `-32022 Unsupported protocol version`), and a client that only speaks that era could not connect to the server at all. The SDK also logged a warning on every single HTTP request complaining about the module's middleware setup. This is fixed: clients using the 2026-07-28 protocol era now connect and work normally, and the spurious warnings are gone. Sites still running mcp/sdk 0.7 are unaffected and keep the previous behavior.

## Impact

No upgrade or configuration changes required.

## Technical details

The root cause was that `mcp_server.services.yml` registered the SDK's `ProtocolVersionMiddleware` as a custom transport middleware (`mcp_server.middleware.protocol_version`), running at the edge of every request before the SDK's transport had decided which protocol era the request belonged to. That made sense on mcp/sdk 0.7, which validates the header itself nowhere else, but from mcp/sdk 0.8 `StreamableHttpTransport` applies the same check internally, scoped to handshake-era requests only, so the module's copy became redundant and, because it runs unconditionally, actively rejected the newer era it didn't know about.

The fix removes the service dynamically rather than editing the static YAML: `McpServerServiceProvider::alter()` now checks `method_exists(StreamableHttpTransport::class, 'handshakeMiddleware')` and, when true (sdk >= 0.8), calls `$container->removeDefinition('mcp_server.middleware.protocol_version')`. This keeps a single codebase working across both the 0.7 and 0.8 SDK generations: on 0.7 the custom middleware stays registered and still guards the handshake; on 0.8+ the SDK's own handshake-scoped check takes over. Coverage was added in `ProtocolVersionTest` (a 2026-07-28 request now reaches the SDK and is served, while an unknown version header still gets `-32022`), and `TransportMiddlewareCollectorTest` was updated to assert the middleware list is empty of `ProtocolVersionMiddleware` on sdk 0.8+.
