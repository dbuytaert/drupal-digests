# #3585917: Tool call responses are silently dropped when the handler renders anything (fiber suspension misread as scheduling protocol)

- **Project:** Drupal AI
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3585917](https://git.drupalcode.org/project/mcp_server/-/work_items/3585917) · 1 contributor · 9 comments

## Summary

In the MCP Server module, a `tools/call` (and `prompts/get`, `resources/read`, `completion/complete`) request whose handler rendered markup or loaded an entity could complete its work successfully but never send a response back to the client. The client would see nothing, and could wrongly retry the call (creating a duplicate) or assume the operation had failed when it had actually succeeded. This is now fixed: any handler that triggers Drupal's own internal suspension mechanics (rendering, entity loading, theme registry lookups) returns its result normally instead of silently dropping it.

## Impact

No upgrade or configuration changes required.

## Technical details

The MCP PHP SDK dispatches each request inside a PHP `Fiber` and interprets any `Fiber::suspend()` call from within the handler as a `ClientGateway` operation addressed back to the client (for example, a sampling request). Drupal 10.3+'s own internals use the same mechanism for unrelated purposes: the renderer and `EntityStorageBase::loadMultiple()` suspend with `FiberResumeType::Immediate` while resolving placeholders, and the theme registry suspends with no payload on a cold cache. When a tool handler triggered one of these, the SDK misread it as its own scheduling protocol, logged `Fiber yielded unexpected payload`, and answered the request as `text/event-stream` instead of `application/json`, so a JSON-only client never saw the result.

The fix adds `Drupal\mcp_server\Capability\FiberShield`, which runs the handler in its own inner fiber. It inspects each suspended payload: if it's an array with a `type` key (a genuine `ClientGateway` operation), it's re-yielded up to the SDK and the reply is passed back down; anything else (Drupal's internal suspends) is resumed immediately in place, exactly as Drupal's synchronous render path already does. `ShieldedReferenceHandler` wraps the SDK's `ReferenceHandler` to cover `tools/call`, `prompts/get`, and `resources/read`, which all flow through it, and `ShieldedCompletionProvider` wraps each argument-completion provider individually because `completion/complete` is dispatched directly by the SDK rather than through the reference handler. `McpServerFactory` wires both decorators in. The issue notes upstream declined to fix this in the SDK itself (`php-sdk#505`), so the module shields its own dispatch paths instead.
