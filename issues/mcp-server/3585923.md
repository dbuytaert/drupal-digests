# #3585923: Session lock is released before streamed (SSE) responses finish

- **Project:** Drupal AI
- **Type:** Major bug report
- **Version:** 2.x-dev
- **Status:** Fixed
- **Discussion:** [#3585923](https://git.drupalcode.org/project/mcp_server/-/work_items/3585923) · 1 contributor · 6 comments

## Summary

MCP Server's per-session lock, introduced to stop two requests from touching the same session at once, was being released too early for streamed (SSE) responses. Because the SDK does its actual work later, while the response is being sent, a second request could sneak in and read or write session state while the first request was still streaming. On PostgreSQL sites using the database lock backend this also produced a nastier symptom: a tool that opened a database transaction and then suspended could have its later rollback resurrect the just-deleted lock row, forcing the next request on that session to wait out the entire lock lease and hit client-side timeouts. This is fixed so the lock is now held for the full duration of the streamed response.

## Impact

Affects site owners.

- **Security:** Session lock could be released while an SSE (streamed) response was still running, letting a concurrent request read or write the same MCP session's state.

## Technical details

The fix is in `McpServerController::handle()`. Previously the lock release lived only in the method's `finally` block, which runs as soon as the controller returns, before a `StreamedResponse`'s callback has actually executed. Now, when the transport's PSR response body is not seekable (the SSE path), the controller wraps the `StreamedResponse`'s existing callback in a new closure that calls the original callback and releases `$lock_name` in its own `finally`, so the lock lives until the SDK's Fiber-driven stream actually completes or throws. A new `$release_lock` flag tells the controller's outer `finally` to skip releasing the lock itself in that case, since the wrapped callback now owns that responsibility. Non-streamed responses and exceptions thrown before a response is produced still release the lock the old way. If a streamed response is constructed but never sent, its callback never runs and thus never releases the lock explicitly. That case relies on `LockBackendInterface::releaseAll()`, which `DatabaseLockBackend` registers as a shutdown function, as covered by the new `testUnsentStreamedResponseLockIsFreedByReleaseAll` kernel test. A companion test, `testStreamedResponseHoldsSessionLockUntilSent`, drives a tool that suspends inside a Fiber and a real `DatabaseLockBackend`, asserting the lock is still held after the controller returns and only released once `$response->sendContent()` finishes.
