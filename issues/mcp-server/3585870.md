# #3585870: Tool definition from the plugin deriver all have the same label ("Tool API")

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Version:** 2.x-dev
- **Status:** Fixed
- **Discussion:** [#3585870](https://git.drupalcode.org/project/mcp_server/-/work_items/3585870) · 1 contributor · 13 comments

## Summary

In the MCP Server module, a Tool plugin can use a deriver to expose several dynamic tools from one class, for example the Tool API bridge exposing each configured Tool API tool as its own MCP tool. Previously every one of those derived tools showed the same label, "Tool API", because the deriver had no way to give each derivative its own name; it just inherited the base plugin's label. Now a deriver must supply a distinct label for each derivative, so clients see the actual name of each tool instead of a single repeated generic label.

## Impact

Affects module maintainers.

- **API change:** `ToolDefinition::withDerivative()` now requires a `label` argument for each derivative, and `description` must be a `TranslatableMarkup` (no longer accepts a raw string).

## Technical details

The bug was in `ToolDefinition::withDerivative()`: the clone it built always reused `$this->label` from the base definition, with no parameter to override it, while other fields like `description` and `inputSchema` could already be overridden per derivative. The fix adds a required `TranslatableMarkup $label` parameter, since (per the updated docblock) "the base label names the family of tools, never one derivative, so each derivative names itself," matching how core's block and local task derivers behave.

While changing the signature, the method was also generalized: `outputSchema`, `readOnly`, and `idempotent` are now overridable per derivative too (previously only `description`, `inputSchema`, and `destructive` were), and every optional parameter uniformly uses "`NULL` keeps the base value" instead of `withDerivative()` special-casing `description`'s type. The `description` parameter's type also narrowed from `TranslatableMarkup|string|null` to `?TranslatableMarkup`; a deriver that builds a description from config text is now expected to wrap it itself with `new TranslatableMarkup('@text', ['@text' => $text])` so config values are never accidentally used as translation source strings. Coverage for the new `withDerivative()` contract lives in `ToolDefinitionTest`.

## Upgrade

Any deriver calling `ToolDefinition::withDerivative()` must pass a `label` argument, and pass `description` as a `TranslatableMarkup` (wrap raw/config text yourself):

```php
$base->withDerivative(
  derivativeId: $id,
  label: $record_label,
  toolId: $tool_id,
  mcpToolConfigId: $id,
  description: $description,
  inputSchema: $input_schema,
  outputSchema: $output_schema,
  readOnly: !$operation->isModifying(),
  destructive: $is_destructive,
  idempotent: $operation->isIdempotent(),
);
```
