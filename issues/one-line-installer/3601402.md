## Summary

When a config sets `is_drupal: false` and names no `launch_path`, the installer no longer opens a browser at the end of the run. Before, it opened the empty docroot, which returned a 403, right under the 'Your project is ready' message. The final summary also stops suggesting `ddev launch` in that case. Drupal builds, and non-Drupal builds that set a launch path such as `:6006`, behave as before.

## Impact

Affects site owners.

- **Config change:** `launch_path` empty with `is_drupal: false` (and no `LAUNCH_PATH` in `.ddev/.env`) now means no browser launch instead of opening the project root.

## Technical details

`step_launch_site` was the only step that never consulted `IS_DRUPAL`. A new helper, `_launch_site_has_target` in `launch_site.sh`, returns true when `IS_DRUPAL` is `true` (or unset) or when `_resolve_launch_path` returns a non-empty value. `_resolve_launch_path` already prefers a `LAUNCH_PATH` line in `.ddev/.env` over the config value, so a hook that writes that line still triggers the launch. An empty-valued `.env` line counts as no target.

When there is no target, `step_launch_site` prints `is_drupal=false and no launch_path — nothing to open.` and returns 0, so the pipeline continues to `agent_handoff`. `print_welcome` calls the same helper. In the no-target case it omits the `ddev launch` handy-command line and the 'run ddev launch' next step. If an agent is configured, it prints 'start building with ddev <agent>' instead. The issue's alternative of an explicit `launch: false` key was not implemented. Docs (`AGENTS.md`-style config reference and the `launch_path` table entry) and bats tests were updated.
