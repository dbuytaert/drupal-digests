# #3586619: Hide context items and usage records from JSON:API

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3586619](https://git.drupalcode.org/project/ai_context/-/work_items/3586619) · 1 contributor · 13 comments

## Summary

In AI Context (CCC) 1.0.0, context items and usage records are no longer available through core JSON:API. Before, a site that enabled JSON:API let every account with **Use Published AI Context in AI Features** page through all published context items over HTTP and read their raw fields, without the CCC delivery rules and without usage being recorded. Sites that read or synced items through JSON:API (for example with Entity Share) lose that access, and 1.0.0 has no supported replacement. Run `drush cr` after updating, because the resources stay available until caches are rebuilt. Core REST can still be enabled on purpose for context items, but no longer offers usage records. If you enabled a REST resource for usage records, delete it before rebuilding the router.

## Impact

Affects site owners.

- **Security:** Removes a bulk JSON:API read path that let any account with **Use Published AI Context in AI Features** page through all published context items with raw fields, bypassing CCC delivery rules.
- **Config change:** A site that enabled a core REST resource for usage records must delete `rest.resource.entity.ai_context_usage` before `drush cr` or `drush updatedb`, or the router rebuild fails.

## Technical details

`ai_context_usage` now has `internal = TRUE` in its `@ContentEntityType` annotation, so JSON:API, core REST discovery and other integrations that skip internal entity types ignore it. A side effect noted in the release note is that Workspaces now ignores usage records, so usage is also recorded while a non-default workspace is active.

`ai_context_item` is deliberately not marked internal, because Content Moderation and Workspaces skip internal entity types and the flag would remove the editorial workflow and moderation transition access checks. Instead, a new `@internal` subscriber, `AiContextJsonApiResourceTypeSubscriber` (registered as `ai_context.jsonapi_resource_type_subscriber`), listens to the string event name `jsonapi.resource_type.build` at priority 1000 and calls `disableResourceType()` for resource types whose name starts with `ai_context_item--`. Using the string event name means it works when JSON:API is not installed. No post-update is added; `drush cr` rebuilds the container, entity type definitions and JSON:API resource types.

A kernel test, `AiContextEntityExposureTest`, checks that with JSON:API enabled both resource types are internal and the `user` type is not, and that items keep the `moderation` handler. Docs changed in `access-boundaries.md` (new "Generic entity APIs" section and updated permission titles), `api-stability.md` (output of generic entity APIs such as core REST or the serializer is not public API; the scope field section is renamed "normalized shape") and `configuration.md`. The issue plans an opt-in for context items later ([#3586600](https://www.drupal.org/node/3586600)), which would need a dedicated read permission ([#3586357](https://www.drupal.org/node/3586357)).

## Upgrade

After updating, rebuild caches so the container and JSON:API resource types pick up the change:

```bash
drush cr
```

If the site enabled a core REST resource for usage records, delete it first, before `drush cr` or `drush updatedb`, and remove it from config sync:

```bash
drush config:delete rest.resource.entity.ai_context_usage
```

Also remove `rest.resource.entity.ai_context_usage.yml` from the config sync directory. Otherwise the router rebuild fails because the REST plugin for usage records no longer exists.
