# #3586541: Make duplicate consumer_id rows resolve consistently and map validator errors to the right row

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3586541](https://git.drupalcode.org/project/ai_context/-/work_items/3586541) · 1 contributor · 14 comments

## Summary

If a duplicated `consumer_id` row gets into `ai_context.consumers` (through `drush config:set`, custom code, or a database edit, since the UI cannot create one), AI Context now treats the first row as the real one everywhere. Before, the consumers listing showed the last row while runtime used the first, so the listing could show push off while content was still pushed. Saving any consumer no longer fails because of an unrelated duplicate. The editor drops the later repeats and shows a warning. Removing a consumer now deletes every row with that ID.

## Impact

No upgrade or configuration changes required.

## Technical details

The first row wins in the consumers listing (`AiContextConsumersForm`), runtime resolution, the consumer editor and the validator message. This matches `AiContextSelectionFactory::loadConsumerConfig()` and update 10028, which already used the first match.

`AiContextConsumerConfigValidator` reports the duplicate violation on the later row. The message now reads `Duplicate consumer ID "%s". Row %s already uses it and is the row that takes effect.` A third repeat is measured against the first row.

`AiContextConsumerForm` removes later repeats from the whole consumer list on save, keeping each ID's first row. After a successful save it logs a warning to the `ai_context` channel and shows a status warning naming the de-duplicated IDs. A second save shows no warning. The remove form deletes every row with the ID, following `AiContextScopeCleanupService::removeConfigListRow()`. `docs/developers/consumer_api.md` now documents that `consumer_id` is unique, which row wins, de-duplication on save, and full removal.

A non-duplicate violation on an unrelated row, such as `max_tokens` below the schema minimum, still blocks every consumer save. The issue lists this as out of scope. I read the merged code in the repo but did not have a diff for this issue.
