## Summary

Subcontext children are now checked before they are delivered with a selected parent. Previously a child with its own scope, for example Roles = Editor, was delivered to every account that received the parent. Children the current user cannot view, or whose delivered translation is not published, were also delivered. This affected the selector path, the Load tool, and the conditional decision prompt sent to the AI provider. Children that fail the checks are now dropped, and they are no longer sent to the provider. Sites that relied on a custom-scope child reaching users outside its scope must change that child's scope.

## Impact

Affects module maintainers and site owners.

- **Security:** Closes an access leak where subcontext children with their own scope, denied view access, or unpublished delivered translations were delivered with the parent and sent to the AI provider.
- **New API:** `AiContextSubcontextResolver::resolve()` accepts optional `$langcode` and `$cacheability` arguments.

## Technical details

The cause was that `AiContextSubcontextResolver::batchLoadChildren()` uses `accessCheck(TRUE)`, which does nothing for this entity type because context items have no query access handler. The published query also matches a child when any translation is published. The fix adds a private `filterDeliverableChildren()` step in `resolve()`, run before any conditional AI decision. For each child it takes the translation the caller will deliver (`AiContextLanguageService::translateItem()`). It drops the child if that translation is unpublished, then if `access('view')` is not allowed. The publication check comes first because administrators, accounts with the unpublished-view permission, and owners pass the view check on a draft. A loop is used instead of `translateItems()` because that method checks access as a boolean and would lose the access cacheability.

Children with their own scope (`inheritsParentScope()` is FALSE) are then passed through `AiContextScopeResolverInterface::filterByRequestContext()`. Children that inherit the parent scope are not re-filtered, because the parent was already selected, including through Always include or Load. A child in the Always include list skips hard filters but still needs view access. The Load tool has no Always include list, so it hard-filters every own-scope child.

`resolve()` gains optional `?string $langcode` and `?CacheableMetadata $cacheability` parameters. When `$langcode` is NULL it is detected. `AiContextSelector` passes the detected language and its cache metadata, so child access results merge into the selection result. `LoadAiContextItemById` passes its language. The language is added to the conditional decision cache key, so decisions differ per language. The service definition gains `@ai_context.scope_resolver` and `@ai_context.language_service` constructor arguments. Docs in `docs/features/subcontext.md` were updated.

## Upgrade

If you construct `AiContextSubcontextResolver` manually (the service definition is updated), pass two new constructor arguments after the provider config resolver: `AiContextScopeResolverInterface $scopeResolver` and `AiContextLanguageService $languageService`. Callers of `resolve()` can optionally pass a language code and a `CacheableMetadata` accumulator:

```php
$resolver->resolve($parents, $always_include, $never_include, $task, $langcode, $cache_metadata);
```
