## Summary

The AI Context items listing page now keeps all of its cache metadata. Before, parts of it were overwritten, so the list cache tag and the per-user cache contexts were dropped. On a default site this changes nothing, because admin routes are not stored in Dynamic Page Cache. It matters only if a site or later change makes this page cacheable. In that case, a new item might not show until caches were cleared, and on older Drupal core versions another user could be served the owner's Draft rows.

## Impact

No upgrade or configuration changes required.

## Technical details

`AiContextItemListBuilder` used `CacheableMetadata::applyTo()`, which assigns `#cache` instead of merging it. In `render()`, the settings config metadata overwrote the `ai_context_item_list` tag that core's `EntityListBuilder::render()` puts on `$build['table']`. The view-access metadata (`listAccessCacheability`) was then overwritten by `scopeLabelCacheability`, so the `user` context and the tags of hidden items were lost. The same pattern was in the settings-access code and in the tooltip helper that writes `#cache` on the child label cell.

Each call site now starts from `CacheableMetadata::createFromRenderArray($build)` (or `$build['table']`), adds the extra metadata with `addCacheableDependency()`, and applies the result once. Two kernel tests were added: `testTableKeepsTheCoreListCacheTag` and `testViewAccessAndScopeLabelMetadataBothSurvive`. The second checks that the `user` context, the hidden Draft's tag and the table tags are all present, and that another user's Draft is not in the rows. The issue notes that `$build['#empty']` never renders; that was split out to [#3586692](https://www.drupal.org/node/3586692) and is not part of this change.
