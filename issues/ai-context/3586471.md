# #3586471: Fix CCC scope index, stored-value cleanup, and request matching

- **Project:** Drupal AI
- **Type:** Major bug report
- **Status:** Fixed
- **Discussion:** [#3586471](https://git.drupalcode.org/project/ai_context/-/work_items/3586471) · 1 contributor · 48 comments

## Summary

Several scope-data bugs in AI Context are fixed. Saving a draft of a published item no longer rewrites the live scope index, so a published Global item stays findable by prefilters while a draft is pending. Unchecking an entity type on the Entity Types settings page is now blocked, with an error naming the usage, while context items or consumer subscriptions still reference it. Language values are no longer deleted on single-language sites. Deleting the last bundle of a type keeps `type:_all`. Taxonomy matching now uses the revision or translation of the requested entity, and language detection honours a caller-supplied path such as `/es/...`. The Global checkbox stays visible on the item form when the Global scope is disabled, so existing global items can be cleared. Inheriting subcontexts score using the parent's values when a scope plugin is missing.

## Impact

Affects module maintainers and site owners.

- **Config change:** Service `ai_context.language_service` now receives `@ai_context.request_info_resolver` instead of `@request_stack`.
- **New API:** `AiContextScopeCleanupService` gains public `getStoredValuesWithPrefix()` and `countStoredValueUsage()`; `AiContextScopeEntityType` implements `validateSettingsForm()`.

## Technical details

Index: `ai_context_ai_context_item_update()` in `ai_context.module` returns early when `!$entity->isDefaultRevision()`. The cascade to inheriting children now runs only if the original revision was a default revision and its scope differs. Publishing a draft therefore no longer compares against a draft whose scope was never written to the children.

Cleanup: `AiContextScopeEntityType::validateSettingsForm()` collects stored values for removed types via `AiContextScopeCleanupService::getStoredValuesWithPrefix()`. It counts usage with `countStoredValueUsage()`, which skips inheriting subcontexts, and sets a form error. `getContentEntityTypeOptions()` keeps a configured type listed even with no bundles. `getValues()` keeps the All option for a bundled type with no bundles, so the generic stale-value diff never reports `type:_all` missing after the last bundle delete. Live and settings-change scrubs skip disabled or unavailable plugins. Entity and bundle delete scrubs still run regardless. This is documented on `AiContextScopeStoredValueInterface`: a plugin returning `NULL` from `getStaleStoredValuesForEntityDelete()` gets a full `getStaleStoredValues()` scan even while the scope is disabled.

Matching: `AiContextScopeResolver` scoring falls back to `$item->getScopeItem()->getScopeValues()` instead of the child's own empty scope. `AiContextLanguageService` now takes `AiContextRequestInfoResolver` (service definition changed) and extracts the language prefix from the single path returned by `getPath()`. Taxonomy changes are in `AiContextScopeTaxonomy` and `AiContextRequestInfoResolver`. The summary describes the intended behaviour; I did not read that diff in full.

## Upgrade

If you construct `AiContextLanguageService` yourself or override its service definition, the third argument changes from `@request_stack` to `@ai_context.request_info_resolver`:

```yaml
arguments:
  - '@config.factory'
  - '@language_manager'
  - '@ai_context.request_info_resolver'
```
