## Summary

The AI Context module declared two scheduling permissions that no code ever checked, so a role given only those could not set "Publish on" or "Unpublish on" dates. They are removed. Scheduler's own permissions for context items now do the work, and an update moves existing roles over. The item form and Content Moderation's "Change to" form now also show an error when the workflow cannot run a schedule, such as an Archived item with an "Unpublish on" date. Before, these saves succeeded and cron then failed on every run, creating a new revision each time.

## Impact

Affects site owners.

- **Database update:** Post-update `ai_context_post_update_0017_use_scheduler_permissions()` updates role config; no schema changes.
- **Config change:** Post-update 0017 rewrites role configuration, removing the two CCC permissions and granting Scheduler's equivalents when Scheduler is installed.
- **Permission change:** `schedule publishing of ai context items` and `view scheduled ai context item` removed; use Scheduler's `schedule publishing of ai_context_item` and `view scheduled ai_context_item`.

## Technical details

Scheduler checks only its own `schedule publishing of ai_context_item` and `view scheduled ai_context_item`. Scheduler Content Moderation Integration (SCMI) validates scheduled transitions through constraints on `publish_state` and `unpublish_state`. Those fields are removed from the item form display, and the default states are set in `AiContextItem::preSave()` after validation, so SCMI never saw them. The "Change to" form saves without entity validation.

The fix adds `AiContextSchedulerDefaults::getScheduledWorkflowErrors()` and `getStateChangeErrors()`. They check the default scheduled state and the transition to it, without modifying the item. They are called from `AiContextItemForm::validateForm()` and `ModerationFormHooks::doValidate()`. Users who cannot see the date fields get the error on the moderation state, and only when the save breaks a schedule that could run before. `AiContextSchedulerDefaults` now takes optional `content_moderation.moderation_information` and `scheduler.manager` arguments, and the class name is an alias of the `ai_context.scheduler_defaults` service. These classes are `@internal`. Saves outside these two forms, the revert form, and existing unrunnable schedules are not checked or changed.

Post-update `ai_context_post_update_0017_use_scheduler_permissions()` removes the old permissions from every role. For non-admin roles it grants the matching Scheduler permission when Scheduler is installed. For admin roles it only strips the stored names. It saves only changed roles and returns a message naming them.

## Upgrade

Run `drush updatedb`, then export and commit configuration. Importing config exported before the update restores the removed permissions and removes the Scheduler ones. Do the export before `drush deploy`, which runs updatedb and then imports config.

If a recipe, install profile or config export has the old names, replace them:

```
schedule publishing of ai context items -> schedule publishing of ai_context_item
view scheduled ai context item -> view scheduled ai_context_item
```

If Scheduler was not installed during the update, grant Scheduler's permissions to the roles named in the update message after installing it. A role that sets dates also needs the matching workflow transition (Publish, Restore or Archive).
