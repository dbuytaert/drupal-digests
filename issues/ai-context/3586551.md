## Summary

Saved per-consumer context overrides (`ai_context.consumers` rows for agents and automators) are now kept whenever a module is uninstalled. Before, some overrides were silently lost while their siblings survived. This happened when several modules were uninstalled in one run with a cross-module dependency, and when an automator was attached to a field on an `automator_chain` bundle and `ai_automators` was uninstalled. Kept rows show in the consumers listing as **Off (type unavailable)**, or **Off (stale)** if the consumer type is still installed (for example when only a module an automator depends on is uninstalled). An admin can remove them with **Remove configuration**. Reinstalling a module that recreates the host entity with the same ID makes the saved override apply again. Deleting a single agent or automator while its module stays installed still removes its row immediately.

## Impact

Affects module maintainers.

- **New API:** New `@internal` service `ai_context.removed_consumer_rows` (tagged `persist`); `AiContextScopeCleanupService` gains `restoreRemovedConsumerRows()`.

## Technical details

The earlier approach kept a `drupal_static` list filled by `hook_module_preuninstall()` and compared it with the deleted entity's type provider. It missed cases where the provider differs from the module being uninstalled, or where the delete happens before the module is listed. Core deletes host entities at two points. `ConfigManager::uninstall()` flags config entities with `isUninstalling()`. Before that, `ModuleInstaller::uninstall()` deletes bundles, and the resulting `FieldConfig` dependents are deleted with a plain `delete()` and no flag.

`ai_context_entity_delete()` now returns early when the host is a `ConfigEntityInterface` with `isUninstalling()` TRUE. For all other host deletes the row is removed as before, but `AiContextScopeCleanupService::removeDeletedConsumerConfig()` first records it in `AiContextRemovedConsumerRows`. That service is `@internal`, tagged `persist` so it survives container rebuilds during an uninstall, and has no constructor dependencies, since a persisted instance would keep the old container's services. It keeps only the first row per consumer ID, matching how duplicate IDs resolve elsewhere.

`ai_context_modules_uninstalled()` calls `restoreRemovedConsumerRows()`, which appends recorded rows to `ai_context.consumers` unless a row with that ID is already present, and clears the list. It runs before the stale-scope scrub so restored rows are scrubbed too. It also runs during config sync, where only the scrub is skipped. It does nothing when `ai_context` itself is uninstalled. `ai_context_module_preuninstall()` and `ai_context_uninstalling_modules()` are removed. Accepted edge case: a row removed earlier in the same request, before an uninstall, is also restored. `docs/developers/hooks.md` and `consumer_api.md` are updated, and `consumer_api.md` now defines "host entity". Kernel tests and a new `ai_context_test_automator_dependent` test module cover the cases.

## Upgrade

Code that implemented or documented reliance on `hook_module_preuninstall()` or `ai_context_uninstalling_modules()` from this module should drop it. Both are removed, and `ai_context_uninstalling_modules()` was `@internal`.
