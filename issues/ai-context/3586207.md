# #3586207: Conditional Subcontext Provider Calls

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3586207](https://git.drupalcode.org/project/ai_context/-/work_items/3586207) · 1 contributor · 40 comments

## Summary

Conditional subcontext children used to cost one synchronous AI provider call per selected parent, which could dominate agent latency and provider usage. There are now two new settings on the Context item settings page (`/admin/config/ai/context/settings/items`). One turns AI decisions for conditional children on or off. The other caps how many parents get an AI decision per context resolution (default 3, range 1 to 20). The toggle defaults to on, so existing behavior is preserved apart from the new cap of 3. If AI decisions are off, all conditional children are included with no provider call. Parents over the cap keep their required children, but their conditional children are dropped. Identical decisions within one request are cached.

## Impact

Affects site owners.

- **Database update:** `ai_context_update_10010()` adds the two new settings to existing sites.
- **Config change:** New `ai_context.settings` keys `conditional_subcontext_enabled` (default true) and `conditional_max_parents` (default 3, range 1 to 20); `subcontext_enabled` checkbox moved to the Context item settings form.

## Technical details

`AiContextSubcontextResolver::resolve()` reads `conditional_subcontext_enabled` and `conditional_max_parents` (clamped to 1..20) and passes a by-reference `$conditional_calls_made` counter through `resolveForParent()` into `resolveConditionalChildren()`. The cap is checked before any prompt or provider work. Once reached, the parent's conditional children are dropped and an info message is logged. Which parents are dropped follows internal processing order, not relevance to the task. Calls are one per parent and are not batched.

A per-instance `$decisionCache` is keyed by `md5(parent id | task | sorted candidate ids)`. It stores approved results, and it also stores empty results from a missing provider, a provider with no `chat()`, a bad response or an exception, so a broken provider is not re-hit within the request. Cap skips are deliberately not cached. A later `resolve()` call with budget left can still make the call.

The form layout changed too. The `subcontext_enabled` checkbox moved from `AiContextSettingsForm` to `AiContextItemSettingsForm`, which gains the two new fields with `#states` visibility. The provider field in `AiContextSettingsForm` gets a `- None -` option. Clearing the provider is now blocked only when conditional AI decisions are enabled and published conditional items exist. The provider description now says whether AI decisions are on. Config schema adds the two keys, with a `Range` constraint of 1 to 20 on `conditional_max_parents`.

## Upgrade

`ai_context_update_10010()` sets `conditional_subcontext_enabled: true` and `conditional_max_parents: 3` in `ai_context.settings` when they are unset. Run `drush updb`. Sites exporting config should export the two new keys.
