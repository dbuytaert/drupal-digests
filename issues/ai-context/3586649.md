## Summary

Uninstalling Dynamic Entity Reference (DER) used to silently delete every Specific Entities value on AI Context items, in all revisions. Reinstalling DER did not bring the values back. Items that had been limited to specific entities then matched everywhere. The uninstall is now blocked while any context item has Specific Entities values on its current revision or on a pending draft. The message lists up to five affected items. Old revisions do not block the uninstall. Instead, after a successful uninstall each old revision that held values gets a revision log note listing the entities it referenced (type, ID, label), so you can re-enter the values by hand. Values are not restored automatically. The docs, including the Specific Entities section of `scopes.md`, are corrected.

## Impact

Affects module maintainers.

- **New API:** `AiContextDynamicEntityReferenceSetup` gains `getItemIdsWithValues()`, `countItemsWithValues()`, `getInstalledFieldName()`, `prepareRevisionLogNotes()`, `writePendingRevisionLogNotes()`, `recoverConfirmedRevisionLogNotes()`, `collectRevisionLogNotes()` and `writeRevisionLogNotes()`. The module also adds `hook_module_preuninstall()` handling for `dynamic_entity_reference`.

## Technical details

`entity_items` is a base field provided by `dynamic_entity_reference`, so core drops its storage on uninstall. `AiContextUninstallValidator` now handles `dynamic_entity_reference`. It calls `AiContextDynamicEntityReferenceSetup::getItemIdsWithValues()`, which combines default revisions, latest revisions, and pending drafts of any translation. It returns reasons as `TranslatableMarkup` so core's template does not double-escape labels. If the check throws, it returns `NULL`, the validator blocks the uninstall, and the error is logged. The legacy `target_entities` field name is supported via `getInstalledFieldName()`.

Old revisions are handled in two phases. `ai_context_module_preuninstall()` calls `prepareRevisionLogNotes()`, which stores notes in State under `ai_context.dynamic_entity_reference_uninstall_prepared_notes`. Nothing is written yet, because the uninstall might still fail. `ai_context_modules_uninstalled()` runs only after success. It calls `writePendingRevisionLogNotes()`, which promotes the prepared notes to `ai_context.dynamic_entity_reference_uninstall_notes` and appends them to the revision log. It uses a direct database update, so presave hooks such as scope cleanup and moderation do not run. It then resets the entity cache and invalidates the item cache tags. This also runs during config sync.

If the write fails, the error is logged, the confirmed notes stay in State, and the other uninstall hooks still run. `ai_context_cron()` retries confirmed notes through `recoverConfirmedRevisionLogNotes()`. A later DER uninstall writes any confirmed notes before it captures new ones, and stops if that write fails. Unconfirmed prepared notes are never written by cron. `ai_context_uninstall()` deletes both State keys. The Revisions overview form now wraps the log in `nl2br()` so multi-line notes display. A test module, `ai_context_der_uninstall_test`, simulates load and write failures. The diff I read omits the kernel test file.

## Upgrade

Before uninstalling Dynamic Entity Reference, clear the Specific Entities values on any context item that uses them. Check pending drafts too. Otherwise the uninstall page, Drush and config import will refuse to remove the module. After the uninstall, old revisions that held values have a revision log note listing the referenced entities. Re-enter the values from those notes if you need them. Run cron before uninstalling DER a second time after reinstalling it, so Drupal purges the deleted field storage.
