## Summary

Cron pruning and the "clear usage" admin action for AI Context usage records now delete in chunks of 200 instead of loading every matching record into memory at once. This reduces the risk of slow cron runs and memory exhaustion on sites with large usage tables. The behavior stays the same: records older than `usage_max_age` and the oldest records beyond `usage_max_records` are removed, and nothing is pruned when both limits are 0. Database indexes are also added for common usage lookups.

## Impact

Affects site owners.

- **Database update:** `ai_context_update_10003()` adds indexes `ai_context_usage_runner_id`, `ai_context_usage_changed` and `ai_context_usage_target_entity` to the `ai_context_usage` table.

## Technical details

`ai_context_cron()` now loops with `->range(0, $batch_size)` (200). Age pruning repeats until a query returns fewer than 200 IDs. Max-record pruning counts the total once, then deletes the oldest records (sorted by `changed` ASC) in chunks of `min($remaining, 200)`, stopping if a query returns nothing.

`AiContextUsageClearForm::submitForm()` now counts the records and calls `batch_set()` with a Batch API operation. The new static `batchDelete()` deletes 200 records per iteration and reports progress. `batchFinished()` sets the status or error message.

Indexes are defined in `_ai_context_usage_index_definitions()` and created by `_ai_context_ensure_usage_indexes()`, which skips indexes that already exist. It runs from `ai_context_install()` and from the new `ai_context_update_10003()`. The `context_item_id` reference field relies on the index Drupal generates itself. The data model and public usage APIs are unchanged. The issue explicitly left normalizing `tools_used` and `routes` out of scope, as usage tracking is expected to move to `ai_observability`. Kernel tests (`AiContextUsagePruningTest`) cover pruning, the batch callback and index existence.
