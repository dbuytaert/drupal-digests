## Summary

The Entity Types scope no longer reveals whether a hidden entity exists or which bundle it belongs to. Before, a user with the `access published ai context` permission could pass an entity type and ID to an agent tool or AI request and see whether a bundle-scoped context item was selected. That worked even for an unpublished node or term they could not view. Now an entity the user cannot view is treated like an ID that does not exist. There is a side effect to check on your site. Editors who can edit an entity but not view it (for example, another author's draft) no longer get Entity Types or Taxonomy Terms matching on that form. Background runs as Anonymous (cron, queues, Drush) also lose bundle-scoped items unless that account can view the entity. A bundle hint sent for an unsaved entity, such as a node add form, still works.

## Impact

Affects site owners.

- **Security:** Minor information disclosure: a user with `access published ai context` could learn whether an entity ID exists and its bundle through the Entity Types scope. Existence and bundle only, no field data.

## Technical details

`AiContextRequestInfoResolver::getEntityTypeFromEntity()` used to load the request entity by ID with no access check. It now calls `loadContentEntity()`, which already checked `access('view')`, and returns NULL when the entity is missing or not viewable. The `getEntityType()` fallback to the caller-supplied bundle hint is unchanged. The resolver now keeps the access result (`getContentEntityAccessResult()`, allowed or denied). It runs on the revision or translation the route upcasts, not the default revision.

`AiContextSelector` adds that access result's cacheability to every selection result, including a denied one. This applies even when the Entity Types and Taxonomy Terms scopes are disabled, so a custom scope cannot reuse another account's result. When access depends on ownership (for example, **View own unpublished content**), the result varies by `user`.

Because access now decides the match, the resolver takes `@current_user` as a new constructor argument. The `ai_context.request_info_resolver` service definition is updated, and any code that instantiates the final class directly must pass an `AccountInterface` as the fifth argument. The entity and `getEntityType()` memos reset when the current request (held as a `WeakReference`) or the account ID changes. An account switch in a queue worker or a nested request therefore re-checks access. `applyRequestInfo()` also clears a route entity saved for an earlier request, so a later caller-supplied entity is applied. Without that, the earlier route entity would hide it. The docs and a new kernel test class, `AiContextEntityBundleAccessTest`, cover these cases. Existing Entity Types tests now set up a current user with `access content`.

## Upgrade

If you construct `AiContextRequestInfoResolver` yourself, for example in tests, pass the current user as the new last argument:

```php
new AiContextRequestInfoResolver(
  $routeMatch,
  $requestStack,
  $entityTypeManager,
  $entityTypeBundleInfo,
  $container->get('current_user'),
);
```

If editors rely on Entity Types or Taxonomy Terms matching on edit forms, make sure their role can view the content it edits.
