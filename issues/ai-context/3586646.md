## Summary

The 1.0.0 docs for AI Context now state which request metadata keys are stable public API. They also explain how a queue worker, cron hook or Drush command can pull context. Integrators such as Content Studio can depend on this behavior. The docs also say that pull ignores the push gates and writes no usage record. They say that usage records list items selected before the token budget is applied. This is a documentation and docblock change only. No behavior changed.

## Impact

Affects module maintainers.

- **New API:** The `entity_context` request metadata keys (entity type, entity ID, bundle, path, plus the top-level `path` fallback) are now documented as public API.

## Technical details

`docs/developers/api-stability.md` gets a "Request metadata keys" section. It lists the accepted `entity_context` keys: `entity_type`, `entity_type_id` or `type`; `entity_id` or `id`; `bundle`; and `path`, with a top-level `path` fallback. The keys are set with `InputBase::setRequestMetadataValue()`. Setting `entity_context` again replaces the whole array. A numeric entity ID is cast to `int`, and a UUID or other string ID is ignored. Bundle and path are untrusted string-matching hints that never load an entity or grant access. Adding an alias is not a break. Removing one or tightening a rule is. The reader class `AiContextProviderRequestContextFactory` stays `@internal`.

`docs/developers/consumer_api.md` gets a "Background jobs and queue workers" section built around `ai_context.selection_factory` and `fromConsumer()`. It documents these points:
- Item queries use `accessCheck(TRUE)`, so the account running the job decides what is selected. Cron runs as anonymous and usually selects nothing.
- Only saved entities can be passed through the public pull API.
- Entity context persists on the current request across pulls.
- Conditional subcontext (`conditional_subcontext_enabled`, `conditional_max_parents`) can make its own AI calls, and it is a site-wide setting.
- Pull writes no usage record.
- Pull does not enforce `push_enabled`, the type kill switch or `isAvailable()`. Callers can use `isPushAllowed()` if they want those honored.

The `AiContextSelectionFactoryInterface::fromConsumer()` docblock now says the same about the push gates and usage records, and points to [#3586600](https://www.drupal.org/node/3586600) for planned pull usage records. `docs/features/usage_tracking.md` says usage records show items selected before rendering, including ones the token budget shortened or dropped. [#3586645](https://www.drupal.org/node/3586645) tracks that.

## Upgrade

Contrib code that reads context from a background job can use the documented pull pattern:

```php
$factory = \Drupal::service('ai_context.selection_factory');
$selection = $factory->fromConsumer('my_type:my_instance', $task, 'node', $nid);
$context = $factory->getResultFromSelection($selection)->getRenderedText();
```

Run the job as an account that holds **Use Published AI Context in AI Features**.
