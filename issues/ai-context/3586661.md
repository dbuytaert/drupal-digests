## Summary

AI Context no longer breaks when the tokenizer cannot load its vocabulary file. That file is downloaded on first use from `openaipublic.blob.core.windows.net` and cached in the Drupal temp directory. Before this fix, a blocked download, a non-writable temp directory or a corrupt cache file made item saves fail with "The changes could not be saved." It also stopped agent tools that load context. Now AI Context uses an approximate token count (bytes divided by 4), logs one warning, and keeps saving items, rendering context and answering agent requests. Stored counts are recalculated by cron once the vocabulary loads. Sites without outbound access can allow the host or copy the vocab file into the temp directory. The new docs describe both options.

## Impact

Affects module maintainers.

- **New API:** `AiContextTokenEstimator::isTokenizerAvailable()`, `markTokenizerUnavailable()` and `reportEncodingFailure()`, and `AiContextTokenCountBackfillScheduler::queueDeferredRecount()` and `deferRecount()`.

## Technical details

`AiContextTokenEstimator::estimate()` now catches `\Throwable` from `setModel()` and `countTokens()`. On failure it returns `(int) ceil(strlen($text) / 4)`. The failure is remembered per model for `UNAVAILABLE_CACHE_TTL` (600 seconds), both in the service and in `cache.default` under `ai_context:tokenizer_unavailable:{model}`. Requests therefore do not retry the download, and `drush cr` clears the memo. One warning is logged per request to the `ai_context` channel. A text that fails to encode while the vocab is loaded gets an approximate count for that text only, and the tokenizer is not marked unavailable. The AI module's own `cl100k_base` fallback in `Tokenizer::setModel()` is uncaught, so the catch has to live in AI Context.

`AiContextRenderer` skips `configureTextChunkerModel()` when the tokenizer is unavailable and trims content with `mb_strcut($content, 0, $max_tokens * 4)` instead of `TextChunker::chunkText()`. It uses the same fallback if the chunker throws mid-render. While approximate counts are in use, the render result gets a max-age of 600 seconds, so cached output does not keep the byte-trimmed text after the vocab loads.

Fallback counts must not stay in storage permanently. `AiContextItem::preSave()` stores the approximate count and calls `queueDeferredRecount()`, which queues one full recount on `ai_context_token_count_backfill`. A state flag, `ai_context.token_count_deferred_recount`, limits this to one waiting recount. `backfillChunk()` checks `isTokenizerAvailable()` before counting and again before writing. When the tokenizer is unavailable it throws the `@internal` `AiContextTokenizerUnavailableException` and writes nothing. The queue worker turns that into `SuspendQueueException`. `processQueuedChunk()` releases the item and returns `deferred: TRUE`, and the settings-form batch shows a warning. `backfillAll()` and update 10023 call `deferRecount()` and finish instead of failing. Docs (`services.md`, `configuration.md`, `debugging.md`) were extended, and the kernel test base gained `stubFailingTokenizerServices()` with `AiContextFailingTestTokenizer`.

## Upgrade

Sites that cannot reach the vocab host have two options. Allow outbound HTTPS to `openaipublic.blob.core.windows.net`, or copy the vocab file unchanged into the Drupal temp directory under the SHA-1 of its URL. The file for `cl100k_base`, which `gpt-4` and unknown models use, is `9b5ad71b2ce5302211f9c61530b329a4922fc6a4`. The file for `o200k_base`, used by `gpt-4o` models, is `fb374d419588a4632f3f557e76b4b70aebbca790`. Sites whose temp directory is emptied on each deploy can set `$settings['file_temp_path']` to a persistent directory. After fixing the cause, run `drush cr` and then cron, so the approximate counts are recalculated.
