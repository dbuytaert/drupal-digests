## Summary

On MariaDB and MySQL, saving any consumer on the AI Context consumer settings form could fail with an "Illegal mix of collations" database error if another consumer's stored `always_include` or `never_include` list held a non-ASCII value such as `café`. The same value made post-update 0008 fail during `drush updatedb`. Such values can get into config through a config import, a recipe, or `drush config:set`. They are now ignored, and the stored value stays in configuration.

## Impact

No upgrade or configuration changes required.

## Technical details

The `uuid` column is ASCII, and MariaDB and MySQL throw instead of matching nothing when it is compared with a non-ASCII value. `AiContextConsumerForm::calculateConsumerContentDependencies()` runs over every stored consumer row on each save, and `_ai_context_post_update_0008_calculate_consumer_content_dependencies()` did the same split. Both sorted identifiers into all-digits and everything else, then queried the everything-else group on `uuid`. The `else` branch is now `elseif (Uuid::isValid($identifier))`, so only numeric IDs and valid UUIDs reach the entity query. `Uuid::isValid()` accepts lower-case UUIDs only, so upper-case UUIDs are dropped too.

The commit also carries the matching guard for `AiContextItemIdentifierResolverTrait::resolveContextItemIdentifiersToIds()` from [#3586741](https://www.drupal.org/node/3586741), which covers the Get Relevant tool path. The issue records that no config schema constraint was added to these sequences, because they also hold legacy numeric IDs and a constraint would make a config import with a bad value fail. New kernel tests, `AiContextConsumerIncludeListNonUuidTest` and `AiContextIncludeListIdentifierTest`, assert the value never appears in query arguments. This holds on SQLite too, which does not throw. PostgreSQL was not checked.
