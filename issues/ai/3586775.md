## Summary

The AI API Explorers page at `/admin/config/ai/explorers` is now a hub of cards grouped by type (Text, Search and ranking, Image, Audio and video, Tools and more). Each card shows the explorer name, description and the providers that can serve it. Explorers with no usable provider stay in the list, dimmed, with a "No provider yet · Set up" label instead of disappearing. There is a search box, type filters and an "Only ready to use" checkbox. A provider that throws while the page checks which providers are usable no longer takes the page down: a notice and a per-card warning appear and the error is logged. An explorer that fails to load is shown as a broken card and logged, and a router rebuild no longer fails because of it.

## Impact

Affects module maintainers and front-end developers.

- **Theme change:** The explorers list is rendered by the new `ai-api-explorer-hub.html.twig` template instead of the core admin block list.
- **API change:** `ExplorerSetupList` controller removed in favor of `ExplorerHub`; `AiApiExplorerAccessChecker` constructor now takes a logger.
- **New API:** New `ai_api_explorer_hub` theme hook and `ai_api_explorer/hub` library; new `ExplorerHub` controller on the existing `ai_api_explorer.list_page` route.

## Technical details

The route `ai_api_explorer.list_page` now points to the new `ExplorerHub::build()` controller, which replaces `ExplorerSetupList` and its `SystemManager::getBlockContents()` output. It renders the new `ai_api_explorer_hub` theme hook (template `ai-api-explorer-hub.html.twig`, preprocess `template_preprocess_ai_api_explorer_hub`) and attaches the new `ai_api_explorer/hub` library (`explorer-hub.css`, `explorer-hub.js`). The search, type filter and ready filter work client side on `data-*` attributes. Explorers are assigned to groups by their operation types, using the `ExplorerHub::GROUPS` constant, with `other` as the fallback. Provider usability comes from the `ai_api_explorer.availability` service (`getProviders()`, `getFailures()`), and cards use `getHubSummary()` when an explorer plugin provides one. Each explorer is built inside a `try/catch (\Throwable)`. A failure is logged to the `ai_api_explorer` logger channel and shown as a broken card with no link.

Hardening elsewhere: `AiApiExplorerRouteSubscriber::alterRoutes()` no longer instantiates every explorer. It takes the route title from the plugin definition, so a plugin that throws in `create()` cannot break a router rebuild. `AiApiExplorerAccessChecker` now takes the logger as a second constructor argument. It catches `\Throwable`, logs it and returns forbidden with max-age 0, so the broken explorer's own page returns 403. `ai_api_explorer_menu_links_discovered_alter()` falls back to the definition's title and description if instantiation fails.

Tests: the old `ExplorerSetupListTest` is replaced by a functional `ExplorerHubTest`, a kernel `ExplorerHubTemplateTest` for the plural strings and the preprocess deprecation, and an `ai_api_explorer_test` `BrokenExplorer` plugin controlled through state.

## Upgrade

Code that referenced `\Drupal\ai_api_explorer\Controller\ExplorerSetupList` must use `\Drupal\ai_api_explorer\Controller\ExplorerHub::build` instead. Any service definition or subclass of `AiApiExplorerAccessChecker` must pass the logger as the second argument:

```yaml
arguments: ['@plugin.manager.ai_api_explorer', '@logger.channel.ai_api_explorer']
```
