## Summary

An AI API Explorer whose operation has no usable provider no longer answers "Access denied" to users who have the `access ai prompt` permission. The page now explains what to set up: it names the operation, says which installed providers can or cannot do it, and shows numbered setup steps with links. It can also point to another explorer as an alternative. If a provider throws an error while being checked, the page shows that error as a notice rather than breaking. Users without the permission still get 403.

## Impact

Affects module maintainers and front-end developers.

- **Theme change:** New `ai-api-explorer-setup.html.twig` template and `template_preprocess_ai_api_explorer_setup()` render the setup page; themes overriding explorer markup may want to style it.
- **New API:** `#[AiApiExplorer]` attribute gains an `operation_types` array, and there is a new `ai_api_explorer.availability` service (`ExplorerAvailability`) plus an `ai_api_explorer_setup` theme hook.

## Technical details

`AiApiExplorerAccessChecker` now returns `AccessResult::allowedIf($plugin->hasAccess($account))->cachePerPermissions()`. It no longer calls `isActive()`, so access depends only on the account. The decision moved into `AiApiExplorerForm::buildForm()`. It calls `$plugin->isActive()` inside a `try/catch (\Throwable)`. If the explorer is inactive or a provider threw, it returns `AiApiExplorerPluginBase::buildSetupNeeded($form, $error)` instead of the normal form.

Plugins declare the operation types they call through the new `operation_types` argument of the `#[AiApiExplorer]` attribute. All bundled explorers were updated; `ToolsExplorer` declares `chat`. The setup page title and status are built from those operation types. An explorer that declares none, such as the Vector DB explorer, gets a "not available on this site" page with no provider steps, because what it lacks is not a provider. The base class has a `getSetupAlternative()` hook and `addSetupAlternative()` for pointing at another explorer.

A new service `ai_api_explorer.availability` (`ExplorerAvailability`) checks each provider separately with `createInstance()`, `getSupportedOperationTypes()` and `isUsable()`. It caches the result for the request. A provider that throws is recorded and logged to a new `ai_api_explorer` logger channel, so one broken provider does not hide the others. Rendering uses the new `ai_api_explorer_setup` theme hook with `ai-api-explorer-setup.html.twig`. `ai_api_explorer_test` gained a `BrokenProvider`, a `TestEmbeddingsProvider` and a `NoProviderTestExplorer`, and `SetupNeededTest` covers the page. The diff also includes a `composer.json` change raising `yethee/tiktoken` from `^0.5.1` to `^1.1.1`.

## Upgrade

Custom explorer plugins should declare the operation types they call so the setup page can name the right provider requirement:

```php
#[AiApiExplorer(
  id: 'rerank_generator',
  title: new TranslatableMarkup('Rerank Explorer'),
  description: new TranslatableMarkup('Contains a form where you can experiment and test the AI rerank operation.'),
  operation_types: ['rerank'],
)]
```

An explorer that omits `operation_types` gets the "not available on this site" page without provider steps when its `isActive()` returns FALSE.
