## Summary

When a Decision automator request is blocked, either by a guardrail set or by the provider's own safety filter, the field now keeps its current values and the log gets a specific notice saying the request was blocked. Before, a block showed up as a generic "general error" warning that looked like a broken integration. Decision provider authors now have a documented way to report a whole-request block: throw `AiUnsafePromptException`.

## Impact

Affects module maintainers.

- **API change:** `DecisionBoolean`, `DecisionChoice` and `DecisionScore` `generate()` no longer throw `AiUnsafePromptException` (including `AiDecisionBlockedException`); they return no values and log a notice.
- **New API:** `DecisionAutomatorTrait::abstainWhenBlocked()` (protected) runs a closure and returns `[]` when `AiUnsafePromptException` is thrown.

## Technical details

The provider contract (`decision_provider_contract.md`) now says that a refusal is per question, while a block of the whole request must throw `AiUnsafePromptException` with the provider's reason code and message. The block should be checked before answers are built, so an empty `answers` is not reported as `AiBrokenOutputException`, and a block that arrives as an HTTP error is mapped the same way. `AiDecisionBlockedException` stays reserved for AI's own guardrails, since it needs a phase and results. No library code changed for this part; the `ai_decision_test` provider gained a `BLOCK_MARKER` that makes it throw, for tests.

In `DecisionAutomatorTrait`, the new protected `abstainWhenBlocked(\Closure $generate, ...)` catches only `AiUnsafePromptException` and returns `[]`. The three rule bases wrap their whole `generate()` body in it (the body moved to a private `generateValues()`). The catch covers the whole body, not each request, so a block on any request of a multi-request rule, for example one request per item on a multi-value Boolean field, keeps the whole field. The notice names model, provider, entity type and id, field and the exception message. For `AiDecisionBlockedException` it also says whether the guardrails blocked before or after generation. Other errors such as `AiBrokenOutputException` still propagate, and `runDecision()` keeps its signature and still throws. The guardrail set description on `DecisionRuleBase` now mentions the notice. `DecisionAutomatorExecutionTest` was updated: the old post-block test now expects no exception, and new cases cover pre-generation blocks, provider blocks across all rules, and errors that are not swallowed.

## Upgrade

Code that calls a Decision rule's `generate()` directly and catches `AiUnsafePromptException` should check for an empty result or the log instead. Custom rules built on `DecisionAutomatorTrait` can opt in:

```php
return $this->abstainWhenBlocked(fn (): array => $this->generateValues($entity, $fieldDefinition, $automatorConfig), $entity, $fieldDefinition, $automatorConfig);
```

Decision providers whose API blocks a whole request should throw `AiUnsafePromptException` rather than return empty answers or refusals.
