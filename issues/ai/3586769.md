## Summary

For AI assistants using the `private_tempstore_pool` chat history mode, once a user had 11 open threads (for example by refreshing the chatbot page instead of using Clear History), every chat request deleted their conversation in slot 0. Old conversation context could also leak into the new thread. Now a full pool evicts the least recently used thread only when a new thread is actually needed, and the evicted thread's stored contexts are cleared too.

## Impact

No upgrade or configuration changes required.

## Technical details

`AiAssistantApiRunner::setAssistant()` used to call `generateUniqueKey()` immediately. Access checks, `AiAssistantApiProcessor::initializeRunner()` and `ResetSession` all call `setAssistant()` before the client's own thread id is set. With a full pool, each of those requests evicted slot 0. The eager generation is removed. The runner now reads its thread id through `getThreadsKey()` everywhere it previously used `$this->threadId` (message history, output contexts, structured results, assistant message building, action instances), so a key is only generated when one is needed.

In `generateUniqueKey()`, a full pool now evicts the slot whose last message has the oldest timestamp, instead of always `assistant_thread_{uid}_0`. Slots with no messages count as timestamp 0. The evicted key is also removed from the runner's temp store (`getTempStore()->delete($evicted_key)`), so `output_contexts` and `structured_results` from the previous conversation no longer carry over. A new kernel test, `AiAssistantApiRunnerThreadPoolTest`, covers both behaviors.
