## Summary

The AI module's 2.x branch now builds its provider layer on Symfony AI's Platform component. Instead of installing a provider module and configuring it as a plugin, site builders create AI Platform entries at `/admin/config/ai/platforms`, each pointing to a platform plugin plus its settings. Multiple instances of the same platform can exist. The module ships a Generic platform (OpenAI compatible APIs such as LiteLLM or OpenRouter) and a Gemini platform. Existing code that calls providers through the old API keeps working through a compatibility layer, but providers defined as old style `AiProvider` plugins are no longer listed or usable for operation types.

## Impact

Affects module maintainers and site owners.

- **Requirements:** Adds `symfony/ai-platform` and `symfony/ai-generic-platform` ^0.6 and `drupal/symfony_http_client` ^1.0; `symfony_http_client` becomes an `ai.info.yml` dependency; test module requires Drupal ^11.2.
- **Database update:** `ai_update_20001()` installs the `symfony_http_client` module.
- **Config change:** New `ai.platform.*` config entity (`id`, `label`, `plugin`, `configuration`) managed at `/admin/config/ai/platforms`.
- **Permission change:** New restricted permission `administer ai platforms`.
- **API change:** `AiProviderPluginManager::getProvidersForOperationType()` now returns only `ai_platform` entity based definitions keyed `ai_platform:<id>`; standalone `AiProvider` plugins are no longer supported. `createInstance()` accepts `ai_platform:<id>` and can return a `PlatformProxy`.
- **New API:** New `#[AiPlatform]` attribute, `AiPlatformInterface` (extends Symfony AI `PlatformInterface`), `AiPlatformPluginBase`, `plugin.manager.ai_platform`, `ai_platform` config entity, `PlatformProxy` and `InputOutputConverter` BC layer; bundled `generic` and `gemini` platform plugins.

## Technical details

A new `ai_platform` plugin type (`#[AiPlatform]`, `AiPlatformInterface extends Symfony\AI\Platform\PlatformInterface`, `AiPlatformPluginBase`, `AiPlatformPluginManager` as `plugin.manager.ai_platform`) wraps a Symfony `PlatformInterface`. Subclasses implement `initializePlatform()`; `invoke()` is final and delegates to it. `getAvailableConfiguration($operation_type, $model_id)` returns per parameter metadata (label, type, default, constraints) for model settings forms. `AiPlatformUsingApiKeyAuthenticationPluginBase` stores a Key module `key_id`. Platform plugin configuration is validated via `plugin.plugin_configuration.ai_platform.*` schema, and the `ai_platform` entity (`AiPlatformConfig`) calculates dependencies on the plugin's module and key.

BC bridge: `AiProviderPluginManager::createInstance()` treats IDs starting with `ai_platform:` (constant `PLATFORM_PREFIX`) as a lookup of an `ai_platform` entity and returns a `PlatformProxy`. `PlatformProxy` implements `AiPlatformInterface`, `AiProviderInterface` and `ChatInterface`; the BC side is marked deprecated in its docblock. It uses the `ai.symfony.input_output_converter` service (`InputOutputConverter`) to translate Drupal `ChatInput`/`ChatOutput` into Symfony messages and results. `getProvidersForOperationType()` now iterates `ai_platform` entities only, so the provider/model selectors and `getDefaultProviderForOperationType()` consumers see platform entries as `ai_platform:<entity_id>`. `ProviderProxy` now accepts any `AiProviderInterface` rather than `AiProviderClientBase`. In `PlatformProxy`, `loadModelsForm()` is a stub with a `@todo`, so the per model settings page does not yet render platform model settings.

Tests use an `EchoAiPlatform` test plugin and an `echo_test` platform entity in `ai_test`; the old `echoai` provider references were replaced.

## Upgrade

Site owners updating: run database updates (`ai_update_20001()` enables `symfony_http_client`) and install the new composer dependencies (`symfony/ai-platform`, `symfony/ai-generic-platform`, `drupal/symfony_http_client`). Then create platform entries at `/admin/config/ai/platforms` and re-select default providers.

Provider module authors: standalone `AiProvider` plugins are no longer returned by `getProvidersForOperationType()`. Implement an `AiPlatform` plugin instead:
```php
#[AiPlatform(
  id: 'gemini',
  label: new TranslatableMarkup('Gemini'),
)]
final class Gemini extends AiPlatformUsingApiKeyAuthenticationPluginBase {
  protected function initializePlatform(): PlatformInterface { /* PlatformFactory::create(...) */ }
}
```
Consumers loading a provider by ID should use the `ai_platform:<entity_id>` form, e.g. `\Drupal::service('ai.provider')->createInstance('ai_platform:echo_test')`.

### Collaboration

The design came out of two competing prototypes: a greenfield integration by mxr576 (!1214, introducing config entities for multi-instance platforms and a separate plugin type) and a backward compatibility focused one by fago (!1250, !1259). fago first posted a BC impact analysis of the ai core submodules and recipes (config and API consumers), concluding most config and recipes were unaffected if operation types stay. After comparing, the group chose mxr576's approach as the base, and fago's MR !1337 merged it with his `InputOutputConverter` and `PlatformProxy` BC pieces. Symfony AI 0.8.0 later added its own Provider abstraction, so the Platform/Provider naming was flagged by mxr576 as needing a follow-up decision (continuing in !1565).
