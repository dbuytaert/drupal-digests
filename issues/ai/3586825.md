## Summary

Chat requests that AI Automators send to a provider now identify which automator made them. Each request gets an `ai_automator:id:{config entity ID}` tag and an `entity_context` metadata array describing the entity and field. Several automators on the same field (for example separate Field Widget Action buttons) previously produced requests with identical tags, so event subscribers could not tell them apart. This was ported to 2.0.x/2.x and backported to 1.4.x after landing on 1.x and 1.5.x ([#3586702](https://www.drupal.org/node/3586702)).

## Impact

Affects module maintainers.

- **API change:** On 1.4.x the `InputBase` request metadata methods (`getAllRequestMetadata()`, `setAllRequestMetadata()`, `getRequestMetadataValue()`, `setRequestMetadataValue()`) are added, and `ProviderProxy` seeds pre and post event metadata from the input. Code that rebuilds the automator config array in `AutomatorConfigEvent` subscribers on 1.4.x must keep the `id` key.
- **New API:** Automator chat requests carry a new `ai_automator:id:{automator config entity ID}` tag and `entity_context` request metadata (`entity_type`, `entity_id`, `uuid`, `bundle`, `field_name`, `automator_id`). New protected `RuleBase::buildEntityContext()` and `RuleBase::attachEntityContext()` helpers.

## Technical details

`RuleBase::getTags()` now adds `ai_automator:id:{id}` when the automator config carries a string ID. `RuleBase::runRawChatMessage()` and the rich-text image description path in `RichTextImageDescriptionTrait` call the new `attachEntityContext()` on the final input, after `applyGuardrailsToInput()`, because that helper can return a clone. `buildEntityContext()` returns `entity_type`, `entity_id`, `uuid`, `bundle`, `field_name` and `automator_id`. `entity_id` is `NULL` for new (unsaved) entities, so presave requests are identified by `uuid`. The metadata is read with `$event->getMetadata('entity_context')`. Rules that build their own `ChatInput` (Chart, VideoToText, `LlmVideo*`, Field Widget Action refine chat) still send untagged requests, as the added docs state.

On 2.0.x/2.x the automator ID, field name and plugin ID are not stored settings. `AiAutomatorEntityModifier::withRuntimeContext()` clones each automator type and adds `automator_id`, `field_name` and `rule` to its settings, so nothing leaks into exported config. These runtime settings are set after the stored ones, so a stray stored setting with the same key cannot override them. `RunAutomatorAction` sets the same three keys, and the tag and metadata read `automator_id`.

On 1.4.x the ID lives in the `id` key of the runtime automator config instead. `AiAutomatorEntityModifier::entityHasConfig()` and `RunAutomatorAction` set it from the config entity ID, after the `plugin_config` keys are unprefixed. `RuleBase::attachEntityContext()` there is guarded with `method_exists($input, 'setRequestMetadataValue')`. The 1.4.x commit also adds request metadata to `InputBase`. `ProviderProxy` seeds the `PreGenerateResponseEvent` metadata from the input and passes the post event metadata to streamed responses. It also re-applies the input's system prompt to the provider after the pre-generate event, so event subscribers can change it.

## Upgrade

Subscribers can target one automator by tag:

```php
public function onPreGenerate(PreGenerateResponseEvent $event): void {
  if (!in_array('ai_automator:id:node.article.field_summary.default', $event->getTags(), TRUE)) {
    return;
  }
  $context = $event->getMetadata('entity_context');
  // $context['entity_id'] is NULL on presave; fall back to uuid or bundle.
}
```

Custom rules that build their own `ChatInput` should call `$this->attachEntityContext($input, $entity, $automatorConfig);` and pass `$this->getTags(...)` to `chat()`. On 2.x, code calling a rule outside `AiAutomatorEntityModifier` or `RunAutomatorAction` must add `automator_id`, `field_name` and `rule` to the settings itself. On 1.4.x, `AutomatorConfigEvent` subscribers that rebuild the config array must keep its `id` key, or the ID tag and `automator_id` are dropped.
