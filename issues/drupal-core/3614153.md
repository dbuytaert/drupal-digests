## Summary

Drupal's installer previously installed the System module as its own dedicated step before installing anything else, a pattern that dates back to Drupal's early history. This change installs System alongside the other required modules (and, for profiles that declare modules, alongside those too) in the same batch, eliminating an extra service-container rebuild during every installation. As part of removing the special-casing this required, the core "testing" install profile (used by Drupal's own and many contrib functional tests) no longer automatically enables the `page_cache` and `dynamic_page_cache` modules. Tests that rely on those modules being present for cache tag or cache header assertions now need to enable them explicitly. Reported savings were significant, one job's test run time dropped from 90 seconds to well under that, and a full functional test job went from over a minute to about two minutes total.

## Impact

No upgrade or configuration changes required.

## Technical details

Previously `drupal_install_system()` called `module_installer->install(['system'], FALSE)` directly as an isolated step, and both `install_profile_modules()` and `install_recipe_required_modules()` explicitly filtered `system` out of the module list they installed afterwards (`array_diff(array_unique($modules), ['system'])`). Now `system` is simply left in those module lists and installed together with the rest in the normal batch via `_install_module_batch()`, cutting one container rebuild out of the install path (and, for profiles with declared modules, another).

Because the default language config write (`system.site` `langcode`/`default_langcode`) used to happen right after installing System in `drupal_install_system()`, that logic moved into `_install_module_batch()`, which gained a new `$install_state` parameter (also threaded through `install_profile_modules()` and `install_recipe_required_modules()`) so it can still set the language once `system` shows up in whichever batch group installs it. Since the service container can now be compiled before System module (and its config) exists, `DrupalKernel::compileContainer()` gained a fallback that reads `$GLOBALS['install_state']['parameters']['langcode']` to seed `language.default_values` when `system.site` config isn't available yet; this is flagged with a `@todo` as a temporary workaround pending moving default-language config out of System module entirely (tracked in [#3337864](https://www.drupal.org/node/3337864)).

`install_config_import_batch()` no longer needs to copy the site UUID from the sync storage into the freshly-created `system.site` config (the "UUID juggle"), because System module's config is now imported directly rather than being created fresh and then overwritten. Correspondingly, `ConfigImporter::validateSiteUuid()` now returns `TRUE` when there's no target `system.site` config yet, since that indicates a fresh install-from-config rather than a UUID mismatch.

The `testing.info.yml`/`testing_multilingual.info.yml` profiles' `install:` keys for `drupal:page_cache` and `dynamic_page_cache` were removed, and many core functional test classes (JSON:API, REST, Views, Block, error/session tests, etc.) were updated to add `page_cache` and/or `dynamic_page_cache` to their `$modules` property, or install them at runtime, wherever the test actually depends on page or dynamic-page caching behavior. This groundwork is what makes [#3428372](https://www.drupal.org/node/3428372), open for over fifteen years, finally achievable, and several immediate follow-ups were spun off: [#3615455](https://www.drupal.org/node/3615455) (install database driver modules alongside others), [#3614401](https://www.drupal.org/node/3614401) (allow install profiles to opt out of being installed), [#3614825](https://www.drupal.org/node/3614825) (allow additional modules to be installed alongside profile modules), and [#3614817](https://www.drupal.org/node/3614817) (reduce parallel functional test jobs given the speedup).

## Upgrade

If your module's functional tests rely on Drupal core's "testing" install profile having `page_cache` or `dynamic_page_cache` enabled by default (for example, to assert cache tags/contexts or `X-Drupal-Cache` headers), add them explicitly to the test class:

```php
protected static $modules = [
  'your_module',
  'page_cache',
  'dynamic_page_cache',
];
```

or install them at runtime where needed:

```php
\Drupal::service('module_installer')->install(['page_cache']);
```

This change is only present on Drupal core's `main` branch (targeting Drupal 12) and was not backported to 10.x/11.x.
