## Summary

When the `rest` or `jsonapi` module is enabled, their `ResourceResponseSubscriber` event subscribers run on every single HTTP response. Previously each one had the full `serializer` service injected eagerly, which in turn pulled in every registered normalizer service and all of their own dependencies, even on requests that never produce a REST or JSON:API resource response. That serializer is now wrapped in a service closure and only instantiated the first time it is actually needed to serialize a response body. One reporter measured about 160 fewer classes loaded per request on a site with many normalizers registered. There is no behavior change for REST or JSON:API responses themselves.

## Impact

Affects module maintainers.

- **API change:** The `$serializer` constructor parameter of `Drupal\rest\EventSubscriber\ResourceResponseSubscriber` changed from `Symfony\Component\Serializer\SerializerInterface` to `\Closure`; call `($this->serializer)()` to obtain the serializer instance. The equivalent `@internal` `Drupal\jsonapi\EventSubscriber\ResourceResponseSubscriber` class changed identically.

## Technical details

Both `Drupal\rest\EventSubscriber\ResourceResponseSubscriber` and `Drupal\jsonapi\EventSubscriber\ResourceResponseSubscriber` now request their serializer service via Symfony's `#[AutowireServiceClosure('serializer')]` (`jsonapi.serializer` for the JSON:API variant) instead of `#[Autowire(service: ...)]`, and the constructor property type changed from `SerializerInterface` to `\Closure`. The subscribers' `onResponse()` methods invoke the closure, `($this->serializer)()`, only at the point where `renderResponseBody()` actually needs the serializer, so the serializer (and the chain of normalizer services it aggregates) is only constructed when a resource response is genuinely being serialized rather than on every request the subscriber is invoked for.

Test doubles in `ResourceResponseSubscriberTest` were updated to pass closures (`fn () => $this->prophesize(SerializerInterface::class)->reveal()`) instead of the serializer instance directly, matching the new constructor signature.

## Upgrade

Code that directly instantiates or subclasses `Drupal\rest\EventSubscriber\ResourceResponseSubscriber` and passes or reads the `$serializer` constructor argument must adapt to the new `\Closure` type:

```php
// Before:
new ResourceResponseSubscriber($serializer, $renderer, $routeMatch);

// After:
new ResourceResponseSubscriber(fn () => $serializer, $renderer, $routeMatch);
```

Any code reading `$this->serializer` directly must call it as a closure: `($this->serializer)()`. The `jsonapi` subscriber is `@internal` and carries no BC guarantee.

### Collaboration

berdir opened the issue after observing the eager serializer injection on a site with 25 normalizer-related services, and measured (via a preload script generated from dynamic page cache hits) that the closure approach loads about 160 fewer classes per request. berdir then extended the same fix to jsonapi's near-identical subscriber. When smustgrave asked whether a change record was needed, berdir argued no: event subscribers are, like hooks, conventionally excluded from Drupal's BC policy, and no subclasses of either class exist in core. catch, committing the patch, agreed with that BC reasoning for event subscribers, but noted the merge produced unexpected commit conflicts, suggesting some other unbackported constructor change to these classes, and flagged that a separate 11.x backport MR would be needed.
