## Summary

Drupal tracks "equivalent updates" so that a database update backported to an older, still-supported branch is recognized as equivalent to the update that originally shipped it in a newer branch, preventing confusing warnings or double-running of updates. Previously this registration only happened when the corresponding `hook_update_N()` actually ran through `update.php`, but hook_update_N() functions never run on a brand-new site install. That meant a site installed directly on the older version (e.g. 10.4) never got the equivalent update recorded, so it could later show incorrect "you are trying to go backwards" warnings once it was upgraded past the version containing the original update. This fix registers those equivalent updates during module installation too, so freshly installed sites behave the same as sites that arrived at that version through running updates.

## Impact

Affects module maintainers.

- **Deprecation:** Calling `UpdateHookRegistry::markFutureUpdateEquivalent()` without the new `$module` and `$ran_update_number` arguments is deprecated in `drupal:11.5.0` and will be required in `drupal:13.0.0`; the method is now `@internal`, use the `#[MarkFutureUpdateEquivalent]` attribute instead (see #3617733).
- **New API:** New `Drupal\Core\Update\Attribute\MarkFutureUpdateEquivalent` PHP attribute for `hook_update_N()` functions, letting the update be registered as equivalent even when the function never runs (e.g. on a fresh site install).

## Technical details

The mechanism is a new `#[MarkFutureUpdateEquivalent(futureUpdateNumber, futureVersionString)]` PHP attribute applied directly to a `hook_update_N()` function, replacing the old pattern of calling `\Drupal::service('update.update_hook_registry')->markFutureUpdateEquivalent()` from inside the update function body. Because attributes can be discovered by reflection without invoking the function, `ModuleInstaller::doInstall()` now loops through every available update number returned by `updateRegistry->getAvailableUpdates($module)` during install, reflects each `{$module}_update_{$version}` function with `ReflectionFunction`, and if it carries the attribute, calls `markFutureUpdateEquivalent()` on its behalf, wrapping the reflection/registration in a try/catch that logs via `Error::logException()`. The same reflection check was added to `update_do_one()` in `update.inc` so the attribute also drives registration when updates run through `update.php` (previously that path relied on the explicit service call still present in the update function body).

`UpdateHookRegistry::markFutureUpdateEquivalent()` gained two new parameters, `$module` and `$ran_update_number`, currently accepted only via `func_get_args()` (commented out in the signature) to avoid a hard API break; calling it the old way now triggers an `E_USER_DEPRECATED` notice and falls back to `determineModuleAndVersion()`. The method is documented `@internal` since the attribute is now the supported way to register these. Core's own `system.install` equivalent-update declarations and the `equivalent_update_test` fixture module were converted to use the attribute, and a new `equivalent_update_test_attribute_install` test module and `testAttributeOnInstall()` test verify the install-time registration path.

## Upgrade

Replace direct calls to `markFutureUpdateEquivalent()` inside an update function body with the attribute:

```php
use Drupal\Core\Update\Attribute\MarkFutureUpdateEquivalent;

#[MarkFutureUpdateEquivalent(11101, '11.1.1')]
function my_module_update_10400(): void {
  // The function can be no-op.
}
```

Calling `\Drupal::service('update.update_hook_registry')->markFutureUpdateEquivalent(11101, '11.1.1')` directly from inside the update function still works but is deprecated and will require the `$module` and `$ran_update_number` arguments in Drupal 13 (see [#3617733](https://www.drupal.org/node/3617733) and the change record at drupal.org/node/3572245).
