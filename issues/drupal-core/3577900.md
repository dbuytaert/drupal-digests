## Summary

Drupal's plugin system has been moving from PHP annotations to PHP attributes for defining plugins. Since Drupal 11.2, plugin managers that only supported annotation-based discovery (and not the newer attribute-based discovery) triggered a silenced deprecation warning that was easy to miss. As of this change, any plugin manager, in core or in contributed and custom modules, that does not also provide an attribute class will now cause a fatal error when it is instantiated. This is intentional: since many contrib modules define plugin types that other contrib modules provide plugins for, forcing plugin-type-providing modules to add attribute support now (rather than waiting for Drupal 13) gives the wider ecosystem more time to update before the final removal of annotation-only discovery.

## Impact

Affects module maintainers.

- **API change:** Constructing `DefaultPluginManager` (or a subclass) with only `$plugin_definition_annotation_name` and no attribute class now throws an `\InvalidArgumentException` at construction time instead of triggering a silenced `E_USER_DEPRECATED` notice.

## Technical details

The change is in `DefaultPluginManager::__construct()` in `core/lib/Drupal/Core/Plugin/DefaultPluginManager.php`. Previously, when a `$plugin_definition_attribute_name` was passed but did not implement `AttributeInterface` (i.e. only an annotation class was effectively usable), the constructor called `@trigger_error(...)` with `E_USER_DEPRECATED`, which is easy for sites and CI to ignore. Now it throws `new \InvalidArgumentException(..., E_USER_WARNING)` with a message pointing to the original deprecation change record (drupal.org node 3395582), so instantiating such a plugin manager fails outright rather than warning.

Accompanying core tests were updated: `DefaultPluginManagerTest::testDefaultPluginManager()` dropped its annotation-only assertions, and `testDefaultPluginManagerAnnotationsOnly()` now expects the thrown exception message instead of a deprecation message. This does not affect plugin managers that already provide both an attribute class and an annotation class for backward compatibility, which remains the supported pattern; only managers exposing annotation-only discovery are affected. This issue was tracked as a follow-up enforcement of the change documented in the existing change record https://www.drupal.org/node/3522776 (itself a "now you have to do it" successor to https://www.drupal.org/node/3395582 from 2023), so no new change record was created.

## Upgrade

If you maintain a plugin manager that extends `DefaultPluginManager` (or implements similar annotation/attribute discovery) and it currently only supports annotation-based plugin discovery, you must add a PHP attribute class before upgrading to Drupal 12, or code that instantiates your plugin manager will throw:

```
InvalidArgumentException: Drupal\Your\Namespace\YourPluginManager only supports
annotation-based discovery, which is no longer supported as of Drupal 12.0.
Provide an Attribute class and an Annotation class for BC. See
https://www.drupal.org/node/3395582
```

To fix, define an Attribute class (implementing the plugin's attribute annotation pattern) and pass both the attribute and annotation class names to the parent constructor, e.g.:

```php
parent::__construct(
  $subdir,
  $namespaces,
  $module_handler,
  $plugin_interface,
  MyPluginAttribute::class,
  MyPluginAnnotation::class
);
```

### Collaboration

Committer catch and berdir discussed how to enforce the requirement: catch initially suggested "unsilencing" the deprecation (making the existing `E_USER_DEPRECATED` visible) as a middle ground rather than a hard break, and smustgrave agreed, noting modules like entity_embed still lacked attribute support. berdir then implemented the unsilencing approach, but reported in comment [#16715227](https://www.drupal.org/node/16715227) that he couldn't find a good way to test for an `E_USER_DEPRECATED`/`E_USER_WARNING` in this case, and revised the MR to throw an exception instead, explaining "I think I'd prefer that option. We really want contrib to pick this up in D12 IMHO." That became the version that was committed. Separately, benjifisher and catch pushed back on the initial issue title as an unclear double negative, leading to the retitling to its current, clearer form.
