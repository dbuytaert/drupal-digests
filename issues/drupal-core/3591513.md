## Summary

The `update_fetch_with_http_fallback` setting, which lets a site fall back to insecure HTTP when it can't reach updates.drupal.org over HTTPS, is now deprecated with no planned replacement. It still works exactly as before, but any site that has explicitly set this in its `settings.php` will see a deprecation warning, and the setting itself will be removed entirely in Drupal 12. In practice, few sites should have this enabled, since it exists only as an insecure fallback for connectivity problems that HTTPS-everywhere has mostly made obsolete.

## Impact

Affects module maintainers.

- **Deprecation:** The `update_fetch_with_http_fallback` settings.php key is deprecated in Drupal 11.5.0 for removal in Drupal 12.0.0, with no replacement.

## Technical details

The actual fetch logic in `\Drupal\update\UpdateFetcher` and `\Drupal\system\SecurityAdvisories\SecurityAdvisoriesFetcher` is untouched: this is a pure deprecation, not a behavior change. The setting was registered in `Drupal\Core\Site\Settings::$deprecatedSettings` with an empty `replacement` key (since there is nothing to migrate to) and a message pointing to the change record. This relies on the `Settings::handleDeprecations()` mechanism to emit the deprecation at bootstrap when the setting is actually configured.

Getting this landed required a companion fix in [#3592037](https://www.drupal.org/node/3592037): originally `Settings::get()` triggered the deprecation warning unconditionally for any key listed in `$deprecatedSettings`, even when the caller was just requesting the default value because the setting was never set in `settings.php`. That caused every kernel test instantiating `UpdateFetcher` or `SecurityAdvisoriesFetcher` to emit a spurious deprecation. Once [#3592037](https://www.drupal.org/node/3592037) fixed `Settings::get()` to only fire when the setting is actually present in storage, this issue could proceed. Several test methods that intentionally set the value (`SettingsValidatorTest`, `UpdateFetcherTest`, `SecurityAdvisoriesFetcherTest`, `SettingsTest::testRealDeprecatedSettings`) were annotated with `#[IgnoreDeprecations]` since they exercise the deprecated code path on purpose.

A follow-up issue, [#3613344](https://www.drupal.org/node/3613344), has been opened to remove the setting entirely on the 12.x branch.</technical>

macsim found and diagnosed a subtle problem while implementing the deprecation: registering the setting in `Settings::$deprecatedSettings` caused `Settings::get()` to fire a deprecation warning on every call, even for sites that never configured it, breaking unrelated kernel tests that merely instantiate `UpdateFetcher` or `SecurityAdvisoriesFetcher`. Macsim laid out two possible fixes in detail and, after discussion with mstrelan, they agreed the root-cause fix belonged in `Settings::get()` itself rather than being patched around.
