## Summary

Drupal core gains an experimental Design Tokens API, a standardized way to declare small, typed design values (dimensions, font families, font weights, numbers, typography) following the W3C Design Tokens Community Group (DTCG) format, and to override their values per CSS selector "scope" (e.g. `:root`, `.card`) through a new `design_token` configuration entity. This follows the same front-end-friendly, YAML-plugin pattern already used by Single Directory Components and the Icon API, aiming to give contrib modules and Drupal themes a common vocabulary for CSS custom properties instead of everyone inventing their own. The API is explicitly marked experimental and not meant for production use yet: it defines the discovery and storage format, but does not yet include a mechanism for actually publishing the overridden values as page CSS, that is left for a follow-up. A new "Administer design tokens" permission controls who can manage the override entities, and existing sites get the new entity type automatically via a database update.

## Impact

Affects module maintainers and site owners.

- **Database update:** `system_update_12002()` installs the new `design_token` config entity type on existing sites when they run database updates.
- **Permission change:** New `administer design tokens` permission required to manage `design_token` config entity overrides.
- **New API:** New `design_token` plugin type (`*.tokens.yml` discovery, W3C DTCG format) and `design_token_value` plugin type (`Dimension`, `FontFamily`, `FontWeight`, `Number`, `Typography`) for declaring design tokens, plus a new `design_token` config entity type for overriding token values by CSS selector scope.

## Technical details

Tokens are discovered from `{provider}.tokens.yml` files (theme or module root) via `YamlDiscovery` inside the new `DesignTokenPluginManager`. Because DTCG data is a nested tree of groups and tokens (a token is any node containing a `$value` key), `DesignTokenPluginManager::parseDtcg()` walks the raw YAML into `Group`/`DesignToken` objects (both implementing `DtcgInterface`) and then `flattenDefinitions()` collapses that tree into flat plugin definitions keyed by dotted path (e.g. `fontSize.small`).

Each token's `$value` is resolved through a separate `design_token_value` plugin type (`#[DesignTokenValue]` attribute, discovered under `Plugin/DesignTokenValue`), which implements `DesignTokenValueInterface::toDtcg()`/`toCss()`. Core ships five initial value types: `Dimension` (restricted to `px`/`rem` per the current DTCG spec, though downstream code can subclass it to add units), `FontFamily`, `FontWeight` (accepts DTCG alias strings like `bold`/`light` via the `FontWeightAlias` enum), `Number`, and the composite `Typography`. Eight more DTCG types (color, shadow, gradient, etc.) are intentionally left for contrib and a later core proposal.

Value overrides live in the new `design_token` config entity (`Drupal\Core\Theme\Entity\DesignToken`), keyed by `path`/`type`, with a `scopes` map from CSS selector to a `DesignTokenValuePluginCollection` of typed values (dots in scope keys are escaped to `%` for config storage via `getConfigScopeName()`/`getCssScopeName()`). `DesignToken::toCss()` serializes a set of token entities into grouped inline CSS (`selector{--name:value;}`). A new `CssSelector` validation constraint blocks `{`, `}`, `;` in scope keys to prevent CSS injection through stored config.

## Upgrade

To declare theme or module design tokens, add a `{provider}.tokens.yml` file using the DTCG format, for example:

```yaml
fontSize:
  small:
    "$type": dimension
    "$value":
      value: 12
      unit: px
```

To override a token's value for a given CSS selector, create a `design_token` config entity:

```yaml
id: my_id
path: foo.bar.baz
type: dimension
scopes:
  ':root':
    value: 12
    unit: px
```

This API is experimental (`@internal`, "not meant for production use"): no publishing mechanism ships yet to turn overridden config entities into page CSS, and the value type list and validation are expected to change before stabilization.

### Collaboration

Contributor kim.pepper repeatedly pushed for making the allowed dimension units (currently hardcoded to `px`/`rem` per the DTCG spec) extensible rather than fixed; pdureau held the line for the initial scope to stay strictly spec-compliant, but showed how downstream code can subclass `Dimension` to add units like `%`. larowlan prototyped a plugin-collection based approach for handling scopes on a separate branch, which grimreaper then adopted into the MR. During final review wim leers and penyaskito raised architectural concerns, incomplete config validation and the assumption that a design token always maps to exactly one CSS property, which led to descoping some features; the first follow-up, [#3590100](https://www.drupal.org/node/3590100) for design token aliases, was split out to keep this initial API landing minimal ahead of the release deadline.
