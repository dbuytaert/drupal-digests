## Summary

Drupal's installer used to carry a special workaround: a static cache and dedicated `InstallerModuleExtensionList`/`InstallerThemeExtensionList` classes that remembered extension file paths across the container rebuilds that happen during installation. That workaround is no longer needed because the base extension list classes can now resolve manually seeded pathnames on their own, so the installer-specific machinery has been removed and the classes that implemented it are deprecated. Along the way, a related bug was fixed: when locating a profile's optional config overrides, `ConfigInstaller` was looking up the profile's directory using the "module" extension type instead of "profile", which is now corrected.

## Impact

Affects module maintainers.

- **Deprecation:** `Drupal\Core\Installer\ExtensionListTrait`, `InstallerModuleExtensionList` and `InstallerThemeExtensionList` are deprecated in 11.5.0 with no replacement (base extension list classes now provide the same behavior); use `Drupal\Core\Extension\ModuleExtensionList` / `ThemeExtensionList` directly. `Drupal\Core\Extension\ExtensionList::setPathname()` is also deprecated as an internal-only method with no replacement. All are removed in Drupal 13.0.0.

## Technical details

`install_begin_request()`, `InstallStorage::getAllFolders()` and `ExtensionInstallStorage::getAllFolders()` no longer prime `ExtensionList::setPathname()` for the active install profile; they rely on the base `ExtensionList`'s ability to resolve pathnames added via `$addedPathNames` directly. `NormalInstallerServiceProvider` no longer swaps the `extension.list.module` and `extension.list.theme` service classes to the installer-specific subclasses. `ModuleExtensionList::__construct()` now writes container-provided pathnames straight into `$this->addedPathNames` instead of calling the now-deprecated `setPathname()`.

`Drupal\Core\Installer\ExtensionListTrait`, `InstallerModuleExtensionList`, and `InstallerThemeExtensionList` are reduced to backward-compatibility shims that trigger a deprecation notice on use; they are removed in Drupal 13.0.0 with no replacement, since `ModuleExtensionList`/`ThemeExtensionList` now cover the same behavior. `ExtensionList::setPathname()` itself is also deprecated (it remains `@internal`) with no replacement.

`ConfigInstaller::installOptionalConfig()` and `getProfileStorages()` now call `$this->extensionPathResolver->getPath('profile', $profile)` instead of `getPath('module', $profile)` to locate the profile's optional config directory, fixing incorrect path resolution for profiles whose directory structure differs from a same-named module.

## Upgrade

Code that extends or type-checks against the deprecated classes should switch to the base extension list classes:

```php
// Before
use Drupal\Core\Installer\InstallerModuleExtensionList;
use Drupal\Core\Installer\InstallerThemeExtensionList;

// After
use Drupal\Core\Extension\ModuleExtensionList;
use Drupal\Core\Extension\ThemeExtensionList;
```

Any code calling `\Drupal\Core\Extension\ExtensionList::setPathname()` directly should stop doing so; it is deprecated with no replacement and will be removed in Drupal 13.0.0. All three classes and the method continue to work until then but emit `E_USER_DEPRECATED` notices.
