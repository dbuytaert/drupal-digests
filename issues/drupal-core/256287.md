## Summary

User roles can now have a description, similar to content types, vocabularies, and menus. On the Roles page (`/admin/people/roles`) a new "Description" column shows this text, and the role edit form gets a "Description" textarea site builders can fill in to document why a role exists. Existing core profiles and the built-in `anonymous`/`authenticated` roles ship with an empty description rather than prose: an earlier version of this patch added default descriptive text for core's roles, but the usability team could not reach consensus on wording after multiple review meetings, so that part was split off into follow-up issues ([#3470972](https://www.drupal.org/node/3470972) and [#3470976](https://www.drupal.org/node/3470976)) and this issue only adds the empty field itself.

## Impact

Affects module maintainers and site owners.

- **Config change:** The `user_role` config entity type gets a new `description` config key (schema type `text`); a post update backfills existing role configs with an empty string.
- **New API:** `\Drupal\user\RoleInterface` gains `getDescription(): string` and `setDescription(string $description): static` for storing an optional description on a role.

## Technical details

The change adds a `protected string $description = ''` property to the `Role` config entity class (`core/modules/user/src/Entity/Role.php`), exposes it via the new `getDescription()`/`setDescription()` methods on both `Role` and `\Drupal\user\RoleInterface`, and adds `description` to the entity's `config_export` list and to `user.role.schema.yml` (type `text`). `RoleForm` now renders a `#type => textarea` field for it, trimmed like the label is, and `RoleListBuilder::buildHeader()`/`buildRow()` add a "Description" column, rendering it defensively only when the row entity is an instance of `RoleInterface`.

Because this is a minor-version addition to an interface without `@internal`/`@api` restrictions, it's allowed per Drupal's BC policy, which permits adding methods to such interfaces in minor releases. All shipped core `user.role.*.yml` config files (including in the `standard` and `demo_umami` install profiles) were updated with `description: ''`, and `user_post_update_add_role_description()` (using `ConfigEntityUpdater`) backfills the empty string for every existing `user_role` config that lacks the key on already-installed sites. REST and JSON:API normalizations for roles now include the `description` property.

## Upgrade

Code that implements `\Drupal\user\RoleInterface` directly (rather than extending `\Drupal\user\Entity\Role`) must implement the two new methods:

```php
public function getDescription(): string;
public function setDescription(string $description): static;
```

Custom or contrib config that defines `user_role` entities should add a `description` key (a plain string, may be empty) to stay consistent with the updated config schema.

### Collaboration

This feature request dates back to 2008 and stalled for years. The main obstacle in its final push was not the code but the wording: rkoller reported back from three separate Drupal usability team meetings (2023-06-09, 2023-06-16, 2023-12-01) that the group could reach no consensus on non-redundant default description text for the `Anonymous user`, `Authenticated user`, `Administrator`, and `Content editor` roles, despite extensive async discussion in a shared document. To unblock the underlying feature, the usability team recommended stripping default descriptions out of scope entirely and deferring them to follow-up issues, which rkoller then filed ([#3470972](https://www.drupal.org/node/3470972), [#3470976](https://www.drupal.org/node/3470976)). megachriz subsequently rerolled the stalled patch into a merge request implementing exactly that reduced scope, dropping the default text, the related config fixture updates, and the now-unneeded `AddUserRoleDescriptionTest`, while tightening the new methods with strict typing per feedback from longwave and smustgrave earlier in the thread.
