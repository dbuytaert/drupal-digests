## Summary

The database exception classes were reorganized so that errors coming from the database client are all subclasses of `DatabaseExceptionWrapper`, and every exception implements the `DatabaseException` interface. Missing and already existing tables now throw dedicated exceptions. Exception messages now show the SQL and its placeholder values on a single line, instead of a multi-line `print_r()` dump.

## Impact

Affects module maintainers.

- **API change:** Exception hierarchy changed, `DatabaseExceptionWrapper` gets an optional `$info` argument, `SchemaDefinitionException` no longer extends `SchemaException`, and `Connection::getDriverClass()` throws `\InvalidArgumentException`.
- **Deprecation:** `TransactionExplicitCommitNotAllowedException` is deprecated in drupal:12.1.0 with no replacement.
- **New API:** New `SqlExecutionInfo`, `SchemaTableDoesNotExistException` and `SchemaTableAlreadyExistsException`.

## Technical details

`DatabaseExceptionWrapper` now takes an optional fourth constructor argument, a `public readonly ?SqlExecutionInfo $info`. The new `SqlExecutionInfo` value object holds `sqlQuery`, `placeholders` and `options`. Its `toCompactString()` collapses whitespace in the query and escapes newlines in string placeholder values. `appendToMessage()` builds the message suffix `: <sql>; [name=value, ...]`.

Inheritance changes: `IntegrityConstraintViolationException`, `DatabaseAccessDeniedException`, `DatabaseConnectionRefusedException`, `DatabaseNotFoundException`, `SchemaException` and `TransactionException` now extend `DatabaseExceptionWrapper`. `ConnectionNotDefinedException` and `DriverNotSpecifiedException` now implement `DatabaseException`. `SchemaDefinitionException` no longer extends `SchemaException` and extends `\RuntimeException` instead. New `Drupal\Core\Database\Exception\SchemaTableDoesNotExistException` (extends `SchemaObjectDoesNotExistException`) and `SchemaTableAlreadyExistsException` (extends `SchemaObjectExistsException`) are thrown by `Schema::createTable()`, `introspectIndexSchema()` and the MySQL `renameTable()`. The MySQL handler also maps error codes 1050, 1051 and 1146 to them. The new exceptions extend the old ones, so existing `catch` blocks keep working.

In the core `ExceptionHandler`, `handleStatementException()` and `handleExecutionException()` now delegate to a new protected `rethrowNormalizedException()` that builds `SqlExecutionInfo`, so SQL and placeholders are available on the exception. The MySQL, pgsql and SQLite handlers follow the same pattern, so statement-level errors are normalized on every driver. `Connection::getDriverClass()` now throws `\InvalidArgumentException` instead of `InvalidQueryException` for the unsupported legacy class lookup. `TransactionExplicitCommitNotAllowedException` is deprecated in drupal:12.1.0 and removed in drupal:13.0.0, with a `trigger_error()` on load.

## Upgrade

Code that parses database exception messages should not rely on the old format (`message: sql; Array (...)`). Read the SQL and placeholders from the new property instead:

```php
try {
  $connection->query($sql, $args);
}
catch (\Drupal\Core\Database\DatabaseExceptionWrapper $e) {
  $sql = $e->info?->sqlQuery;
  $placeholders = $e->info?->placeholders;
}
```

Stop referencing `TransactionExplicitCommitNotAllowedException`. Contrib database drivers should have their exception handlers throw `SchemaTableDoesNotExistException` and `SchemaTableAlreadyExistsException` and pass a `SqlExecutionInfo` to the wrapper exceptions. The issue mentions two change records for these points, but I did not read them.
