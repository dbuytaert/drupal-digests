## Summary

Views builds a large in-memory data structure describing every database table exposed to Views (via `hook_views_data()`), and caches it both as one big entry and as many smaller per-table entries. Per-table entries were previously stored in the regular persistent cache (`cache.default`); they are now stored in the `cache.discovery` bin, which is chained with a fast, per-process backend like APCu when available. Since the set of tables is finite and rebuilt rarely, this lets repeat lookups for the same table on a page be served from local memory instead of the primary cache backend (Redis, database, etc.), reducing cache reads on pages that use Views. The single "all views data" entry stays in `cache.default` because it can be very large and the maintainers were concerned that pushing it into a fast in-memory bin could evict other cached data on large, multilingual sites.

## Impact

Affects module maintainers.

- **Deprecation:** `\Drupal\views\ViewsData::cacheGet()` and `cacheSet()` are deprecated in Drupal 11.5.0 and removed in 12.0.0, with no replacement.

## Technical details

The initial commit simply swapped the constructor's `#[Autowire]` target for `ViewsData::$cacheBackend` from `cache.default` to `cache.discovery`, but this was reverted after `berdir` pointed out that the combined "all tables" entry can be tens of megabytes on sites with many languages or entity bundles, and forcing all of that into the chained-fast (APCu-backed) bin risked frequent APCu expunges and a performance regression rather than an improvement.

The follow-up `perf` commit instead adds a second injected backend, `$chainedFastBackend` (`cache.discovery`), used only for the per-table cache entries in `ViewsData::get()`, while `getData()` keeps using `$cacheBackend` (`cache.default`) for the full "all tables" entry. A new `ViewsData::CACHE_TAGS` constant centralizes the `views_data` and `config:core.extension` cache tags used when setting either bin. The old protected `cacheGet()`/`cacheSet()` helpers, which always prefixed the langcode and used `$cacheBackend`, are no longer used internally and are deprecated with `@trigger_error`; callers should use the injected cache backends directly, following how the rest of the class now works.

Performance test fixtures (`FrontPageTest`, `StandardPerformanceTestTrait`, `Umami`/`Standard` profile test YAMLs) were updated to reflect the shift: `discovery` cache-get counts go up and `default` cache-get counts go down by the same amount, confirming per-table lookups now hit `cache.discovery`.

## Upgrade

Subclasses or code relying on `\Drupal\views\ViewsData::cacheGet()` or `cacheSet()` will get a deprecation notice starting in Drupal 11.5.0 and must stop using them before 12.0.0, since there is no direct replacement method. Interact with the injected `$cacheBackend` (`cache.default`, for the "all data" entry) or the new `$chainedFastBackend` (`cache.discovery`, for per-table entries) directly instead:

```php
// Before (deprecated):
$data = $this->cacheGet($cid);
$this->cacheSet($cid, $data);

// After, for per-table entries:
$data = $this->chainedFastBackend->get($this->prepareCid($cid));
$this->chainedFastBackend->set($this->prepareCid($cid), $data, Cache::PERMANENT, static::CACHE_TAGS);
```

### Collaboration

catch proposed moving the whole `ViewsData` cache to `cache_discovery` and alexpott committed it, but berdir flagged a regression risk: on large or heavily multilingual sites the combined "all tables" cache entry can be megabytes in size, and pushing that into APCu-backed chained-fast storage risks frequent expunges that hurt performance more broadly (citing real-world monitoring data from sites using an APCu-expunge sensor). alexpott reverted the commit the same day. berdir then measured actual cache entry sizes with a script run against a production-like Redis dataset, showing the "all tables" entries were an order of magnitude larger than the sum of per-table entries, and suggested moving only the per-table entries into the fast bin. catch implemented that split (two injected cache backends), and the two also floated further ideas (a `hook_views_data_table()`-style API, and not caching views data per-language) that were not pursued in this issue. berdir later reviewed again and preferred catch's simplified follow-up that dropped the old `cacheGet`/`cacheSet` helpers entirely in favor of calling the backends directly, calling it "much nicer."
