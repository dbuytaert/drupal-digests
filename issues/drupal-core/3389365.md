## Summary

Migrating a Drupal 7 site's translated block titles (via the `i18n_block` module) into Drupal could silently mis-migrate translations when the same block delta was placed in more than one theme, for example the same "User login" block in both `bartik` and `seven`. The underlying migration test (`MigrateBlockContentTranslationTest`) had been skipped for over a year because it failed randomly, masking this bug. This issue diagnoses and fixes the real defect and re-enables the test, so Drupal 7 to Drupal 9+ upgrades that use i18n block translations now migrate reliably.

## Impact

No upgrade or configuration changes required.

## Technical details

The `d7_block_translation` migrate source plugin's `getIds()` declared only `delta` and `language` as the migrate map's unique identifiers, omitting `theme`. Because the same `delta` (e.g. `user/login`) can exist as separate rows for different themes in a Drupal 7 site, this let the migrate map's `source_ids_hash` collide across themes, causing the translation for a block in one theme to overwrite or be skipped in favor of another. The fix adds `theme` to `getIds()` (aliased to the block table alias `b`) in `core/modules/block/src/Plugin/migrate/source/d7/BlockTranslation.php`, and adds `theme` to the `source` list of the `migration_lookup` process plugin in `core/modules/config_translation/migrations/d7_block_translation.yml` so the lookup into `d7_block` correctly disambiguates by theme as well as module and delta.

Separately, the test class's `$modules` list had lost the `config_translation` module (removed in an unrelated cleanup, [#3554484](https://www.drupal.org/node/3554484)) even though it provides the `d7_block_translation` migration itself, which had made the test inconsistent. That dependency is restored and the `markTestSkipped()` call is removed from `MigrateBlockContentTranslationTest::testBlockContentTranslation()`.

### Collaboration

The bug took over a year and a half to pin down because the test failed intermittently rather than consistently. acbramley found it failed 100% of the time locally and traced the migrate map to a single stale row, and quietone identified that the missing `config_translation` module dependency (removed in [#3554484](https://www.drupal.org/node/3554484)) was needed because it supplies the `d7_block_translation` migration. Even after that fix, longwave found the test still failed 3 of 100 CI runs and, with debugging help from Claude, identified the deterministic root cause: `theme` was missing from the source plugin's `getIds()`, which let the migrate map's row hash collide across themes. A follow-up 200-run repeat job confirmed the fix.
