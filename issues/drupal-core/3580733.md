## Summary

On sites using core's experimental default_admin theme, visiting admin pages built from Views status fields (such as /admin/people) triggered a PHP 8.5 deprecation warning, "Using null as an array offset is deprecated", because the "Published"/"Unpublished" badge template tried to look up a translation using a language code that could be null. The same faulty logic also meant the published/unpublished badge could show the wrong color on views not based on nodes (for example taxonomy term listings), since it relied on a variable that only exists for node-based views. Both problems are fixed: the warning no longer appears, and the badge now reflects the correct publication state for any publishable entity type shown in a status field.

## Impact

Affects front-end developers.

- **Theme change:** The `default_admin` theme's `views-view-field--status.html.twig` template no longer resolves the row's translated entity itself; it now receives a computed `is_published` boolean/null variable from a new preprocess hook, and no longer receives an `entity` variable.

## Technical details

The old `views-view-field--status.html.twig` template inlined Twig logic to fetch the row's entity translation via `row._entity.getTranslation(row.node_field_data_langcode)` before checking `isPublished()`. `node_field_data_langcode` is a row property that only exists for node-based views, so on other views (or monolingual sites) it evaluated to `NULL`, which is what triggered the deprecation inside `ContentEntityBase::hasTranslation()`, and also silently produced the wrong publication state for non-node entities like taxonomy terms.

The fix moves this logic out of the template entirely. A new `hook_preprocess_HOOK()` implementation, `PreprocessHooks::preprocessViewsViewFieldStatus()` (theme suggestion `views_view_field__status`, which fires for any views field with the machine ID `status` on any entity type), resolves the row's entity through the field handler's own `EntityField::getEntity()` (respecting configured relationships via `row._relationship_entities`), and only sets a boolean `is_published` variable when the field's underlying entity field type is `boolean`. Otherwise `is_published` is `NULL`. The template was simplified to branch purely on `is_published`: `TRUE` renders the `marker--published` span, `FALSE` renders the plain `marker` span, and `NULL` renders the raw `output` with no marker at all, so fields that aren't a real published flag (e.g. `views_test_data.status` handled by the `boolean` plugin) pass through unaffected.

Because the entity is now resolved through the field handler, translation handling follows the view's configured rendering language instead of a hardcoded node-specific row property, fixing the mismatch for non-node views. Follow-up issues [#3608223](https://www.drupal.org/node/3608223) and [#3619121](https://www.drupal.org/node/3619121) were opened to move this kind of status-badge formatting into a proper Views field formatter rather than being hardcoded in the theme layer.

## Upgrade

Themes that override `core/themes/default_admin/templates/views/views-view-field--status.html.twig` need to update their copy: the template no longer receives an `entity` variable and instead receives `is_published` (`TRUE`, `FALSE`, or `NULL`):

```twig
{% if is_published is null %}
  {{ output -}}
{% elseif is_published %}
  <span class="marker marker--published">{{ output -}}</span>
{% else %}
  <span class="marker">{{ output -}}</span>
{% endif %}
```

### Collaboration

The fix went through several rounds of design disagreement before landing. penyaskito's initial proposal was to simply delete the translation lookup from the template, but berdir and alexpott argued the theme layer should not be resolving entity translations at all, and considered removing the status badge feature from default_admin entirely (with alexpott noting it should be reintroduced later with the multilingual issue fixed properly). jurgenhaas then produced MR!16557, moving the logic into a preprocess hook that computes a boolean published state; boromino reviewed it and suggested extracting named helper methods (`getResultRowEntity()`, `isPublishedStatusField()`) for clarity, which jurgenhaas applied. godotislate then explored two further alternatives, MR!16768 (preprocess using the field handler's entity resolution) and MR!16769 (template-only), after finding the original approach didn't handle entities like `user` that lack a published key or `EntityPublishedInterface`. berdir pushed back against using `getFieldMap()` in MR!16768 due to performance concerns raised in [#3565128](https://www.drupal.org/node/3565128), so godotislate removed it in favor of calling `EntityField::getEntity()` directly. The group ultimately converged on MR!16768 as the pragmatic minimal fix, with berdir and jurgenhaas agreeing to defer the "proper" solution (a configurable Views boolean formatter) to follow-up issues [#3608223](https://www.drupal.org/node/3608223) and [#3619121](https://www.drupal.org/node/3619121).
