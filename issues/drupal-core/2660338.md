## Summary

Drupal's internal logic for picking which plural form of a translated string to show (for example "1 apple" versus "3 apples", or the more complex rules some languages like Polish use) has been reorganized, and the old procedural helper `locale_get_plural()` is now deprecated and will be removed in Drupal 13. There is no behavior change for site visitors or translators: plural translations render exactly as before. The change is part of the long-running effort to remove procedural functions from `locale.module` and stop Drupal Core code from depending directly on the optional Locale module. Sites and modules that call `locale_get_plural()` directly (rare, since it was never part of the public plural-translation API) need to stop doing so before Drupal 13.

## Impact

Affects module maintainers.

- **API change:** `TranslationInterface` gains a new method `selectPluralForm(int|float $count, string $string, ?string $langcode = NULL): string`; custom classes implementing the interface directly must add it.
- **Deprecation:** The procedural `locale_get_plural()` function is deprecated in drupal:11.5.0 for removal in drupal:13.0.0, with no direct replacement.

## Technical details

The plural-index logic that lived in `locale_get_plural()` moved behind a new `TranslationInterface::selectPluralForm()` method. The base implementation in `Drupal\Core\StringTranslation\TranslationManager` only distinguishes singular from plural (always returning index 1 for any count other than 1); the real per-language formula lookup now lives in a new `Drupal\locale\TranslationManager`, which extends the core class and injects the existing `PluralFormulaInterface` (`locale.plural.formula`) service to replicate what `locale_get_plural()` used to compute via `\Drupal::service('locale.plural.formula')->getFormula()`. `LocaleServiceProvider::alter()` swaps the `string_translation` service's class to this new `Drupal\locale\TranslationManager` whenever the Locale module is enabled; `core.services.yml` switched the `string_translation` service definition from a fixed argument list to `autowire: true` so the extra constructor dependency resolves automatically.

`PluralTranslatableMarkup::translateString()` now calls `getStringTranslation()->selectPluralForm()` instead of branching on `function_exists('locale_get_plural')` and `\Drupal::hasService('locale.plural.formula')`, removing a hardcoded Core-to-Locale dependency noted in a long-standing `@todo` referencing this issue. Two smaller, verifiable side effects landed with the refactor: `selectPluralForm()` types `$count` as `int|float`, so a non-numeric count passed to `formatPlural()` now throws a `TypeError` instead of silently mis-selecting a form; and `PluralTranslatableMarkup::getArguments()` now lets an explicitly supplied `@count` argument override the displayed value while the real `$count` still drives plural-form selection.

Related cleanups in the same area are tracked in [#1577902](https://www.drupal.org/node/1577902) (removing `drupal_static()` usage across core) and [#1273968](https://www.drupal.org/node/1273968) (original formula-caching work in `locale.module`, referenced in review as prior art for the static caching that was ultimately dropped here after benchmarking showed no measurable performance gain).

## Upgrade

There is no direct replacement for `locale_get_plural()`. Use the normal plural translation API instead of computing the index yourself:

```php
// Before:
$index = locale_get_plural($count, $langcode);

// After: let the translation system render the correct plural form directly.
$markup = \Drupal::translation()->formatPlural($count, '@count item', '@count items', [], ['langcode' => $langcode]);
```

If you implement `Drupal\Core\StringTranslation\TranslationInterface` directly (rather than extending `TranslationManager`), add the new required method:

```php
public function selectPluralForm(int|float $count, string $string, ?string $langcode = NULL): string {
  // ...
}
```

### Collaboration

After years of stalled patches, berdir picked this up and initially tried a decorator approach, then reconsidered: "I'm not found of decorators generally and this also comes with changes to a pretty fundamental interface," and instead built a small new service/interface, calling the result "much cleaner." When andypost worried that removing the decades-old static caching in `locale_get_plural()` might hurt performance (citing [#1273968](https://www.drupal.org/node/1273968)), berdir benchmarked calling the function 100,000 times, found the caching made no measurable difference, and removed it. Nicxvan reviewed the architecture closely and wrote up an explanation of gettext plural formulas in the issue thread to document the reasoning for future readers.
