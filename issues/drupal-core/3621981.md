## Summary

Drupal core's new default admin theme (the successor to Claro) had an undocumented convention: if a site placed a file named `admin-custom.css` in the public files directory, core would automatically detect and load it after the theme's own CSS, letting site builders inject custom admin styling without modifying the theme. This issue removes that feature entirely on the grounds that core shouldn't be reaching into the public files directory for this purpose. Sites that were relying on an `admin-custom.css` file in `public://` to tweak the admin theme's appearance will need a different approach, such as a sub-theme or a dedicated library.

## Impact

No upgrade or configuration changes required.

## Technical details

The removal spans three places that worked together to implement the convention. The `admin_custom_css` library definition in `default_admin.libraries.yml`, which pointed at `public://admin-custom.css` with `weight: 50`, was deleted. `Drupal\default_admin\Hook\ThemeHooks::cssAlter()`, the `hook_css_alter()` implementation that bumped the custom file's CSS aggregation group to `201` so it would load after `admin.css`, was removed. And the conditional in `ThemeHooks::pageAttachmentsAlter()` that checked `file_exists('public://admin-custom.css')` and attached the `default_admin/admin_custom_css` library when the file existed was also removed. All three pieces were deleted together, leaving no vestigial hook or library reference.

The pattern originated in the contrib Gin theme and had previously been proposed for Claro in [#3169297](https://www.drupal.org/node/3169297) (closed "won't fix") before it was carried into core's new default_admin theme; this issue takes it back out of core rather than keeping it as an implicit, undocumented convention.</technical>
