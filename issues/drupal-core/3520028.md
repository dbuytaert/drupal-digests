## Summary

The interactive (browser-based) Drupal installer no longer shows a "Choose profile" step. Previously, if more than one non-hidden install profile was available and no distribution was present, the installer displayed a form asking you to pick one (and, if a config sync directory existed, offered to "use existing configuration" instead). That step is now skipped entirely: installing plain Drupal core through the UI installs the Standard profile automatically, with no extra click. Installing a distribution, or supplying `profile`, `existing_config`, or `recipe` on the install URL, or installing via Drush, is unaffected, since those paths already bypassed or replaced this step. If you maintain an install profile that end users are expected to pick from a list in the UI (rather than via a distribution), that picker is gone; a contributed module (`profile_selector`, mentioned in the issue as a proof of concept) can restore it.

## Impact

Affects module maintainers.

- **API change:** `install_select_profile()` no longer returns a form render array (now `: void`); when multiple profiles exist and none was specified, it silently defaults to `standard` instead of prompting. The `Drupal\Core\Installer\Form\SelectProfileForm` class was removed entirely.
- **Deprecation:** `Drupal\FunctionalTests\Installer\InstallerTestBase::setUpProfile()` is deprecated in `drupal:11.4.0` and removed in `drupal:12.0.0`, with no replacement; profile selection during install tests is now automatic via `$this->profile` and `visitInstaller()`'s `$query` parameter.

## Technical details

`install_tasks()`'s `install_select_profile` task entry no longer sets `display_name`/`display`, so it is never rendered as a progress-bar step. `install_select_profile()` in `install.core.inc` changed its signature from returning `array|null` to `: void`; the branch that used to `return install_get_form('Drupal\Core\Installer\Form\SelectProfileForm', $install_state)` when multiple profiles were available now instead sets `$install_state['parameters']['profile'] ??= 'standard'` and lets installation continue automatically. The entire `Drupal\Core\Installer\Form\SelectProfileForm` class, including its "install from existing configuration" radio option, was deleted; installing from an existing config sync directory is now driven purely by the `existing_config` URL parameter, as already used by `InstallerConfigDirectoryTestBase` tests. A follow-up, [#3591080](https://www.drupal.org/node/3591080), is filed (postponed) to make this fallback apply the Standard recipe rather than the Standard profile.

`Drupal\FunctionalTests\Installer\InstallerTestBase::setUpProfile()` is kept as a deprecated no-op that triggers `E_USER_DEPRECATED` (deprecated in `drupal:11.4.0`, removed in `drupal:12.0.0`, no replacement) so existing test suites calling it don't fatal. `visitInstaller()` gained a `$query` array parameter and now automatically appends `profile=$this->profile` to the `install.php` request whenever `$this->profile` is set, replicating what the removed form used to submit. Tests exercising a distribution or existing-config flow, where the profile must be auto-detected, now set `protected $profile = NULL;` instead of overriding `setUpProfile()`.

## Upgrade

If your installer tests override `setUpProfile()` to submit a profile selection form, remove that override; the profile is now passed automatically. Rely on the `$profile` property or the new `$query` parameter instead:

```php
// Before: relied on setUpProfile() submitting a form.
protected function setUpProfile(): void {
  // custom logic
}

// After: set the profile property, or pass it via visitInstaller().
protected $profile = 'my_profile';

// Or, for distributions/existing-config installs where the profile
// must be auto-detected rather than forced:
protected $profile = NULL;
```

Calling the deprecated `InstallerTestBase::setUpProfile()` directly now only triggers a deprecation notice and does nothing.
