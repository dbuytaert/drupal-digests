## Summary

The route lookup cache no longer stores entries for requests that have a query string, and no longer stores lookups that find no route (404s). Previously every distinct path plus query string combination created its own cache entry. Those entries were all invalidated at once by the single `route_match` tag whenever a path alias changed, so hit rates on busy sites were low and the cache could fill with entries that were never reused. Requests for plain paths that resolve to a route are cached as before. Lookups with query strings now run the route and path alias queries each time, so sites may see a few extra queries on those requests.

## Impact

Affects module maintainers.

- **New API:** New protected `RouteProvider::useRouteCache(Request $request): bool`, which subclasses can override to control whether a route lookup is cached.

## Technical details

`RouteProvider::getRouteCollectionForRequest()` now computes the cache ID only when the new protected method `useRouteCache()` returns TRUE. By default that is `$request->query->count() === 0`. When it returns FALSE, the cache `get()` is skipped as well as the `set()`. The lookup is also only written to the cache when the resulting collection has routes or resources, so empty (404) results are never stored. The `FALSE` handling for previously cached empty results on the read path is unchanged, so existing entries are still read.

The cache ID logic and the `route_match` cache tag are untouched. Further improvements are tracked in [#3621551](https://www.drupal.org/node/3621551). The original report was about empty results being cached with insufficient context (for example language or domain). Maintainers could not reproduce a routing-level cause, and the change was reframed as a performance task. Alternatives discussed included removing the cache entirely and adding cache contexts to the 404 lookup ([#3580545](https://www.drupal.org/node/3580545)). Tests updated: `testRouteCaching()` now asserts no cache entry for query-string and non-existing paths, `PathWorkspacesTest::testPathAliasesWithTranslation()` assertions changed, and the performance test fixtures (query and cache get counts, including the standard login flow) were adjusted.

## Upgrade

Code that asserts or relies on `route:` cache entries for query-string or 404 requests will no longer find them. A subclass that wants different behavior can override the new method:

```php
protected function useRouteCache(Request $request): bool {
  return $request->query->count() === 0;
}
```

### Collaboration

Berdir profiled the route cache on Umami with Blackfire and xhprof. He found that most of the cost on a miss was the cache write, and that the hit rate on active sites was poor. He first built an experimental MR that removed the cache entirely, then narrowed the change after catch said he preferred only skipping lookups with query strings and those with no results. Scott Euser tested manually on a standard install. He confirmed that four page visits left 16 route cache entries before the change and 2 after, and that creating an alias for a former 404 path worked straight away.
