## Summary

Drupal core now has an `ex:uninstall` console command (aliases `exun`, `pm:uninstall`, `pmu`) that uninstalls modules or themes from the command line. It takes a comma-separated list of machine names. It lists the extensions it will remove, including dependents pulled in automatically, and asks for confirmation before removing the dependents. `--yes` skips the prompt and `--dry-run` shows what would happen without changing anything. It is the counterpart to the `ex:install` command, as part of the CLI in Core initiative.

## Impact

Affects module maintainers.

- **API change:** Both installer interfaces gained a new abstract method, so custom implementations of `ModuleInstallerInterface` or `ThemeInstallerInterface` must implement it.
- **New API:** `ModuleInstallerInterface::getModulesToUninstall()` and `ThemeInstallerInterface::getThemesToUninstall()` resolve the full, ordered set of extensions an uninstall would remove.

## Technical details

The command is `Drupal\Core\Extension\Command\ExtensionUninstallCommand`, marked `@internal`. It classifies each name as a module or theme, reports unknown names, and refuses to mix modules and themes in one invocation. It resolves the full set through the new `getModulesToUninstall()` or `getThemesToUninstall()` method. For modules it then runs `validateUninstall()`, the same checks as the uninstall form, and reports blockers before changing anything. In non-interactive mode, extra dependents without `--yes` throw `UserAbortException`.

To make this possible, the dependency resolution that used to sit inside `ModuleInstaller::uninstall()` and `ThemeInstaller::uninstall()` was extracted into the two new public interface methods. `getModulesToUninstall()` returns the installed modules to remove, including installed dependents when `$uninstall_dependents` is TRUE. They are sorted by module weight, the order `uninstall()` uses. It throws `UnknownExtensionException` for unknown modules or dependents. `ModuleInstaller::uninstall()` still returns FALSE in those cases, so its behavior for callers is unchanged.

`getThemesToUninstall()` throws for themes that are not installed, the default theme and the admin theme. With `$uninstall_dependents` TRUE it adds installed sub-themes to the list. `ThemeInstaller::uninstall()` passes FALSE, so it still throws if a base theme's sub-theme is not listed explicitly. `ModulesUninstallConfirmForm::buildForm()` now also calls `getModulesToUninstall()`, so the confirmation list includes dependents in uninstall order.

## Upgrade

Custom classes implementing `ModuleInstallerInterface` or `ThemeInstallerInterface` must add the new methods:

```php
public function getModulesToUninstall(array $module_list, bool $uninstall_dependents = TRUE): array;
public function getThemesToUninstall(array $theme_list, bool $uninstall_dependents = TRUE): array;
```
