## Summary

Drupal's `RouteSubscriberBase` class, used to write route event subscribers, previously only supported altering existing routes. It now also supports defining brand new routes, giving module developers an object-oriented alternative to declaring a `route_callbacks` entry in a `*.routing.yml` file. As a result, the Views module no longer needs `views.routing.yml` at all; its route subscriber now builds views routes directly through this new mechanism.

## Impact

Affects module maintainers.

- **API change:** `RouteSubscriberBase::alterRoutes()` is no longer `abstract`; it now has a no-op default implementation, so subclasses that only add routes no longer need to implement it.
- **New API:** `RouteSubscriberBase::buildRoutes()` lets an event subscriber define new routes during the `RoutingEvents::STATIC` phase, the object-oriented equivalent of a `route_callbacks` YAML entry.

## Technical details

Since routes moved to PHP attribute discovery ([#3311365](https://www.drupal.org/node/3311365)), there was a gap: `YamlRouteDiscovery` handles the `RoutingEvents::STATIC` event to add both YAML-defined routes and any `route_callbacks`, but `RouteSubscriberBase` only subscribed to `RoutingEvents::ALTER`. This meant a class that wanted to both define and alter routes had no single, consistent OO entry point for the "define" half.

The fix adds a protected `buildRoutes(): RouteCollection` method to `RouteSubscriberBase`, defaulting to an empty `RouteCollection`, and wires it to `RoutingEvents::STATIC` via a new `onBuildRoutes(RouteBuildEvent $event)` listener that merges the returned collection into the event's route collection. `alterRoutes()` changed from `abstract` to a no-op default, so a subclass now only needs to override whichever of the two phases it actually uses.

`Drupal\views\EventSubscriber\RouteSubscriber` was converted to this pattern: its former `routes()` method (previously invoked via `route_callbacks` in `views.routing.yml`) was renamed to `buildRoutes()` and hooked up through `getSubscribedEvents()`, and `views.routing.yml` was deleted since it contained nothing but that `route_callbacks` entry. The public `routes()` method is kept, delegating to `buildRoutes()`, for backwards compatibility; a follow-up issue ([#3618565](https://www.drupal.org/node/3618565)) is postponed to deprecate it once this change is settled.</technical>

## Upgrade

Classes extending `RouteSubscriberBase` that only need to alter existing routes are unaffected. Classes that previously added new routes via a `route_callbacks` entry in a `*.routing.yml` file can instead extend `RouteSubscriberBase` and override `buildRoutes()`:

```php
protected function buildRoutes(): RouteCollection {
  $collection = new RouteCollection();
  // Add routes to $collection.
  return $collection;
}
```

No `getSubscribedEvents()` override is needed for this; the base class now subscribes to `RoutingEvents::STATIC` automatically.
