## Summary

Rebuilding the service container, for example when modules are installed or uninstalled during update hooks, used to keep the old container and everything it referenced in memory. Core already fixed this for the installer only. It now applies on every rebuild. The reporter saw an update that installs and uninstalls several modules grow to 666MB. With the change it stayed at roughly 300MB or less. Sites that hit the error `You have requested a synthetic service ("kernel")` when modules with injected hook classes (such as pathauto) were enabled also reported that the merge request fixed it.

## Impact

Affects module maintainers.

- **API change:** `DrupalKernel::attachSynthetic()` now resets the previous container, and `Container::reset()` and `PhpArrayContainer::reset()` keep synthetic services (and `request_stack`) instead of clearing everything. The `InstallerKernel::attachSynthetic()` override is removed.

## Technical details

`DrupalKernel::attachSynthetic()` now calls `$this->container?->reset()` on the previous container after attaching synthetic services to the new one. This replaces the override that previously lived only in `InstallerKernel`, which is deleted. The old `reset()` simply emptied `$services`. Calling it on every rebuild would have dropped synthetic services such as `kernel` and `keyvalue`, which can't be built by the container. That is what caused the synthetic service exceptions in tests. `Container::reset()` and `PhpArrayContainer::reset()` now clear private services and unset only non-synthetic services, and they always keep `request_stack`. `request_stack` is not synthetic but must not be reset. `PhpArrayContainer` checks the `synthetic` key in the definition, which may be a serialized string. `Container` checks `isSynthetic()`.\n\nBecause the old container is now reset, objects that outlive a rebuild can no longer rely on it. `ModuleInstaller::updateKernel()` records the service IDs of its `uninstallValidators` through `ReverseContainer::getId()` before the rebuild. Afterwards it replaces them with a `RewindableGenerator` that fetches the same services from the new container. `MimeTypeGuesser::registerWithSymfonyGuesser()` moves from `DrupalKernel::preHandle()` to `initializeContainer()`, so Symfony's static MIME guesser is re-registered with the new container on each rebuild. In the thread, the concern was that this call is on the early critical path before a page cache hit. Following up by adding `MimeTypeGuesser` to the early bootstrap autoload classmap was deferred to [#3612177](https://www.drupal.org/node/3612177). The diff also includes a comment update in a router installer test.

## Upgrade

Custom code that caches services in properties across a container rebuild, such as module installs or updates inside one request, may now hold services from a reset container. Re-fetch them from `\Drupal::getContainer()` after the rebuild, as `ModuleInstaller::updateKernel()` now does for its `moduleHandler`, `connection`, `updateRegistry` and `uninstallValidators`. Tests that persist services with injected dependencies, such as event dispatchers registered via `register()`, may need adjusting.

### Collaboration

berdir first moved the installer-only reset into the base kernel, but it broke many tests. After discussion he switched to a soft reset that keeps synthetic services. godotislate suggested using the reverse container to look up the uninstall validators' service IDs and rebuild them after the rebuild, which led to the `ModuleInstaller::updateKernel()` change. alexpott questioned the `MimeTypeGuesser` move, and berdir explained it is there because a rebuild re-registers the guesser.
