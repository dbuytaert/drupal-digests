## Summary

Drupal's asset library system can now mark specific CSS or JavaScript libraries so their files are always bundled into their own aggregate, regardless of which other libraries happen to be attached on a given page. Previously, the exact set of libraries in an aggregate, and therefore its URL and query string, varied depending on everything else loaded on that particular page, so browsers and CDNs often re-downloaded effectively the same CSS or JS just because the query string differed slightly from page to page. By setting the new `aggregate_target` key on a library, its aggregate gets a predictable, page-independent URL, which increases browser and CDN cache hit rates for repeat and multi-page visits. Core has already applied this to several always-loaded libraries (`core/drupal`, `core/drupalSettings`, `system/base`, parts of Umami and Claro) and switched some small vendor JS libraries to `preprocess: false` instead, since aggregating a single already-minified file offers no benefit.

## Impact

Affects module maintainers.

- **API change:** `AssetResolverInterface::getCssAssets()` and `::getJsAssets()` gained an optional `$with_dependencies` parameter (default `TRUE`); custom implementations of the interface must add it to stay compatible.
- **New API:** New `aggregate_target` library definition key (with `css` and `js` sub-keys, each accepting `true` or an arbitrary string) forces a library's assets into a dedicated, page-independent aggregate.

## Technical details

Library definitions can now declare `aggregate_target: {css: ..., js: ...}`, where the value is either `true` (unique per library) or an arbitrary string shared by several libraries meant to be co-located. `LibraryDiscoveryParser::buildByExtension()` normalizes this to `['css' => FALSE, 'js' => FALSE]` when absent, and also records each CSS file's SMACSS `category` so it can be checked later. `CssCollectionGrouper::group()` and `JsCollectionGrouper::group()` track, per group, whether all files belonging to a targeted library (and, for CSS, a given category) landed contiguously in a single group via a `$first_seen_libraries`/`$seen_index` mechanism; if a library's files get split across groups because of per-file weights or other libraries interleaving, the `libraries` key is dropped from those groups and the aggregate silently falls back to the pre-existing include/exclude/delta behavior.

When a group does carry a `libraries` key, `CssCollectionOptimizerLazy::optimize()` and `JsCollectionOptimizerLazy::optimize()` build the asset URL using a compressed `libraries` query argument (and, for CSS, a `category` argument, since a single library can still span multiple categories) instead of `include`/`exclude`/`delta`. `CssAssetsController`/`JsAssetsController::deliver()` and their shared `AssetControllerBase` were updated to accept these new parameters and, when present, call `AssetResolverInterface::getCssAssets()`/`getJsAssets()` with the new `$with_dependencies = FALSE` argument so the aggregate is rebuilt from exactly the listed libraries rather than pulling in their full dependency trees.

Core's `core.libraries.yml`, `system.libraries.yml`, `big_pipe.libraries.yml`, Umami's and Claro's `.libraries.yml` files were updated to use `aggregate_target` on libraries that are effectively always loaded together (e.g. `core/drupal` and `core/drupalSettings` share `js: 'drupal'`; `loadjs`, `drupal.htmx`, and `htmx` share `js: 'htmx'`). Umami's global library was split into `global` and a new `global_tweaks` dependency to isolate files whose custom weights would otherwise have prevented the aggregate target from applying.

## Upgrade

To opt a library into a dedicated aggregate, add `aggregate_target` to its definition in a `*.libraries.yml` file:

```yaml
mylibrary:
  aggregate_target:
    css: true
    js: 'mygroup'
  css:
    theme:
      css/mylibrary.css: {}
  js:
    js/mylibrary.js: {}
```

Use `true` for a library-specific aggregate, or an arbitrary string shared across libraries that are always expected to load together. This only takes effect if all of the library's files end up contiguous within a single asset group; libraries that set custom per-file weights, or that get split apart by other libraries' weights, transparently fall back to the previous aggregation behavior.

Code that implements `AssetResolverInterface` directly (rather than extending `AssetResolver`) needs to add the new `bool $with_dependencies = TRUE` parameter to `getCssAssets()` and `getJsAssets()` to remain compatible with the interface.

### Collaboration

berdir tested the in-progress patch against a real multi-theme project and reported that adding the new key to a global library increased the CSS file count more than expected, because the library spanned multiple SMACSS CSS groups and had per-file weights (e.g. `drupal.progress`'s negative weight forced it into its own aggregate). That real-world testing led catch to trace the root cause to legacy CSS group/weight handling and to open a follow-up, [#3568157](https://www.drupal.org/node/3568157), to strip unnecessary explicit weights from core CSS files. The back-and-forth between catch and berdir over several comments also settled the final naming: berdir proposed renaming the key from `unique_css_aggregate` to something like "target", and catch followed up by renaming it to `css_aggregate_target`/`js_aggregate_target` (which later became the nested `aggregate_target: {css, js}` structure) and changing the `every_page` value to `global`, since the aggregate is still varied by theme and language regardless.
