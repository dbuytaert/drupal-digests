## Summary

Drupal's schema definition API (introduced in [#3411490](https://www.drupal.org/node/3411490)) can now declare "generated" columns: columns whose value the database computes automatically from an expression over other columns, rather than one that application code writes. This was motivated by the need to index data inside JSON columns (see [#3343634](https://www.drupal.org/node/3343634)): since MariaDB doesn't support indexing arbitrary SQL expressions, the practical way to index derived data is to expose it as a generated column and index that. A generated column can be "stored" (computed on write and kept on disk, like a regular column) or "virtual" (computed on read, saving storage but not supported for indexing on PostgreSQL). This is a new opt-in capability for code that adopts the new schema API; it does not change any existing database table.

## Impact

Affects module maintainers.

- **New API:** New `Column::generated()` factory and `Drupal\Core\Database\SchemaDefinition\GeneratedColumnStorage` enum let schema definitions declare database-computed (generated) columns, stored or virtual.

## Technical details

The core addition is `Column::generated()`, a static factory on the `Column` value object that requires a `ColumnType`, a `GeneratedColumnExpression` (a small `Expression` subclass holding the raw SQL expression text), and a `GeneratedColumnStorage` enum case (`Virtual` or `Stored`). `Column::validate()` rejects a generated expression on a `Serial` column, and `Table::validate()` rejects a generated column in the primary key, since MariaDB and SQLite don't allow that. `Column::toArray()` puts the whole `Column` object under the array spec's `generated` key, which the `mysql`, `pgsql`, and `sqlite` driver `createFieldSql()` implementations translate into `GENERATED ALWAYS AS (...) VIRTUAL|STORED` clauses (with `DEFAULT NULL` suppressed for generated columns).

SQLite required the most work because it has no `ALTER TABLE` support for adding a `STORED` generated column (only `VIRTUAL` can be added in place; `STORED` forces the driver's usual create-new-table-and-copy-data path), and its `PRAGMA table_info` doesn't report generated columns at all. The driver's `introspectSchema()` now uses `PRAGMA table_xinfo` (which exposes a `hidden` flag distinguishing ordinary, virtual-table, `VIRTUAL` generated, and `STORED` generated columns) and, for generated columns, recovers the original column definition text by parsing the `CREATE TABLE` statement out of `sqlite_master` (new `getColumnDefinitions()`, `splitColumnDefinitions()`, `skipQuotedRun()`, `skipComment()` helpers), since SQLite exposes no pragma for a generated column's expression or storage kind. That recovered text is stored under a `sqlite_definition` key and reused verbatim by `createFieldSql()`/`processField()` on rebuild; if recovery fails, a `SchemaException` is thrown rather than silently dropping the column. Table rebuilds (`alterTable()`) also exclude generated columns from the data-copy mapping, since the database rejects writes to them.

### Collaboration

The implementation went through a design pivot before landing here: the issue was originally going to add expression indexes, but MariaDB's lack of support for indexing arbitrary expressions ruled that out, leaving generated columns as the only portable path (per the issue's Problem/Motivation section). mondrake built the initial MR on top of the then-in-progress [#3411490](https://www.drupal.org/node/3411490) value-object schema API and got all three core-supported databases implemented, then postponed the issue twice pending that dependency and [#3604286](https://www.drupal.org/node/3604286) (for the `Expression` class). catch, reviewing before commit, questioned whether virtual generated columns were worth the added API surface; amateescu explained they let MySQL, MariaDB and SQLite index derived data while paying storage cost only for the index, not a duplicated column, which settled the design and was folded into the issue summary before commit.
