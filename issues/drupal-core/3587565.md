## Summary

Entity storage previously had no memory of failed load attempts within a request: if code tried to load an entity ID that doesn't exist (a common case for config entities, such as per-bundle language content settings that not every bundle defines), it would query the persistent cache backend again on every subsequent attempt for that same ID. Now the fact that an ID was not found is also recorded in the per-request static cache, so repeated lookups of the same missing ID skip the cache backend entirely for the rest of the request. Drupal core's performance test suite shows this measurably reduces cache backend reads on real pages: cold-cache node page requests dropped from 225 to 217 cache gets, cold-cache front page requests from 233 to 225, and the administrator node page from 265 to 257 (mostly in the `config` cache bin), with no change in database query counts.

## Impact

No upgrade or configuration changes required.

## Technical details

In `EntityStorageBase::loadMultiple()`, after `doLoadMultiple()` runs, any requested IDs that are still missing are now recorded via a new `setNotFoundStaticCache()` method, and checked on subsequent calls via `getNotFoundFromStaticCache()`. Both use a new `buildNotFoundCacheId()` helper that wraps `buildCacheId()` with a `not_found:` prefix, so a storage's own `buildCacheId()` override (for example `ConfigEntityStorage::buildCacheId()`, which appends config override keys) is automatically reflected in the not-found cache key too. `resetCache()` now clears both the entity cache and the not-found cache entries for the given IDs. `setStaticCache()` was also changed to iterate `$entities` by its array key (`foreach ($entities as $id => $entity)`) rather than deriving the cache key from `$entity->id()`, since the not-found bookkeeping needs to track the originally requested ID.

A new unit test, `testLoadMultipleNoResult()`, asserts that loading the same nonexistent ID twice in a request results in only a single persistent-cache `getMultiple()` call. This builds on the earlier bulk-loading work in [#3560633](https://www.drupal.org/node/3560633) that reduced repeated config entity lookups for per-bundle settings.

### Collaboration

catch initially considered adding separate load methods for not-found entities but was concerned it would complicate cache invalidation; noticing that the existing UUID lookup cache already followed a similar pattern, they instead added a distinct `not_found:` cache key prefix with dedicated get/set methods. During development this approach broke `ConfigEntityStorage`, which overrides `buildCacheId()` to append config override keys, catch fixed it by having `buildNotFoundCacheId()` delegate through `buildCacheId()` in the base class, so storage-specific overrides are automatically honored without needing their own fix.
