## Summary

Drupal's YAML parser now understands PHP class constants and enum cases, so configuration, service definitions, and recipe files can reference `SomeClass::SOME_CONSTANT` or `SomeEnum::SomeCase` instead of hard-coding literal values that have to be kept in sync by hand. A companion `enum` config schema type lets module authors declare that a config value must be an instance of a specific PHP enum, with validation enforcing it. To make this safe during module installation and config import, when a module or recipe is being installed its enums and constants are made autoloadable even before the module is fully active, so its own default configuration can reference them. Support is deliberately limited to class-based constants and enums; global constants defined in procedural `.module` files are not supported.

## Impact

Affects module maintainers.

- **Deprecation:** `Drupal\Core\Config\FileStorageFactory` and its `getSync()` method are deprecated in favor of the `config.storage.sync` service.
- **New API:** YAML (including configuration, services and recipes) can now contain `!php/const Some\Class::CONST` and `!php/enum Some\Enum::Case` tags; a new `enum` config schema type with an `enum_class` key validates that a config value is an instance of that enum.

## Technical details

The core change is small: `Drupal\Component\Serialization\YamlSymfony::decode()` now passes `SymfonyYaml::PARSE_CONSTANT` alongside the existing flags, which enables Symfony's `!php/const` and `!php/enum` YAML tags. `Yaml::encode()` (Symfony writer) serializes PHP enums using `!php/const`, which the parser also accepts back, and `!php/enum` is additionally supported on decode for compatibility with Symfony's documented syntax and to keep behavior consistent regardless of which YAML backend is in use.

A new `Drupal\Core\TypedData\Plugin\DataType\Enum` primitive type (schema id `enum`) plus `EnumConstraint`/`EnumConstraintValidator` validate that a decoded value is a `\UnitEnum` instance of the class named in the schema's `enum_class` key; `Comparator::checkValue()` and `TypedConfig::castValue()` were updated to recognize `\UnitEnum` values.

The harder problem was config install/import: enums and constants referenced in a module's or recipe's own default configuration are not autoloadable via Composer until the providing module is installed. This is solved with a new `Drupal\Core\Config\AutoloadingStorage` decorator that temporarily registers a throwaway `ClassLoader` (PSR-4 mapped to the extension's `src` directory) around `read()`/`readMultiple()` calls. The `config.storage.sync` service is now produced by a new `SyncFactory` class, which diffs the `core.extension` list in the sync storage against the active storage to find newly-appearing modules/themes and wraps the sync `FileStorage` in `AutoloadingStorage` for just those extensions. `ModuleInstaller::checkConfigurationToInstall()` does the same for the module(s) currently being installed. `StorageComparer` was updated to treat `AutoloadingStorage` the same as `FileStorage` for its static-cache optimization. Recipes get analogous handling: `parseRecipeContents()` in `Drupal\Core\Recipe\RecipeData` catches the `InvalidDataTypeException` Symfony throws for an unresolvable `Drupal\{extension}\...` constant/enum, and if that extension exists on disk but isn't installed yet, registers a temporary classloader for it and retries parsing.

Support for constants defined in procedural `.module` files was explicitly dropped rather than solved, since it would require preloading `.module` files before parsing config, a complication the maintainers decided wasn't worth it for a legacy pattern that's being phased out.

## Upgrade

Prefer `!php/const` and `!php/enum` over literal values in your own config/service YAML, e.g.:
```yaml
cardinality: !php/const Drupal\Core\Field\FieldStorageDefinitionInterface::CARDINALITY_UNLIMITED
status: !php/enum Drupal\my_module\MyEnum::SomeCase
```
Declare a matching config schema for enum-typed values:
```yaml
my_module.settings:
  mapping:
    status:
      type: enum
      enum_class: '\Drupal\my_module\MyEnum'
```
If your code calls `Drupal\Core\Config\FileStorageFactory::getSync()` directly, switch to the service instead:
```php
// Before:
$storage = FileStorageFactory::getSync();
// After:
$storage = \Drupal::service('config.storage.sync');
```

### Collaboration

The design took years to settle because of a real safety concern: alexpott identified in comment #46 that reading config during import can require autoloading code for a module that isn't installed yet, which risks crashing on missing classes. neclimdul (#78) and phenaproxima (#84) pushed back hard, worried that letting config schema influence what gets autoloaded was a "danger zone" that could snowball to cover removed modules, themes and profiles too. alexpott resolved the disagreement by scoping `AutoloadingStorage` narrowly: it only wraps the sync storage (never active storage) and only for extensions genuinely being installed, and argued failures in this area should fail loudly rather than be silently tolerated. Wim Leers separately pushed for decoding `!php/enum` (not just `!php/const`) to match Symfony's own documented behavior and keep the PECL and Symfony YAML backends consistent, which alexpott agreed to add. Late in the process mondrake decided that supporting global constants declared in procedural `.module` files, a gap mikelutz had surfaced with a failing test, wasn't worth the added complexity and dropped it before the final commit.
