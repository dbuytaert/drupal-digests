## Summary

Drupal now automatically strips a fixed set of dangerous characters, including shell metacharacters like `` ` $ ; | & ` ``, quotes, angle brackets, control characters, and path separators, from the names of newly uploaded files, replacing them with underscores. This closes off a potential command-injection or XSS vector that could arise if a filename containing such characters was later passed unsafely to a shell command or rendered without escaping. The change applies to every site automatically and cannot be turned off; only newly uploaded files are affected, existing filenames are left untouched. Filenames that would otherwise collapse to nothing (e.g. `...` or files with only unsafe characters before the extension) now fall back to `unnamed` instead of becoming empty, and a leading dash or dot left after sanitization is also handled so the result can't be mistaken for a command-line option or a hidden dotfile. Whitespace in filenames is unaffected, that remains governed by the existing optional `filename_sanitization` setting.

## Impact

No upgrade or configuration changes required.

## Technical details

The logic lives in `\Drupal\file\EventSubscriber\SecurityFileUploadEventSubscriber::sanitizeName()`, which already ran last in the `FileUploadSanitizeNameEvent` chain and already stripped null bytes unconditionally, so the new mandatory stripping was added there rather than in the configurable `FileEventSubscriber`. A new `INSECURE_CHARACTERS` PCRE constant (built with Unicode property classes `\p{Cc}` for control characters and `\p{Cf}` for invisible format/bidi-override characters, plus a literal set of shell metacharacters, quotes, path separators, `#` and `%`) is matched and replaced with `_` via `preg_replace()`. After that substitution, a leading `-` is trimmed (since many CLI tools parse a leading dash as an option), and if the result is empty or starts with `.` it is prefixed with the `FALLBACK_FILENAME` constant `unnamed`, relying on the existing suffixing in `FileSystem::createFilename()` to disambiguate collisions (`unnamed_0`, `unnamed_1`, etc).

The issue went through several design iterations, an earlier approach tried to also default-enable whitespace replacement and made the character list configurable via `file.settings`, but both were dropped: whitespace substitution was judged too disruptive to ship as a default and was left as the existing opt-in setting, and making the blocked-character list configurable was rejected because a misconfigured list could reintroduce the vulnerability. Characters are now replaced rather than deleted outright, a change from an earlier iteration, so that e.g. `Love&War.pdf` becomes `Love_War.pdf` rather than `LoveWar.pdf`, preserving more of the original separation between words. A related follow-up, [#3562543](https://www.drupal.org/node/3562543), fixed a crash in the whitespace-replacement regex when fed invalid UTF-8 and landed first as a prerequisite.

### Collaboration

The issue spent over a year iterating on scope. mcdruid (the reporter) and kim.pepper went back and forth on whether to strip a fixed list of "dangerous" characters versus making the list configurable, and whether to default-enable whitespace replacement; a usability team review (summarized by mcdruid in comment #26 and confirmed by benjifisher in #30) concluded that stripping punctuation should be non-negotiable but replacing whitespace should remain an opt-in default. Attempting to flip the whitespace default uncovered an unrelated bug (a `preg_replace()` call returning `null` on malformed UTF-8 input), which kim.pepper and mcdruid debugged together and split off into the prerequisite issue [#3562543](https://www.drupal.org/node/3562543). After that landed, mcdruid disclosed using Claude to help work out the final implementation pushed to the MR, abandoning the configurable, whitespace-replacing approach in favor of a simpler, non-configurable, replace-not-remove scheme. cmlara then pushed back strongly on making the protection non-configurable and on stripping characters that appear in legitimate filenames, arguing it could create a false sense of safety in downstream code and cause reputational issues if parts of filenames like `Love&War.pdf` were silently dropped. That critique led alexpott and mcdruid to change the implementation from removing characters to replacing them with `_`, and longwave and xjm weighed in to support keeping the list non-configurable, reasoning that configurability of a security control increases risk of misconfiguration for comparatively little benefit. larowlan, reviewing the final regex character by character with regex101, committed the change and it was backported to 11.5.x by xjm shortly before the beta1 tag.
