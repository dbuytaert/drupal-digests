## Summary

The `_role` route access check now explicitly denies access when an account has no roles at all. Core accounts always carry at least the anonymous or authenticated role, so ordinary sites see no change. The guard protects against future changes, such as a different default for `getRoles()`, or custom account objects that return no roles.

## Impact

Affects site owners.

- **Security:** `RoleAccessCheck` now returns forbidden for any account with no roles, a defensive guard with no known exploit in current core.

## Technical details

`\Drupal\user\Access\RoleAccessCheck::access()` now calls `$account->getRoles()` once, and if the result is empty returns `AccessResult::forbidden('No user roles found.')` before parsing the `_role` requirement. Previously an empty role list on a `_role` route fell through to `AccessResult::neutral()` with the `user.roles` cache context. The same `$roles` variable is reused in the `array_diff()` (comma, AND) and `array_intersect()` (plus, OR) branches. The forbidden result carries no `user.roles` cache context.

Because forbidden wins over allowed when access results are combined, an account without roles is now denied outright, where before another access checker could still grant access. The thread established that the bug was not reproducible in current core: an empty array already led to neutral. The change is a guard against future changes. `RoleAccessCheckTest` gains a `$forbidden_accounts` data provider argument covering `$account_none` (empty roles) and `$account_null` (`NULL` roles).
