## Summary

The base class behind Drupal's select, checkboxes/radios, and single on/off checkbox field widgets was refactored to process submitted form values the same way most other field widgets do, through `massageFormValues()` and `extractFormValues()`, instead of doing that work inline in its form-element validation callback. This is an internal code-quality cleanup with no intended change in what gets saved: the same values (single or multiple selections, required or optional fields, checkbox/radio or select rendering) are stored as before. It was manually verified by re-testing all these widget combinations and comparing the saved database values against the previous behavior.

## Impact

No upgrade or configuration changes required.

## Technical details

Previously, `OptionsWidgetBase::validateElement()` (a static `#element_validate` callback) both validated the required-field constraint and transposed and filtered the raw submitted values, writing the result back with `$form_state->setValueForElement()`. That bypassed the `massageFormValues()` hook that `WidgetInterface` defines and that most other widgets use.

`validateElement()` now only checks the required constraint. Value processing moved to a new `OptionsWidgetBase::extractFormValues()` override, which first normalizes single-valued widgets (radios, single select) that submit a scalar into an array via `NestedArray::getValue()`/`$form_state->setValue()`, then calls `parent::extractFormValues()` (from `WidgetBase`), which in turn invokes the new `massageFormValues()`. That method filters out the `_none` placeholder option and unchecked checkbox values (integer `0`, which must be excluded with a strict comparison since `0 == 'any string'`), then transposes the values from field-keyed to delta-keyed arrays (`[$this->column => $value]`), matching the format `WidgetBase::submit()` expects.

`massageFormValues()` also detects when values are already shaped as `delta => [column => value]` and returns them filtered but otherwise unchanged. This preserves compatibility with subclasses such as `content_moderation`'s `ModerationStateWidget`, which overrides `validateElement()` entirely and calls `$form_state->setValueForElement()` with values already in that shape rather than relying on the parent's massaging logic.</technical>

### Collaboration

The initial patches from swentel stalled for years because of an edge case yched identified in #comment-8460695: single-valued widgets like radios or a single select can submit a scalar `#value` rather than an array, so removing the `is_array()` normalization broke those widgets, as confirmed by failed test runs. The issue was picked up again a decade later by smustgrave, who rewrote the fix using `extractFormValues()`/`massageFormValues()`; smustgrave disclosed using Claude Code to help locate `extractFormValues()` and to identify that unchecked checkboxes submit integer `0`, which had to be filtered out to avoid breaking checkbox widget tests. Reviewer dcam raised questions that put the issue into Needs Work, then, once answered, performed manual testing across single and multiple values, required and optional fields, and both the select and checkbox/radio widgets, comparing saved database values against the unmodified code before approving. Committer catch noted the change is a net addition of code rather than a removal, but committed it since other core widgets already implement `massageFormValues()`, making this consistent with the rest of core.
