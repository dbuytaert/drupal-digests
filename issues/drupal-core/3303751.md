## Summary

Sites with a large number of enabled modules and themes were seeing significantly slower site installs, database updates, and test runs because `UpdateRegistry` (the service that tracks and runs `hook_post_update_NAME()` implementations) re-scanned the filesystem for every module, theme, and profile each time it needed to check for update files on a given extension. On a site or test suite with 150+ extensions, this added up to a large, repeated cost. The registry now scans the filesystem for extensions once and reuses the result, cutting a substantial amount of time off installs, updates, and functional test runs, especially on slower filesystems like Docker or WSL2.

## Impact

Affects module maintainers.

- **Deprecation:** Calling `UpdateRegistry::__construct()` without the new `$memoryCache` argument is deprecated in Drupal 11.5.0 and will be required in 12.0.0.

## Technical details

The expensive work happened in `UpdateRegistry::scanExtensionsAndLoadUpdateFiles()`, which built a new `ExtensionDiscovery` and called `scan('module')`, `scan('theme')`, and `scan('profile')` on every invocation, even though the result rarely changes within a request. This logic was extracted into a new `discoverExtensions()` method that first checks an injected `MemoryCacheInterface` (`cache.memory`) for a cached copy under the `update_registry.extensions` cache ID, populating it and tagging it `config:core.extension` on a miss so it's invalidated automatically when the installed extension list changes (module/theme install or uninstall).

To get the memory cache into the class, `UpdateRegistry::__construct()` gained a new `MemoryCacheInterface|string|null $memoryCache = NULL` parameter inserted before the existing `$updateType` parameter. For backward compatibility, if a string is passed in that slot (the old calling convention where `$updateType` was the sixth argument) it's treated as `$updateType` and the memory cache falls back to `\Drupal::service('cache.memory')`, with a deprecation notice raised. The `update.post_update_registry` service definition in `core.services.yml` was updated to pass `@cache.memory` explicitly.

## Upgrade

Update any code that instantiates `UpdateRegistry` directly (for example Drush's deploy hook command) to pass a `MemoryCacheInterface` service as the sixth constructor argument, before `$updateType`:

```php
new UpdateRegistry(
  $root,
  $sitePath,
  $module_list,
  $keyValue,
  $theme_handler,
  \Drupal::service('cache.memory'),
  'post_update',
);
```

Calling the constructor without the `$memoryCache` argument still works in Drupal 11.5.x but triggers a deprecation notice and will be removed in Drupal 12.0.0.

### Collaboration

An initial patch from the issue reporter (`phma`) sat for years before `nicxvan` and `longwave` reworked it: `longwave` proposed an alternative in MR!16818 that avoided threading a boolean flag through several methods and added test coverage proving discovery happens once and is then cached, which `nicxvan` preferred over the original patch. The two then iterated on whether to use `CacheBackendInterface` or `MemoryCacheInterface` (settling on the latter now that [#3590964](https://www.drupal.org/node/3590964) supported it), and on where the caching logic should live, with `nicxvan` moving it into `discoverExtensions()` so any future caller benefits. `catch` profiled the change against a curtailed run of the node module's `GenericTest`, confirming it saved about 20 calls to `ExtensionDiscovery::scan()` (roughly half the time spent in `UpdateRegistry::getUpdateFunctions()`), and noted the saving multiplies across a full test run executed thousands of times.
