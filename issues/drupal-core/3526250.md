## Summary

Render elements use the `#access` property to control whether they are shown. Previously, if `#access` was set to something other than a boolean or an access result object (for example a string, or any other unexpected value), it was silently treated as granting access, which could hide subtle security bugs. Now, using an invalid `#access` value triggers a deprecation notice so developers can catch and fix these cases before they become a hard error. This does not change current rendering behavior yet; invalid values are still evaluated as granting access, but a warning is now raised.

## Impact

Affects module maintainers.

- **Deprecation:** Setting `#access` on a render element to anything other than `TRUE`/`FALSE` or an `AccessResultInterface` object is deprecated in `drupal:11.4.0` and will throw from `drupal:13.0.0`.

## Technical details

The check was added in `Renderer::doRender()` in `core/lib/Drupal/Core/Render/Renderer.php`: when `#access` is set but is neither `is_bool()` nor an instance of `AccessResultInterface`, a `@trigger_error()` with `E_USER_DEPRECATED` fires before the existing access logic runs. The underlying evaluation logic is unchanged, so an invalid value (anything not strictly `FALSE`) still results in the element being rendered, matching the pre-existing behavior.

The issue notes an inconsistency between `Renderer::doRender()` and `FormBuilder::isElementAccessible()`: the renderer hides an element only when `#access === FALSE`, while the form builder only allows it when `#access === TRUE`, so an invalid non-boolean value is handled differently by each. This deprecation is a first step toward eventually requiring strictly valid values, which would resolve that inconsistency; it does not change either code path's logic itself.

A follow-up, [#3593606](https://www.drupal.org/node/3593606), was opened to also trigger an `E_USER_WARNING` for invalid `#access` values starting in Drupal 12.0, since the silent `@trigger_error` deprecation only surfaces in code with deprecation testing enabled, and is less likely to be noticed by custom, site-specific code that isn't covered by automated tests.</technical>
