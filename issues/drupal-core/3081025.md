## Summary

When Drupal detects an "untrusted" callback (for example in a render array), it now always throws an exception rather than offering an option to only log a silenced deprecation warning instead. This closes a long-standing loophole left over from the original security hardening work in [#2966327](https://www.drupal.org/node/2966327): Drupal core itself has thrown the exception unconditionally since Drupal 9, but the old `$error_type` escape hatch was still present in the API for anyone who wanted to opt into the softer, warning-only behavior. That option is now deprecated and will disappear in Drupal 13.

## Impact

Affects module maintainers.

- **Deprecation:** `TrustedCallbackInterface::THROW_EXCEPTION` and `TrustedCallbackInterface::TRIGGER_SILENCED_DEPRECATION` are deprecated, and the `$error_type` parameter of `DoTrustedCallbackTrait::doTrustedCallback()` / `StaticTrustedCallbackHelper::callback()` is removed from the method signature; passing a 5th argument now triggers a deprecation notice and is removed in Drupal 13.0.0.

## Technical details

`DoTrustedCallbackTrait::doTrustedCallback()` and `StaticTrustedCallbackHelper::callback()` dropped the `$error_type` parameter from their signatures; the method body no longer branches on `TRIGGER_SILENCED_DEPRECATION` and simply throws `Drupal\Core\Security\UntrustedCallbackException` whenever a callback fails the trusted-callback check. `Renderer::doCallback()` was updated accordingly to call `doTrustedCallback()` without an error-type argument.

Because `$extra_trusted_interface` was the 5th parameter and `$error_type` the 4th, removing `$error_type` from the signature would silently break any caller still passing both. To preserve backward compatibility, both methods now use `func_num_args()`/`func_get_arg(4)`: if a 5th argument is still supplied, it is treated as the (now 4th-position) `$extra_trusted_interface` value and a deprecation notice is triggered rather than a hard fatal. The two now-unused `TrustedCallbackInterface` constants (`THROW_EXCEPTION`, `TRIGGER_SILENCED_DEPRECATION`) are marked `@deprecated` in their docblocks rather than removed outright, consistent with the Drupal core deprecation policy.

## Upgrade

Remove any explicit `$error_type` argument (`TrustedCallbackInterface::THROW_EXCEPTION` or `TrustedCallbackInterface::TRIGGER_SILENCED_DEPRECATION`) from calls to `doTrustedCallback()` or `StaticTrustedCallbackHelper::callback()`. If you need to pass `$extra_trusted_interface`, it is now the 4th argument:

```php
// Before:
$this->doTrustedCallback($callback, $args, $message, TrustedCallbackInterface::THROW_EXCEPTION, RenderCallbackInterface::class);

// After:
$this->doTrustedCallback($callback, $args, $message, RenderCallbackInterface::class);
```

Untrusted callbacks always throw `Drupal\Core\Security\UntrustedCallbackException` now; there is no replacement for the silenced-deprecation behavior.

### Collaboration

This issue sat postponed for years: in 2020 `alexpott` argued it shouldn't proceed until [#2966711](https://www.drupal.org/node/2966711) (trusted callbacks for form arrays) was settled, "possibly never", since contrib might still want the deprecation path for its own callback types. `dww` and `berdir` independently reached the same conclusion after digging into `core/lib/Drupal/Core/Security/DoTrustedCallbackTrait.php` and discovering that Drupal 9's `Renderer.php` was already unconditionally throwing exceptions, so the issue was really about removing now-dead plumbing rather than closing a live security gap. When `larowlan` revived the issue in 2025 ahead of Drupal 12, `alexpott` used a code search across contrib (turning up a real caller in `twig_field_value`) to confirm that simply deleting the `$error_type` parameter would break existing code, and added the `func_num_args()`-based deprecation shim so those callers get a warning instead of a fatal error.
