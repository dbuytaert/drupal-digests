## Summary

Continuing the work started in [#3411490](https://www.drupal.org/node/3411490), the `hook_schema()` implementations of core's regular (non-test) modules, comment, dblog, file, layout_builder, node, user, and workspaces, have been converted from the traditional nested associative array format to the newer object-oriented `SchemaDefinition` API. Modules that still return the legacy array format keep working, but now trigger a deprecation notice, since Drupal 13 will require the object-based format. While doing this conversion, the team discovered that dblog's `watchdog.wid` column was not actually unsigned as its own documentation claimed; an update function now corrects existing sites' schema to match.

## Impact

Affects module maintainers and site owners.

- **Database update:** `dblog_update_12100()` deletes any rows with a negative `wid` and converts the `watchdog.wid` primary key column to an unsigned big integer, matching the schema as actually declared.
- **Deprecation:** Returning a legacy array from `hook_schema()` (rather than a `Drupal\Core\Database\SchemaDefinition\Schema` object) to `ModuleInstaller::installSchema()`/`uninstallSchema()` or to `SchemaInspector::getTablesSpecification()` is deprecated in `drupal:12.1.0` and will be removed in `drupal:13.0.0`.

## Technical details

The converted `hook_schema()` implementations now build a `Schema` object out of `Table`, `Column`, `Index`, `PrimaryKey`, and `ForeignKey` value objects (e.g. `Column::varcharAscii(name: 'entity_type', length: EntityTypeInterface::ID_MAX_LENGTH, ...)`) instead of returning nested PHP arrays. `ModuleInstaller::installSchema()` and `uninstallSchema()` now call `@trigger_error(..., E_USER_DEPRECATED)` whenever a module's `_schema()` hook returns anything other than a `Schema` instance (and the array is non-empty), pointing to https://www.drupal.org/node/3557405.

Validation was tightened on the `SchemaDefinition` value objects themselves: `Column::validate()` now throws a `SchemaDefinitionException` if `length` is missing for `Varchar`/`VarcharAscii` columns, `Schema::validate()` rejects duplicate table names, and `Table::validate()` (via a new `columnNames()` method) rejects duplicate column names within a table.

The conversion surfaced a real discrepancy: `dblog_schema()`'s `watchdog.wid` was declared `unsigned: TRUE` under the new definition, but the live database column was not actually enforced as unsigned. `dblog_update_12100()` removes any rows with negative `wid` values and runs `changeField()` to make the column unsigned, with a new `UpdatePathTest` exercising the negative-id-then-update scenario. Conversion of schemata defined by test modules was explicitly postponed to a follow-up issue, per review feedback from amateescu, to keep this change reviewable.

## Upgrade

Module maintainers should convert their `hook_schema()` implementations from arrays to `SchemaDefinition` objects to avoid deprecation notices, for example:

```php
function mymodule_schema(): Schema {
  $tables[] = new Table(
    name: 'mymodule_table',
    description: '...',
    columns: [
      Column::int(
        name: 'id',
        description: '...',
        unsigned: TRUE,
        notNull: TRUE,
        default: new IntValue(0),
      ),
    ],
    primaryKey: new PrimaryKey(['id']),
  );

  return new Schema(
    type: SchemaDefinitionType::Module,
    name: 'mymodule',
    tables: $tables,
  );
}
```

Sites with existing dblog data will have their `watchdog.wid` column corrected to unsigned via `dblog_update_12100()` when running database updates.
