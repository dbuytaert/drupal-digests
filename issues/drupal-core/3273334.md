## Summary

In an AJAX-enabled view with a multi-select exposed filter, you can now clear the selection. Previously, if the filter was already in the page URL (for example `/admin/content?type[]=page`), deselecting the value and pressing Filter re-selected it. The query string parameters for exposed filters are now correctly dropped before the AJAX request, so the submitted form values win. Query parameters in the resulting URLs can appear in a different order.

## Impact

No upgrade or configuration changes required.

## Technical details

The bug was in `core/modules/views/js/ajax_view.js`. When building the AJAX request, the code removes existing exposed filter params from the page's query string, but it only matched `input[name="..."]` by exact name. `select` and `textarea` elements were never matched, and a multi-select named `type[]` did not match a URL param such as `type[0]` or `type[]`. A multi-select with nothing selected submits no value, so the stale URL param was passed through and re-applied.

The fix collects the base names of every `[name]` element in the exposed form into a `Set`, stripping any `[...]` suffix with a `stripArraySuffix()` helper. It then filters URL params by checking their suffix-stripped name against that set. This removes all exposed form fields from the URL, not only checkboxes and multi-selects, which can change the order of params in generated URLs. The committer noted this is closer to the original intent of the `// Remove current exposed filters.` comment. Existing FunctionalJavascript tests in the views and admin tests were updated for the new param order (for example `title=Page%20Two&type=All&status=All`). A new `testUnselectMultiSelectExposedFilter` covers clearing the selection and the `type[0]`/`type[1]` URL form. It was backported to 12.0.x, 11.x and 11.5.x.
