## Summary

Kernel test classes that share their environment (via the `ShareEnvironment` attribute from [#1411074](https://www.drupal.org/node/1411074)) now build the container once for the first test method and load it from cache for the remaining methods. Test classes that don't share the environment behave as before for container building. In the author's measurements, a 26-method test went from about 19s to about 15s. With xhprof enabled, per-method time dropped from about 2.5s to about 700ms. The saving is smaller for tests that install modules in several methods.

## Impact

Affects module maintainers.

- **API change:** `KernelTestBase::$container` is now typed `?ContainerInterface` instead of `?ContainerBuilder`; `KernelTestBase::$keyValue` is now the booted container's `keyvalue` service rather than a memory factory.
- **New API:** New `@internal` `Drupal\Core\Test\KernelTestDrupalKernel` and a protected `DrupalKernel::getContainerFromCacheIfCacheable()` hook.

## Technical details

`KernelTestBase::bootKernel()` now creates a `Drupal\Core\Test\KernelTestDrupalKernel` (marked `@internal`) instead of a plain `DrupalKernel`, passing `static::sharesEnvironment()` as the cache flag. When the environment is shared, it calls `setContainerNeedsRebuild(FALSE)` and `setOverrideUseCache(TRUE)`, so the first method compiles and caches the container and later methods load it. To support this, `DrupalKernel::initializeContainer()` now calls a new protected `getContainerFromCacheIfCacheable()`, which holds the old "module list not set and no forced rebuild" check, and the subclass overrides it. The subclass appends a `cacheSuffix` to `getContainerCacheKey()` and increments it in `rebuildContainer()` and `resetContainer()`. A container rebuilt inside a test method is therefore cached under its own key and does not overwrite the initial one. `bootKernel()` calls `resetCacheSuffix()` and then `resetContainer()`, so every method starts from the same cached initial container with fresh service state. There is an `@todo` pointing at [#2218651](https://www.drupal.org/node/2218651).\n\nKernelTestBase no longer registers its own synthetic `keyvalue` service (memory factory, or database factory for shared environments). The container's normal key value service is used, and `$this->keyValue` is set from `$this->container->get('keyvalue')` after boot. As a result the `key_value` table now exists in kernel test databases. Core tests were adjusted: `SchemaTest` expected table lists now include `key_value`, a menu link content test lists `key_value` among its tables, and the installer test drops `key_value` in `setUp()` so the installer sees an uninstalled site. `$container` is now typed `?ContainerInterface`. A new `KernelTestSharedContainerTest` uses the `container_rebuild_test` module's counter to assert the container is built once across three data-provider iterations. Follow-ups were opened for sharing caches between methods ([#3629052](https://www.drupal.org/node/3629052)) and deprecating `KernelTestBase::$keyValue` ([#3629287](https://www.drupal.org/node/3629287)). The PhpDumper container work in [#3583505](https://www.drupal.org/node/3583505) is expected to be compatible with this approach.

## Upgrade

Core tests that inspect the database table list needed `key_value` added, for example in `SchemaTest`:

```php
$this->assertEquals(['config', 'key_value', 'select'], $tables);
```

Contrib kernel tests that type-hint `$this->container` as `ContainerBuilder` or assume an in-memory `$this->keyValue` may need adjusting. In the issue thread the committer expected existing tests to keep working and planned to update the shared-environment change record (https://www.drupal.org/node/3623403) with conversion steps.
