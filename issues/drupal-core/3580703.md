## Summary

The Update Status module's last remaining legacy procedural functions have been deprecated in favor of object-oriented equivalents. There is no behavior change for site visitors or administrators using the update reports UI; this is purely an internal API migration. Custom code or contrib modules that call these functions directly will see deprecation notices starting in Drupal 11.5 and must switch to the replacements before Drupal 13.0, when the old functions are removed.

## Impact

Affects module maintainers.

- **Deprecation:** Nine procedural functions in `update.module` are deprecated for removal in Drupal 13.0.0: `_update_no_data()`, `update_get_available()`, `update_create_fetch_task()`, `update_refresh()`, `update_fetch_data()`, `update_fetch_data_finished()`, `_update_message_text()`, `_update_project_status_sort()`, `update_storage_clear()`.
- **New API:** `UpdateManagerInterface` gains `getAvailable(bool $refresh)` and `reset(): void` methods.

## Technical details

Most of the deprecated functions were already thin wrappers around service calls; they now just trigger an `E_USER_DEPRECATED` error and delegate to the same service. `update_get_available()` moves its full logic onto a new `UpdateManagerInterface::getAvailable()` method (implemented in `UpdateManager`), and `update_storage_clear()` becomes `UpdateManagerInterface::reset()`, which clears both the `update` key/value store and the `update_available_releases` expirable temp store. `update_create_fetch_task()`, `update_refresh()`, and `update_fetch_data()` simply forward to the existing `update.processor` and `update.manager` services.

Two functions have no direct replacement because they were internal implementation details, not really general-purpose utilities: `update_fetch_data_finished()`'s logic moved to a new `UpdateController::updateFetchDataFinished()` method (the batch finish callback is now `self::class . ':updateFetchDataFinished'` instead of the bare function name), and `_update_project_status_sort()`'s comparison logic was inlined as an anonymous function inside `UpdateRequirements::runtime()`. The message-building helpers `_update_no_data()` and `_update_message_text()` moved into a new `UpdateMessageTrait` (`noData()` and `getText()`), which is now used by `UpdateHooks`, `UpdateRequirements`, and `UpdateThemeHooks`. A new `Drupal\update\Hook\UpdateExtensionHooks` class centralizes the `hook_themes_installed`/`uninstalled` and `hook_modules_installed`/`uninstalled` implementations that previously lived in `UpdateHooks` and called `update_storage_clear()`; they now call `$this->updateManager->reset()`.

While migrating callers, the author noticed some code was reading from the key/value collection `update_available_release` (singular) instead of the correct `update_available_releases` (plural), including in Package Manager's admin cache-clearing code and a related test; those were corrected as part of this change. `Drupal\package_manager\ProjectInfo`'s constructor also gained a required `UpdateManagerInterface $updateManager` argument so it can call `getAvailable()` as a service instead of the deprecated function, which affects its callers `SupportedReleaseValidator` and related tests.</technical>
<parameter name="upgrade">Replace calls to the deprecated functions with their service-based equivalents:

```php
// Before:
update_get_available($refresh);
// After:
\Drupal::service(\Drupal\update\UpdateManagerInterface::class)->getAvailable($refresh);

// Before:
update_create_fetch_task($project);
// After:
\Drupal::service('update.processor')->createFetchTask($project);

// Before:
update_refresh();
// After:
\Drupal::service(\Drupal\update\UpdateManagerInterface::class)->refreshUpdateData();

// Before:
update_fetch_data();
// After:
\Drupal::service('update.processor')->fetchData();

// Before:
update_storage_clear();
// After:
\Drupal::service(\Drupal\update\UpdateManagerInterface::class)->reset();
```

`_update_no_data()` and `_update_message_text()` are replaced by `noData()` and `getText()` on the new `\Drupal\update\UpdateMessageTrait`, which classes needing them should `use`. `update_fetch_data_finished()` and `_update_project_status_sort()` have no replacement; their logic is now private to `UpdateController` and `UpdateRequirements` respectively.

If you construct `\Drupal\package_manager\ProjectInfo` directly, it now requires an `UpdateManagerInterface` service as a second constructor argument:

```php
// Before:
new ProjectInfo($project_name);
// After:
new ProjectInfo($project_name, \Drupal::service(\Drupal\update\UpdateManagerInterface::class));
```
