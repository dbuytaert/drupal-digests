## Summary

Entity view and form displays calculate their config dependencies from the widget and formatter plugins used on each field, so that deleting something a plugin depends on (a view mode, an image style, a taxonomy vocabulary, etc.) is blocked or handled safely. This calculation was broken whenever a display used the same plugin on more than one field: only the last field's dependencies were kept, so the others were silently dropped. A common trigger is two comment fields each set to show a different comment view mode, or two image fields using different image styles. If the missing dependency was later deleted, the display could break with a fatal error instead of being cleanly protected. Existing sites do not need to change anything, but should run database updates after upgrading so the new post update hooks can recalculate and fix the dependencies stored in their existing displays.

## Impact

Affects site owners.

- **Config change:** New `field_post_update_recalculate_entity_form_display_dependencies()` and `field_post_update_recalculate_entity_view_display_dependencies()` post update hooks resave all `entity_form_display` and `entity_view_display` config entities to recalculate their dependencies.

## Technical details

`EntityFormDisplay::getPluginCollections()` and `EntityViewDisplay::getPluginCollections()` build a `EntityDisplayPluginCollection` keyed by `$configuration['type']` (the plugin ID). When two fields on the same display use the same widget or formatter, the second field's configuration overwrote the first's in that array, so `ConfigEntityBase::calculateDependencies()`, which iterates the plugin collection to merge in each plugin's `calculateDependencies()` result, only ever saw one instance's dependencies. The fix rekeys both collections by `$field_name` instead of plugin type, which is guaranteed unique per display; `calculateDependencies()` never relied on the array keys, so this is safe.

Because existing config was calculated with the old, lossy keying, two new post update functions, `field_post_update_recalculate_entity_form_display_dependencies()` and `field_post_update_recalculate_entity_view_display_dependencies()`, use `ConfigEntityUpdater` to resave every `entity_form_display` and `entity_view_display`, forcing dependencies to be recalculated with the corrected code. Test coverage includes a new `field_dynamic_dependencies_test` module with a formatter/widget pair whose `calculateDependencies()` adds a configurable module dependency, used in `EntityDisplayDependenciesTest` to prove dependencies from multiple fields using the same plugin are all retained, plus `RecalculateDependenciesUpdateTest` to verify the update path against a pre-fix fixture.
