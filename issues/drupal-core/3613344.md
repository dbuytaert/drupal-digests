## Summary

Drupal 12 removes the `update_fetch_with_http_fallback` setting, which previously let a site fall back to plain HTTP when HTTPS requests to updates.drupal.org failed while checking for available updates or security advisories. This insecure fallback option was deprecated in Drupal 11.5 ([#3591513](https://www.drupal.org/node/3591513)) and is now gone with no replacement. Sites that still have this setting uncommented in `settings.php` should remove it; it no longer has any effect and update/security-advisory checks will always use HTTPS.

## Impact

Affects module maintainers.

- **API change:** `Drupal\update\UpdateFetcher::__construct()` and `Drupal\Core\Update\SecurityAdvisoriesFetcher::__construct()` no longer accept a `Settings` argument; the internal `Drupal\package_manager\Validator\SettingsValidator` class and its service definition were removed entirely.
- **Deprecation:** The `update_fetch_with_http_fallback` settings.php setting, deprecated in Drupal 11.5, is removed in Drupal 12 with no replacement.

## Technical details

The change strips the `update_fetch_with_http_fallback` handling out of the two places that read it: `Drupal\update\UpdateFetcher::doRequest()` and `Drupal\Core\Update\SecurityAdvisoriesFetcher::doRequest()` (formerly `Drupal\system\SecurityAdvisories\SecurityAdvisoriesFetcher`) now issue a single HTTPS `GET` and no longer catch a failed HTTPS attempt to retry over `http://`. Both classes' constructors drop the injected `Settings $settings` parameter along with the `$withHttpFallback` property. The corresponding entry in `Drupal\Core\Site\Settings::$deprecatedSettings` is removed, leaving that array empty.

Package Manager's `Drupal\package_manager\Validator\SettingsValidator`, which existed solely to block updates while the fallback setting was enabled, is deleted along with its service definition and `SettingsValidatorTest`. The commented-out documentation block for the setting is removed from `default.settings.php`. Test coverage for the HTTP-fallback code paths (`testHttpFallback`, `testUpdateFetcherHttpFallback`) was removed accordingly, and `Drupal\Tests\Core\Site\SettingsTest::testRealDeprecatedSettings` is marked skipped rather than deleted outright, since it needs at least one real "deprecated with no replacement" setting to exercise its data provider and none currently exists for the Drupal 12 transition.</technical>
<parameter name="upgrade">Remove any uncommented `update_fetch_with_http_fallback` line from `settings.php`; it has no effect on Drupal 12 and update checks always use HTTPS:

```php
# $settings['update_fetch_with_http_fallback'] = TRUE;
```

If custom code instantiates or extends `Drupal\update\UpdateFetcher` or `Drupal\Core\Update\SecurityAdvisoriesFetcher` directly, remove the `Settings $settings` constructor argument, for example:

```php
// Before:
new UpdateFetcher($config_factory, $http_client, $settings, $logger);
// After:
new UpdateFetcher($config_factory, $http_client, $logger);
```
