## Summary

Drupal core's command line tool gains a `config:import` command (alias `cim`), the counterpart to `config:export` ([#3594337](https://www.drupal.org/node/3594337)). It imports the staged configuration from the sync storage into the active site, the same way the Configuration module's synchronize page does, but from the terminal. It prints a table of the pending creates, updates, deletes and renames, asks for confirmation (skippable with `--yes` / `-y`), then runs the import and reports success or errors. It is part of the CLI in Core initiative ([#3582246](https://www.drupal.org/node/3582246)).

## Impact

No upgrade or configuration changes required.

## Technical details

`ConfigImportCommand` is marked `@internal` and uses Symfony Console attributes (`#[AsCommand]`, `#[Option]`). It runs the sync storage through `ImportStorageTransformer`, so import transform event subscribers apply. It builds a `StorageComparer` against the active storage and exits successfully with "There are no changes to import." when nothing differs. Otherwise it renders the change list and asks for confirmation. Declining throws `UserAbortException`. The command then gets a `ConfigImporter` from `ConfigImporterFactory`. If `alreadyImporting()` is true, it warns that another request may be synchronizing and returns failure. Otherwise it calls `validate()` and `import()`. A `ConfigImporterException` (for example the site UUID mismatch) is printed as an error and returns failure. Errors collected on the importer also produce failure, with each error printed.

The `renderTable()` method that previously lived in `ConfigExportCommand` moved into a new `ConfigCommandTrait`, now used by both commands, so the export and import commands share the same change table. The functional test in the diff notes that batch errors are not shown, because the command line does not run batches yet.
