## Summary

The long-standing procedural helpers `drupal_static()` and `drupal_static_reset()`, used to define reset-able static variables inside functions, are now formally deprecated and will be removed in Drupal 13.0.0. Sites and modules that still call these functions directly will start seeing deprecation notices and should switch to the `memory` cache backend instead. Core's own remaining internal callers (in batch processing, CSS optimization, machine name form validation, comment search indexing, and admin theme settings overrides) have already been converted to use `\Drupal::cache('memory')` directly.

## Impact

Affects module maintainers.

- **Deprecation:** `drupal_static()` and `drupal_static_reset()` are deprecated in drupal:11.5.0 and removed in drupal:13.0.0; use `\Drupal::cache('memory')->get()`, `->set()`, and `->delete()` instead.

## Technical details

The deprecation notices are added directly inside `drupal_static()` and `drupal_static_reset()` in `core/includes/bootstrap.inc`. Because both functions can legitimately be called many times per request (and core itself still needs to call `drupal_static_reset()` globally to flush all statics in a few places), a naive `@trigger_error()` on every call would spam PHPUnit's deprecation handling and logs. To avoid that, each function first checks a per-`$name` marker in `\Drupal::cache('memory')`; the deprecation is triggered only the first time a given `$name` is seen in the request, then the marker cache entry suppresses further triggers for that name.

A special sentinel value, `'clear_all_skip_deprecation'`, was introduced so that core's own "reset every static" call sites (`drupal_flush_all_caches()`, `KernelTestBase::tearDown()`, and `FunctionalTestSetupTrait::tearDown()`) can still clear all statics via `drupal_static_reset()` without triggering the deprecation on themselves; these call sites are marked with `// @phpstan-ignore function.deprecated`.

Remaining core call sites that used `drupal_static()` as a lightweight per-request cache (`_batch_needs_update()` in `core/includes/batch.inc`, `FormElementBase`/`MachineName::getTransliterationLanguageOverrides()`, `CommentHooks::nodeUpdateIndex()`, and `Settings::userOverrideEnabled()` in `core/themes/default_admin`) were rewritten to read and write `\Drupal::cache('memory')` directly, matching the pattern already used elsewhere for `drupal_static_reset()` replacements like `options.allowed_values`. `ResettableStaticTest` was updated with `#[IgnoreDeprecations]` and `expectUserDeprecationMessage()` assertions to cover the new deprecation paths.

## Upgrade

Replace direct calls to `drupal_static()` and `drupal_static_reset()` with the memory cache backend. For example, code that previously did:

```php
$overrides = &drupal_static(__CLASS__ . '_' . __METHOD__, []);
```

should become:

```php
$cid = __CLASS__ . '_' . __METHOD__;
$cached = \Drupal::cache('memory')->get($cid);
$overrides = $cached->data ?? [];
// ... after computing/updating $overrides:
\Drupal::cache('memory')->set($cid, $overrides);
```

And a reset call like:

```php
drupal_static_reset('my_cache_id');
```

becomes:

```php
\Drupal::cache('memory')->delete('my_cache_id');
```

Calling `drupal_static_reset()` with no arguments (to reset all statics) is also deprecated; there is no direct drop-in replacement for clearing every memory cache entry at once, so only internal core bootstrap code retains this ability via the `'clear_all_skip_deprecation'` sentinel.
