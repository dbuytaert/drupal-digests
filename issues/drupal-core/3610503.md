## Summary

Importing configuration (for example via `drush config:import`) used to read each changed config object from the database one at a time, which could mean hundreds or thousands of individual queries on a site with a large config set. This change batches those reads into chunks of 500, cutting the number of queries down to a handful. The issue author measured a couple hundred milliseconds saved on a Umami config import, with larger savings expected on sites with more configuration. Combined with the related config file parsing cache improvements in [#3591680](https://www.drupal.org/node/3591680), this is expected to cut more than half the time off a typical `drush` config import.

## Technical details

The fix is in `StorageCopyTrait::replaceStorageContents()`, which is used whenever one config storage is synced into another (config import, config staging, etc.). Previously it looped over every config name and called `$source_collection->read($name)` and `$target_collection->read($name)` individually. Now it splits the list of names into `array_chunk($names, 500)` batches and calls `readMultiple()` once per chunk on both the source and target storage, then compares the in-memory arrays to decide whether to write or delete each item. For storage backends like `DatabaseStorage`, `readMultiple()` already issued a single `SELECT ... WHERE name IN (...)` query, so batching through it turns what could be thousands of round trips into a handful.

Making `MemoryStorage::readMultiple()` actually get exercised (it previously wasn't reachable from this code path) exposed a latent bug: it used `array_intersect_key($this->config[$this->collection], array_flip($names))`, which errors when the collection is empty or missing. It now delegates to `read()` per name, consistent with the class's other methods, which are only used in tests.</technical>
