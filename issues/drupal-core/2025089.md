## Summary

Drupal has long had three procedural helper functions for adding, removing, or bulk-changing the permissions on a user role: `user_role_grant_permissions()`, `user_role_revoke_permissions()`, and `user_role_change_permissions()`. These are now deprecated in favor of equivalent methods directly on the role entity's `RoleInterface`. Core's own call sites (tests, `filter.module`, the permissions form, and several contrib-adjacent modules) have all been converted to the new object-oriented API. Sites and contributed modules that call the old functions will get a deprecation notice and must switch before Drupal 13, where the functions are removed.

## Impact

Affects module maintainers.

- **Deprecation:** `user_role_grant_permissions()`, `user_role_revoke_permissions()` and `user_role_change_permissions()` are deprecated in favor of `RoleInterface::grantPermissions()`, `RoleInterface::revokePermissions()` and `RoleInterface::changePermissions()`.
- **New API:** `RoleInterface` gains `grantPermissions(array $permissions)`, `revokePermissions(array $permissions)` and `changePermissions(array $permissions)` methods for bulk permission changes on a role entity.

## Technical details

`RoleInterface` gains three new methods: `grantPermissions(array $permissions): static`, `revokePermissions(array $permissions): static`, and `changePermissions(array $permissions): static`. The existing singular `grantPermission()` and `revokePermission()` methods on `Role` are now thin wrappers that cast their argument to an array and delegate to the new plural methods, so no behavior changes there. `changePermissions()` (previously only a procedural function's logic) is now a first-class interface method: it filters the given associative array into permissions to grant versus revoke and calls the other two methods accordingly.

The three deprecated procedural functions in `user.module` now load the role with `\Drupal::entityTypeManager()->getStorage('user_role')->loadOverrideFree($rid)`, call the corresponding new `RoleInterface` method, save, and emit an `E_USER_DEPRECATED` trigger_error. Call sites throughout core (comment, file, filter, image, media, node, responsive_image, system, taxonomy, user tests, and `filter.module`'s `FilterFormat::postSave()` and the permissions form submit handler) were updated to the pattern `Role::loadOverrideFree($rid)->grantPermissions([...])->save()` (or `revokePermissions()`/`changePermissions()`), replacing direct calls to the deprecated functions. See [#3620216](https://www.drupal.org/node/3620216) for the `loadOverrideFree()`/`loadMultipleOverrideFree()` API this conversion depends on.

## Upgrade

Replace calls to the deprecated procedural functions with the equivalent `RoleInterface` methods on a loaded role entity:

```php
// Before:
user_role_grant_permissions($rid, ['administer nodes']);
user_role_revoke_permissions($rid, ['administer nodes']);
user_role_change_permissions($rid, ['administer nodes' => TRUE, 'access content' => FALSE]);

// After:
use Drupal\user\Entity\Role;

Role::loadOverrideFree($rid)->grantPermissions(['administer nodes'])->save();
Role::loadOverrideFree($rid)->revokePermissions(['administer nodes'])->save();
Role::loadOverrideFree($rid)->changePermissions([
  'administer nodes' => TRUE,
  'access content' => FALSE,
])->save();
```

Note `loadOverrideFree()` can return `NULL` if the role doesn't exist, so guard with `?->` where appropriate, as done in `media_install()` and `node_install()`.

### Collaboration

The API shape was debated for years between andypost and alexpott: whether `grantPermissions()`/`revokePermissions()` should take an array argument or be variadic extensions of the singular methods, and whether the plural methods were even worth adding alongside the singular ones. alexpott argued a dedicated plural array-accepting method was clearer than overloading the singular method with variadic arguments, which andypost preferred for its type-safety of individual string arguments. When nicxvan picked up the implementation, they resolved the long-standing disagreement by following alexpott's array-based approach, and opened a follow-up ([#3621087](https://www.drupal.org/node/3621087)) to address the singular/plural question for `UserCreationTrait` separately. berdir's review noted the diff didn't change the actual list of permissions, only how the calls were made, and estimated contrib has roughly 700 call sites that would need similar conversion, suggesting Rector automation.
