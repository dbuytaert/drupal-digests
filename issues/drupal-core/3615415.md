## Summary

On PostgreSQL, every single database query used to be passed through a `preg_replace()` call looking for LIKE and regular-expression operators so it could add a `::text` type-cast to the field they act on (PostgreSQL doesn't auto-cast non-text columns for those operators). That regex ran on every query regardless of whether it used those operators, and it worked over the final SQL string so it could also mismatch inside expressions or string literals. This change moves the cast into query compilation, so it is only added to the specific conditions that need it, removing the per-query overhead for the many queries that never use LIKE or regex operators. Raw SQL strings (not built with the query builder) still get the old rewrite as a fallback, but relying on that is now deprecated since it will be removed in Drupal 13.

## Impact

Affects module maintainers.

- **API change:** The array returned by `Connection::mapConditionOperator()` supports a new `field_suffix` key that `Condition::compile()` appends to the field before the operator; database drivers overriding the condition operator map should be aware of it.
- **Deprecation:** Relying on the PostgreSQL driver's `Connection::prepareStatement()` to auto-add a `::text` cast to fields used with `LIKE`/regex operators in raw SQL strings is deprecated in `drupal:11.5.0` and removed in `drupal:13.0.0`.
- **New API:** New public method `Connection::getConditionFieldSuffix()` returns the SQL suffix (e.g. a type-cast) a driver needs appended to a field for a given condition operator, for use when building raw SQL condition snippets.

## Technical details

`Condition::compile()` now supports a `field_suffix` directive in the array returned by `Connection::mapConditionOperator()`, appended to the compiled field fragment before the operator. The PostgreSQL driver's `$postgresqlConditionOperatorMap` sets `'field_suffix' => '::text'` for `LIKE`, `LIKE BINARY`, `NOT LIKE`, `REGEXP` and `NOT REGEXP`, plus identity entries for `ILIKE`, `NOT ILIKE`, `~*` and `!~*` so code (such as Views' `StringFilter`) that builds conditions with those PostgreSQL-native operators directly also gets the cast.

For code that builds raw SQL condition snippets outside the query builder (e.g. `Query::where()`), a new `Connection::getConditionFieldSuffix($operator)` method exposes the same suffix so it can be added manually. `pgsql\Connection::prepareStatement()` keeps its old `preg_replace()` fallback for raw SQL, but now guards it behind a `stripos()`/`str_contains()` check so it only runs for strings actually containing `LIKE` or `~*`, made the regex idempotent (skips fields already cast), and raises an `E_USER_DEPRECATED` notice when it rewrites a query, pointing at the change record for removal in Drupal 13. `StringFilter`'s operator handlers (`opEqual`, `opContains`, `opStartsWith`, `opEndsWith`, `opNotLike`, `opRegex`, etc.) were updated to call `getConditionFieldSuffix()` and append it to the expression themselves, since they build raw where-expression snippets rather than using `Condition::compile()`.

## Upgrade

Custom database drivers that override `mapConditionOperator()` can add a `field_suffix` entry to have it appended to the field automatically during condition compilation.

Code that issues raw SQL strings against PostgreSQL using `LIKE`, `NOT LIKE`, `ILIKE`, `REGEXP`, or `~*`/`!~*` should add the cast explicitly instead of relying on the driver to rewrite the query, since that fallback is deprecated and removed in Drupal 13:

```php
$suffix = $connection->getConditionFieldSuffix('LIKE');
$query->where("[title]$suffix LIKE :pattern", [
  ':pattern' => '%foo%',
]);
```
