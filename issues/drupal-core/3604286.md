## Summary

Drupal's database `Upsert` query (insert-or-update in one statement) previously always fell back to overwriting a row with the values that were meant to be inserted whenever the insert half of the operation hit an existing key. There was no way to say "update this column based on its current value" (for example, incrementing a counter atomically). This change extends `Upsert` so a per-column update expression can be supplied, and several core subsystems that previously used the older, less efficient `Merge` query (which does a separate select plus insert/update) were converted to use it: cache tag invalidation counters, file usage counts, and the search index word score. As a bonus, cache tag invalidations, and the other converted operations, now happen in a single atomic database round trip instead of two.

## Impact

Affects module maintainers.

- **New API:** New `Drupal\Core\Database\Expression` value object and `Drupal\Core\Database\Query\UpsertUpdateExpression` subclass let an `Upsert` query run a column specific SQL expression (e.g. incrementing a counter) instead of overwriting the column with the insert value when a row already exists.

## Technical details

The core addition is `Drupal\Core\Database\Expression`, a simple value object holding an expression string plus keyed arguments, and `Drupal\Core\Database\Query\UpsertUpdateExpression`, a thin subclass of it used specifically for upsert update overrides. `Upsert::fields()` was extended so entries can mix plain column names (for the insert list) with `column => new UpsertUpdateExpression(...)` pairs; the latter are collected into a new `$updateExpressions` property and their arguments are merged into the bound query parameters in `execute()`. If `fields()` receives an associative array mixing plain insert values with an `UpsertUpdateExpression`, or an expression entry without a string column key, it throws `\InvalidArgumentException`.

Each driver's `Upsert::__toString()` (mysql's `ON DUPLICATE KEY UPDATE`, pgsql's and sqlite's `ON CONFLICT ... DO UPDATE`) now substitutes the raw expression for a column instead of `VALUES($field)` / `EXCLUDED.$field` when one was supplied. The mysql driver's `execute()` binds expression arguments with `bindValue()` rather than `bindParam()`, since by-reference binding inside a loop would make every placeholder share the same final loop variable.

Using this, `Drupal\Core\Cache\CacheTagsChecksum::doInvalidateTags()`, `Drupal\file\FileUsage\DatabaseFileUsageBackend::add()`, and `search_index` word scoring in `search.module` were converted from `merge()`/`expression()` to `upsert()` with an `UpsertUpdateExpression` for the incrementing column. Conversions of `Drupal\Core\KeyValueStore\DatabaseStorage`, `StringDatabaseStorage`, and `TaxonomyHooks` were explicitly left out of scope, per discussion in the issue, and remain on `Merge`. `hook_entity_predelete()` and `hook_ENTITY_TYPE_predelete()` example code in `core/lib/Drupal/Core/Entity/entity.api.php` was updated to demonstrate the `Upsert` equivalent of the old `Merge` pattern.

## Upgrade

Custom code using `Merge` purely to emulate an atomic counter or expression based update can switch to `Upsert` with an `UpsertUpdateExpression`, for example:

```php
$connection->upsert('example_deleted_entity_statistics')
  ->key(['type', 'id'])
  ->fields([
    'type',
    'id',
    'count' => new UpsertUpdateExpression('{example_deleted_entity_statistics}.[count] + :count', [':count' => $count]),
  ])
  ->values([
    'type' => $type,
    'id' => $id,
    'count' => $count,
  ])
  ->execute();
```

This is not a breaking change: `Upsert::fields()` remains backward compatible for plain column/value usage.

### Collaboration

During review, mondrake found and reverted an in-progress attempt to also convert `StringDatabaseStorage`, after discovering it produced duplicate key errors from a unique index added on all non `lid` columns, deciding to leave that conversion for a separate follow-up. The design of the update expression API itself changed mid-review: mondrake initially attached the expression to the insert values, then realized that didn't work when a single upsert call queues multiple value sets, and reworked it so the expression is specified once per column alongside the field list instead. Later, amateescu's review caught an actual bug in the mysql driver's parameter binding (`bindParam()` versus `bindValue()`), which mondrake fixed by binding by value to avoid all placeholders sharing the same loop variable reference.
