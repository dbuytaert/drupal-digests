## Summary

Fields displayed with the "Summary or trimmed" formatter could be cut off in the wrong place. If the underlying HTML used a non-breaking space (`&nbsp;`) instead of a plain space after a sentence's period, which CKEditor commonly does, the trimming logic did not recognize that period as a valid sentence break. Instead it could fall back to cutting the text at an unrelated period, such as after the abbreviation "Dr.", producing a summary that stopped after just two words. The fix teaches the trimming algorithm to also treat "period followed by `&nbsp;`" as a normal sentence ending, so trimmed summaries end at real sentence boundaries as intended.

## Impact

No upgrade or configuration changes required.

## Technical details

The fix is in `TextSummary::generate()` in `core/modules/text/src/TextSummary.php`, which powers the text Trimmed formatter. The method picks a cut point by searching, in priority order, for paragraph tags, then line breaks, then sentence-ending punctuation, using a `$break_points` array of `pattern => offset` pairs matched against the reversed truncated string. Previously the sentence-ending group only included patterns with a literal trailing space, such as `'. ' => 1`. When CKEditor-authored content used `&nbsp;` after a period instead of a plain space, none of those patterns matched, so the algorithm never found the real sentence boundaries and fell through to whatever period happened to be nearest the end, including one inside an abbreviation like "Dr.".

The change adds `'.&nbsp;' => 6` to that break-point group, ahead of `'. '`. The `6` offset accounts for the length of the `&nbsp;` entity so the cut lands immediately after the period rather than mid-entity. The initial proposal in the merge request used a bare `'&nbsp;' => 6` breakpoint, but manual testing (see below) showed that could still ignore sentence boundaries when an editor inserted a stray `&nbsp;` mid-sentence, so the final pattern requires the preceding period as well.</technical>
