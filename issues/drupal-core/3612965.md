## Summary

Drupal core's `composer.json` now allows sites to install either Guzzle 7 or Guzzle 8 as the underlying HTTP client library, even though Drupal 11 itself continues to ship and be tested with Guzzle 7 by default. This backports the Guzzle 8 compatibility work originally done for Drupal 12 in [#3612544](https://www.drupal.org/node/3612544), giving Drupal 11 site owners the option to move to Guzzle 8 in case Guzzle 7 reaches end of life before Drupal 11 does.

## Impact

Affects site owners.

- **Requirements:** `guzzlehttp/guzzle` constraint widened from `^7.10` to `^7.10 || ^8.0` (and `guzzlehttp/psr7` to `^2.8.0 || ^3.0`); Drupal 11 still ships and is tested with Guzzle 7 (bumped to 7.15.5) by default.

## Technical details

The version constraints for `guzzlehttp/guzzle` and `guzzlehttp/psr7` in core's `composer.json` were widened to `^7.10 || ^8.0` and `^2.8.0 || ^3.0` respectively, but `composer.lock` keeps the actually-installed version on Guzzle 7 (bumped to 7.15.5) rather than jumping to Guzzle 8, so nothing changes for sites that don't touch their own lock file.

To make Drupal's own code and test suite tolerate whichever version a site chooses, several compatibility shims were added: `FileCookieJarShim` now only defines its hardened backport of `GuzzleHttp\Cookie\FileCookieJar` when `GuzzleHttp\ClientInterface::MAJOR_VERSION < 8`, since Guzzle 8 ships that hardening natively, and its test skips itself under Guzzle 8. `DrupalTestBrowser::doRequest()` catches `GuzzleHttp\Exception\BadResponseException` instead of `RequestException` to match Guzzle 8's exception hierarchy. `BrowserTestBase::loginHttps()` falls back to parsing the raw `Set-Cookie` header via `SetCookie::fromString()` because Guzzle 8 no longer stores secure cookies received over the test's insecure HTTPS mock connection in its `CookieJar`. Kernel-test HTTP handler callables must now return a `GuzzleHttp\Promise\PromiseInterface` (via `GuzzleHttp\Promise\Create::promiseFor()`) instead of a bare `Response`, since Guzzle 8 changed the handler signature to `($request, array $options)`. A couple of assertions on Guzzle exception message text in `UpdateAdvisoriesTest` and `UpdateFetcherTest` were loosened to accept either the Guzzle 7 or Guzzle 8 message formatting. The `php-http/guzzle7-adapter` dev dependency was dropped.

## Upgrade

No action is required for existing sites: Drupal 11 continues to lock to Guzzle 7 by default. Sites or modules that want to move to Guzzle 8 can now do so, since core's constraint permits it:

```
"guzzlehttp/guzzle": "^7.10 || ^8.0"
```

Run `composer require guzzlehttp/guzzle:^8.0` to opt in. Code that directly catches `GuzzleHttp\Exception\RequestException` and expects it to cover bad HTTP responses should be aware Guzzle 8 uses `GuzzleHttp\Exception\BadResponseException` for that case.
