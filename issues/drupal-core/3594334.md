## Summary

Drupal core now ships its own console command for installing modules and themes, `ex:install` (also invokable as `exin`, `pm:install`, `pm:enable`, `enable`, or `en`), part of the "CLI in Core" initiative ([#3582246](https://www.drupal.org/node/3582246)). Previously this required a contributed tool like Drush. The command accepts a comma-separated list of module or theme machine names, resolves and reports any dependencies that will be pulled in, checks installation requirements the same way the admin "Extend" page does, and asks for confirmation before installing dependencies that were not explicitly requested (bypassable with `--yes`/`-y`). A `--dry-run` option previews what would happen without making changes. On success it lists Help, Permissions, and Configure links for each installed extension, mirroring what a site builder sees after installing from the UI. Modules and themes cannot be mixed in a single invocation.

## Impact

Affects module maintainers.

- **New API:** New `ModuleInstallerInterface::getModulesToInstall()` and `ThemeInstallerInterface::getThemesToInstall()` methods return the dependency-resolved list of modules/themes that would be installed, without installing them.

## Technical details

The command lives in `Drupal\system\Command\ExtensionInstallCommand` (marked `@internal`) and classifies each requested name as a module or theme by checking the reset module/theme extension lists before delegating to installer services.

To support "show what would happen" without installing, `ModuleInstallerInterface` and `ThemeInstallerInterface` gained new methods, `getModulesToInstall()` and `getThemesToInstall()`, which return the dependency-resolved, install-ordered list of extensions (already-installed ones omitted) without side effects, throwing `MissingDependencyException`, `ObsoleteExtensionException`, or `UnknownExtensionException` on invalid input. `ModuleInstaller::install()` and `ThemeInstaller::install()` were refactored to call these new methods internally rather than duplicating the resolution logic, with the side effect that deprecation notices for `DEPRECATED`-lifecycle extensions are now emitted only for the extensions the caller explicitly requested, not for dependencies pulled in automatically. `ModulesListForm::buildModuleList()` (the admin Extend confirmation form) was also refactored to call `getModulesToInstall()` via new `classifyByStability()` and `groupDependenciesByParent()` helper methods, so the CLI and the UI now share the same dependency-resolution and validation code path. The methods were added directly to the interfaces rather than left as class-only additions, per Drupal's BC policy allowing this in minor releases when there is a 1-1 interface/class relationship (raised by catch in review).

## Upgrade

Code that implements `Drupal\Core\Extension\ModuleInstallerInterface` or `Drupal\Core\Extension\ThemeInstallerInterface` directly (rather than extending the core `ModuleInstaller`/`ThemeInstaller` classes) must implement the new interface methods:

```php
public function getModulesToInstall(array $module_list, bool $enable_dependencies = TRUE): array;
```

```php
public function getThemesToInstall(array $theme_list, bool $install_dependencies = TRUE): array;
```
