## Summary

Three long-standing procedural functions in update.module, `update_process_project_info()`, `update_calculate_project_data()`, and `update_calculate_project_update_status()`, are now deprecated and will be removed in Drupal 13. They still work today, but calling them triggers a deprecation warning. Any custom code that inspects a site's available updates (custom update-status pages, contrib modules hooking into update checking, tests) should switch to the new `calculateProjectData()` method on the update manager service instead of calling the procedural function directly.

## Impact

Affects module maintainers.

- **Deprecation:** `update_process_project_info()`, `update_calculate_project_data()`, and `update_calculate_project_update_status()` are deprecated in drupal:11.5.0 (removed in 13.0.0) in favor of `UpdateManagerInterface::calculateProjectData()` and the internal `UpdateCalculator` service.
- **New API:** `UpdateManagerInterface::calculateProjectData(array $available): array` was added as the public replacement for `update_calculate_project_data()`.

## Technical details

The three procedural functions keep working as thin wrappers: each triggers an `E_USER_DEPRECATED` warning and then delegates to the new services. `update_process_project_info()` calls `\Drupal::service(UpdateCalculator::class)->processProjectInfo()`, `update_calculate_project_data()` calls the new `UpdateManagerInterface::calculateProjectData()`, and `update_calculate_project_update_status()` calls `UpdateCalculator::updateProjectStatus()`.

`UpdateManagerInterface::calculateProjectData(array $available): array`, implemented on `UpdateManager`, is the one non-internal addition: it moves the logic previously in `update_calculate_project_data()` onto the manager, which already owns project storage and the `update_project_data` key/value cache. The rest of the logic moved into an `@internal` `UpdateCalculator` service (`processProjectInfo()` and `updateProjectStatus()`) plus two new `@internal` value objects, `UpdateProject` and `UpdateServerProjectInfo` (both `\ArrayObject` subclasses with `createFromArray()`/`toArray()`), which replace the loosely-typed arrays that `update_calculate_project_update_status()` previously mutated by reference.

`UpdateManager::__construct()` gained an optional `?UpdateCalculator $updateCalculator` constructor parameter; omitting it (as any custom subclass still would) triggers a deprecation notice and falls back to `\Drupal::service(UpdateCalculator::class)`. Separately, `package_manager`'s `ProjectInfo` class had the `UpdateManagerInterface` dependency removed from its constructor since it now calls `\Drupal::service(UpdateManagerInterface::class)->calculateProjectData()` directly. A follow-up commit only corrected the change-record link in the deprecation messages (from node 3566774 to 3587768).

## Upgrade

Replace direct calls to the deprecated functions:

```php
// Before
$data = update_calculate_project_data($available);

// After
$data = \Drupal::service(\Drupal\update\UpdateManagerInterface::class)->calculateProjectData($available);
```

```php
// Before
update_process_project_info($projects);

// After
\Drupal::service(\Drupal\update\UpdateCalculator::class)->processProjectInfo($projects);
```

`update_calculate_project_update_status(&$project_data, $available)` becomes `UpdateCalculator::updateProjectStatus()`, but its parameters changed type from arrays to value objects:

```php
// Before
update_calculate_project_update_status($project_data, $available);

// After
$project_data = \Drupal::service(\Drupal\update\UpdateCalculator::class)
  ->updateProjectStatus(
    \Drupal\update\UpdateProject::createFromArray($project_data),
    \Drupal\update\UpdateServerProjectInfo::createFromArray($available)
  )->toArray();
```

### Collaboration

Early on, dww (a module maintainer) pushed back on the plan, noting the update module already has several incomplete services that interact in "interesting" ways, and that he'd rather see a more holistic reorganization before introducing new ones. nicxvan replied that they would try not to make things worse while still moving forward with the deprecations. After several rounds of rework, berdir reshaped the final design before commit: the main `calculateProjectData()` method was moved onto `UpdateManager` (since it already deals with storage), letting `UpdateCalculator` depend on `UpdateManager`'s public methods, and giving the new `UpdateProject`/`UpdateServerProjectInfo` value objects a real API boundary (marked `@internal` for now) instead of just a protected method's array shape.
