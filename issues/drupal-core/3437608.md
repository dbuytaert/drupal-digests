## Summary

The `system.performance` config is now fully validatable. Page cache max age must be an integer between 0 and 31536000 seconds. When Fast 404 is enabled, its `paths` and `exclude_paths` must be valid regular expressions and its `html` must be a valid HTML document, and all three keys are required. When Fast 404 is disabled, those keys may be omitted, but if present they are still validated. Core also gains reusable `Html` and `ValidRegex` constraints and matching schema types that contrib and custom config schemas can use.

## Impact

Affects module maintainers and site owners.

- **Config change:** `system.performance` is now `FullyValidatable`; `cache.page.max_age` must be 0 to 31536000, and `fast_404` paths, exclude_paths and html are validated and required when `fast_404.enabled` is true.
- **New API:** New `Html` (mode `fragment` or `document`) and `ValidRegex` validation constraints, and new `html_fragment`, `html_document` and `regex` config schema data types.

## Technical details

`core.data_types.schema.yml` gains three types: `regex` (constraint `ValidRegex`), `html_fragment` (`Html` with `mode: fragment`) and `html_document` (`Html` with `mode: document`). The constraints live in `Drupal\Core\Validation\Plugin\Validation\Constraint` as `HtmlConstraint`/`HtmlConstraintValidator` and `ValidRegexConstraint`/`ValidRegexConstraintValidator`. They sit in core's Validation namespace rather than a component, to avoid a new dependency from the Utility component. `HtmlConstraint` throws an `InvalidArgumentException` for any mode other than `fragment` or `document`; the validator parses with `Masterminds\HTML5` and adds each parser error as a violation, and ignores NULL. `ValidRegexConstraintValidator` checks `@preg_match($value, "") !== FALSE` and reports the `preg_last_error_msg()` text in the violation.

In `system.schema.yml`, `cache.page.max_age` gets a `Range` of 0 to 31536000, matching `PerformanceForm::buildForm()`. `fast_404` is now a dynamic type `system.performance.fast_404.[enabled]`, resolving to `system.performance.fast_404.1` (enabled: `paths`, `exclude_paths`, `html` required) or `system.performance.fast_404.0` (disabled: the same keys with `requiredKey: false`), both extending `system.performance.fast_404.*`. Consequently, enabling Fast 404 without those keys fails with `SchemaIncompleteException` on save. `Fast404Test` and `CommandsTest` were adjusted accordingly (the latter now calls `installConfig(['system'])`). Coverage of the HTML validator is questioned in follow-up [#3639758](https://www.drupal.org/node/3639758).

## Upgrade

Custom schemas can reuse the new types:
```yaml
my_module.settings:
  type: config_object
  mapping:
    pattern:
      type: regex
      label: 'Regular expression'
    page_html:
      type: html_document
      label: 'HTML page'
```
Code that enables `fast_404` in `system.performance` programmatically must also set `paths`, `exclude_paths` and `html`.

### Collaboration

The scope shifted considerably during review. Early on, `max_age` was limited to multiples of 60 via `DivisibleBy`; catch disagreed and it became a plain 0 to 31536000 range, with form UX changes split to [#3451592](https://www.drupal.org/node/3451592). mikelutz added the `ValidRegex` constraint and the `regex` type. alexpott objected to HTML validation depending on a parser from the Utility component, which led mikelutz to move it into a full `Html` constraint in core's Validation namespace with a fragment/document mode. alexpott also questioned why the schema varies with `fast_404.enabled`. bbrala traced the pattern to existing examples such as `core.date_format.*` and `editor.image_upload_settings.*`, and showed that defining the disabled state too keeps values validated while letting the keys be absent.
