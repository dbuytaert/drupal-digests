## Summary

Drupal now offers a second, object-oriented way to define database table structures for `hook_schema()` and similar schema-defining code, alongside the traditional nested associative array. Instead of building a `$schema['mytable'] = ['fields' => [...], 'primary key' => [...]]` array, module developers can construct a `Table` object made up of `Column`, `Index`, `PrimaryKey`, `UniqueKey`, and `ForeignKey` value objects. These objects validate their own arguments when created (for example, rejecting a `length` argument on an `int` column, or a string default on a numeric column), which surfaces schema definition mistakes immediately instead of failing later or silently producing a wrong table. This is purely additive: existing `hook_schema()` implementations that return arrays keep working exactly as before, nothing needs to change immediately. Core's own conversion of its `hook_schema()` implementations to the new objects is being done incrementally in follow-up issues.

## Impact

Affects module maintainers.

- **New API:** New `Drupal\Core\Database\SchemaDefinition` namespace (`Table`, `Column`, `Index`, `PrimaryKey`, `UniqueKey`, `ForeignKey`, `Schema`, plus `ColumnType`/`ColumnSize`/`SchemaDefinitionType` enums) and `Schema::createSchemaFromDefinition()`/`createTableFromDefinition()` for defining database table structures as an alternative to nested arrays.

## Technical details

The new value objects live under `Drupal\Core\Database\SchemaDefinition` and are immutable and database-abstract: `Table` holds `columns`, `primaryKey`, `uniqueKeys`, `indexes`, `foreignKeys`, and `description`; `Column` carries type (`ColumnType` enum: `Char`, `Varchar`, `VarcharAscii`, `Text`, `Int`, `Serial`, `Float`, `Numeric`, `Blob`), `size` (`ColumnSize` enum), and validated modifiers like `length`, `unsigned`, `precision`/`scale`, `binary`, `serialize`. Column defaults are typed `StringValue|IntValue|FloatValue|NullValue|null`, which lets the API distinguish "no default specified" (PHP `null`, the argument omitted) from "the default is explicitly `NULL`" (`new NullValue()`), a distinction the array API could not make cleanly. Every object exposes `toArray()`, converting itself back to the legacy array shape, so `Schema::createTable()` and the database drivers do not need to change at all: `Schema::createSchemaFromDefinition(Schema $schema)` and the new final `createTableFromDefinition()` method simply call `$table->toArray()` under the hood. Constructor-time validation throws `SchemaDefinitionException` (a `DatabaseException`) for invalid combinations, e.g. `notNull` on a `Serial` column, `unsigned` on a non-numeric column, or a `NULL` default combined with `notNull: TRUE`.

`ModuleHandler::installSchema()`/`uninstallSchema()` were updated to accept either an array or a `Schema` object back from `hook_schema()`, so both styles can coexist during migration. `Drupal\Core\Batch\BatchStorage::schemaDefinition()` and `locale_schema()` were converted as worked examples, along with the `hook_schema()` documentation in `database.api.php`. A `SchemaDefinitionType` enum (`Module`, `Storage`, `Entity`, `Migrate`, `Test`) tags where a `Schema` came from, anticipating a future registry of abstract schema definitions discussed in the issue. Extensibility for database-driver-specific needs (e.g. PostgreSQL GIN/GIST indexes) is handled via a `dbSpecificExtra` array property on `Column`/`Table`/`Index` rather than by subclassing, since the value object classes are `final`. Follow-ups [#3557481](https://www.drupal.org/node/3557481) (converting core's `hook_schema()` implementations) and [#3568040](https://www.drupal.org/node/3568040) (converting storage classes' `ensureTableExists()` methods) build directly on this API.</technical>

```php
function hook_schema(): Schema {
  $tables[] = new Table(
    name: 'users_data',
    description: 'Stores module data as key/value pairs per user.',
    columns: [
      Column::int(
        name: 'uid',
        description: 'The {users}.uid this record affects.',
        unsigned: TRUE,
        notNull: TRUE,
        default: new IntValue(0),
      ),
      Column::varcharAscii(
        name: 'name',
        description: 'The identifier of the data.',
        length: 128,
        notNull: TRUE,
        default: new StringValue(''),
      ),
    ],
    primaryKey: new PrimaryKey(['uid', 'name']),
    indexes: [
      new Index(name: 'name', columns: ['name']),
    ],
  );

  return new Schema(
    type: SchemaDefinitionType::Module,
    name: 'hook',
    tables: $tables,
  );
}
```

### Collaboration

The design went through substantial back and forth on how to keep the value objects extensible without sacrificing type safety. Daffie flagged that making `Column`/`Table`/`Index` `final` would block the PostgreSQL driver from adding GIN/GIST index support ([#3397622](https://www.drupal.org/node/3397622)); mondrake held that db-specific concerns belong outside this "abstract" schema layer, and the two converged on adding a `dbSpecificExtra` property (an `indexes extra` array key when converted to the legacy shape) rather than removing `final` or allowing subclassing. geek-merlin separately proposed keying such extras by `class-string` for better static-analysis inference, which mondrake acknowledged as useful for a future iteration. Alexpott pushed to keep the legacy array output completely untouched by this issue and questioned an early `Property::Undefined` sentinel; mondrake replaced it with dedicated `StringValue`/`IntValue`/`FloatValue`/`NullValue` wrapper objects so that "no default given" and "default is explicitly NULL" could be distinguished without a special enum case.
