## Summary

The `user_update_10000` update hook (which removes non-existent permissions from roles during the Drupal 9 to 10 upgrade) could fatally error and halt the whole update batch if a site had a broken `user.role.*` configuration entry missing its `permissions` key entirely, for example due to an incomplete or corrupted config import in a site's history. Instead of crashing, the update hook now detects this case, logs a notice identifying the broken role, and skips it, letting the rest of the update process complete. The broken role's config is left in place (not deleted); administrators are pointed to the logs to investigate and clean it up manually.

## Impact

No upgrade or configuration changes required.

## Technical details

In `user_update_10000()`, before calling `array_diff($role_config->get('permissions'), $existing_permissions)`, the code now checks whether `$role_config->get('permissions')` returns `NULL`. If so, it logs a notice via `\Drupal::logger('update')` naming the role (`$role_config->getName()`) and reporting that it "has no permissions and should be removed", then `continue`s to the next role instead of calling `array_diff()` with a null argument (which previously threw a `TypeError` under PHP 8's strict typing and aborted the update run).

The fix intentionally does not delete or repair the broken config, since removing configuration during an update hook was considered too risky without certainty about side effects; it only prevents the fatal error and surfaces the problem in the logs (`admin/reports/dblog`) for the site administrator to address separately.

Test coverage was added in `UserUpdatePathTest`, inserting a `user.role.broken_role` config row with empty serialized data (`a:0:{}`) directly into the `config` table, then asserting the update completes, the dblog notice appears, and the broken role's config row is left untouched in the database.</technical>
