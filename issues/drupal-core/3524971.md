## Summary

Drupal 11.x now ships a hardened replacement for Guzzle's `\GuzzleHttp\Cookie\FileCookieJar` class, closing off a publicly known "gadget chain" that can be abused to write an arbitrary file to the server. On its own this class isn't reachable by an attacker, it only becomes dangerous if a site (core or, more likely, a contrib or custom module) also has a PHP Object Injection vulnerability that lets attacker-controlled data reach `unserialize()`. With this fix in place, even if such a vulnerability existed elsewhere, this particular gadget chain would no longer be usable to write files. This is defense in depth, not a fix for a standalone vulnerability, and requires no action from site owners beyond updating.

## Impact

Affects site owners.

- **Security:** Backports Guzzle 8.0's hardening of `\GuzzleHttp\Cookie\FileCookieJar` (a private `autoSave` flag disabled by `__wakeup()`) into an early-loaded shim, closing a PHP Object Injection-chained arbitrary file write gadget on Drupal 11.x. Not independently exploitable; requires a separate deserialization vulnerability.

## Technical details

The underlying issue is in Guzzle itself: `FileCookieJar::__destruct()` calls `save()`, which writes `$this->filename` to disk. If an attacker can get arbitrary serialized data into `unserialize()` (via some other PHP Object Injection bug), they can craft a `FileCookieJar` instance with an attacker-chosen `$filename` and cookie payload; when PHP garbage-collects it, `__destruct()` writes that payload to the attacker's chosen path, a classic deserialization file-write gadget (documented in PHPGGC's `Guzzle/FW/1` chain). Guzzle's maintainers eventually landed a fix for Guzzle 8.0 (https://github.com/guzzle/guzzle/pull/3334) adding a private `$autoSave` flag that `__wakeup()` sets to `false` and `__destruct()` checks before saving, so an unserialized instance never persists to disk. Drupal core was still on Guzzle 7.x, which lacks this hardening.

Rather than removing or aliasing the class (approaches discussed earlier in the issue, including using the `core.moved_classes` mechanism from [#3502882](https://www.drupal.org/node/3502882)), the committed fix backports the Guzzle 8.0 hardened implementation verbatim into a new `core/includes/guzzle_file_cookie_jar_shim.php`, registered in `composer.json`'s `autoload.files` list alongside `bootstrap.inc`. Composer's `files` autoload entries are `require`d unconditionally and very early, before PSR-4 autoloading for anything else kicks in, so this shim's `class GuzzleHttp\Cookie\FileCookieJar` (guarded by a `class_exists(..., false)` check) gets declared first and pre-empts the classloader from ever loading Guzzle's own, unhardened copy of the file. The shim preserves full functionality, normal instantiation still auto-saves on `__destruct()`, but any instance produced via `unserialize()` has `autoSave` forced to `false` by `__wakeup()`, so the file-write gadget is inert. This is a temporary measure: the `@todo` in the shim notes it should be removed once Drupal updates to Guzzle 8, which already happened on the `main` branch in [#3612544](https://www.drupal.org/node/3612544); this fix was committed only to the `11.x` branch since it will still be supported for some time and the composer.json changes did not backport cleanly to older branches.

### Collaboration

The approach evolved considerably over the issue's life. mcdruid initially explored removing the class from the autoloader or aliasing it via the `core.moved_classes` mechanism from [#3502882](https://www.drupal.org/node/3502882), but found in testing that if the original vendor file was still present on disk, PHP would still autoload the real class instead of the alias, undermining that approach. cmlara pushed back on the earlier "just remove it" direction, pointing out that auditing only Drupal-namespace contrib code for usage risks false negatives since the class could be used anywhere in a site's full dependency stack, and that removing the class without a replacement risked white-screen-of-death failures for sites that do legitimately use it. This feedback steered the fix away from removal and toward the front-running shim approach that longwave suggested (citing the precedent in [#3224421](https://www.drupal.org/node/3224421)), which preserves the class's full API while neutralizing the gadget.
