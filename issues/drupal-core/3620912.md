## Summary

Drupal's user account cancellation logic (blocking, deleting, or reassigning content when a user account is cancelled) has moved out of loose procedural functions in user.module and into a new `AccountCancellation` service. The four old functions, `user_cancel()`, `_user_cancel()`, `_user_cancel_session_regenerate()`, and `user_cancel_methods()`, still work but now emit deprecation warnings and simply delegate to the new service. This is purely an internal reorganization: end users see no behavior change, but module maintainers who call these functions directly need to update their code before Drupal 13.

## Impact

Affects module maintainers.

- **Deprecation:** `user_cancel()`, `_user_cancel()`, `_user_cancel_session_regenerate()`, and `user_cancel_methods()` are deprecated in favor of the new `Drupal\user\AccountCancellation` service (`cancel()`, `cancelAccount()`, `regenerateSession()`, `cancelMethods()`), removed in Drupal 13.0.0.
- **New API:** New `Drupal\user\AccountCancellation` service consolidating user account cancellation logic (`cancel()` and `cancelMethods()` are the public entry points).

## Technical details

The new `Drupal\user\AccountCancellation` service, registered in `user.services.yml`, exposes `cancel(array $edit, int $uid, string $method)` (replacing `user_cancel()`), `cancelMethods()` (replacing `user_cancel_methods()`), plus the batch callbacks `cancelAccount()` (replacing `_user_cancel()`, marked `@internal`) and `regenerateSession()` (replacing `_user_cancel_session_regenerate()`, marked `@internal`). The deprecated procedural functions now just call `\Drupal::service(AccountCancellation::class)` and trigger `E_USER_DEPRECATED` warnings.

Several core classes that called the old functions now take the service as a constructor argument instead: `UserController`, `AccountSettingsForm`, `UserCancelForm`, `UserMultipleCancelConfirm`, `EntityResource` (JSON:API), and `UserCancelMethodsConstraint`. In each case the new `?AccountCancellation $accountCancellation = NULL` parameter is optional for backward compatibility; omitting it triggers a deprecation notice and falls back to `\Drupal::service(AccountCancellation::class)`. `hook_user_cancel()` and `hook_user_cancel_methods_alter()` are still invoked the same way, just from `AccountCancellation::cancel()` and `AccountCancellation::cancelMethods()` instead of the old functions, so implementations of those hooks are unaffected.

This change is scoped narrowly to conversion without behavior changes; a follow-up issue, [#3621541](https://www.drupal.org/node/3621541), plans further API redesign of `UserController`'s closures.

## Upgrade

Replace direct calls to the deprecated functions with the `AccountCancellation` service:

```php
// Before:
user_cancel($edit, $uid, $method);
user_cancel_methods();

// After:
\Drupal::service(\Drupal\user\AccountCancellation::class)->cancel($edit, $uid, $method);
\Drupal::service(\Drupal\user\AccountCancellation::class)->cancelMethods();
```

If your custom class extends or constructs any of `UserController`, `AccountSettingsForm`, `UserCancelForm`, or `UserMultipleCancelConfirm` with an explicit argument list, add the new `?AccountCancellation $accountCancellation = NULL` constructor parameter (or inject `Drupal\user\AccountCancellation` via `::create()`) to avoid the deprecation notice.
