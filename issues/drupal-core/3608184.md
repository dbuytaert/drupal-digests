## Summary

When an entity has several multi-value ("multiple cardinality") fields, Drupal core previously ran one query per field and then re-sorted the results in PHP. This change combines those queries into a single, more efficient query per chunk of fields, cutting down the number of database queries needed to load such entities. This is a purely internal performance optimization to entity loading. There is nothing for site owners or module developers to configure or change; Drupal's own performance tests recorded fewer queries on pages like the front page and node pages after this change.

## Impact

No upgrade or configuration changes required.

## Technical details

This is a follow-up to [#3607938](https://www.drupal.org/node/3607938), which found that naively joining multiple multi-value field tables together in one query produces a cartesian product (a row for every combination of deltas across fields). This issue's fix, in `SqlContentEntityStorage::loadMultipleCardinalityFields()`, avoids that by building a "delta spine": a subselect that `UNION`s the `(entity_id, langcode, delta)` rows from each dedicated field table in the chunk, giving the full set of valid delta combinations for the loaded entities. Each field's dedicated table is then `LEFT JOIN`ed onto that spine (aliased `delta_join`) matching on ID, langcode and delta, so every field's value lines up on the correct row without multiplying against other fields. When a chunk contains only one multiple-cardinality field, the union step is skipped entirely and the query selects straight from that field's table, since a single table can't multiply against itself.

`loadFromDedicatedTables()` now chunks the multiple-cardinality fields together (via `array_chunk()` using the same `FIELD_MINIMUM_CHUNK_SIZE` used for single-cardinality fields) and calls `loadMultipleCardinalityFields()` once per chunk instead of once per field, and the previous PHP-side `ksort()` re-sort of deltas is removed since the query now does `ORDER BY` on the delta from the spine. The method signature was reworked accordingly: the `$base_query`, `$base_table`, `$base_id_key`, and `$base_langcode_alias` parameters were dropped since the query is now built independently of the base entity query, and an `$ids` parameter was added to constrain the spine and field tables directly. `EXPLAIN` output shared in the issue confirmed the union/join query hits indexes on every branch, and Drupal's `PerformanceTest` suites were updated to reflect the reduced query counts (for example the Umami front page cold cache dropped from 184 to 178 queries, and the standard profile node page cold cache dropped from 204 to 195).

### Collaboration

catch explored several alternatives before landing on this approach: a new database table pre-populated with sequential delta values to join against (rejected as "a bit painful" and hard to size for sites with very high cardinality), and separately ruled out `UNION` of the actual field data (column type mismatches), a temporary table, a MySQL sequence, and `GROUP BY` (no reliable delta to group on), documenting why each wouldn't work. alexpott then proposed building the delta spine from a `UNION` subselect of just the `(id, langcode, delta)` tuples instead of a physical table, and further simplified it to drop the join to the base entity table entirely. catch called this approach avoiding "the crime against databases" of the earlier table-based idea and moved the issue to RTBC. After commit, real-world benchmarking by nicxvan and scott_euser on sites with large multi-value fields showed a lower query count but not a clear wall-time win in their tests; catch explained that the benefit shows up mainly as reduced per-query overhead and database connection headroom rather than raw execution time, which matters more at scale and when the database is on a separate server from the web head.
