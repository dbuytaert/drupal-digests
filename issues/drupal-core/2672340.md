## Summary

Previously, whenever a user role was created (through the API, a recipe, or during configuration sync), Drupal silently created two extra configuration entities alongside it: a "user_add_role_action" and a "user_remove_role_action", the actions used for bulk-assigning or removing that role from users. This caused a real bug: an install profile or recipe that already exported both the role and its matching action configuration would fail on install with a `ConfigDuplicateUUIDException`, because the hook tried to create the action a second time. Now, these helper actions are only created when a role is added through the admin "Add role" UI form. Programmatic role creation (custom code, drush, recipes, config sync) no longer creates them automatically. Maintainers of install profiles or recipes that define custom roles need to also export the corresponding `system.action.user_add_role_action.*` and `system.action.user_remove_role_action.*` configuration if they want those bulk actions to exist.

## Impact

Affects module maintainers.

- **API change:** Creating a `user_role` entity outside of the admin UI role form (via code, drush, config import, or a recipe) no longer automatically creates the paired `system.action.user_add_role_action.<rid>` and `system.action.user_remove_role_action.<rid>` config entities.

## Technical details

The fix removes the `#[Hook('user_role_insert')]` implementation (`userRoleInsert()`) that lived in the user module's hook class and fired on every `user_role` entity insert, config-synced or not. That logic (skip for the anonymous/authenticated roles, create `user_add_role_action.<rid>` and `user_remove_role_action.<rid>` if not already present) is now inlined directly into `RoleForm::save()`, so it only runs when a role is saved through the admin role-add/edit form. Because the hook no longer runs, `standard` and `demo_umami` install profiles and the `administrator_role`/`content_editor_role` recipes now ship explicit `system.action.user_add_role_action.*` and `system.action.user_remove_role_action.*` YAML config files (e.g. for `administrator`, `author`, `editor`, `content_editor` roles) instead of relying on the removed hook to generate them at install time. Kernel and functional tests that relied on the old implicit creation (`UserActionConfigSchemaTest`, `BulkFormTest`) were updated to create the actions explicitly.

## Upgrade

If your install profile, recipe, or custom code creates roles programmatically and you want the bulk "add/remove role" actions to exist, export them explicitly as configuration, following the pattern core now ships, for example:

```yaml
langcode: en
status: true
dependencies:
  config:
    - user.role.administrator
  module:
    - user
id: user_add_role_action.administrator
label: 'Add the Administrator role to the selected user(s)'
type: user
plugin: user_add_role_action
configuration:
  rid: administrator
```

Add a matching `user_remove_role_action.<rid>` file for the remove action. These actions are otherwise only created automatically when a role is created via the admin "Add role" form.

### Collaboration

The change sat dormant for years after alexpott clarified in comment #18 that `user_user_role_insert()` "is doing something that does not have to happen at all. It's a UI niceness but from an API point-of-view just gets in the way", distinguishing this from a superficially similar issue ([#2980237](https://www.drupal.org/node/2980237)) raised by idebr. When joegraduate revived the patch, smustgrave pushed back on backward-compatibility grounds, arguing the change could silently break contrib tests and install profiles that rely on the automatic action creation, and suggested a formal deprecation path. joegraduate and nicxvan discussed why a conventional deprecation wasn't practical here since the behavior lives inside a hook implementation rather than an invokable API, with nicxvan noting hook implementations aren't strictly covered under Drupal's BC policy. The resolution that shipped was to update core's own install profiles and recipes to export the actions explicitly, so the fix's own change record documents the migration path for anyone else relying on the old implicit behavior.
