## Summary

Two of the last remaining procedural functions in `options.module` are now deprecated, continuing core's effort to eliminate legacy `.module` files. Code calling `options_allowed_values()` to fetch a list field's allowed values should switch to the new `Drupal\options\OptionsAllowedValuesInterface` service. `_options_values_in_use()` is also deprecated with no public replacement, since its only use was internal to the module's own field-storage-update-forbid check. `drupal_static_reset('options_allowed_values')` is deprecated too, since allowed values are no longer cached in a static variable. There is no behavior change for site owners; this only affects code that calls these low-level functions directly.

## Impact

Affects module maintainers.

- **Deprecation:** `options_allowed_values()`, `_options_values_in_use()`, and `drupal_static_reset('options_allowed_values')` are deprecated in Drupal 11.5.0 for removal in Drupal 13.0.0.
- **New API:** New `Drupal\options\OptionsAllowedValuesInterface` service (`getAllowedValues()`) replaces `options_allowed_values()`, caching results per field via the `cache.memory` backend instead of a static variable.

## Technical details

The original design challenge, visible across years of discussion on this issue, was that `options_allowed_values()` is called both from field item plugins (which have an entity available) and from the options module's Views filter/argument plugins (`ListField`, `NumberListField`, `StringListField`), which call it without an entity. Earlier patches tried folding the logic directly into `ListItemBase::getSettableOptions()`, but that didn't work for the Views handlers, so the logic was extracted into a new service instead.

`Drupal\options\OptionsAllowedValuesInterface`, implemented by `Drupal\options\OptionsAllowedValues` and registered as an autowired service, exposes `getAllowedValues(FieldStorageDefinitionInterface $definition, ?FieldableEntityInterface $entity = NULL): array`. It replaces the old `drupal_static()` cache in `options_allowed_values()` with per-field entries in the `cache.memory` backend, keyed by entity type, field name, and whether an entity was passed, and tagged with the field storage's own cache tags plus a new `options_allowed_values` cache tag so invalidating one field doesn't wipe every field's cached values. `ListItemBase::getSettableOptions()`, `ListItemBase::generateSampleValue()`, and the three Views plugins now call this service (the Views plugins receive it via constructor dependency injection, with a deprecated fallback to `\Drupal::service()` for callers that don't yet pass it).

`_options_values_in_use()`'s logic moved into a new protected method, `Drupal\options\Hook\OptionsHooks::hasValuesInUse()`, used only by the module's own `field_storage_config_update_forbid` hook implementation; no public API replaces it. The `hook_field_storage_config_update_forbid()` example in `options.api.php` was updated to query the entity directly with `\Drupal::entityQuery()` instead of calling the deprecated function.</technical>
<parameter name="upgrade">Replace direct calls to the deprecated function:

```php
// Before:
$values = options_allowed_values($field_storage_definition, $entity);

// After:
$values = \Drupal::service(\Drupal\options\OptionsAllowedValuesInterface::class)
  ->getAllowedValues($field_storage_definition, $entity);
```

Prefer constructor injection of `Drupal\options\OptionsAllowedValuesInterface` over `\Drupal::service()` where possible (e.g. in plugins or services).

`_options_values_in_use()` has no replacement; if custom code relied on it, reimplement the entity query directly:

```php
$result = \Drupal::entityQuery($entity_type_id)
  ->accessCheck(FALSE)
  ->condition($field_name . '.value', $values, 'IN')
  ->count()
  ->range(0, 1)
  ->execute();
```

Replace `drupal_static_reset('options_allowed_values')` calls with cache tag invalidation, e.g.:

```php
\Drupal\Core\Cache\Cache::invalidateTags([\Drupal\options\OptionsAllowedValues::CACHE_TAG]);
```

### Collaboration

The design was debated at length before landing. larowlan questioned in a review comment whether introducing a whole new `OptionsAllowedValuesInterface` service was the right call, versus consolidating the logic into `ListItemBase::getSettableOptions()` and having the Views plugins use `FieldStorageDefinitionInterface::getOptionsProvider()->getSettableOptions()`, an approach explored years earlier in [#2329937](https://www.drupal.org/node/2329937). nicxvan confirmed that had in fact been the original approach in this issue but was abandoned because it broke the Views handlers, which call the allowed-values logic without an entity available. After longwave raised a caching concern on the merge request, daffie rebased the branch and fixed the cache invalidation so each field's allowed values are cached and invalidated independently rather than sharing one cache entry, a fix nicxvan explicitly credited to daffie when marking the issue RTBC again.
