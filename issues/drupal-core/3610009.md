## Summary

Drupal's hook discovery no longer looks for procedural hook implementations inside include files (`.inc`) or other custom subdirectories that a module's `.module` file `require_once`s. Historically Drupal would scan any file extension and most subdirectories of a module for legacy hook implementations, a leftover from pre-OOP-hooks Drupal. Now only `.module`, `.profile`, and `.install` files (or `.theme` for themes) at the top level, plus `src` and `src/Hook`, are scanned. Modules that still keep procedural hooks in separate include files will find those hooks quietly stop being invoked after upgrading, since discovery simply no longer looks there rather than throwing an error.

## Impact

Affects module maintainers.

- **Deprecation:** `HookCollectorPass` (and `ThemeHookCollectorPass`) no longer scan `.inc` files, arbitrary subdirectories, or the `file_scan_ignore_directories` setting for procedural hook implementations; only `.module`/`.profile`/`.install` (or `.theme`) files and `src`/`src/Hook` are scanned.

## Technical details

The change is in `HookCollectorPass::filterIterator()` (and the equivalent in `ThemeHookCollectorPass`), which decides which files and directories the hook-collecting compiler pass recurses into. Previously, for directories it allowed `src`/`src/Hook` unconditionally, and otherwise allowed any directory except `tests`, `js`, `css` (and `templates` for themes) and any names configured via the `file_scan_ignore_directories` setting, as long as the directory contained no `.info.yml` file. For files, it accepted the `inc`, `module`, `profile`, `install` extensions (`inc`, `theme` for themes). This MR strips both mechanisms down: directories are only followed into `src` or `src/Hook`, and files are only picked up if their extension is `module`, `profile`, or `install` (`theme` for themes). `inc` is dropped entirely and the `file_scan_ignore_directories` check is removed from this pass (the setting is untouched elsewhere, e.g. `ExtensionDiscovery` and `FileSystem::scanDirectory()`).

The motivation, per [#3571067](https://www.drupal.org/node/3571067), is that hook discovery previously kept scanning include files even though explicit/implicit include-file loading for hooks was removed. Modules that still `require_once` a separate file with legacy procedural hooks (like `better_exposed_filters.module` including a helper file) got picked up accidentally, and when they stopped matching (e.g. a leftover include with a stale function name) it produced a confusing `InvalidArgumentException: Class "..." does not exist.` Removing `.inc` scanning altogether, instead of trying to special-case or better-report the error, was chosen as the simpler fix since discovery can't reliably tell whether a function in an arbitrary include file is actually a hook. The corresponding kernel tests (`testIgnoreDirectories` in `HookCollectorPassTest` and `ThemeHookCollectorPassTest`) and their fixture test modules/themes were removed along with the code path.</technical>
<parameter name="upgrade">If a module or theme still implements legacy procedural hooks in a separate include file and loads it manually, for example:

```php
// mymodule.module
require_once __DIR__ . '/mymodule.inc';
```

```php
// mymodule.inc
function mymodule_entity_type_alter(array &$entity_types) { ... }
```

move the hook implementation directly into `mymodule.module` (or `mymodule.install`/`mymodule.profile`), or convert it to an OOP hook class under `src/Hook`. Hooks left in `.inc` files, or in any directory other than `src`/`src/Hook`, will no longer be discovered or invoked, with no error raised.
