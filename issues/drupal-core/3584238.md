## Summary

Drupal's database transaction system has, since its inception, committed a transaction automatically when the PHP `Transaction` object holding it went out of scope and was garbage collected. This implicit "commit on destruct" behavior is now deprecated: code should instead call `$transaction->commitOrRelease()` explicitly once the wrapped database operations have completed. The old behavior still works for now (it's removed only in Drupal 13.0.0), so most sites and contributed modules will keep working unchanged, but developers writing custom code that opens transactions directly should update it to avoid deprecation notices and to avoid relying on PHP's unpredictable object destruction order. A few internal helper methods added earlier as a workaround for this same destruction-order problem (`Connection::commitAll()`, `Database::commitAllOnShutdown()`, `TransactionManagerBase::commitAll()`) are also deprecated with no replacement, since they exist only to support the mechanism being phased out.

## Impact

Affects module maintainers.

- **Deprecation:** Implicit commit of a `Transaction` object on destruction is deprecated (removed in Drupal 13.0.0). Also deprecated for removal: `Connection::commitAll()`, `Database::commitAllOnShutdown()`, `TransactionManagerBase::commitAll()`, with no replacement.

## Technical details

`TransactionManagerBase::purge()`, called when a `Transaction` object's destructor runs, now emits `@trigger_error(..., E_USER_DEPRECATED)` pointing to `Transaction::commitOrRelease()` as the replacement, unless a new private `$exceptionThrown` flag is set. That flag is set whenever `push()`, `unpile()`, `commit()`, `rollback()`, `addPostTransactionCallback()`, or `processRootCommit()` throws (`TransactionNameNonUniqueException`, `TransactionOutOfOrderException`, `TransactionCommitFailedException`, `LogicException`), so that objects destroyed during exception unwinding don't produce a spurious deprecation notice, and is reset to `FALSE` whenever a new root transaction begins. `TransactionManagerBase::commitAll()`, `Connection::commitAll()`, and `Database::commitAllOnShutdown()` are marked `@deprecated in drupal:11.5.0 ... removed from drupal:13.0.0` using only doc-comment deprecation (no `@trigger_error`), since these run implicitly on every request shutdown and would otherwise flood deprecation logs; PHPStan (`@phpstan-ignore`) is relied on instead to catch remaining usages statically.

Separately, `ContentEntityStorageBase::save()` now catches `\Throwable` instead of `\Exception` around the save operation before rolling back its transaction. Per mondrake's comment on the issue, the narrower `\Exception` catch could let a PHP `Error` escape without rolling back, leaving the transaction to be released (committed) via destruction instead of rolled back, exactly the kind of bug this deprecation effort is meant to surface and prevent.

Class doc comments on `Transaction` and `Connection` were updated to no longer describe destruction-triggered commit as the intended usage pattern, directing developers toward calling `commitOrRelease()` explicitly instead. See the change record at drupal.org/node/3524461. Related issues [#3569127](https://www.drupal.org/node/3569127) and [#3569316](https://www.drupal.org/node/3569316) dealt with fallout from the underlying destruction-order transaction work this deprecation follows up on.

## Upgrade

Code that opens a transaction directly and lets it commit implicitly when the variable goes out of scope should call `commitOrRelease()` explicitly instead:

```php
try {
  $transaction = \Drupal::database()->startTransaction();
  // ... perform database operations ...
  my_other_function($id);

  // The transaction has completed, commit it here.
  $transaction->commitOrRelease();

  return $id;
}
catch (Exception $e) {
  $transaction->rollback();
  throw $e;
}
```

Do not call `Connection::commitAll()`, `Database::commitAllOnShutdown()`, or `TransactionManagerBase::commitAll()`: they are deprecated with no replacement and will be removed in Drupal 13.0.0.
