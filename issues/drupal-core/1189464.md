## Summary

Drupal has had two ways to run long tasks: the Queue API (normally only drained by cron) and the blocking Batch API. This issue adds a middle ground: an "instant queue runner" service that modules can hand a queue name to during a request, and a handful of items (5 by default) from that queue get processed right after the response has been sent to the browser, without blocking the user. This is opt-in per queue, not automatic for all queues, so existing sites see no behavior change until a module or contrib project starts using it. The maintainers point to use cases like closing a timing-attack window on the password reset form ([#3316209](https://www.drupal.org/node/3316209)), instant search indexing, and image style pre-warming as the reasons this landed now.

## Impact

Affects module maintainers and site owners.

- **Config change:** New `instant_queue.config` container parameter with a `maximumItems` key (default 5) caps how many items per queue the instant runner processes per request.
- **New API:** New `Drupal\Core\Queue\InstantQueueRunnerInterface` service lets modules register a queue name so a few of its items get processed right after the response is sent, instead of waiting for cron.

## Technical details

The new `Drupal\Core\Queue\InstantQueueRunner` service implements `InstantQueueRunnerInterface` (a single `registerQueue(string $queue_name): void` method) and `DestructableInterface`, and is tagged `needs_destruction` so its `destruct()` runs during `kernel.terminate`. During a request, code that adds an item to a queue also calls `registerQueue()`; the runner just counts how many times each queue name was registered. In `destruct()`, for each registered queue it claims and processes up to `min(maximumItems, $count)` items (default `maximumItems` is 5, configurable via the `instant_queue.config` container parameter), stopping early if a worker throws `SuspendQueueException`.

To avoid duplicating the claim/process/exception-handling logic, the per-item processing loop previously inlined in `Cron::processQueue()` was extracted into a new `Drupal\Core\Queue\QueueProcessTrait::processItem()`, which handles `DelayedRequeueException`, `RequeueException`, `SuspendQueueException`, and generic `\Throwable` logging via `Error::logException()`. Both `Cron` and `InstantQueueRunner` now use this trait, so the exception semantics for queue workers are identical whether items run via cron or via the instant runner.

Nothing in core actually calls `registerQueue()` yet: no core queue was converted as part of this change, and integration with `automated_cron` was deliberately dropped from scope (comment [#16451928](https://www.drupal.org/node/16451928)) in favor of a simpler, opt-in-per-caller design without added concurrency protection. A follow-up ([#3617085](https://www.drupal.org/node/3617085)) proposes using it for field purging.

## Upgrade

Modules that want a queue item processed shortly after the request that created it, instead of waiting for cron, can inject the new interface and register the queue name after adding the item:

```php
public function __construct(
  protected QueueFactory $queueFactory,
  protected \Drupal\Core\Queue\InstantQueueRunnerInterface $instantQueueRunner,
) {}

public function someMethod() {
  $this->queueFactory->get('my_queue')->createItem($data);
  $this->instantQueueRunner->registerQueue('my_queue');
}
```

Sites can change how many items get processed per queue per request by overriding the `instant_queue.config` container parameter (default `maximumItems: 5`) in a `services.yml`.

### Collaboration

This issue sat open for over a decade with several proposed designs (1px-gif poor-man's-cron style pings, async HTTP requests, ReactPHP/Fibers). catch repeatedly steered it back toward using the post-response terminate event rather than async HTTP, noting in comment [#15616106](https://www.drupal.org/node/15616106) and [#16452204](https://www.drupal.org/node/16452204) that async self-requests don't work reliably on all hosting environments, and that terminate-based processing became solid after [#3295790](https://www.drupal.org/node/3295790) fixed destructable services actually blocking. sukr_s built the first working merge request implementing this with automated_cron integration and a concurrency semaphore, but after review catch decided in comment [#16451928](https://www.drupal.org/node/16451928) that this carried more complexity than needed (automatic integration with all queues via automated_cron, and the semaphore) and opened a second, simplified MR that made registration opt-in per caller and extracted the shared per-item processing logic into `QueueProcessTrait`. After commit, berdir raised an unresolved concern (comment [#16749447](https://www.drupal.org/node/16749447)) that capping by item count rather than by time could still exhaust php-fpm worker processes on hosts with very low process counts, since a slow queue item keeps a process busy in the background even though the response was already sent.
