## Summary

The cache tags invalidator no longer instantiates every cache tag invalidator service and every cache bin when it is built. They are loaded lazily, only when tags are actually invalidated. This removes a source of circular service references (for example a logger that reads config in its constructor, combined with a config override that triggers plugin discovery), and avoids constructing services that are never needed on a request. Sites or modules that subclass `CacheTagsInvalidator` or replace the `cache_tags.invalidator` service may need updating.

## Impact

Affects module maintainers and site owners.

- **Config change:** `cache_tags.invalidator` service definition now uses `!tagged_iterator` arguments instead of `service_collector` tags.
- **API change:** `CacheTagsInvalidator` has a new constructor taking `iterable $invalidators`, `$bins` and `$memoryBins`; the `$invalidators` and `$bins` properties are now `iterable`.

## Technical details

The `cache_tags.invalidator` service in `core.services.yml` dropped the three `service_collector` tags (`addInvalidator` for `cache_tags_invalidator`, `addBin` for `cache.bin` and `cache.bin.memory`). It now passes `!tagged_iterator cache_tags_invalidator`, `!tagged_iterator cache.bin` and `!tagged_iterator cache.bin.memory` as constructor arguments. `CacheTagsInvalidator` gained a constructor with promoted `protected iterable $invalidators = []`, `$bins = []` and `$memoryBins = []`.

Because tagged iterators now include every service with the `cache.bin` tags, not just those implementing the invalidator interface, `invalidateTags()` checks `instanceof CacheTagsInvalidatorInterface` for each bin before calling it. `addInvalidator()` and `addBin()` still work: they rebuild the property as an array spreading the existing iterable plus the new item, so runtime additions and repeated iteration are supported. Operations such as `resetChecksums()` and `purge()` only touch the invalidators, not the bins. New kernel test `CacheTagsInvalidatorTest` asserts the tagged services are not initialized until `invalidateTags()` is called.

The change was committed to `main` and 12.0.x. The committer preferred breaking subclasses in 12.0.x rather than later. Related: [#3612284](https://www.drupal.org/node/3612284) (circular reference discovered in the raven module), [#3632318](https://www.drupal.org/node/3632318).

## Upgrade

If you extend `CacheTagsInvalidator` with your own constructor, pass the new arguments to the parent constructor:

```php
public function __construct(
  protected iterable $invalidators = [],
  protected iterable $bins = [],
  protected iterable $memoryBins = [],
) {}
```

If you define a replacement service, supply the same tagged iterators as core does:

```yaml
cache_tags.invalidator:
  class: Drupal\Core\Cache\CacheTagsInvalidator
  arguments: [!tagged_iterator cache_tags_invalidator, !tagged_iterator cache.bin, !tagged_iterator cache.bin.memory]
```

Subclasses with no constructor of their own need no change. `addInvalidator()` and `addBin()` remain available.
