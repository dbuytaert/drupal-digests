## Summary

`CsrfRequestHeaderAccessCheck`, the service that decides which routes need the `X-CSRF-Token` header check, used an outdated way of detecting which HTTP methods a route allows. It looked for the legacy `_method` route requirement to decide whether a route was read-only (and could skip the check), but modern routes declare allowed methods with the `methods` property instead, so that optimization silently never applied to them. This didn't cause a security problem, since the check itself already allows GET, HEAD, OPTIONS and TRACE requests, but it meant the check was being unnecessarily evaluated on read-only routes defined the modern way. The fix drops the outdated, partially broken logic and instead declares the check statically for any route that has the `_csrf_request_header_token` requirement, regardless of how its methods are declared.

## Impact

Affects module maintainers.

- **API change:** `Drupal\Core\Access\CsrfRequestHeaderAccessCheck` now implements `Drupal\Core\Routing\Access\AccessInterface` instead of `AccessCheckInterface`; its `applies(Route $route)` method has been removed.

## Technical details

Previously `CsrfRequestHeaderAccessCheck` implemented `AccessCheckInterface`, which requires an `applies(Route $route)` method that Drupal calls dynamically per route to decide whether to attach the checker. That method inspected the deprecated `_method` route requirement and only skipped attaching the check if all required methods were read-only; routes using the modern `methods` route property never had `_method` set, so the method-based skip never kicked in for them.

The fix, following a suggestion from longwood in the thread that the check "doesn't need to be dynamic at all," removes `applies()` and the `_method` inspection entirely. `CsrfRequestHeaderAccessCheck` now implements the plain `AccessInterface` and is registered in `core.services.yml` with `applies_to: _csrf_request_header_token` on its `access_check` service tag, so Drupal's `CheckProvider` attaches it statically based purely on the presence of that requirement key. The actual read/write distinction is still enforced at runtime inside `access()`, which already unconditionally allows `GET`, `HEAD`, `OPTIONS` and `TRACE` requests before checking for the CSRF token header. A new kernel test, `CsrfRequestHeaderAccessCheckTest`, asserts the checker is attached to routes declaring `_csrf_request_header_token` regardless of their declared methods, and not attached when the requirement is absent.

## Upgrade

If custom code extends `CsrfRequestHeaderAccessCheck` or type-hints against `AccessCheckInterface` specifically for this class, update to the new contract: implement `Drupal\Core\Routing\Access\AccessInterface` and rely on the `applies_to` service tag attribute instead of overriding `applies()`. For example, in a service definition:

```yaml
access_check.header.csrf:
  class: Drupal\Core\Access\CsrfRequestHeaderAccessCheck
  arguments: ['@session_configuration', '@csrf_token']
  tags:
    - { name: access_check, applies_to: _csrf_request_header_token, needs_incoming_request: TRUE }
```

Routes that rely on this checker should also prefer the `methods` route property over the deprecated `_method` requirement key.

The initial patch by sourav_paul just added a `methods`-based check alongside the `_method` fallback. Months later longwood, while working on the related [#3613245](https://www.drupal.org/node/3613245), reconsidered the whole approach: rather than patching the method-detection logic, he proposed converting the checker to a static `applies_to` access check keyed on `_csrf_request_header_token`, which let the entire `applies()` method be deleted. catch, who committed the change, noted it was "nice to be able to replace all that code with a one-liner."
