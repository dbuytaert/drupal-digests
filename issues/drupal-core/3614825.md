## Summary

Drupal's test runner used to install a test's install profile first, then make a second call to install any extra modules listed in the test's static `$modules` property (and the default theme), each of which rebuilds the service container. This change lets those extra modules and the default theme be installed in the same pass as the profile's own modules and themes, cutting the number of container rebuilds during test setup and speeding up the test suite. There is no behavior change for site owners; it only affects how Drupal core and contrib tests execute. As part of the change, the method some test classes override to add modules, `installModulesFromClassProperty()`, is deprecated and will be removed in Drupal 13.

## Impact

Affects module maintainers.

- **Deprecation:** `FunctionalTestSetupTrait::installModulesFromClassProperty()` is deprecated in Drupal 12.0.0 and removed in 13.0.0; override `getModulesFromClassProperty()` instead to supply extra modules for a test.

## Technical details

`install_profile_modules()` and `install_profile_themes()` in `install.core.inc` now read `$install_state['extra_modules']` and `$install_state['default_theme']` and merge them into the profile's own module and theme lists before making a single call to the module/theme installer, instead of installing the profile first and the extras separately. `install_install_profile()` also writes `default_theme` into `system.theme` config when present.

On the test side, `FunctionalTestSetupTrait::installParameters()` now populates those two `install_state` keys from a new `getModulesFromClassProperty()` method (which just returns the modules collected recursively from `static::$modules`) and from `$this->defaultTheme`. `installDrupal()` no longer calls `installModulesFromClassProperty()`/`installDefaultThemeFromClassProperty()` after the profile install step, because the extra modules and theme are now installed as part of the profile install itself. `installModulesFromClassProperty()` remains as a deprecated BC wrapper around `getModulesFromClassProperty()` for the few callers, such as `PerformanceTestTrait`, that still invoke it directly. `WebDriverTestBase` and `PerformanceTestBase` were switched from overriding `installModulesFromClassProperty()` to overriding `getModulesFromClassProperty()`.

Because `path_alias` can now be installed in the same batch as another module that creates a path alias from its own `hook_install()`, `PathAliasRepository::pathHasMatchingAlias()` now catches `DatabaseException` and returns `FALSE` instead of fataling when its own table doesn't exist yet; a related edge case involving route-dependent modules is tracked separately in [#3616642](https://www.drupal.org/node/3616642). Several test-only modules gained explicit `dependencies` in their `.info.yml` files (e.g. on `layout_builder`) because they could no longer rely on being installed after the module they depend on.

## Upgrade

Test classes that override `installModulesFromClassProperty()` to add extra modules should override `getModulesFromClassProperty()` instead:

```php
// Before:
protected function installModulesFromClassProperty(ContainerInterface $container): void {
  self::$modules = [
    'js_testing_ajax_request_test',
    'js_testing_log_test',
  ];
  parent::installModulesFromClassProperty($container);
}

// After:
protected function getModulesFromClassProperty(): array {
  $modules = parent::getModulesFromClassProperty();
  $modules = array_merge($modules, ['js_testing_ajax_request_test', 'js_testing_log_test']);
  return $modules;
}
```

`installModulesFromClassProperty()` still works but triggers an `E_USER_DEPRECATED` notice and will be removed in Drupal 13.
