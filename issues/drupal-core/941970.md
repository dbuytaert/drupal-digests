## Summary

Saving a View in Drupal no longer unconditionally rebuilds the router (menu) and clears the block plugin cache. Previously, saving any view, even one with only a block display, or a page display where nothing routing-related changed, triggered a full router rebuild. Now Views checks whether something that actually affects routing (a path, route name, arguments, access, enabled status, or, for page displays, menu/tab options) or serialization formats (for REST export displays) actually changed before requesting a rebuild, and block displays only queue a block-cache clear when relevant. This can noticeably speed up saving views, particularly for block-only views or views config imports, since the same site request will no longer pay for a router rebuild it doesn't need.

## Impact

Affects module maintainers.

- **Deprecation:** `views_invalidate_cache()` is deprecated in Drupal 11.5.0 and removed in 13.0.0; use `\Drupal\views\Views::invalidateCache()` for cache invalidation and call the `router.builder`/`views.route_subscriber` services directly when a route rebuild is actually needed.
- **New API:** New `\Drupal\views\PostSaveViewInterface::postSaveView()`, implemented by views plugins (default empty in `PluginBase`), lets a plugin flag on a shared `\Drupal\views\PostSaveProcess` object that a router rebuild or plugin-manager cache clear is required after a view is saved.

## Technical details

The core mechanism is a new value object, `\Drupal\views\PostSaveProcess`, passed through `View::postSave()` to every display handler, its per-type handlers, and its plugins. Instead of each plugin acting immediately, it can call `$postSaveProcess->setRouterRebuild()` or `$postSaveProcess->addDiscoveryToClear($discovery)` to flag work; `View::postSave()` performs the router rebuild (`router.builder`'s `setRebuildNeeded()` plus resetting `views.route_subscriber`) and clears queued plugin manager caches at most once per save, deduplicated by class name.

Plugins participate via the new `PostSaveViewInterface::postSaveView(PostSaveProcess $postSaveProcess, ?DisplayPluginInterface $original_display = NULL)`. `PathPluginBase` implements it to flag a rebuild when the display is new, when the view's enabled status changed, or when any of `getRouteAffectingOptions()` (`path`, `route_name`, `arguments`, `access`, `enabled`) differs from the original display; `Page` extends that option list with `menu` and `tab_options`. The REST `Serializer` style plugin flags a rebuild only when the `formats` option changes, since formats are baked into the route. The `Block` display plugin queues the block plugin manager (`plugin.manager.block`) via `addDiscoveryToClear()` instead of unconditionally clearing it.

`views_invalidate_cache()` is split: cache-tag invalidation and the `hook_views_invalidate_cache()` invocation move to the new `\Drupal\views\Views::invalidateCache()`, called from `View::postSave()` and `postDelete()`, while the deprecated procedural function keeps its old unconditional `router.builder->setRebuildNeeded()` behavior for backward compatibility. A new kernel test, `ViewsSaveProcessTest`, asserts that changing multiple paths or formats across several displays in one save still triggers only one router rebuild and one block-cache clear, and that resaving without relevant changes triggers none.</technical>
<parameter name="upgrade">Replace direct calls to the deprecated function:

```php
// Before:
views_invalidate_cache();
```

```php
// After:
use Drupal\views\Views;

Views::invalidateCache();
// Only if the change actually affects routing:
\Drupal::service('router.builder')->setRebuildNeeded();
\Drupal::service('views.route_subscriber')->reset();
```

Custom views plugins (display, style, etc.) that need to react to a view being saved should implement `\Drupal\views\PostSaveViewInterface::postSaveView()` and call `$postSaveProcess->setRouterRebuild()` or `$postSaveProcess->addDiscoveryToClear($discovery)` instead of performing router rebuilds or cache clears directly in their own save/postSave logic.

### Collaboration

This issue originated in 2010 and went through many stalled patch attempts before converging on its current design. Lendude drove the final round of patches from 2016 onward, iterating in response to review from dawehner, damiankloip, and alexpott, who pushed the design from a style-plugin-specific `postSaveView()` call toward the generalized approach where any plugin type implementing `PostSaveViewInterface` (moved up to the shared `PluginBase`) is invoked uniformly from `View::postSave()`. In 2022, catch reassessed the issue's severity, noting that router rebuild/link discovery had already been decoupled and rebuilds coalesced via `setRebuildNeeded()` since the original report, and reclassified it from a critical bug to a task since the remaining benefit was limited to reducing rebuild counts for admins and config deploys rather than fixing a severe performance regression.
