## Summary

Drupal has long supported "tabledrag": draggable table rows used for reordering things like block regions, menu items, or field weights. The logic that wires this behavior to a table (previously the procedural `drupal_attach_tabledrag()` function) has been moved into the `Table` form element as a proper static method, and the old function is now deprecated. This is part of the ongoing effort to remove procedural code from `common.inc`. Site builders and users won't notice any functional difference; draggable tables continue to work exactly as before. Module developers who called `drupal_attach_tabledrag()` directly (for example, custom admin tables with reorderable rows) should switch to the new method ahead of Drupal 13.

## Impact

Affects module maintainers and front-end developers.

- **Theme change:** Tables using `#tabledrag` now render with an added `tabledrag-enabled` class and a `data-drupal-tabledrag` attribute; the JS no longer relies solely on the table's `id`.
- **Deprecation:** `drupal_attach_tabledrag()` is deprecated in drupal:11.5.0 and removed in drupal:13.0.0; use `\Drupal\Core\Render\Element\Table::attachTabledrag()` instead.
- **New API:** New public static method `\Drupal\Core\Render\Element\Table::attachTabledrag()` contains the logic formerly in `drupal_attach_tabledrag()`.

## Technical details

The function body of `drupal_attach_tabledrag()` in `core/includes/common.inc` was moved verbatim into a new public static method, `\Drupal\Core\Render\Element\Table::attachTabledrag()`, and the original function now just triggers an `E_USER_DEPRECATED` error and delegates to it. All core callers (`Table::preRenderTable()`, `FieldUiTable::tablePreRender()`, and the Views UI rearrange-filter form) were updated to call the new method directly.

As part of the move, the internal counter used to generate a unique tabledrag instance ID per table (previously stored via `drupal_static()`) was reworked twice during the issue's long history: first to a static class property, then, after concerns raised about correctness in the memory cache and long-running PHP contexts, to `\Drupal::cache('memory')` keyed by `Table::TABLE_DRAG_CACHE_ID`, so the counter doesn't get reset unexpectedly between requests handled by the same PHP process (e.g. FrankenPHP, RoadRunner). The table's HTML `id` is still printed for backward compatibility, but the internal selector used to wire up the JS behavior was switched from the raw `id` to a dedicated `data-drupal-tabledrag` attribute (plus a `tabledrag-enabled` class), and `core/misc/tabledrag.js`'s `once()` selector was updated to match on `[data-drupal-tabledrag="${base}"]` instead of `#${base}`.

### Collaboration

This issue took over six years to land because of a substantive, recurring technical debate. Early on, `claudiu.cristea` and `andypost` argued over whether the new method should be called via `self::` or `static::` so subclasses could override just `attachTabledrag()` without duplicating `preRenderTable()`; `claudiu.cristea`'s late-static-binding explanation (with a 3v4l.org example) settled it in favor of allowing proper overriding.

`catch` then pointed out that relying on an incrementing counter tied to a table's HTML `id` is unsafe with dynamic page cache, since two independently-cached blocks rendered in different requests could collide on the same ID, and proposed switching to a `data-*` attribute (issue [#1090592](https://www.drupal.org/node/1090592) territory). `nod_` significantly simplified the resulting JS patch, showing that only the `once()` selector needed to change, without new CSS classes or state-tracking. `alexpott` later caught a subtle off-by-one regression in the counter refactor (starting at 1 instead of 0) introduced by the static-property rewrite. Years later, `catch` re-raised the original concern that a static property still didn't solve the multi-request collision problem, and `nicxvan` and `catch` worked out the eventual fix: storing the counter in the `memory` cache bin instead of a static property.
