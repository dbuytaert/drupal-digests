## Summary

The "negate" option on condition plugins (for example "Show for the listed pages") is now saved as a true boolean instead of `0`/`1` from a checkbox. Config entities that use condition plugins outside the block UI, such as Google Tag containers when the moderation dashboard is enabled, could previously end up with a wrongly typed value and stop showing. Those forms no longer need to cast the value themselves.

## Impact

No upgrade or configuration changes required.

## Technical details

`ConditionPluginBase::validateConfigurationForm()` was an empty method. It now calls `$form_state->setValue('negate', (bool) $form_state->getValue('negate'))`, so the value is cast before `submitConfigurationForm()` copies it into `$this->configuration['negate']`. The config schema declares `negate` as boolean, but checkbox form elements submit `0`/`1`. Core's `BlockForm::validateVisibility()` already did this cast for blocks only; other forms embedding condition plugins had to repeat it. The diff does not remove the `BlockForm` cast, though the issue suggested it could go.

The change landed after a first commit was reverted from `main`, because its unit test broke pipelines under newer PHPUnit mocking. The shipped version adds `ConditionPluginBaseTest`, a data-provider unit test that uses a small concrete `TestConditionPluginBase` class instead of a mock builder. It checks that `0`, `1`, `'0'`, `'1'`, `''`, `FALSE` and `TRUE` all end up as strict booleans. Related: [#2815829](https://www.drupal.org/node/2815829) casts config values by schema at a lower level on form submit, but the thread found it did not fix this case.

## Upgrade

Sites that applied a local patch for this issue can remove it after updating core. Config entities already saved with a non-boolean `negate` (for example a Google Tag container) need to be re-saved through their form so the value is stored as a boolean. This is based on comments in the thread, not on the diff.
