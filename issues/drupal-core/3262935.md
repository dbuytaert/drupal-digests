## Summary

Link field validation used to show the same generic message, "The path '@uri' is invalid.", for many unrelated problems: an inaccessible path, an unsupported protocol, a URL pointing to a non-existent entity, a missing route parameter, or a URL of the wrong type (internal vs. external) for the field's settings. Editors and developers had no way to tell which of these actually happened without digging into the code. Each failure case now gets its own specific message (e.g. "The URL '@uri' has an invalid protocol.", "The URL '@uri' doesn't exist.", "The URL '@uri' is missing a required parameter.", or a message naming the field when an internal-only or external-only field rejects the wrong kind of link), and messages now say "URL" instead of "path" to match the actual field label used in the UI.

## Impact

Affects module maintainers.

- **API change:** `LinkExternalProtocolsConstraint`, `LinkNotExistingInternalConstraint`, and `LinkTypeConstraint` no longer have a single `$message` constructor property; each now exposes multiple named message properties for its distinct failure cases.

## Technical details

Following the Symfony validator convention where constraint messages live as properties on the `Constraint` class rather than being decided ad hoc in the validator, the single `$message` constructor property on `LinkNotExistingInternalConstraint` was split into `$notFoundMessage`, `$invalidParameterMessage`, and `$missingParameterMessage`. `LinkNotExistingInternalConstraintValidator` now catches `RouteNotFoundException`, `InvalidParameterException`, and `MissingMandatoryParametersException` separately and builds a violation with the matching message for each, instead of collapsing all three into one generic message via a shared `$allowed` flag.

Similarly, `LinkTypeConstraint`'s `$message` became `$invalidMessage`, `$onlyInternalMessage`, and `$onlyExternalMessage`. `LinkTypeConstraintValidator` was refactored to add a violation directly at the point where the URL is found to be external-but-internal-only or internal-but-external-only, rather than setting a `$uri_is_valid` boolean and reporting one generic message afterward. The two type-mismatch messages now interpolate `@field-label` (from `$field_definition->getLabel()`), so the message names the actual field instead of saying "the link field". `LinkExternalProtocolsConstraint`'s default message changed to "The URL '@uri' has an invalid protocol.", and `LinkAccessConstraint`'s wording changed from "path" to "URL" without adding new message variants.</technical>
<parameter name="upgrade">Code that instantiates these constraints with a custom message, or reads their `message` property, needs to use the new property names. For example:

```php
// Before
new LinkTypeConstraint(message: 'Custom message');

// After
new LinkTypeConstraint(
  invalidMessage: 'Custom invalid message',
  onlyInternalMessage: 'Custom internal-only message',
  onlyExternalMessage: 'Custom external-only message',
);
```

The same pattern applies to `LinkNotExistingInternalConstraint`, whose single `message` argument is replaced by `notFoundMessage`, `invalidParameterMessage`, and `missingParameterMessage`.</upgrade>
