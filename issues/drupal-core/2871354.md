## Summary

Text formats that use the "Limit allowed HTML tags" filter store their list of permitted tags/attributes (`allowed_html`) as a single string. Because elements were historically just appended wherever the admin form or another module happened to place them, two functionally-identical configurations could produce very different-looking strings, making config exports hard to diff and hard to review in version control. Drupal now sorts that list alphabetically whenever it is saved, so equivalent configurations always serialize to the same string and future changes show up as small, readable diffs instead of noise. A one-time update also re-sorts `allowed_html` on any existing filter format that has Filter HTML enabled, and CKEditor 5's internal list of allowed elements is sorted the same way for consistency.

## Impact

Affects site owners.

- **Config change:** The `allowed_html` setting stored by the Filter HTML (`filter_html`) plugin is now kept alphabetically sorted; existing filter formats are resorted by a new `filter_post_update_sort_allowed_html()` update, producing a one-time config diff.

## Technical details

The fix lands the simple approach originally proposed in this issue rather than the redesigned, structured schema (nested sequences keyed by element/attribute) that was prototyped and reviewed at length over several years: that redesign hit an unresolved backwards-compatibility problem, since Drupal's config schema has no version tracking, so changing `allowed_html` from a `string` to a `sequence` risked breaking config import from sites still exporting the old string format, a concern raised in the thread by Gábor Hojtsy and effulgentsia.

Instead, `FilterHtml::setConfiguration()` now runs the incoming `allowed_html` string through a new public static method, `FilterHtml::sortAllowedHtmlTags()`, which extracts each `<tag attrs>` token with a regex and sorts them with `sort($tags, SORT_STRING)` before re-imploding them. The schema and stored representation remain an unstructured string, so no BC-breaking schema change was needed. A new `filter_post_update_sort_allowed_html()` (`filter.post_update.php`) uses `ConfigEntityUpdater` to resave every `filter_format` config entity that has an enabled `filter_html` filter, so the sort applies retroactively without requiring an admin to resave the format manually. Separately, `HTMLRestrictions::toCKEditor5ElementsArray()` now calls `sort($readable)` on its own generated element list for the same consistency reason, which is why CKEditor 5 test expectations for allowed-tag strings changed throughout the patch.

### Collaboration

This issue was filed in 2017 by Sam152 (sam152) with the simple sorting idea shown in the summary. dawehner offered to help and the conversation quickly escalated into a much more ambitious rewrite: converting `allowed_html` from a string into a structured, keyed schema (element/attribute maps) to get a genuinely diffable config format, which sam152 iterated on through many patch rerolls, and wim leers gave an unusually thorough line-by-line review ([#12092262](https://www.drupal.org/node/12092262)) praising the "eye to detail" and walking through edge cases like default-configuration merging via `FilterPluginCollection::initializePlugin()`. That redesign got to RTBC-adjacent state, but larowlan and then Gábor Hojtsy raised a blocking concern: Drupal's config schema has no version tracking, so retyping `allowed_html` from `string` to `sequence` could silently drop or corrupt allowed-HTML settings (a potential security issue) when importing configuration exported by an older core version. Gábor Hojtsy and effulgentsia explored alternatives (a new parallel config key, a union string-or-sequence schema type) but no consensus was reached, and the issue stalled for years on that unresolved BC question before eventually landing with the original, much simpler sorting-only approach.
