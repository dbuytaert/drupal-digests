## Summary

Drupal's `composer.json` files (root and `core/`) had their minimum allowed dependency versions raised so that even the lowest versions Composer is willing to resolve are not affected by known CVEs. The runtime dependency `guzzlehttp/guzzle` now requires at least `8.0.1`, and the development-only dependencies `composer/composer` and `phpunit/phpunit` had their floors raised too. This is a hardening change with no behavioral effect on a normal `composer update`: sites that already install recent versions of these libraries are unaffected, but the change closes a gap where `composer update --prefer-lowest` or a minimal fresh install could previously land on a vulnerable version.

## Impact

Affects site owners.

- **Requirements:** Minimum allowed `guzzlehttp/guzzle` version raised from `^8.0` to `^8.0.1` in core's runtime requirements; dev-only minimums for `composer/composer` (`^2.8.1` to `^2.10.3`) and `phpunit/phpunit` (`^12.5.15` to `^12.5.22`) were also raised.

## Technical details

The issue was triggered by running `composer audit --locked` combined with `composer update --prefer-lowest` (with `COMPOSER_NO_SECURITY_BLOCKING=1` to bypass Composer's own blocking) to see which CVEs would affect the lowest versions Drupal's constraints technically allow, as opposed to the versions actually pinned in `composer.lock`. That audit found advisories affecting `composer/composer`, `google/protobuf`, `guzzlehttp/guzzle`, `guzzlehttp/psr7`, `squizlabs/php_codesniffer`, and `symfony/polyfill-intl-idn` at their lowest allowed versions.

The committed fix (`d29add7e` on `main`, cherry-picked to `11.x` and `12.0.x`) bumps the floor for the packages Drupal can actually constrain: `guzzlehttp/guzzle` from `^8.0` to `^8.0.1` in both root and `core/composer.json`, and the `require-dev` minimums for `composer/composer` (`^2.10.3`) and `phpunit/phpunit` (`^12.5.22`). `composer.lock` and its `content-hash` were regenerated to match. `google/protobuf` and `squizlabs/php_codesniffer` were left alone since they are transitive dependencies Drupal doesn't declare directly. `symfony/polyfill-intl-idn` was deliberately left unconstrained: per discussion between gábor hojtsy and xjm, its CVE-2026-46644 is considered a hardening-only issue rather than an exploitable vulnerability, and both the 11.x and main lockfiles already resolve above the affected range, so no explicit version constraint or conflict was added for it.
