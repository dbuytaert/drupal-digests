## Summary

Drupal core (`main`, also cherry-picked to 12.0.x) now uses PHP 8 constructor property promotion across existing code. Injected services and values are declared once in the constructor signature (`protected FooInterface $foo,`) instead of as separate property declarations plus assignments. Site owners have nothing to do. The change affects module developers only if they call core constructors with named arguments, because some parameter names changed.

## Impact

Affects module maintainers.

- **API change:** Many core constructor parameters were renamed from snake_case to camelCase to match their promoted properties (e.g. `$csrf_token` to `$csrfToken`), which only breaks callers using named arguments; see change record 3635267.

## Technical details

The change was produced by running Rector's `ClassPropertyAssignToConstructorPromotionRector` with `INLINE_PUBLIC` enabled, so untyped public and protected properties are also promoted. The Rector output was then run through PHP CS Fixer and `phpcbf` to put each promoted constructor on multiple lines with a trailing comma. A few tests that assert on line numbers were fixed by hand, and the PHPStan baseline was regenerated. The shipped diff covers hundreds of files, including `core/lib/Drupal/Component`, `core/lib/Drupal/Core` and the `composer` scaffold and package code. Visible examples are `AccessManager`, the Ajax commands, the action plugins and the scaffold operations such as `AppendOp`.

Property names, visibility and property types do not change. Existing untyped properties stay untyped, for example `protected $reason`. What changes is that constructor parameters which were snake_case now take the camelCase property name. For example `$csrf_token` becomes `$csrfToken` in `CsrfAccessCheck` and `$request_stack` becomes `$requestStack` in `Time`. Where the property and parameter already matched, nothing is renamed. The `@var` property docblocks were dropped with the properties. The constructor `@param` docblocks were kept, with the parameter names updated. Removing those docblocks is tracked separately in [#3565152](https://www.drupal.org/node/3565152). Follow-ups for adding type declarations and `readonly` to promoted parameters are in [#3635274](https://www.drupal.org/node/3635274).

Participants decided not to support named arguments for constructors, so the renames were not given a deprecation layer. Where a constructor mixed promoted and plain parameters, such as plugin constructors that call `parent::__construct()`, only the matching parameters were promoted. The rest are still assigned in the body.

## Upgrade

Only code that calls core constructors with named arguments is affected. Switch to the new camelCase parameter names, or use positional arguments. For example, `CsrfAccessCheck`:

```php
// Before
new CsrfAccessCheck(csrf_token: $token);
// After
new CsrfAccessCheck(csrfToken: $token);
```

Subclasses that override a constructor and call `parent::__construct()` positionally are unaffected.

### Collaboration

The approach was settled over several years. Early threads established that renaming snake_case constructor arguments would not be treated as a BC break, since named arguments are not supported for constructors. They also agreed on multiline promoted signatures. mstrelan then built the final approach, running Rector and PHP CS Fixer from a separate directory to get around a PHPStan/Rector version conflict that had stopped earlier refresh attempts. The Rector setup came from longwave (the `INLINE_PUBLIC` option) and mondrake (a refreshed config). catch wrote the change record and opened the follow-up issues.
