## Summary

Drupal's `user` module used to send all of its notification emails (registration, password reset, account activated/blocked/canceled, cancellation confirmation) through a single internal function, `_user_mail_notify()`. Despite its underscore prefix marking it as internal, this function turned out to be called directly by dozens of contributed modules. Its logic has now been extracted into a new `NotificationHandler` service, one method per notification type (`sendPasswordReset()`, `sendStatusActivated()`, `sendRegisterAdminCreated()`, etc.). `_user_mail_notify()` itself still works exactly as before but is now formally deprecated, with a longer-than-usual grace period: it will be removed in Drupal 13.0.0 rather than sooner, specifically to give contrib maintainers time to update. This groundwork lets an experimental future mail system swap in a different notification implementation without touching `user` module internals directly.

## Impact

Affects module maintainers.

- **Deprecation:** `_user_mail_notify()` is deprecated in drupal:11.5.0 for removal in drupal:13.0.0; its logic moved into the new (currently `@internal`) `Drupal\user\NotificationHandler` service.

## Technical details

The new `Drupal\user\NotificationHandler` class lives in `core/modules/user/src/NotificationHandler.php`, is registered as an unaliased, autowired service (`Drupal\user\NotificationHandler: ~`), and is marked `@internal` with no interface: the maintainers deliberately did not want to commit to a public contract yet (see the long back-and-forth over whether to make it public, settled by an `@internal`-for-now compromise). It injects `logger.channel.user` and `plugin.manager.mail` as lazy `\Closure` values via `#[AutowireServiceClosure]` rather than eager services. All the old `$op`-dispatch logic from `_user_mail_notify()` is preserved in a protected `sendToUser(string $op, UserInterface $account): ?bool` method; the public methods (`sendCancelConfirm()`, `sendPasswordReset()`, `sendStatusActivated()`, `sendStatusBlocked()`, `sendStatusCanceled()`, `sendRegisterAdminCreated()`, `sendRegisterNoApprovalRequired()`, `sendRegisterPendingApproval()`) each wrap it and cast the result to `bool`, discarding the old `NULL` vs `FALSE` distinction that `_user_mail_notify()` still exposes for BC.

Call sites across `user` module were updated to use the new service: `UserAuthenticationController`, `UserCancelForm`, `UserPasswordForm`, `RegisterForm`, `Drupal\rest\Plugin\rest\resource\UserRegistrationResource`, and `User::postSave()`. Several of these classes' constructors gained an optional `?NotificationHandler $notification_handler = NULL` parameter (with a deprecation notice when omitted) so that existing subclasses keep working until they're updated to pass the new service explicitly.

Note a regression verified against the current `main` branch: in `user.module`'s `_user_cancel()`, the `user_cancel_delete` case calls `$notificationHandler->sendStatusCancelled($account)` (double "l"), but `NotificationHandler` only defines `sendStatusCanceled()` (single "l"). Calling this method currently throws `Error: Call to undefined method Drupal\user\NotificationHandler::sendStatusCancelled()`, which means deleting a user account with the "notify user by email" option checked will fatal rather than send the cancellation email.

Two related follow-ups were opened during review: [#3540702](https://www.drupal.org/node/3540702) and [#3540704](https://www.drupal.org/node/3540704) (postponed) to consider dedicated public methods for the registration and password-reset `$op` values, and [#3578758](https://www.drupal.org/node/3578758) to investigate actual contrib usage patterns of `_user_mail_notify()` before deciding whether `NotificationHandler` should eventually drop its `@internal` marker.

## Upgrade

Direct calls to the deprecated function:

```php
// Before:
_user_mail_notify('password_reset', $account);

// After:
\Drupal::service(\Drupal\user\NotificationHandler::class)->sendPasswordReset($account);
```

Other `$op` values map to: `sendCancelConfirm()`, `sendStatusActivated()`, `sendStatusBlocked()`, `sendStatusCanceled()`, `sendRegisterAdminCreated()`, `sendRegisterNoApprovalRequired()`, `sendRegisterPendingApproval()`.

`_user_mail_notify()` keeps working until Drupal 13.0.0 but now triggers an `E_USER_DEPRECATED` notice:
```
_user_mail_notify() is deprecated in drupal:11.5.0 and is removed from drupal:13.0.0. Use the methods from Drupal\user\NotificationHandler service instead. See https://www.drupal.org/node/3539363
```

If you subclass `UserAuthenticationController`, `UserCancelForm`, `UserPasswordForm`, `RegisterForm`, or `UserRegistrationResource`, update your constructor to accept and pass through the new `?NotificationHandler $notification_handler` parameter to avoid the deprecation notice triggered when it is omitted.

### Collaboration

The design went through several rounds of disagreement before landing. znerol's first MR removed backward compatibility for custom `$op` values passed to `_user_mail_notify()`, but reverted that in [#16218115](https://www.drupal.org/node/16218115) after concluding "dispatching op to method call in `_user_mail_notify()` is actually more work than keeping BC." The bigger dispute was whether the new service should be public API or `@internal`: adamps argued repeatedly that since developers have no alternative, `NotificationHandler` should not be `@internal` and should ship with an interface, while berdir countered that `_user_mail_notify()` was always an unsupported underscore-prefixed function and core is "under no obligation to provide a 1:1 replacement" ([#16223586](https://www.drupal.org/node/16223586), [#16450444](https://www.drupal.org/node/16450444)). kristiaanvandeneynde helped broker the eventual compromise in [#16507483](https://www.drupal.org/node/16507483): deprecate the old function, land the new logic behind an `@internal` service, and open a follow-up ([#3578758](https://www.drupal.org/node/3578758)) to investigate actual contrib usage before deciding whether to make it public.
