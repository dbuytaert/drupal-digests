## Summary

On PostgreSQL, Drupal used to send a separate `SET NAMES 'UTF8'` statement to the database right after opening every connection, and Drupal opens a new database connection on every request. That statement is now folded into the connection's startup packet instead, so PostgreSQL sites save one network round trip per request. There is no behavior change: the client encoding is still forced to `UTF8`.

## Impact

No upgrade or configuration changes required.

## Technical details

The fix is in the pgsql driver's `Connection` class. `Connection::open()` now appends `client_encoding=UTF8` to the PDO DSN string it builds (alongside `host`, `dbname`, and `port`), which libpq applies as part of the connection startup packet rather than a separate query. The corresponding `$this->connection->exec("SET NAMES 'UTF8'")` call was removed from `Connection::__construct()`; `init_commands` handling there is unchanged and still runs as before.

Tests added include a kernel test (`Drupal\Tests\pgsql\Kernel\pgsql\ConnectionTest`) asserting `SHOW client_encoding` returns `UTF8` and that multi-byte UTF-8 strings round-trip correctly, including verifying the DSN setting takes precedence over a `PGCLIENTENCODING` environment variable. A unit test (`Drupal\Tests\pgsql\Unit\ConnectionTest`) asserts that constructing a `Connection` with no `init_commands` triggers no `exec`, `query`, or `prepare` calls on the underlying PDO object at all, confirming the extra round trip is gone.
