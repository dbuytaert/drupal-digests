## Summary

Field storage config validation now rejects a cardinality lower than the number of values already stored for that field. Before, validation could not catch this. Setting `cardinality` to 1 on a field where some entity already holds 2 values now fails with a message like "The field 'field_int' of entity type 'entity_test' has more entries (2) than the cardinality (1) allows." Unlimited cardinality (-1) is always accepted. The change landed in `main`, and later comments record backports to `11.x` and `11.5.x`. It also unblocks the parent effort [#3324140](https://www.drupal.org/node/3324140) to convert field storage and field config form validation into validation constraints.

## Impact

Affects module maintainers and site owners.

- **Config change:** `field.storage.*.*` config schema: `cardinality` now carries the `NoFieldItemsExistWithHigherCardinality` constraint.
- **New API:** New `NoFieldItemsExistWithHigherCardinality` validation constraint plugin (with `entityType` and `fieldName` options) in the `field` module.

## Technical details

The constraint is a plugin class, `Drupal\field\Plugin\Validation\Constraint\NoFieldItemsExistWithHigherCardinality`. It was originally named `NoEntitiesExistYetWithHigherCardinality` and was renamed because it counts field items, not entities. It takes `entityType` and `fieldName` options. `field.storage.*.*` in `field.schema.yml` wires it to the `cardinality` key using `%parent.entity_type` and `%parent.field_name`.

`NoFieldItemsExistWithHigherCardinalityValidator` resolves those expressions with `TypeResolver::resolveExpression()` and skips validation in three cases:
- The cardinality is unlimited.
- The `field_storage_config` entity doesn't exist yet.
- The storage has custom storage (`hasCustomStorage()`).

Otherwise it runs an aggregate entity query with `MAX` on `field_name.%delta`, with access checks off. It adds 1 to the result, because deltas start at 0, and adds a violation if that count is greater than the cardinality. An early version compared the raw max delta, which allowed two extra values. This was caught when a test was added that actually calls the validator.

The kernel test expects a `SchemaIncompleteException` when `FieldStorageConfig::save()` is called with the lowered cardinality. A unit test covers the constraint's defaults and message. The constructor uses explicit typed properties instead of the base `Constraint` option handling, because of the Symfony 7.4 deprecations ([#3555534](https://www.drupal.org/node/3555534)). Per the thread, the `main` commit has no exception handling in the validator, and the backport adds `#[HasNamedArguments]` and a catch for the exception that occurs in tests.
