## Summary

Content editors could get a fatal PHP error ("Invalid translation language specified", a 500 error page) simply by opening the "Add translation" link for a language that had already been translated, for example by clicking it in two browser tabs, or navigating back after saving a translation. This was easy to hit in ordinary editing workflows for both content entities and menu links. The fix makes `ContentTranslationController::add()` detect that the target translation already exists before building the add form, and instead shows the message "A translation already exists for [language]" and redirects the editor to the existing translation's edit form.

## Impact

No upgrade or configuration changes required.

## Technical details

The crash happened because `ContentTranslationController::add()` unconditionally cloned the entity and called `addTranslation()` for the target language, which throws an `InvalidArgumentException` in `ContentEntityBase::addTranslation()` if that translation already exists. This could occur through races such as two open tabs each adding the same translation, a browser "back" navigation returning to a stale add-translation URL, or another user saving the same translation concurrently.

The fix adds a guard in `add()`: if `$entity->hasTranslation($target->getId())` is true, it calls `$this->messenger()->addError()` with a translated message and returns a `Symfony\Component\HttpFoundation\RedirectResponse` to `$entity->getTranslation($target->getId())->toUrl('edit-form')->toString()` instead of proceeding to build the form. The method's return type was widened from `array` to `array|\Symfony\Component\HttpFoundation\RedirectResponse` to reflect this. A new kernel test, `ContentTranslationConcurrencyTest`, exercises this by creating an entity with an existing French translation and calling the controller's `add()` method directly, asserting a redirect response and the error message text.
