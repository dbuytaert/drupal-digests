## Summary

A fatal `TypeError` could occur during common content operations (saving or deleting nodes, flushing caches, language switches) on Drupal 11.3+, causing the `cachetags` table to not be updated and leaving caches permanently stale until manually rebuilt. The error was intermittent but reliably reproducible on PHP 8.4 and in multi-replica PHP-FPM setups. This fix ensures cache tag invalidation and all other post-transaction callbacks complete correctly on every request.

## Impact

No upgrade or configuration changes required.

## Technical details

PHP's object destruction order during request shutdown is undefined. If `Connection::__destruct()` executed before `Transaction::__destruct()`, the `Connection` would set its internal `$this->connection` PDO property to `NULL`. When `Transaction::__destruct()` subsequently ran `purge()` → `processPostTransactionCallbacks()`, any registered callback that used the database (such as `DatabaseCacheTagsChecksum::rootTransactionEndCallback` → `doInvalidateTags()`) would call `Connection::prepareStatement()` with a null PDO, throwing `StatementWrapperIterator::__construct(): Argument #2 ($clientConnection) must be of type object, null given`.

The fix adds a `$this->processPostTransactionCallbacks()` call at the end of `TransactionManagerBase::commitAll()`. `commitAll()` is already invoked during PHP shutdown via `commitAllOnShutdown` to unwind any open transaction stack. By also draining the post-transaction callback queue there, all callbacks execute while the `Connection` object is still fully initialized, before any destructors can run. The same pattern applies to any module that registers its own callbacks via `TransactionManagerInterface::addPostTransactionCallback()`.

A new kernel test `testPostTransactionsAlwaysExecutedBeforeConnectionIsDestroyed` in `TransactionTest` verifies the scenario: it closes the connection and unsets the transaction in the same destructor-race order, then confirms the callback's side-effects are present after reopening the connection. A one-line PHPStan suppression comment (`// @phpstan-ignore unset.possiblyHookedProperty`) was removed from the test file in the 11.x and 11.4.x follow-up commits to pass static analysis. The related cleanup issue [#3406985](https://www.drupal.org/node/3406985) (converting core transactions to explicit `commitOrRelease()`) was a related but separate effort and did not fix this callback-ordering problem.
