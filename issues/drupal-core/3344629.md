## Summary

Three response subscribers no longer trigger "Passing null to parameter #1 ($haystack) of type string is deprecated" when a response carries a Content-Type header whose value is NULL. This showed up as unsilenced deprecations in PHPUnit runs (for example the Gatsby module's kernel test), as image generation problems for a site using a webp convert effect, and as failing contrib tests such as JSON:API Extras. Anonymous access to a Views data export that required authentication also triggered it. Those responses are now skipped by the subscribers, as any non-matching content type would be.

## Impact

No upgrade or configuration changes required.

## Technical details

`HeaderBag::get('Content-Type', '')` returns NULL, not the default, when the header exists with a `[null]` value, so the `''` default did not protect `stripos()` and `str_contains()`. The fix changes the call to `$response->headers->get('Content-Type') ?? ''` in `ActiveLinkResponseFilter`, `RssResponseRelativeUrlFilter` and the JSON:API `ResourceResponseValidator`. The root cause, discussed in the thread, is that `Request::getMimeType()` returns NULL when the format is not registered in `Request::$formats`. Drupal normally registers formats in `NegotiationMiddleware::handle()`. The JSON:API, REST and serialization subscribers then call `headers->set('Content-Type', NULL)`. `Response::prepare()` cannot repair this because it only acts when the header is absent. Tightening those writers was left for a follow-up, since it would change behavior (no header versus an empty one). Tests were added: `ResourceResponseValidatorTest::testOnResponseNullContentType()` and an `ActiveLinkResponseFilter` unit test that promotes `E_DEPRECATED` to an exception.
