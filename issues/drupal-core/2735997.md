## Summary

When a View uses aggregation (Sum, Average and similar) on a Decimal or Float field, the field settings now include the Round, Precision and Decimal point options. Before, those options were missing for aggregated decimal fields, so you could not control decimal places or the decimal separator in the output. Base decimal fields on entity types also now get numeric filter and contextual filter (argument) handlers instead of the generic standard ones. An earlier attempt at this issue was reverted after it broke COUNT and date aggregation output. This version leaves the aggregation handler override alone.

## Impact

Affects module maintainers.

- **New API:** Views field definitions for decimal and float fields now carry `'float' => TRUE`, which exposes precision and decimal point settings on aggregated fields.

## Technical details

When aggregation is on, `Sql::getAggregationInfo()` swaps in the `numeric` field handler for functions like Sum and Average. `NumericField::buildOptionsForm()` only shows precision and decimal point settings when the handler definition contains `float => TRUE`, and Views data never set that flag for decimal or float fields. The fix sets `$data[...]['field']['float'] = TRUE` in two places. `FieldViewsDataProvider::defaultFieldImplementation()` does it for configurable fields whose schema column type is `float` or `numeric`, which covers the decimal field type. `EntityViewsData::mapSingleFieldViewsData()` does it for base fields.

In `EntityViewsData`, the `numeric` column type was previously unhandled and fell into the default branch. It is now grouped with `float`, `double` and `decimal`, so base decimal fields get the `numeric` argument and filter plugins. The common `field` and `sort` ids were hoisted above the column-type switch. Integer columns keep the `numeric` argument and filter but get no `float` flag.

This is the second attempt. The first commit removed the `field => numeric` override from `getAggregationInfo()`, which caused regressions (see [#3517853](https://www.drupal.org/node/3517853), [#3518896](https://www.drupal.org/node/3518896)) and was reverted. The form submit exception found along the way was split to [#3613882](https://www.drupal.org/node/3613882). Tests added: kernel tests for `FieldViewsDataProvider` and `EntityViewsData`, a `QueryGroupByTest::testAggregateDecimalOutput()` check that a summed value of 5.789 renders as `5,79`, and a `FieldUITest` functional test. The commit landed on `main` and 12.0.x, and was backported to 11.x and 11.5.x.
