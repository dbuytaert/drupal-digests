## Summary

Field Validation's Regex rule lets site builders validate a field's value against a PCRE pattern. If the pattern was malformed, most commonly missing its required delimiters (a common mistake when migrating rules from Drupal 7, where delimiters were optional), the module previously let a raw PHP warning from `preg_match()` leak straight into the site, both while configuring the rule and later while validating real content. This is fixed: the rule's configuration form now validates the pattern up front and shows a clear, actionable error, and the pattern field's description explicitly states that the expression must include delimiters (e.g. `/^[a-z0-9]+$/`). As a safety net, if a bad pattern still slips through and is run against actual field data, the module now traps the underlying warning, logs it, and reports a normal validation failure instead of a PHP warning.

## Impact

No upgrade or configuration changes required.

## Technical details

The fix lands in two places. `RegexConstraintFieldValidationRule::validateConfigurationForm()` (new) runs the submitted `pattern` through `preg_match()` under a temporary `set_error_handler()` that traps the `E_WARNING` `preg_match()` emits on a malformed pattern (rather than relying on the `@` operator, which is unreliable across error-handler configurations); on failure it calls `$form_state->setErrorByName('pattern', ...)` with a message including the underlying PCRE error. Because this plugin form is nested inside `FieldValidationRuleFormBase`, which builds a separate `FormState` object for the plugin's own `validateConfigurationForm()` call, that base class was also changed to copy any errors recorded on the nested `FormState` back onto the real `$form_state` via `setErrorByName('data][' . $name, ...)`, otherwise the plugin-level error would be silently swallowed.

At runtime, `FieldValidationConstraintValidator::validate()` and `validatePropertyValue()` no longer call `$validator->validate()` directly; they now go through a new `safeValidate()` helper that installs the same kind of temporary `E_WARNING` handler around the Symfony constraint validator call. If a warning fires (e.g. from Symfony's `RegexValidator`) and the validator did not already record a violation, `safeValidate()` logs the warning via the `field_validation` logger channel and adds a fallback `"This value is not valid."` violation, so a bad pattern saved before this fix (or introduced via config import) no longer surfaces a raw PHP warning to content editors.</technical>
