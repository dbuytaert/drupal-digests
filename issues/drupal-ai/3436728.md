## Summary

Simple OAuth now checks whether an OAuth client (a "consumer" entity) is published before granting it access. Previously, unpublishing a consumer did not actually stop it from working: it could still request new access tokens via the client credentials or refresh token grants, and tokens it had already obtained kept working against protected resources. Now an unpublished consumer is treated as if it doesn't exist: attempts to obtain a token fail with an `invalid_client` error, and requests bearing a token issued by a now-disabled client are rejected with "The client is disabled." The client selection dropdown in the client credentials token creation form also stops listing unpublished consumers.

## Impact

Affects site owners.

- **Security:** Unpublished (disabled) consumers can no longer obtain new OAuth tokens or use previously issued bearer tokens; this closes an access control gap.
- **Requirements:** Minimum `drupal/consumers` dependency raised to `^1.24` for the consumer entity `status` field.

## Technical details

The fix relies on the `status` field added to the `consumer` entity by the consumers module (see [#3436723](https://www.drupal.org/node/3436723)), and bumps the `drupal/consumers` dependency to `^1.24` to guarantee its availability.

`ClientRepository::getClientEntity()` now adds `'status' => 1` to the `loadByProperties()` lookup used to find a consumer by `client_id`, so an unpublished consumer resolves to no client entity at all, which makes `validateClient()` return `FALSE` for both the client credentials and refresh token grant types. `Oauth2ClientCredentialsTokenCreateForm` applies the same `status` condition to the client entity query and the storage lookup used during validation, so unpublished consumers disappear from the form's client list.

For tokens issued before a consumer was unpublished, `SimpleOauthAuthenticationProvider::authenticate()` now calls `$account->getConsumer()->isPublished()` and throws an `OAuthUnauthorizedHttpException` ("The client is disabled.") when it returns `FALSE`, so previously granted bearer tokens stop working as soon as their consumer is disabled. Kernel tests cover all three paths: rejecting an unpublished client at the client credentials grant, at the refresh token grant, and at resource access with an already-issued bearer token.

## Upgrade

Update the `drupal/consumers` dependency to at least 1.24, which is where the consumer `status` field this feature relies on was introduced:

```json
"drupal/consumers": "^1.24",
```

Any code relying on a disabled/unpublished consumer still being able to authenticate or use previously issued tokens will now be blocked; disable a consumer only when access should actually be revoked.
