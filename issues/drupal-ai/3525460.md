## Summary

Field Validation's `composer.json` previously pinned `symfony/expression-language` to `^6.3`, which made it impossible to install alongside modules like module_builder that require `symfony/expression-language:^7`. The requirement has been widened to `^6.3 || ^7` so Composer can pick whichever major version satisfies all of a site's dependencies, removing that install-time conflict. If your site ends up resolving to v7 (because of another dependency), be aware that Symfony changed the `in` and `not in` operators in v7 to use strict comparison instead of loose comparison. This module's own code doesn't use those operators, but if you have written Expression constraint rules using `in`/`not in`, their behavior could change silently: double check them after the underlying library version changes on your site.

## Impact

Affects site owners.

- **Requirements:** `composer.json` now allows `symfony/expression-language` `^6.3 || ^7` instead of only `^6.3`, resolving a conflict with modules (e.g. module_builder) that require v7.

## Technical details

The fix is a one-line change to `composer.json`, widening `symfony/expression-language` from `"^6.3"` to `"^6.3 || ^7"`. `symfony/intl` was deliberately left at `^6.3` since it wasn't part of the module_builder conflict this issue was filed to fix.

The module's own `\Drupal\field_validation\Plugin\Validation\Constraint\ExpressionConstraint` doesn't invoke `in`/`not in` itself, so no code changes were needed here, but the loosened constraint means the effective version of `symfony/expression-language` on a given site is no longer guaranteed to be v6: it depends on whatever else is installed. Under v7, `in`/`not in` comparisons became strict (e.g. `'1' in [1, 2, 3]` evaluates to `true` under v6 but `false` under v7), so any site-authored Expression constraint rule relying on loose comparison could behave differently depending on which major version Composer resolves.
