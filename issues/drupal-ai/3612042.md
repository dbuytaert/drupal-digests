## Summary

The AI module already had a data structure for reporting an AI provider's rate limit status (remaining requests, remaining tokens, and time until each resets), but the OpenAI provider never filled it in. This change makes the OpenAI provider read the rate limit information that OpenAI includes on every API response and populate that structure, so code that inspects a chat response's rate limits now gets real numbers back for OpenAI instead of nothing.

## Impact

Affects module maintainers.

- **New API:** `OpenAiProvider::chat()` now populates `ChatOutput::getRateLimits()` (a `ChatProviderLimitsDto`) with request and token limits parsed from OpenAI's `x-ratelimit-*` response headers, instead of leaving it empty.

## Technical details

`OpenAiProvider::chat()` calls the OpenAI PHP SDK's `responses()->create()`, which used to be cast to an array immediately, discarding the response object and its metadata. The fix keeps a reference to the raw SDK response (`$raw_response`) alongside the array conversion, then passes it to a new `setResponsesRateLimits()` method that reads `$response->meta()->requestLimit` and `$response->meta()->tokenLimit` (limit and remaining counts) and builds a `Drupal\ai\Dto\ChatProviderLimitsDto`, set on the `ChatOutput` via `setRateLimits()`.

OpenAI reports reset windows as Go style duration strings (e.g. `6m0s`, `1h20m30s`), but the DTO expects seconds as an integer. A new `parseResetDuration()` helper regex matches value/unit pairs (`ms`, `s`, `m`, `h`, checked in that order so `ms` isn't misread as `m`), converts each to seconds, sums them, and rounds up so a reset is never reported sooner than it actually is. If either header is entirely missing, `setResponsesRateLimits()` returns early and the DTO stays empty, matching `ChatProviderLimitsDto::empty()`.

This only affects the Responses API code path (`responses()->create()`), which since [#3558801](https://www.drupal.org/node/3558801) is the sole path `chat()` uses for both streamed and non-streamed requests.
