## Summary

The Field Validation module's "not blank" rule failed to catch empty values in the middle of a multi-value field. For example, a field limited to two values where only the first was filled in would save without any validation error, even though the same rule correctly flagged the case where both values were left blank. This is now fixed: leaving any value blank in a bounded multi-value field triggers the "this value should not be blank" error, matching how the required validator behaved in Drupal 7. Two things to be aware of before upgrading: the check now runs on any save, not just form submissions, so migrations or code that creates entities programmatically with fewer values than the field allows will also start failing validation; and the error is reported at the field level rather than pointing at the specific empty value, since the widget no longer has a row to attach it to once the blank value has been stripped out.

## Impact

No upgrade or configuration changes required.

## Technical details

The root cause was upstream of the validator: `EntityFormDisplay::extractFormValues()` calls `FieldItemList::filterEmptyItems()` before validation runs, stripping blank deltas and reindexing what remains. On a two-value field with only the first value filled, the second delta simply no longer exists by the time `FieldValidationConstraintValidator` inspects the field, so there is nothing left to flag.

The fix, in `FieldValidationConstraintValidator`, compares the field storage's cardinality (via `FieldStorageDefinitionInterface`) against `$items->count()`. When cardinality is bounded and greater than the number of items present, each missing delta is validated with a `NULL` value the same way a fully empty field already was, running any `not_blank_constraint_rule` (and other property constraints) against it. Unlimited-cardinality fields are left untouched, since there is no way to know how many widget rows were actually rendered for those, so padding them would produce false positives. The duplicated constraint-instantiation logic used for both the per-delta loop and the new missing-delta loop was extracted into a shared `validatePropertyValue()` helper. A missing delta reports its violation at the field-level property path rather than a per-delta path, because core's `WidgetBase::flagErrors()` looks up deltas in `$field_state['original_deltas']`, which no longer contains a stripped delta and throws a `TypeError` if a violation targets it directly.
