# #3592002: Normalize agent-written prop values against their schema and report values the component source cannot store

- **Project:** Drupal Canvas
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3592002](https://git.drupalcode.org/project/canvas/-/work_items/3592002) · 1 contributor · 34 comments

## Summary

Canvas's AI page builder tools (`place_components`, `edit_components`) validate and store the component prop values an LLM writes as YAML. In practice, models like GPT-5.2 often write the same value in a technically-different but equivalent textual shape, for example a percentage wrapped in an extra pair of quotes, or a number or boolean written as a quoted string. Those used to fail schema validation outright, forcing the AI agent to retry the whole component placement. Separately, when the model supplied a value a prop genuinely could not store, such as a partial image object or a bare URL for a media-backed field, that prop was silently dropped rather than rejected, so the component got placed without it and could render broken (a Twig error, or an empty props form) until the page was reloaded. This fix normalizes AI-supplied prop values against their schema before validating and storing them, and turns previously-silent dropped values into a clear validation error naming the prop, so the AI has a chance to correct its output instead of producing a broken component.

## Impact

Affects module maintainers.

- **API change:** `AiResponseValidator::validateComponentStructure()` now returns the normalized component groups `array` instead of `void`; callers must use the returned value, not their original input, to get the prop values that were actually validated and should be stored.

## Technical details

The fix adds `CanvasAiPropValueNormalizer` (`canvas_ai.prop_value_normalizer`, marked `@internal`), whose `normalizeProps()`/`normalizeValue()` walk each prop's JSON schema (from `propSources[$prop]['jsonSchema']`): it strips one matching outer quote pair before treating a value as an enum member or a URI-formatted string, casts numeric/boolean-looking strings to their typed form, and recurses into object properties and array items. Free-form string props without an `enum` or `format` hint are left untouched, so prose keeps its quotes. `AiResponseValidator::convertToComponentTreeData()` now runs each component's props through this normalizer before calling `clientModelToInput()`, and `validateComponentStructure()`'s signature changed from `void` to returning the normalized `$componentGroups`, so a caller that doesn't use the return value gets unnormalized data back.

A second change, `collectUnstorableValueViolations()`, compares the AI-supplied props against the `$inputs` array `clientModelToInput()` actually produced: any prop present in the input but missing from the output (previously silently dropped) becomes a `ConstraintViolationException` naming the prop, with a hint to supply a valid entity ID when the prop's `sourceTypeSettings.storage.target_type` points at a reference field (e.g. media).

Both changes are wired into `PlaceComponents` and `EditComponents`, which now use `validateComponentStructure()`'s return value (`EditComponents` echoes back only the normalized values for the props each edit actually changed). `SetAIGeneratedComponentStructure` and `SetAIGeneratedTemplateData` still call `validateComponentStructure()` but, per the diff, were not updated to capture its return value, so only two of the four AI tools mentioned in the issue pick up the normalized (rather than as-written) values downstream.

## Upgrade

Code calling `AiResponseValidator::validateComponentStructure()` directly must now use its return value instead of relying on the input array being mutated or validated in place:

```php
// Before:
$this->responseValidator->validateComponentStructure($operation['components']);

// After:
$operation['components'] = $this->responseValidator->validateComponentStructure($operation['components']);
```
