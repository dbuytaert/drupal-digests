## Summary

Uninstalling the Block Content module on a site running Canvas and Layout Builder no longer crashes with "Table 'block_content' doesn't exist". Before, the failed uninstall left the site with block_content marked enabled but its tables gone, and only a database restore recovered it. This follows [#3582851](https://www.drupal.org/node/3582851), which fixed the same crash on install.

## Impact

Affects module maintainers.

- **API change:** Public property `BlockManagerDecorator::$moduleInstallInProgress` renamed to `$moduleInstallOrUninstallInProgress`.

## Technical details

During uninstall core drops the module's tables, and Layout Builder's `ExtraFieldBlockCacheTagInvalidator` then clears the block plugin cache. That reached `BlockManagerDecorator::clearCachedDefinitions()`, which regenerated block components and queried the dropped `block_content` table through the BlockContent deriver.

The install-only guard flag on `BlockManagerDecorator` is now `moduleInstallOrUninstallInProgress` (renamed from `moduleInstallInProgress`). `ComponentSourceHooks` sets it in a new `hook_module_preuninstall()` implementation, `modulePreuninstall()`, and clears it in a new `hook_modules_uninstalled()` implementation, `modulesUninstalled()`. While the flag is set, `clearCachedDefinitions()` still clears the decorated manager's cache but skips `generateComponents()`. The code comments say core rebuilds the container after the tables are gone, which also resets the flag, and the cache clear that follows regenerates components without the uninstalled module. A kernel test in `BlockManagerDecoratorTest` installs `layout_builder` and `block_content`, uninstalls `block_content`, and checks that components for remaining block plugins still exist.

## Upgrade

Custom code that touches the renamed property needs updating:

```php
// Before
$block_manager->moduleInstallInProgress = TRUE;
// After
$block_manager->moduleInstallOrUninstallInProgress = TRUE;
```
