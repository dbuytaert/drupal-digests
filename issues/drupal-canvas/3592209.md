## Summary

Canvas gains an optional `canvas_workflows` sub-module that adds a review process to workspaces. Each workspace can be assigned a core Workflows workflow (shipped default: Draft, In review, Approved) and cannot be published, from Canvas, the Workspaces UI or cron, until it reaches an approved state. Approved workspaces can also be scheduled to publish at a set time via cron. Editing an approved workspace sends it back to draft and cancels its schedule. Choosing a workspace's review workflow needs the new `administer canvas workspace review` permission. Canvas works unchanged without the module installed.

## Impact

Affects module maintainers and site owners.

- **Config change:** New `canvas_workspace_review` workflow type and default workflow config shipped by the `canvas_workflows` sub-module.
- **Permission change:** New `administer canvas workspace review` permission, plus generated `use {workflow} transition {transition}` permissions.
- **New API:** New `hook_canvas_workspace_staged_write()` in Canvas, fired on staged writes and draft discards into a workspace.

## Technical details

The sub-module defines a `canvas_workspace_review` workflow type (`WorkspaceReviewWorkflowType`) whose states carry an `approved_for_publish` flag, and ships a default `canvas_workspace_review` workflow config with `submit_for_review`, `approve` and `send_back` transitions. Each transition gets a generated `use {workflow} transition {transition}` permission via `WorkspaceReviewPermissions`. `hook_entity_base_field_info()` adds base fields to the workspace entity: `canvas_review_workflow` (empty means no review), `canvas_workspace_status`, `canvas_scheduled_publish_at`, `canvas_scheduled_publish_by` and `canvas_scheduled_publish_error`. Only workspaces of core's `default` provider are reviewable; Main and module-created workspaces are not. `hook_entity_field_access()` forbids edits to every field except `canvas_review_workflow`, which needs the new permission, because core grants workspace edit and publish through the same permissions. Changing the workflow resets the state and schedule in `hook_workspace_presave()`.

`WorkspaceReviewPublishSubscriber` listens to `WorkspacePrePublishEvent` at priority 100 and calls `stopPublishing()` for a review-required workspace that is not approved, ahead of Canvas's validation subscriber (so a review refusal surfaces as a 409 rather than a 422). On `WorkspacePostPublishEvent` it clears the state and schedule. Scheduled publishing is run by `WorkspaceScheduledPublishCronHook`; per the ADR a missing or blocked scheduling user means the schedule is cancelled, and a failure cancels it and stores the error.

In the main module, a new `hook_canvas_workspace_staged_write(WorkspaceInterface $workspace)` (documented in `canvas.api.php`) fires after Canvas persists an auto-save that changes staged content, fallback-store writes included, and after a draft is discarded. The sub-module uses it to demote the workspace; `hook_entity_presave()` covers saves made outside Canvas, such as node forms, skipping Canvas's own via `WorkspaceAutoSave::isStagingWriteOf()`, and `WorkspaceAutoSave::isPublishTimeStaging()` exempts publish-time staging. The workspace API representation is extended via `hook_canvas_workspace_normalize_alter()` with `status`, `statusLabel`, `statusIsApproved`, `statusIsInitial`, `requireReview`, `reviewWorkflow`, `canSetReviewWorkflow`, `availableTransitions`, `scheduledPublishAt` and `scheduledPublishError`. New `@internal` routes under `/canvas/api/v0/` (`workspace-review-workflows`, and `workspaces/{workspace}/` `review-workflow`, `status`, `schedule`) are served by `ApiWorkspaceReviewController`. The UI work (`workflowsExtensionAvailable` drupalSettings flag, status badge, schedule dialog) and ADR 23 are part of the same commit. Part of the diff was not available to me (e.g. `WorkspaceReview.php`, `WorkspaceScheduledPublish.php`, and the main-module `AutoSaveManager` change), so details of those come from the issue body and the ADR in the diff.

## Upgrade

To react to Canvas staged writes in a custom module:

```php
function hook_canvas_workspace_staged_write(\Drupal\workspaces\WorkspaceInterface $workspace): void {
  if ($workspace->hasField('my_module_reviewed')) {
    $workspace->set('my_module_reviewed', FALSE)->save();
  }
}
```

Site owners: enable `canvas_workflows` (requires `workflows` and `workspaces`) and grant `administer canvas workspace review` and the per-transition permissions to the relevant roles. On install, existing default-provider workspaces get the shipped workflow. Uninstalling removes the fields and the shipped workflow, after which workspaces publish without review.
