# #3592101: Make React Code Components portable across Drupal and headless frontends

- **Project:** Drupal Canvas
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3592101](https://git.drupalcode.org/project/canvas/-/work_items/3592101) · 1 contributor · 4 comments

## Summary

React Code Components (the small React components authors write for Canvas) previously had to use Drupal-specific APIs to read page metadata, site branding, and content, which meant they could not be reused as-is in a headless frontend. This change makes the same component code work unmodified in both Drupal-rendered pages and React-based headless applications (Next.js, TanStack Start, Astro). Existing components keep working in Drupal and in Canvas Workbench previews without any changes; the `canvas pull` CLI command can also automatically rewrite eligible components to the new APIs when the connected site and installed package support it. Headless applications also gain a same-origin JSON:API proxy so browser-side requests (including draft/preview reads) can reach Drupal safely without exposing credentials.

## Impact

Affects module maintainers.

- **Deprecation:** `getPageData()`, `getSiteData()`, `new JsonApiClient()`, `Region`, and `RegionsProvider` are deprecated; they keep working in Drupal-rendered Code Components and Workbench but throw actionable migration errors in headless React apps.
- **New API:** New `drupal-canvas/react` exports `usePageContext()`, `useSiteContext()`, `CanvasContextProvider`, `useJsonApiClient()`, and `JsonApiClientProvider` give React Code Components a single, framework-portable way to read page/site data and make JSON:API requests.

## Technical details

The core addition is a shared `CanvasContext` (`{ page, site }`) carried by a new `CanvasContextProvider` (`packages/drupal-canvas/src/context.tsx`) and read with `usePageContext()`/`useSiteContext()`. Rendering integrations, the Drupal island renderer, the headless `CanvasComponentTree`, and both Workbench preview paths, mount the provider automatically; a missing provider or missing `page`/`site` value makes the hooks return `null` and emit a deduplicated `warnOnce()` warning rather than fetching data or defaulting. Headless SDK's `fetchPage()` now returns this context alongside the component tree as `page.context`.

JSON:API access is consolidated the same way: `useJsonApiClient()`/`JsonApiClientProvider` (`packages/drupal-canvas/src/jsonapi-client-context.tsx`) expose a shared `JsonApiClient` built on `@drupal-api-client/json-api-client` (`createJsonApiClient()` in `jsonapi-client.ts`), replacing separate client implementations previously used by the `drupal-canvas` package and the headless SDK's draft client. Browser requests in headless apps go through a new same-origin proxy (`packages/headless/src/server/jsonapi-proxy.ts`, and `jsonapi-proxy.ts`/`jsonapi-proxy.test.ts` in `drupal-canvas`) that authenticates from the draft-preview session cookie, restricts requests to the configured backend and endpoint set, and keeps authenticated responses out of shared caches.

Legacy API compatibility is enforced with an explicit runtime marker rather than environment sniffing: `declareCanvasRuntime()`/`getCanvasRuntime()` (`packages/drupal-canvas/src/runtime.ts`) is set by Drupal and Workbench integrations, and `assertLegacyRuntime()` (`migration.ts`) throws an actionable error, including an AI-agent migration prompt, when `getPageData()`, `getSiteData()`, or `new JsonApiClient()` is invoked outside those two environments. On the PHP side, `CanvasContentContextBuilder` and changes to `CodeComponentDataProvider` and `SiteDataController` supply this context data and advertise `capabilities.contextHooks` from `/canvas/api/v0/site-data`, which the CLI's pull codemod (`packages/cli/src/utils/getter-codemod.ts`, `context-hook-support.ts`) checks before rewriting a component's safe, unconditional `getPageData()`/`getSiteData()` calls to the new hooks. `Region` and `RegionsProvider` are deprecated in favor of the page-variants model from ADR 19.

## Upgrade

No action is required to keep existing Code Components working in Drupal or Workbench. To make a component portable to headless frontends, migrate off the deprecated APIs:

```tsx
// Before
import { getPageData, getSiteData } from 'drupal-canvas';

// After
import { usePageContext, useSiteContext } from 'drupal-canvas/react';

export default function PageHeader() {
  const page = usePageContext();
  const site = useSiteContext();
  if (!page || !site) return null;
  return (
    <header>
      <a href={site.branding.homeUrl}>{site.branding.siteName}</a>
      <h1>{page.pageTitle}</h1>
    </header>
  );
}
```

Replace direct client construction the same way:

```tsx
// Before
const client = new JsonApiClient({ baseUrl });

// After
import { useJsonApiClient } from 'drupal-canvas/react';
const client = useJsonApiClient();
```

Running `canvas pull` against a site that advertises `capabilities.contextHooks` (and with `drupal-canvas/react` installed) converts eligible files automatically and reports any calls it could not safely convert.
