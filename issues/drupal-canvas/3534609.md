## Summary

Link values entered into a code component's "link" prop (in Canvas, formerly Experience Builder) were rendered as the raw path the editor typed, such as `/page/1`, instead of the page's actual URL alias like `/about-us`. This also meant the language prefix was missing on multilingual sites. Editors would type or paste a path, publish the page, and the link in the rendered HTML simply didn't match the site's real URLs. This is now fixed: links in code components resolve through Drupal's normal outbound URL processing, so aliases and language prefixes are applied just like they are for links entered anywhere else on the site.

## Impact

No upgrade or configuration changes required.

## Technical details

The link prop's value is resolved into an href string by `LinkUrl::getValue()`, a computed typed-data property. Previously it returned the stored `uri` unchanged whenever `\parse_url($uri, PHP_URL_SCHEME)` came back `NULL`, i.e. whenever the value was a bare path without a scheme. Regular link fields normally get an `internal:` scheme prefix added by `LinkWidget::massageFormValues()` when saved through the standard widget, but code components' explicit-input form (`GeneratedFieldExplicitInputUxComponentSourceBase::clientModelToInput()`) never ran that step, so values stayed schemeless and `\Drupal\Core\PathProcessor\PathProcessorManager::processOutbound` (which runs both `AliasPathProcessor` and `PathProcessorLanguage`) was never invoked.

Rather than patching the widget path, the fix normalizes the URI inside `LinkUrl::getValue()` itself, so outbound processing always runs regardless of how the value was stored: the special route tokens `<nolink>`, `<none>`, `<button>` are rewritten with a `route:` scheme; `<front>` is rewritten to the site's front page path; and any other bare value starting with `/` gets an `internal:` prefix before `$item->getUrl()->toString()` is called. Values that are neither an absolute path nor already schemed (e.g. a lone `?query` or `#fragment`) are left untouched. A new unit test (`LinkUrlTest`) and a Cypress e2e test with a `xb_test_code_components_with_link_prop` fixture component cover these cases.

During investigation, a separate but related bug surfaced: `entity_autocomplete` on the standard link widget hardcodes the `node` entity type (core [#2423093](https://www.drupal.org/node/2423093)), which made autocomplete work for articles but not for XB pages when reproducing this issue; that remains a distinct problem. A UI bug where the "Full URL" link type reverted to "Relative link" after navigating away was split into [#3541331](https://www.drupal.org/node/3541331).</technical>
