## Summary

Canvas now has a `dr canvas:audit:usage` command that lists where components are used. Give it a component source plugin ID (for example `sdc`), a component ID, or a component ID and version separated by `@`. It reports usages in content entity revisions, config entities (such as patterns) and auto-saves. This helps when you need to find where a known-broken component or version has been placed. Use `--revisions=all|default|latest` to narrow which content revisions are searched, and `--format=table|json` for human or machine output. The component audit page also now lists config entity usages only under the component version their tree actually uses. Before, it listed them without regard to version.

## Impact

Affects module maintainers.

- **API change:** `ConfigAuditBase::getConfigEntityDependenciesUsingAuditTarget()` and `componentTreeUsesAuditTarget()` accept `$version_ids`, `getAutoSavesUsingAuditTarget()` no longer throws for versions, and `getComponentTreeConfigEntityTypeIds()` is now public.
- **New API:** New `dr canvas:audit:usage` command (requires Drupal >= 11.4 `dr` CLI) with a versioned `--format=json` report described by `docs/audit-usage.schema.json`.

## Technical details

`AuditUsageCommand` (marked `@internal`) is a thin wrapper over the existing `ComponentAudit` service that powers the component audit page. It resolves the target to pairs of component and versions: a component source plugin ID expands to all components of that source, a bare component ID to all of its versions, and `ID@version` to one version. Unknown targets, unknown `--format` or `--revisions` values, and a missing target with `--no-interaction` exit with `2`. When the target is omitted in interactive mode, it prompts for source, then component, then version.

The JSON report is an envelope with `report_version` (`AuditUsageCommand::REPORT_VERSION`, 1), `target`, `revisions` and `usages`. Each usage has `component`, `version`, `kind` (`content`, `config` or `auto-save`), `entity_type`, `id`, `revision`, `default`, `latest` and `label`. `revision`, `default` and `latest` are null for config and auto-save usages. Auto-save labels come from the auto-saved entity. The command first searches all requested versions at once, and only repeats the search per version when that finds something.

The audit layer needed version support to make this work. Config entity dependencies come from the config dependency graph, which does not track versions. So `getConfigEntityDependenciesUsingAuditTarget()` now takes `$version_ids` and inspects each dependent's component tree when versions are given. `ComponentAudit::componentTreeUsesAuditTarget()` checks `getComponentVersion()` on each item. `ColorAudit` throws a `LogicException` if versions are passed, since colors have no versions. The "not yet implemented" exception in `getAutoSavesUsingAuditTarget()` is removed. `ComponentAuditController::createConfigTable()` now passes `[$component->getLoadedVersion()]`. The diff also adds `docs/cli.md`, a contributor doc listing rules that every Canvas `dr` command must follow, and kernel tests.

## Upgrade

Callers that previously relied on `getConfigEntityDependenciesUsingAuditTarget($component, $type)` ignoring versions are unaffected, because `$version_ids` defaults to `[]`. To restrict to specific versions, pass them, for example `getConfigEntityDependenciesUsingAuditTarget($component, $config_entity_type_id, [$version])`. Subclasses of `ConfigAuditBase` must update their `componentTreeUsesAuditTarget()` signature to `(ComponentTreeItemList $tree, ConfigEntityInterface $target, array $version_ids = []): bool`.
