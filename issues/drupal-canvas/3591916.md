# #3591916: Component version hashes go stale on single-process installs: prop-shape re-resolution is deferred to teardown and skipped on a cold cache

- **Project:** Drupal Canvas
- **Type:** Critical bug report
- **Version:** 1.x-dev
- **Status:** Fixed
- **Discussion:** [#3591916](https://git.drupalcode.org/project/canvas/-/work_items/3591916) · 1 contributor · 3 comments

## Summary

Sites built with the Canvas module and installed in a single process (for example via `drush site:install` applying recipes, as opposed to the browser installer) could end up with Component config entities whose version hash did not match the site's actual configuration. This happened when one recipe created config that changes how a component's properties are stored, such as the first image media type changing how an image prop is saved. If a later recipe in the same install shipped a component tree (a page region, content template, or pattern) referencing the corrected version hash, that hash did not actually exist yet on the freshly installed site, causing a hard render failure. The bug was invisible in bug reports because running `drush cr`, installing another module, or saving a View or Menu afterward silently fixed the stale hashes. This is now corrected: single-process installs produce the same, correct component version history as the browser installer.

## Impact

No upgrade or configuration changes required.

## Technical details

The root cause was in `PersistentPropShapeRepository`, which caches "storable prop shapes" (how a component prop is actually stored, e.g. as a plain image field vs. a Media Library reference) and computes Component version hashes from them. When a cache tag invalidation queued a prop shape for re-resolution (`resolveBeforeWrite`), that queue was previously only drained at `destruct()` (request/process teardown), never before the current process's own component-generation pass read the shapes. Additionally, `updateCache()` had a cold-cache guard that skipped `generateComponents()` entirely, which is always true on a fresh install, so the corrected shapes got cached without ever regenerating the Components that depend on them.

The fix adds `resolveInvalidatedPropShapes()` to `PropShapeRepositoryInterface`, implemented in `PersistentPropShapeRepository` to synchronously drain the queued re-resolutions (and a no-op in `EphemeralPropShapeRepository`, which never caches). This is now called from `JsonSchemaPropsComponentDiscoveryBase::getPropsForComponentPlugin()`, right before it reads prop shapes to compute prop field definitions and version hashes, so `RecipeSubscriber::ensureComponentsExist()`, `hook_rebuild()`, and module-install triggers all see up-to-date shapes. `updateCache()`'s cold-cache guard was also narrowed: it now only skips regeneration when nothing was actually invalidated during the process (i.e. shapes were merely resolved for the first time), but always regenerates when `resolveBeforeWrite` was non-empty, even on a cold cache, since that means the storable shapes genuinely changed mid-process.

A related, separate gap, array-item prop shapes not carrying the `config:media_type_list` cache tag, is tracked separately in [#3591917](https://www.drupal.org/node/3591917) and was not addressed here.
