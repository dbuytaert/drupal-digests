# #3592019: Sync brand kit colors through canvas.brand-kit.json in the Canvas CLI

## Summary

The Canvas CLI can now version brand kit colors the same way it already does fonts. Previously, a project's color palette could only be managed in the Canvas editor UI, so it wasn't tracked in git, reviewable in a merge request, or portable between environments, and offline Workbench previews couldn't render components with the site's real colors. Now `canvas.brand-kit.json` carries a `colors` map alongside `fonts`: `canvas pull` writes the site's palette into the file, `canvas push` creates or updates colors on the site to match, and `canvas validate` checks the file offline (JSON syntax, schema, and semantic rules like duplicate names). Workbench previews now render the local palette from this file even without a site connection. Brand kit sync (fonts and colors) is also switched on by default for `pull`/`push` when the file is present, whereas previously fonts had to be opted into explicitly.

## Impact

Affects module maintainers and site owners.

- **Permission change:** `canvas_oauth`'s default scope now includes `canvas:brand_kit` whenever brand kit sync is enabled, and the `canvas_oauth` authentication provider now allowlists the `Color` and `Folder` config entity routes for Bearer-authenticated requests.
- **API change:** Brand kit sync (fonts and colors) is now on by default for `canvas pull` and `canvas push` when `canvas.brand-kit.json` exists; `--include-brand-kit` (positive form) is deprecated in favor of `--no-include-brand-kit` to opt out.
- **New API:** `canvas.brand-kit.json` gains a `colors` map (CSS variable key to CSS color string or `{value, name, displayFormat}` object), synced by `canvas pull`/`canvas push` and checked by `canvas validate`.

## Technical details

The file format mirrors a Tailwind theme/W3C design tokens shape: each key becomes a CSS custom property (`brand-red` maps to `--brand-red`), map order is palette order, and the display name is derived from the key unless a `{value, name, displayFormat}` wrapper asserts one. Serialization (`packages/cli/src/lib/colors/color-pull.ts`) is lossless by construction: `serializeColorValue` writes a plain CSS string only when it round-trips to the exact same color token, otherwise it falls back to the object form, so a pull immediately after a push produces no diff. `color-push.ts` matches file entries to server `Color` entities by CSS variable, only reassigns weights when relative order actually differs (`needsWeightReassignment`), and only applies a derived name/display format on creation, never renaming a color set in the UI (`assertedName`). Push is non-destructive by default: server-only colors are reported via `serverOnly`, and the new `--prune-colors` flag opts into deletion, with in-use colors reported and failing the command at the end rather than aborting mid-run. Offline validation (`color-validate.ts`) mirrors the server's unique-name constraint (trimmed, case-insensitive) before any request is made.

Component color props that reference a brand kit color use a `canvas-color:<key>` example value; pull rewrites the server's `canvas-color:<uuid>` form to the file's `canvas-color:<cssVarKey>` form, and push does the reverse when serializing components, matching by the `cssVariable` the discovery layer resolves.

Server-side, `CanvasOauthAuthenticationProvider` now allowlists `Color::ENTITY_TYPE_ID` and `Folder::ENTITY_TYPE_ID` routes so Bearer-authenticated CLI requests can reach the color config entity endpoints, and `openapi.yml` documents `BrandKit.colors` as a read-only, derived list (colors are managed through the dedicated color endpoints, not by writing `BrandKit.colors` directly). Enabling brand kit sync now also adds `canvas:brand_kit` to the default OAuth scope automatically (`packages/cli/src/config.ts`).</technical>
<parameter name="upgrade">Brand kit sync (fonts and colors) is now on by default whenever `canvas.brand-kit.json` exists. To keep the previous opt-in behavior, disable it explicitly:

```bash
npx canvas pull --no-include-brand-kit
npx canvas push --no-include-brand-kit
# or
CANVAS_INCLUDE_BRAND_KIT=false
```

The positive `--include-brand-kit` flag is deprecated (it still works but emits a warning); scripts that used it to opt in no longer need it. Existing OAuth tokens will pick up the new `canvas:brand_kit` scope on their next refresh.

To add colors to a project's `canvas.brand-kit.json`:

```json
{
  "colors": {
    "brand-red": "#cc0000",
    "overlay": "hsla(220, 60%, 50%, 0.5)",
    "accent": { "value": "#0000cc", "name": "Accent blue" }
  }
}
```

Run `npx canvas pull` to populate it from the site, or `npx canvas push` to send local entries; add `--prune-colors` to also delete site colors absent from the file (colors currently in use by a component or template are reported and left in place).</upgrade>
