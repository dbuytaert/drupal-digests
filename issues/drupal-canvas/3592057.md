# #3592057: Support mapping multi-valued list fields to array-type component props

- **Project:** Drupal Canvas
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3592057](https://git.drupalcode.org/project/canvas/-/work_items/3592057) · 1 contributor · 3 comments

## Summary

Canvas's automatic field-to-prop mapping now recognizes multi-valued list fields (`list_string`, `list_integer`, `list_float` with unlimited or multiple cardinality) as valid sources for component props that expect an array of scalars, such as `{"type": "array", "items": {"type": "string"}}`. Previously, even though this was a natural mapping, Canvas excluded any multi-valued field from its suggestions, so these list fields never showed up when configuring a content template's component mapping. Site builders can now select these fields in that scenario.

## Impact

No upgrade or configuration changes required.

## Technical details

The exclusion lived in two places that both blanket-rejected any field with cardinality other than 1: `ApiUiContentEntityReferenceControllers::listEntityFields()`(ish) and `MultiValuedFieldNotSupportedConstraintValidator`. Both now carve out an exception via `\is_a($field_definition->getItemDefinition()->getClass(), ListItemBase::class, TRUE)`, so multi-valued fields whose item class extends `Drupal\options\Plugin\Field\FieldType\ListItemBase` (i.e. the list field types) are no longer rejected outright.

On the matching side, `EntityFieldPropSourceMatcher` already skipped `list_float` and `list_integer` field types except for a small set of "allowed" prop schemas (`type: number`/`integer`), via the `IGNORE_FIELD_TYPES` constant (renamed its `exceptions` key to `allowed` for clarity). `list_string` could not be added there because its field item class, `ListStringItem`, isn't referenceable from this namespace per the `phpat.shapeMatcher` architecture rule, so a new `IGNORE_FIELD_TYPES_BY_ID` constant was added, keyed by field type ID string instead of class, currently containing only `list_string` restricted to `{"type": "string"}` props (no `enum`). Both constants are consulted in the field-scanning loop that builds prop match suggestions. Since array-typed props strip `type: array` down to their `items` schema and set `$cardinality` from `maxItems` before delegating to the scalar matcher, these allowed-schema checks now also apply correctly to multi-valued list fields feeding array props.

One side effect: a previously-existing match of `one_from_an_string_list` against `type: string&$ref=…color` was removed from the test fixtures, since a single-valued `list_string` field with a color-format constraint is no longer considered an unconditional match under the new allowed-schema rule.
