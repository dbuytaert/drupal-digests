# #3592097: Include language alternates in Headless content API

## Summary

Headless frontends built on Canvas can now get everything needed for a language switcher directly from the content API response, instead of having to derive it themselves. Each `fetchPage()` response's `route` object now lists every enabled language with its localized name, native name, a URL, whether that translation actually exists and is viewable, and whether it is the one currently being served. This mirrors the translation data already exposed to Code Components via `getPageData()`, so both APIs behave consistently.

## Impact

Affects module maintainers.

- **New API:** `route` in the Headless content API response now includes `negotiatedLanguage` and a `translations` list (`langcode`, `name`, `nativeName`, `url`, `translationAvailable`, `current`, `external`) for every enabled language.

## Technical details

The new `Drupal\canvas_headless\CanvasContentTranslationLinks` service builds this data in `CanvasContentController`, and delegates the actual per-language enumeration to a new shared helper, `Drupal\canvas\EntityTranslationMetadata::build()`. That helper was extracted from the existing logic in `CodeComponentDataProvider` (which now calls it too), so Code Components and the headless API share one source of truth for `langcode`, `name`, `nativeName`, `translationAvailable`, and `current`. `translationAvailable` reflects both existence and view access; a denied or missing translation reports `false` and falls back to the entity's own URL in that language.

For the headless case, URL generation is more involved than the Code Component fallback: `CanvasContentTranslationLinks::switchLinks()` walks enabled language negotiation methods in configured order (following `LanguageNegotiationUI` delegation to the interface-language session negotiator), builds each link via the module's `LanguageSwitcherInterface` plugins, and strips out Canvas's editor-preview query parameters while forcing the session query parameter when session negotiation is active, so a translation link is unambiguous regardless of prior session state. Generated absolute URLs are then normalized by the new `Drupal\canvas_headless\CanvasContentUrl::normalize()`, which strips the scheme, host, and Drupal base path from same-site URLs (an external one is left absolute and flagged with `external: true`) so frontends can safely feed the result back into `fetchPage()`. The near-identical logic previously duplicated in `CanvasContentResponseSubscriber` for redirect targets was consolidated into this same helper.

The OpenAPI schema (`RouteTranslation`) and the SDK's TypeScript types (`DrupalRouteTranslation`, `DrupalRoute` in `packages/headless/src/page.ts`) were updated to document the new required `negotiatedLanguage` and `translations` fields, and `docs/multilingual-sites-with-canvas-headless.md` explains the filtering and public-URL-mapping pattern for consumers building a switcher.</technical>
<parameter name="upgrade">No breaking changes to existing fields. Frontends consuming `fetchPage()` and using the SDK's TypeScript types should update to a version that includes `negotiatedLanguage` and `translations` on `DrupalRoute`, since these are now required properties of the response schema. To build a switcher of only viewable translations:

```ts
const page = await fetchPage("/fr/page/1");
if (page && !("redirect" in page)) {
  const languageLinks = page.route.translations
    .filter((translation) => translation.translationAvailable)
    .map((translation) => ({
      label: translation.nativeName,
      active: translation.current,
      href: toPublicUrl(translation.langcode, translation.url),
    }));
}
```

Entries with `external: true` are absolute URLs (e.g. from domain-based language negotiation) and are not valid `fetchPage()` input; map them to a public URL instead of passing them back in.</parameter>
