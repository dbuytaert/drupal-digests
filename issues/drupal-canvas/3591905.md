# #3591905: `drush config:import` can fail to update a Component whose `active_version` changed

## Summary

Deploying a Canvas site with `drush deploy` (or plain `drush config:import`) could silently fail to update a `Component` whenever that component's version had changed, for example after adding or removing a prop on a code component. The import would log an error and leave the component at its old version, with no obvious way to tell without checking logs. This particularly affected code components, since the previously known workaround, running a cache rebuild before importing, did not help them: their new configuration only exists in the import itself, so a cache clear just recomputed the old version. This fix makes `drush config:import` and `drush deploy` reliably bring `Component` entities up to date, restoring the expected deploy workflow: edit a component in one environment, export configuration, and import it cleanly in another.

## Impact

No upgrade or configuration changes required.

## Technical details

The bug was in how Drupal core's config import updates an existing config entity: `ConfigEntityStorage::updateFromStorageRecord()` copies every exported property from the sync record, including `active_version`, onto the already-loaded entity object. But `VersionedConfigEntityBase::$loadedVersion` is derived, non-exported state that is only set once in the constructor. After the property copy, `active_version` pointed at the new hash while `$loadedVersion` still pointed at the old one, and `VersionedConfigEntityBase::preSave()` throws an `EntityStorageException` whenever those two disagree. `ConfigImporter::importInvokeOwner()` catches that exception per-object and just logs it, so the import as a whole appeared to succeed while the `Component` silently stayed on its old version.

The fix adds a new `VersionedConfigEntityStorage` (extending `ConfigEntityStorage`) that overrides `updateFromStorageRecord()` to call `$entity->resetToActiveVersion()` after the parent copies the record's properties, re-deriving `$loadedVersion` from the just-updated `active_version`. `Component` now declares this as its `storage` handler directly. A new `VersionedConfigEntityHooks::entityTypeAlter()` also assigns `VersionedConfigEntityStorage` automatically to any entity type implementing `VersionedConfigEntityInterface` that hasn't already customized its storage class, so other versioned config entity types get the same protection without extra wiring. The invariant that a deliberately loaded historical version cannot be saved (even while syncing) is preserved, since `resetToActiveVersion()` only runs on the property-copy path triggered by config import, not on manual `loadVersion()` calls.
