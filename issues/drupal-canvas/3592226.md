## Summary

On the `1.x-workspaces` branch, every Canvas draft is now staged in the active core Workspace, or in the Main workspace when none is active, instead of in the 1.x key-value auto-save store. This is PR 3 of a planned series. It covers the storage and manager layers. The controllers (PR 5) and per-item publish replacement (PR 7a) land separately. Per the issue, `ApiAutoSaveControllerTest` fails after this PR until PR 7a, and the 1.x `post()` publish is unsafe inside a workspace until then. This is an intermediate step on a feature branch. Its description is a plan, and the merge request was never linked to it.

## Impact

Affects module maintainers and site owners.

- **Database update:** Per-workspace key-value collections `canvas.auto_save.{workspace}` and `canvas.auto_save_meta.{workspace}` replace the single 1.x `canvas.auto_save` collection.
- **API change:** `AutoSaveManager` auto-save keys become workspace-prefixed (`{workspace}:{type}:{id}[:{langcode}]`), and Canvas content drafts are now staged in the active workspace instead of the 1.x key-value store.
- **New API:** New `AutoSaveFallbackStore` and `WorkspaceAutoSave` services under `src/AutoSave/Workspace/`; `AutoSaveManager` delegates to them.

## Technical details

The design is ADR 0022, which landed in PR 2. Content entity drafts become the entity's single tracked pending revision in the active workspace, and the previous one is deleted. Config entity drafts, and content drafts the storage layer rejects (for example an invalid component tree that throws in presave), go to a per-workspace fallback store, `AutoSaveFallbackStore`. That store uses the collections `canvas.auto_save.{ws}` for draft rows and `canvas.auto_save_meta.{ws}` for client instance, draft path and attribution. It caps workspace IDs at 100 characters and offers `deleteWorkspace()` and `workspaceIds()`. Exactly one store holds a target's current draft: a fallback row shadows the primary store until the next successful primary persist. Staging never validates. `ClientDataToEntityConverter` converts and validates inside the staging workspace so core's one-workspace-per-entity lock passes. Writes are idempotent, and dirty state is computed at read time by hashing staged data against Live.

`WorkspaceAutoSave` (about 1,300 lines per the issue) holds the persist, read, discard and delete logic. `AutoSaveManager` delegates to it, adds workspace-prefixed keys, and gains `executeInStagingWorkspace()`, `getEntityForLayoutEditing()`, `deleteTranslation()` and a `forcePreserve` option. `onCanvasConfigEntitySave()` checks `isPublishTimeStaging()`. A cross-workspace lock raises `WorkspaceEntityLockedException`, which `ApiExceptionSubscriber` maps to a 409 with a new `ErrorCodesEnum` code (8). The 1.x hash-based conflict detection is kept: the base hash of a content draft is recorded in the metadata collection, and fallback rows keep `original_hash`. It is compared against `WorkspaceAutoSave::loadUnchangedBase()`. `AutoSaveWorkspacePublishSubscriber::validateItem()` adds the `AutoSaveEntityConflictConstraint` violation for a Page draft with an unresolved conflict. `ContentTemplate` is now created enabled, and the translation synchronizer skips staged non-default translations. `AutoSaveManager::groupContentEntityAutoSaves()` and `autoSavePublish()` stay until PR 7a. The planned tests include `WorkspaceAutoSaveStagingTest`.
