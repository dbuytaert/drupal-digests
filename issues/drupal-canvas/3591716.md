# #3591716: Boolean props auto-enable when another prop is changed in the Canvas form

- **Project:** Drupal Canvas
- **Type:** Critical bug report
- **Version:** 1.x-dev
- **Status:** Fixed
- **Discussion:** [#3591716](https://git.drupalcode.org/project/canvas/-/work_items/3591716) · 1 contributor · 23 comments

## Summary

In the Canvas experience builder, editing a component with boolean properties (for example a "card-program" component) could cause all of its boolean toggle switches to visually flip to ON as soon as any other, unrelated prop was changed, even though the user never touched the toggle. This was purely a display and initial-state bug: it could mislead editors into thinking a boolean prop was enabled when it was not. The fix ensures boolean `false` values are correctly preserved and displayed as OFF throughout the component editing form, including after AJAX form rebuilds (such as those triggered by media library widgets).

## Impact

Affects front-end developers.

- **Theme change:** The `input--checkbox--inwidget-boolean-checkbox.html.twig` template now reads `element[#checked]` instead of `element[#value]` for its `current_value` variable, and always renders `1` or empty string rather than a raw value.

## Technical details

Two distinct bugs combined to produce the symptom. First, in `layoutModelSlice.ts`, `_addNewComponentToLayout`'s `buildInitialData()` built a new component's initial prop values using `prop.default_values?.resolved || []`. Since `false || []` evaluates to `[]` (a truthy value) rather than `false`, any boolean prop defaulting to `false` was silently coerced away from its actual value. This was changed to the nullish coalescing operator (`?? []`), which only falls back to `[]` when the value is `null` or `undefined`, preserving an explicit `false`. The same `|| []` to `?? []` fix was applied to the `source` field.

Second, on the server side, Drupal's `Checkbox::valueCallback()` returns the integer `0` (not PHP boolean `false`) for an unchecked checkbox during an AJAX form rebuild. The `input--checkbox--inwidget-boolean-checkbox.html.twig` template passed `element[#value]` directly into the `current_value` attribute consumed by the React `DrupalToggle` component. Twig rendered the integer `0` as the string `"0"`, and since `!!"0" === true` in JavaScript, `DrupalToggle` interpreted this as checked. The template was changed to use `element[#checked]`, a proper boolean set by `processCheckbox`, and both `default_value` and `current_value` are now rendered as either `1` or an empty string, never the ambiguous `"0"`. As a defensive third layer, `DrupalToggle.tsx` gained a `parseChecked()` helper that explicitly treats the string `"0"` and the number `0` as falsy when computing its initial checked state.
