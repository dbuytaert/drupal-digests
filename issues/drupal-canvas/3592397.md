## Summary

Canvas content templates can now be created for entity types other than nodes, which accidentally made the new exposed slots feature available for them too. Exposed slots are now limited to `node` content templates in the `full` view mode. In the editor, the "Enable editing" option for slots is disabled on templates for other entity types, and the API and config validation reject exposed slots on them.

## Impact

Affects site owners.

- **Config change:** `exposed_slots` in `canvas.content_template.*.*.*` now validates that the template's entity type is `node` (new `entityTypeId` option on `ValidExposedSlot`).

## Technical details

`ValidExposedSlotConstraint` gets a new `entityTypeId` option (default `EXPOSED_SLOTS_ENTITY_TYPE_ID`, `node`) and an `entityTypeMismatchMessage`. It is set next to `viewMode: full` in the `canvas.content_template.*.*.*` config schema. `ValidExposedSlotConstraintValidator` compares `ContentTemplate::getTargetEntityTypeId()` against it and adds a violation before checking the component tree.

`ApiContentTemplateSlotFieldController::create()` (the slot-fields endpoint that creates `canvas_slot_` fields) now throws a 422 `UnprocessableEntityHttpException` with `Exposed slots are only allowed for the node entity type.` for non-node templates, before the existing view mode check, so no field is created.

On the UI side, a new `EXPOSED_SLOTS_ENTITY_TYPE_ID` constant mirrors the PHP one. `SlotExposePanel` and `SlotMenuItems` now also read `entityType` from the route params and disable "Enable editing" unless both entity type and view mode match. The docs and `canvas.content_template` schema comments were updated accordingly. Tests cover config validation and the HTTP API for a `user` template.
