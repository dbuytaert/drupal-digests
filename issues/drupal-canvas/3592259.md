## Summary

Code components can now translate their interface text. A component calls `useTranslation()` from `drupal-canvas/react` and uses `t()` and `formatPlural()` with the same arguments as `Drupal.t()` and `Drupal.formatPlural()`. Unlike `Drupal.t()`, this also works when a component is exported to a headless app. When a component is published, pushed with the Canvas CLI, or imported from config, its strings appear on the User interface translation page (`/admin/config/regional/translate`). Translations for the page's interface language are then delivered to the component. Untranslated strings show the English source. Workbench gets a language selector for previews, and the headless SDK returns translations in `page.context.translations`.

## Impact

Affects module maintainers and site owners.

- **Config change:** `canvas.js_component.*` gains an optional `translatableStrings` sequence of `source`, `plural`, `context` items, validated against Locale storage rules.
- **New API:** New `useTranslation()` hook and `TranslationsProvider` in `drupal-canvas/react` (provider also exported by the headless-react, headless-next and headless-tanstack-start packages), optional `translations` key on `CanvasContext`, new `translatableStrings` property on `canvas.js_component.*`, and new `canvas.api.interface_translation.*` routes.

## Technical details

Drupal does not parse JavaScript, so the tools that hold the source extract the strings: the code editor, the Canvas CLI, the Headless SDK (when building component metadata) and Workbench. All use one shared Babel scope-analysis extractor, the private `@drupal-canvas/translatable-strings` package. It follows bindings returned by `useTranslation()` (aliases, member access, shadowing) and only picks up string literals, with a context only from a static string literal in the options object. Dynamic calls are skipped silently. Invalid literals (empty string, U+0003, non-ASCII or over 255 character context) are errors: the CLI and Headless SDK builds fail, and the editor reports them.

Strings are stored in a new `translatableStrings` property on `canvas.js_component.*` config, a deduplicated sorted list of `{source, plural?, context?}`. An empty list means no strings and `null` or omitted means unknown. The schema enforces Locale's rules (NotBlank, no U+0003, ASCII context up to 255 characters). Saving a component registers its strings with Locale. Strings no component uses anymore are removed unless they are translated or have another recorded use. Metadata from older Headless SDKs that omits the property keeps the stored strings, while source saved by writers that don't send it makes them unknown (see the new ADR 23).

On Drupal-rendered pages the translations and plural formula for the page's interface language go into `drupalSettings.canvasData.v0.translations`, including strings of imported components. The issue describes the interface language cache context and `locale` cache tag on the render output. I did not verify that part in the diff. The `CanvasContext` `translations` key (type `Translations`: `strings` and optional `pluralFormula`) feeds the hook, and `TranslationsProvider` replaces rather than merges translations for components below it. `t()` and `formatPlural()` support only `@` placeholders and return text, not HTML. Two new routes, `canvas.api.interface_translation.languages` (GET) and `canvas.api.interface_translation.lookup` (POST, `/canvas/api/v0/interface-translation/{langcode}`), served by `ApiInterfaceTranslationController`, let Workbench read existing translations without registering strings. They require `administer code components`, `administer content templates` or `administer page template`. `preview-build` gets a `--langcode` option.

## Upgrade

Components that hand-edit exported config must keep `translatableStrings` in sync with their source. The code editor, CLI and Headless SDK derive it automatically, and the CLI's YAML validation lists it among keys authors must not provide.
