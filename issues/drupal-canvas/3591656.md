# #3591656: Support multi-target-bundle references in code component content-entity-reference props

- **Project:** Drupal Canvas
- **Type:** Normal feature request
- **Version:** 1.x-dev
- **Status:** Fixed
- **Discussion:** [#3591656](https://git.drupalcode.org/project/canvas/-/work_items/3591656) · 1 contributor · 7 comments

## Summary

In Drupal Canvas, code components can declare props that pull data from content entity fields, including fields reached through an entity reference. Until now, if that reference field could point to more than one bundle (for example a "Related content" field that can hold either an Article or a Page), Canvas could not actually render it: the render path threw an explicit error rather than silently producing wrong output, and the Canvas UI's field picker did not let you browse into such a field at all. This issue adds real, end-to-end support: at render time Canvas now resolves the referenced entity first and then picks the correct set of fields for whatever bundle that entity actually turns out to be, and the field picker now lets you browse into a multi-bundle reference field on a per-target-bundle basis. Component authors and site builders no longer need to avoid multi-bundle reference fields when wiring up content-entity-reference props.

## Impact

No upgrade or configuration changes required.

## Technical details

`JsComponent::buildReferencePayload()` previously threw a `\LogicException` whenever a reference expression's target was a `ReferencedBundleSpecificBranches` (the coalesced form produced when a reference field targets multiple bundles, one branch per bundle). It now defers target selection until the referencer resolves to a concrete entity: for each `ReferencedBundleSpecificBranches` target it calls the new `ReferencedBundleSpecificBranches::getBranchForEntityOrNull()` to pick the branch matching the resolved entity's entity type and bundle, and for a plain single-bundle target reached through a multi-bundle referencer (an un-coalesced cross-bundle pick) it matches by the target's host entity type and bundle. When nothing matches the resolved entity's bundle, it falls back to a `__type`-only payload, and cacheability now explicitly includes the traversed entity via `addCacheableDependency($entity)` since that case has no leaf pick to carry the entity's own cache tags.

On the picker side, `ApiUiContentEntityReferenceControllers` now offers browsing into a multi-target-bundle reference field, returning one `targetBundles` entry per bundle. To avoid producing an inexpressible "branch inside a branch" (nested branching, which the string expression format can't yet represent and which the parser rejects), a further multi-bundle descent is withheld once the parent chain already passed through one multi-bundle reference (`parentDescendsThroughMultiTargetBundleReference()`); that follow-up is tracked in [#3591865](https://www.drupal.org/node/3591865). The old `MultiTargetBundleReferenceNotSupportedConstraint` (and its validator) is removed since multi-bundle references are no longer categorically rejected. Two new constraints take its place for the cases still unsupported: `EntityFieldExpressionsMustNotNestBranches` rejects selections that would coalesce into a nested branch, and `EntityFieldExpressionsMustNotMixBundlesInObject` rejects picks that read several different fields per bundle across bundles into one object (unrenderable, because each bundle-specific property would throw against the other bundle's entity); mixed-bundle objects becoming a supported branch is tracked in [#3591873](https://www.drupal.org/node/3591873). A new `NestedBranchNotSupportedException` lets `Coalescer` distinguish nested-branch failures from other invalid branch sets, so validation can report the precise "not yet supported" message. The other expression validators (raw-URI, internal-property, multi-valued-field guards) now descend into every branch of a multi-bundle reference instead of skipping it outright, since a violation hidden inside one bundle's branch is still a violation.
