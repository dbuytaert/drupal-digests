## Summary

Canvas content templates (and other config entities with a `component_tree` field) could have their component order silently scrambled once a tree contained 10 or more components at the same level, or once a component's position key had multiple ':'-separated segments (e.g. items nested in a slot). This happened whenever Canvas normalized the stored order, such as on save or config import. A tree stored as `0, 1, 2, ..., 9, 10, 11` would come back as `0, 1, 10, 11, 2, 3, ...`, and this corrupted order then propagated to the Canvas layout API and to preview rendering. This fix ensures component order is preserved correctly regardless of how many components a level or slot contains.

## Impact

No upgrade or configuration changes required.

## Technical details

The root cause was that Canvas encodes a component tree's structure into string keys, such as `4`, `4:the_body:0`, or `4:the_body:0:<uuid>`, and then relies on sorting those keys to recover the intended order. Three call sites, `ComponentTreeConfigEntityBase::preSave()`, and `ComponentTreeConfigEntityTransformer::import()` and its internal `computeExportSequenceKeys()`, used PHP's `ksort()`, which compares keys as plain strings. That makes `10` sort before `2`, since lexicographic comparison looks at the first character first.

The fix replaces all three `ksort()` calls with `uksort($tree, \strnatcmp(...))`, using PHP's natural-order string comparison so that whole-number segments within the ':'-delimited keys are compared numerically (`9` before `10`) while still keeping parent keys (`4`) ordered before their child keys (`4:the_body:0`). `ComponentTreeConfigEntityBase::preSave()` additionally gained a new `componentTreeSequenceIsPositionEncoded()` helper, which checks whether the tree's keys are still position-encoded (not yet re-keyed by UUID) so the natural sort is applied only when needed, covering the config install/update path that bypasses the sync import transformer.
