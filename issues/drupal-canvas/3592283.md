## Summary

Three Brand Kit color UX tweaks in Canvas. Deleting a color now opens a centered confirmation dialog, matching folder deletion, instead of a popover anchored to the row. When editing a color, Save stays disabled and the "this will affect N components" usage notice stays hidden until the color value or CSS variable name actually changes. New Color props in the code editor now default to white instead of red.

## Impact

No upgrade or configuration changes required.

## Technical details

The popover `DeleteColorPopover` (and its CSS module) was removed and replaced by `DeleteColorDialog`, built on the shared `Dialog` component and mounted in the app's `Dialogs` list. It is driven by a new `deleteColorConfirm` entry in `dialogSlice` (`DialogDataMap`), which `ColorRow` opens via `setDialogWithDataOpen` with the color as data, closing the edit popover first. The usage/blocked/prior-version messaging and `useDeleteColorMutation` logic are carried over unchanged. The shared `Dialog` buttons gained `data-testid` attributes `dialog-cancel-button` and `dialog-confirm-button`.

In `ColorFormPopover`, the form state now tracks `originalVariableName`. A `hasChanges` flag compares the current variable name with the original and compares the color space, components and alpha against `originalColor`. In edit mode `isConfirmDisabled` also requires `hasChanges`, and the usage info box is rendered only when `hasChanges` is true. The info text gained `data-testid="color-variable-edit-info"`.

The default color example for the Color prop type changed from `#ff0000ff` to `#ffffff` in the derived prop types, and `FALLBACK_DEFAULT_COLOR` in the color prop field changed to match.
