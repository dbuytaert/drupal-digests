## Summary

On the `1.x-workspaces` branch, a user who can view a workspace but not edit it can now use the Canvas editor in that workspace. Before, they could switch to it, but the Canvas API returned 403 for reads, so the page list and page selector failed to load. Writes into the workspace are now decided by normal content access, the same as core's entity forms, not by permission to edit the workspace itself.

## Impact

Affects site owners.

- **Permission change:** Canvas API requests in a named workspace no longer require `edit own workspace` / `edit any workspace`; `view` access to the workspace plus content entity permissions is enough.

## Technical details

`WorkspaceRequestSubscriber::onRequest()` had a check that threw `AccessDeniedHttpException` unless the active workspace granted `update` to the current user. In core, `update` on a workspace means `edit own workspace` / `edit any workspace`. That permission covers the workspace entity and publishing it, not the content inside it. The `canvas_requires_workspace` route option made the check run on GET requests too, which caused the 403s. The check is removed. The header required check (400), the header and active workspace mismatch (409) and the `live` handling are unchanged. No `view` check replaces it, because core's `WorkspaceManager::getActiveWorkspace()` already falls back to Live when the user lacks `view`.

The now-unused `$currentUser` constructor argument and the `AccessDeniedHttpException` import are removed from the subscriber. Publishing a workspace still goes through the `canvas.api.workspaces.*` routes, which the subscriber skips, and still needs the core edit permissions. In `ApiAutoSaveControllerTest`, `testNamedWorkspaceWritesNeedUpdateAccess()` became `testNamedWorkspaceViewerUsesCanvasApi()`. It asserts that a viewer can list, stage and discard, and that a user without entity access is refused with a 403 from entity access.
