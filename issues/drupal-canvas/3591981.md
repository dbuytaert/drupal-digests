# #3591981: Provide consistent Code Component metadata validation across CLI and Drupal

- **Project:** Drupal Canvas
- **Type:** Normal feature request
- **Status:** Fixed
- **Discussion:** [#3591981](https://git.drupalcode.org/project/canvas/-/work_items/3591981) · 1 contributor · 3 comments

## Summary

Canvas Code Components are described by an authored `component.yml` file, but until now the rules for what counts as valid metadata were scattered across the CLI, JSON Schema prop definitions, Drupal config schema, and PHP entity constraints. That made local feedback incomplete and meant errors could surface only partway through a `canvas push`, after other components had already been updated. This change publishes a single, hand-authored JSON Schema for the authored `component.yml` envelope and adds a Drupal endpoint that authoritatively validates a component's metadata against the target site without saving it. The Canvas CLI now runs local structural and ESLint checks first, then calls the target site to confirm acceptance, and `canvas push` preflights every component's metadata before making any changes so a rejected component no longer leaves a push partially applied. Sites without the new endpoint fall back to the previous per-component, save-time validation.

## Impact

Affects module maintainers.

- **New API:** New authenticated, non-mutating `POST /canvas/api/v0/code-components/validate` endpoint runs the same entity and metadata constraint chain as create/update and returns `204` or structured constraint violations without saving anything.

## Technical details

The envelope contract lives in the repository-root `component-metadata.schema.json` (draft-07, published at the `1.x` rolling raw URL), requiring only `name` and `machineName` and rejecting unknown keys and projected `x-allowed-*` keys; it is statically bundled into the CLI rather than fetched at runtime, and prop definitions under `props.properties` are validated directly as JSON Schema (including their first example) rather than generated from Drupal's config schema. A new private `packages/json-schema-validation` workspace package (`createCanvasAjv`) centralizes a strict draft-07 Ajv instance with `ajv-formats` and `ajv-formats-draft2019`, shared by the UI and CLI, replacing the UI's local `ui/src/utils/ajv.ts`.

On the Drupal side, `ApiCodeComponentMetadataController::validatePayload` (route `canvas.api.code_component.validate`, permission `administer code components`) builds an in-memory `JavaScriptComponent` create or update candidate from the posted payload and runs `getTypedData()->validate()`, returning `204` on success or throwing a `ConstraintViolationException` with the structured violations otherwise; unresolvable `json-schema-definitions://` references are converted into a violation instead of a fatal error. In `packages/cli`, `validate.ts` and `push.ts` (via new `utils/target-component-metadata.ts` and `services/api.ts` additions) submit each component's normalized payload to this endpoint when an authenticated API service is available, and `canvas push` now calls `preflightCodeComponentPayloads()` before any create, update, or delete, aborting the push with "Nothing was pushed" if any component fails. When the target endpoint or authentication is unavailable, the CLI emits a warning that only local checks ran and continues, and older sites without the route retain the previous partial, per-save validation. The old duplicate validators `validate-content-entity-reference.ts` and ESLint rules `component-content-entity-reference-props` and `component-prop-example-value-image-url` were removed in favor of the Drupal-side authoritative checks plus a new, more general `component-required-props` ESLint rule.
