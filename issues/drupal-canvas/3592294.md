## Summary

Main, the workspace that holds Canvas drafts, now exists only inside the Canvas editor. Previously, opening the editor stored Main in the session, so the user stayed in Main on every admin page, where config forms were rejected and node saves were staged. Now leaving Canvas from Main always lands in Live, however the user got to Main. A named workspace chosen in the Canvas switcher still follows the user around the site, and Workspaces UI is now required so the toolbar shows it and offers the switch back to Live. No new permission is added and no update changes any role: anyone who could open the editor before still can. Main is labeled "Canvas drafts" and no longer appears in core's workspace list or switcher. External clients such as the CLI and Workbench must now send `X-Canvas-Workspace: live` on routes that load or save content, and they read and write Live as on 1.x.

## Impact

Affects module maintainers and site owners.

- **Requirements:** `workspaces_ui` is now a module dependency of Canvas, in addition to `workspaces`.
- **Database update:** `canvas_update_11201()` now also installs `workspaces_ui`.
- **Config change:** The Main workspace (`canvas_default`) is now labeled "Canvas drafts" and uses the new `canvas_main` workspace provider.
- **API change:** Routes with the `canvas_requires_workspace` option (page list, create, get, get by UUID, patch, delete, content template draft, media upload, content entity reference preview, content template preview entity suggestions) answer 400 without the `X-Canvas-Workspace` header; the value is a workspace ID or `live`.
- **New API:** New `CanvasMainWorkspaceProvider` and `CanvasMainWorkspaceNegotiator` services, new `X-Canvas-Workspace: live` header value, and a `canCreate` flag in the workspace list API response.

## Technical details

Main is created with a new `CanvasMainWorkspaceProvider` (`canvas_main`) instead of core's default provider, so core leaves it out of the listing page, parent selector and switcher form. The provider's `checkAccess()` allows `view` on Main only when the main request is an editor request and the account passes `CanvasUiAccessCheck::access()`; a guard flag answers the nested access call with neutral, because that check runs entity access which asks for the active workspace again. `publish` follows `AutoSaveManager::PUBLISH_PERMISSION`, `delete` is always forbidden, and other operations are core's.

`CanvasMainWorkspaceNegotiator` (tag `workspace_negotiator`, priority 10, below core's session negotiator) makes Main active for authenticated requests to `/canvas` and `/canvas/api/*`, with an optional language prefix. `/canvas/content-api` and any request with `X-Canvas-Workspace: live` are not editor requests. Main is never stored: `ApiWorkspaceController::activate()` calls `switchToLive()` for Main, and `CanvasController::__invoke()` no longer calls `setActiveWorkspace()`. Both classes are registered in `CanvasServiceProvider` only when `workspaces` is installed, since they extend Workspaces classes.

`WorkspaceRequestSubscriber` gained the `X-Canvas-Workspace` header contract. Routes with the new `canvas_requires_workspace` route option (set in `canvas.routing.yml`) answer 400 without the header. The value `live` while the request runs in a workspace is a 409. The UI sends the ID of the workspace its page was loaded with. `MainWorkspaceHooks::formAlter()` strips core's `active_workspace_id` value and `workspace` query parameters from forms built in Main, so follow-up requests to paths outside the editor (for example the media library) run in Live instead of failing to switch into Main. `MainExcludingWorkspaceSelection` replaces core's `WorkspaceSelection` class to keep Main out of matched or limited option lists. `ApiControllerBase` now returns 409 for core's `EntityWorkspaceConflictConstraint` violations. `ApiWorkspaceController::list()` adds `canCreate`. Uninstalling Canvas now deletes Main via `WorkspaceAutoSaveRevisionHooks::deleteMainWorkspaceOnUninstall()`. ADR 0022 decision 1 and its consequences were rewritten accordingly.

The issue described option C as moving the external routes to new `/canvas/external-api/v0/` paths; the committed code instead keeps the existing routes and URLs for both the editor and external clients and distinguishes them by the header.

## Upgrade

External clients of the routes with `canvas_requires_workspace` must send the header, or get a 400:

```
X-Canvas-Workspace: live
```

The Canvas CLI (`packages/cli/src/services/api.ts`) and Workbench preview requests now send it. Canvas OAuth clients need the same header on content, media upload, content template draft, content entity reference preview and content template preview entity suggestion requests (the last route is newly handled by `CanvasOauthAuthenticationProvider`). Sites need no role changes; `canvas_update_11201()` installs `workspaces_ui` if missing.
