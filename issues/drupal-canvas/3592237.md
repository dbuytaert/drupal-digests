## Summary

In the `1.x-workspaces` branch, the Canvas publish endpoint now publishes the whole active workspace as one unit, through core's workspace publish, instead of publishing selected auto-save items one by one. The request must name the workspace and list the pending changes the editor reviewed. If the workspace is not the active one, or the pending list has changed since the review, the request is refused with a 409 and nothing is published. Any invalid item blocks the whole publish with a 422. Discarding a draft is now refused when the user cannot update the entity, or when another workspace has locked it.

## Impact

Affects module maintainers and site owners.

- **Permission change:** Publishing now also requires core's `publish` access to the active workspace, not only the Canvas publish permission. The `publishChanges` UI flag in drupalSettings follows the same rule. Discarding an auto-save now requires entity `update` access.
- **API change:** `POST /canvas/api/v0/auto-saves/publish` now publishes the whole active workspace. The body must be `{workspace, pendingChanges}`, where `pendingChanges` maps auto-save key to `data_hash`. A body without them is a 400. Per-item selection and the old 409/424 codes for unexpected/unmatched items and global assets are gone. `DELETE /canvas/api/v0/auto-saves/{entityTypeId}/{entityId}` gains 403 and 409 responses.
- **New API:** New `\Drupal\canvas\Workspace\CanvasWorkspacePublisher` service (marked `@internal`), new `ErrorCodesEnum` cases `ActiveWorkspaceMismatch` (10) and `PendingChangesOutdated` (11), and a `BuildsAvatarUrlTrait`.

## Technical details

`ApiAutoSaveController::post()` is rewritten and the per-item machinery is removed: sibling-translation expansion, global asset dependency checks, `applyAutoSaveTranslationSnapshots()`, conflict-aware validation, the manual transaction, and `AutoSaveManager::groupContentEntityAutoSaves()`. `post()` returns a 400 if `workspace` or `pendingChanges` is missing. It throws `WorkspaceConflictException::noLongerExists()` or `::notActive()` (codes 9 and 10) when the named workspace is gone or is not the active one. It checks core's `publish` access on the workspace and returns a 403 if denied. `stalePendingChangesResponse()` then compares the reviewed `key => data_hash` map with `getPublishableAutoSaves()`. It returns a 409 with one `PendingChangesOutdated` (code 11) error per added, edited or discarded key.

The actual publish goes through the new `CanvasWorkspacePublisher::publish()`. It wraps core's `$workspace->publish()` in a database transaction, covering the pre-publish subscribers that apply staged config as well as core's own revision promotion. It runs inside `executeInWorkspace()` and counts the auto-save rows for the success message. If the publish fails, it restores the previously active workspace, because core only switches back after the callback returns. If the published workspace was deleted and is still active in the session, it switches to Live. In the controller, `WorkspacePublishValidationException` maps to a 422 with one error per item, and any other `WorkspacePublishException` from core or a subscriber maps to a 409 with pointer `workspace` and no code. Other exceptions become a 500. An empty workspace returns 204 'No items to publish.'

`ApiAutoSaveController::get()` now adds the `workspace` cache context. `delete()` calls `WorkspaceAutoSave::assertNotLockedInAnotherWorkspace()` (409, with the owner in `meta.workspace` per `openapi.yml`) and checks entity `update` access after the 404 check. `CanvasController` computes `publishChanges` from the Canvas permission combined with core's `publish` access to the staging workspace, and adds that access result's cacheability to the response. `buildAvatarUrl()` moved into `BuildsAvatarUrlTrait`. `ContentTemplate::autoSavePublish()` is kept, because `WorkspaceAutoSave::stageFallbackDrafts()` still calls it. `openapi.yml` documents the new `PublishAllRequest` schema and the extra responses. Two `@todo Workspaces MR 22` markers note that non-default-translation rows are still hidden from the pending list and the published count.

## Upgrade

Clients of the publish endpoint must stop sending per-item selections. The body is now:

```json
{
  "workspace": "spring_campaign",
  "pendingChanges": { "<auto-save key>": "<data_hash>" }
}
```

`pendingChanges` is the map returned by `GET /canvas/api/v0/auto-saves/pending`. Callers that relied on the old 409/424 item codes (`UnexpectedItemInPublishRequest`, `UnmatchedItemInPublishRequest`, `GlobalAssetNotPublished`) should handle the new codes 10 and 11 and the code-less 409 from a pre-publish gate. Users publishing need core's `publish` access to the workspace, which the tests grant through the `edit any workspace` permission.
