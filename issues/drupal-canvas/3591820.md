# #3591820: Publishing a symmetrically-translated canvas_page 422s when a default-language edit changes a non-translatable component input

- **Project:** Drupal Canvas
- **Type:** Critical bug report
- **Version:** 1.x-dev
- **Status:** Fixed
- **Discussion:** [#3591820](https://git.drupalcode.org/project/canvas/-/work_items/3591820) · 1 contributor · 6 comments

## Summary

Sites that translate `canvas_page` entities with `content_translation` could hit an HTTP 422 error when trying to publish a page after editing a non-translatable ("symmetric") component input, such as an image's `width`, a section's `padding_bottom`, or a heading's `element` (h1 to h6) tag, on a component instance that also exists in another language's translation. The publish would be rejected even though saving the same change directly would have succeeded. This is now fixed: publishing converges the non-default translation's copy of the changed input to match the default translation, and the publish succeeds as expected.

## Impact

No upgrade or configuration changes required.

## Technical details

The root cause was an ordering mismatch between validation and synchronization. `content_translation`'s presave hook is what converges "symmetric" (non-translatable) field columns across a translated entity's translations, but that convergence only happens inside `EntityInterface::save()`. Canvas's publish path, `ApiAutoSaveController::getConflictAwareContentEntityViolations()`, validates the entity with `$entity->validate()` before `save()` runs, so `ComponentTreeSymmetricalTranslationConstraint` saw the pre-sync, stale, intermediate state (the auto-save snapshot only ever carries the edited default-language translation) and rejected it.

The fix introduces `SymmetricalTranslationSynchronizationTrait`, used by both `ClientDataToEntityConverter` and `ApiAutoSaveController`. It wraps `content_translation.synchronizer` (injected as an optional `$translationSynchronizer` constructor argument, since `content_translation` is an optional dependency) and exposes `synchronizeTranslations()`/`canSynchronizeTranslations()`. `getConflictAwareContentEntityViolations()` now validates a cloned copy of the entity with translations synchronized, while leaving the entity that is actually saved untouched, so `content_translation`'s presave hook remains the single synchronization pass. This distinction matters because `FieldTranslationSynchronizer::synchronizeItems()` is not idempotent after a structural edit (an insert or reorder): running it twice on an already-synchronized entity maps inputs to the wrong deltas and corrupts translations. `ClientDataToEntityConverter::convert()` similarly synchronizes in place before validating, but only on auto-save (never before an actual `save()`), and only when the entity in hand is the default translation, since a non-default translation being edited is itself a synchronization target and must not be silently overwritten before its own violation can be reported.</technical>
