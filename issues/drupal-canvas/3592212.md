## Summary

A full config import could be refused with "Unable to import: the configuration change would delete the in-use Canvas component..." even though the exported component config was present. This happened when the same component (for example a page template or `marker.page_content`) had been created separately on each environment by an update, so the UUIDs differed. Config import now allows this case when the incoming component has the same source and still contains every version the existing one has. Imports that would drop the active version or a historical version are still blocked.

## Impact

No upgrade or configuration changes required.

## Technical details

Core's storage comparer treats config with a different UUID as a delete plus a create under the same name. `ComponentConfigImportValidator::onConfigImporterValidate()` saw the delete and flagged the Component as in use. It now computes the intersection of the `delete` and `create` changelists to find recreated names. A recreated Component is no longer reported as endangered if the new private helper `isRecreatedWithAllVersions()` returns TRUE. That helper requires the incoming `source` to equal the active one and requires `active_version` to be set. Every version from the active `Component::getVersions()` must also appear in the incoming `active_version` or in the keys of `versioned_properties` (excluding `VersionedConfigEntityBase::ACTIVE_VERSION`). The reasoning is that content references Components by ID and version, not UUID. Tests cover recreating with and without the backing `js_component` also getting a new UUID. They also cover blocked imports when the active version or a historical version is missing.
