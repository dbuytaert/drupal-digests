## Summary

Canvas editors can now list, create, switch to and delete workspaces from a workspace switcher in the Canvas UI. When another workspace already holds pending changes to the entity being edited, the editor shows a lock notice with the owning workspace and, if the user may view it, a way to switch. Mutating Canvas API requests are also checked against the workspace the client says it is showing, so a second browser tab that switched workspaces cannot silently write into the wrong one. The CI rule that let Cypress and Playwright failures pass on the `1.x-workspaces` branch is removed.

## Impact

Affects module maintainers and site owners.

- **Permission change:** Writing into a named (non-Main) workspace via a mutating `canvas.api.*` request now requires `update` access on that workspace.
- **New API:** New `hook_canvas_workspace_normalize_alter()` and `canvas.api.workspaces.*` routes (list, create, delete, activate); optional `X-Canvas-Workspace` request header.

## Technical details

`ApiWorkspaceController` (`@internal`) adds four routes: `canvas.api.workspaces.list` (GET, only top-level workspaces the user may `view`, plus `activeWorkspaceId`), `create` (POST with a `label`; the ID comes from the new `WorkspaceMachineName` service, validated with `$workspace->validate()`, 400 on failure), `delete` and `activate`. Delete uses the workspace access handler, so deleting Main is a 403; a workspace with child workspaces is a 409; deleting the active workspace first calls `switchToLive()`. Activation goes through `WorkspaceManagerInterface::setActiveWorkspace()`, so core negotiators and non-Canvas surfaces see the same workspace. `WorkspaceNormalizer` builds the `Workspace` payload (`id`, `label`, `isDefault`, `isActive`, `pendingChangesCount`, `access.delete`, `access.publish`) and invokes `hook_canvas_workspace_normalize_alter()`.

`WorkspaceRequestSubscriber` runs on `KernelEvents::REQUEST` for POST/PATCH/PUT/DELETE on `canvas.api.*` routes, except `canvas.api.workspaces.*`, `canvas.api.log_error` and `canvas.api.notifications.read`. If `X-Canvas-Workspace` is present and differs from the session's staging workspace, it throws `WorkspaceConflictException::noLongerExists()` or `::notActive()` (409). The header is optional, so clients such as the CLI that omit it bypass the check. When staging into a named workspace, the active workspace needs `update` access or the request gets a 403.

The layout response from `ApiLayoutController` gains `lockedInWorkspace` (`id`, `label`, `canSwitch`, `updated`, `owner`), built by `buildWorkspaceLockInfo()` from the new `WorkspaceAutoSave::getOwningWorkspaceLockInfo()`. It is only built for content entities; the owner is shown only if the current user has `view label` access. `WorkspaceAutoSave::getOwningWorkspaceId()` now also covers config entities: since core's tracker does not know config drafts, it looks for a fallback-store draft in another workspace, so a config draft is locked to one workspace at a time (the editor shows no notice for config, the second editor's write gets the 409). The editor boot settings gain `workspaces.activeWorkspace` via `buildWorkspaceSettings()`. ADR 0022 and `openapi.yml` document the error convention: 404 for an unknown ID in the URL, 409 with `source.pointer: workspace` for an unusable workspace, 409 `EntityLockedInAnotherWorkspace` for foreign-owned entities, 403 for refused access.

## Upgrade

Implement the new alter hook to add keys to the workspace payload:

```php
function hook_canvas_workspace_normalize_alter(array &$normalized, \Drupal\workspaces\WorkspaceInterface $workspace): void {
  $normalized['myModuleReviewed'] = (bool) $workspace->get('my_module_reviewed')->value;
}
```

Custom API clients that know their workspace may send `X-Canvas-Workspace: <workspace id>` on mutating requests to get a 409 instead of a write into the wrong workspace.
