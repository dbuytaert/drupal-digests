## Summary

The Canvas workspace API now only deals with workspaces that belong to the Canvas flow: top-level workspaces of core's default provider, plus Main. Workspaces registered by another module's workspace provider no longer appear in the Canvas workspace switcher, and they can no longer be activated or deleted through Canvas. This matches what core's own workspace UI already does.

## Impact

No upgrade or configuration changes required.

## Technical details

`ApiWorkspaceController` gained a private static `isInCanvasFlow()` helper. It returns FALSE for sub-workspaces (`hasParent()`) and for any workspace whose `provider` field is not `DefaultWorkspaceProvider::getId()` or `CanvasMainWorkspaceProvider::ID`. `list()` skips such workspaces next to the existing `view` access check, replacing the earlier inline `hasParent()` check.

`activate()` and `delete()` call a new `assertInCanvasFlow()` before the access checks. It throws a `NotFoundHttpException` whose previous exception is a `ParamNotConvertedException`, so the response matches an unknown workspace ID (empty 404 body) and the API does not reveal workspaces it does not list. As a result, sub-workspaces now also get a 404 from `activate()` and `delete()`, where before only `list()` hid them. The OpenAPI descriptions for the three operations were updated. A new test module `canvas_test_workspace_provider` registers a `ForeignWorkspaceProvider`, and `ApiWorkspaceControllerTest` covers the list, activate and delete cases.
