# #3591996: RecipeAppliedEvent listener installs a module and invalidates the container for every listener after it

- **Project:** Drupal Canvas
- **Type:** Critical bug report
- **Status:** Fixed
- **Discussion:** [#3591996](https://git.drupalcode.org/project/canvas/-/work_items/3591996) · 1 contributor · 6 comments

## Summary

Applying a Drupal CMS style "Site" recipe that enables Canvas together with a theme that defines page regions could crash the site installation with a fatal error: "You have requested a synthetic service (\"kernel\"). The DIC does not know how to construct this service." This happened because Canvas's recipe listener installed a helper module mid dispatch, which rebuilt Drupal's service container while other modules' recipe listeners (for example drupal_cms_helper's, which saves `system.site` config) were still queued to run against the old, now stale container. The fix reorders Canvas's internal recipe handling so the step that can trigger a module install, and therefore a container rebuild, always runs last. Site owners installing Drupal CMS or any Site type recipe alongside Canvas no longer hit this installation failure.

## Impact

No upgrade or configuration changes required.

## Technical details

`RecipeSubscriber::getSubscribedEvents()` previously mapped `RecipeAppliedEvent` to a single `onApply()` method that, for `Site` type recipes, called `PageVariantMigration::migrateDefaultTheme()` inline. That method's `createFromPageRegions()` conditionally installs `canvas_page_template_component` via `ModuleInstallerInterface::install()` when missing, and `InstallerKernel::attachSynthetic()` calls `$this->container?->reset()` on every install to bound memory growth. Any `RecipeAppliedEvent` listener still queued behind Canvas's, holding a reference to the pre-reset container (including synthetic services like `@kernel`, which Canvas's own `ComponentSourceManager` depends on), would then fail to resolve.

The fix splits the event registration into two listeners: the original `onApply()` (unchanged, re-runs config actions targeting `Component` entities) and a new static `migrateSiteTemplate()` registered at priority `PHP_INT_MIN` in `RecipeSubscriber::getSubscribedEvents()`, guaranteeing it runs after every other `RecipeAppliedEvent` subscriber, including third-party ones such as drupal_cms_helper's. `migrateSiteTemplate()` performs the same `PageVariantMigration::migrateDefaultTheme()` call for `Site` recipes, but since it now runs last, the container rebuild triggered by installing `canvas_page_template_component` can no longer invalidate a container that other listeners still need.
