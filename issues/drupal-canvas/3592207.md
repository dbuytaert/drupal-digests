## Summary

When a site goes into maintenance mode while someone has Canvas open, the editor no longer fails with an unexplained error. Canvas now shows a blurred, blocking overlay reading "Site is currently under maintenance" and stops editor actions behind it. Once the site is back online, the page redirects to the login page with a destination back to the page being edited.

## Impact

No upgrade or configuration changes required.

## Technical details

`baseQuery` in the Canvas UI now detects an HTTP 503 whose `Content-Type` does not contain `json` (Drupal's maintenance response is plain text or HTML, and the message is configurable, so it can be empty or valid JSON). It dispatches the new `setMaintenanceMessage` action, stored as `maintenanceMessage` in `queryErrorSlice` (falling back to `Site under maintenance.` for an empty body). A JSON 503, such as the artifact upload lock from `ApiArtifactController`, is still returned as a regular error. The CSRF-retry path was adjusted so a 503 on the retried request is also detected.

The request promise intentionally never settles in the maintenance case, so error boundaries, toasts and optimistic update rollbacks do not run. `ErrorBoundary` also renders nothing while a maintenance message is set.

The new `MaintenanceModeOverlay` component is rendered in `App` outside the error boundary. It is a Radix `AlertDialog` that takes focus and stops `keydown` propagation, so document-level shortcuts such as delete and undo cannot change the editor behind it. While shown, it sends a `HEAD` request to the current URL every 10 seconds. When the response is no longer 503, it navigates to `getDrupalSettings().canvas.loginUrl` with a `destination` parameter, because Drupal logs out users without the maintenance access permission. Vitest and Playwright tests cover the overlay.
