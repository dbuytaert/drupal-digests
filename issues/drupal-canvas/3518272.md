## Summary

Canvas content templates are no longer limited to nodes. Any content entity type that qualifies can now have a content template, such as taxonomy terms or users, where before only `node` was accepted. The Templates UI lists the additional entity types alongside Content types. Eligibility follows Field UI: the type must have a "Manage display" screen, be stored, have its own page, and not be a Canvas component-tree entity such as Canvas Page. Saving a template for an ineligible type fails validation.

## Impact

Affects module maintainers and site owners.

- **Config change:** `content_entity_type_id` on content templates is validated with `ContentTemplateEntityType` instead of being limited to `node`.
- **API change:** View modes endpoint moved to `/canvas/api/v0/ui/content_template/view_modes` with a response keyed by entity type; `DrupalSettings.entityTypeLabels` narrowed and `contentTemplateEntityTypes` added.
- **New API:** New `ContentTemplateRepository` service and `ContentTemplateEntityType` constraint; `ContentTemplate::loadFor()` added.

## Technical details

The first commit was an interim restriction. It added a `Choice: [node]` constraint to `content_entity_type_id` in the content template config schema, so Canvas Pages could not get templates. The second commit replaces it with a `ContentTemplateEntityType` validation constraint.

The new `Drupal\canvas\ContentTemplateRepository` service holds the rule in `isSupportedEntityType()`. An entity type is eligible when all of these hold: `field_ui_base_route` is set, its storage class is not `ContentEntityNullStorage`, its `canonical` link template exists and differs from `edit-form` (`comment` is explicitly excluded because its canonical URL redirects), and its entity class does not implement `ComponentTreeEntityInterface`. The service also provides `getSupportedEntityTypeIds()`, `getBundleCollectionLabel()` and `getViewModeDisplayRouteName()`. The documented rationale is in `docs/config-management.md`.

`ContentTemplateRoutes` (marked `@internal`) is removed. `ViewModeRouteSubscriber` now replaces the controller of `entity.entity_view_display.{entity_type_id}.view_mode` for every supported entity type, and `ViewModeAccessCheck` only applies template permission logic on that route. This leaves other routes using the same access checker, such as Layout Builder's, to the decorated checker. Entity types with no bundle entity type use the entity type ID as their single implicit bundle. `ContentTemplate` gains `loadFor($entity_type_id, $bundle, $view_mode)`. `ApiConfigControllers` and `ApiUiContentTemplateControllers::listViewModes()` iterate the supported types and add the `entity_types` cache tag. `suggestedPreviewEntityId` may now be a string, for entity types with non-integer IDs.

HTTP API change: the route `canvas.api.ui.content_template.view_modes.list` moves from `/canvas/api/v0/ui/content_template/view_modes/node` to `/canvas/api/v0/ui/content_template/view_modes`. The response is now keyed by entity type ID, then bundle, then view mode. `DrupalSettings` in `@drupal-canvas/types` gains `contentTemplateEntityTypes` (`label`, `bundleCollectionLabel`, `bundleLabel`), and `entityTypeLabels` is narrowed to a bundle-keyed map. The headless test module's schema alter workaround for `taxonomy_term` is removed.

## Upgrade

Clients of the view modes endpoint must change the path and read the extra entity type level:

```
- /canvas/api/v0/ui/content_template/view_modes/node
+ /canvas/api/v0/ui/content_template/view_modes
```

Code that read `entityTypeLabels[type]` as a string must now treat it as `{ [bundle: string]: string }`. Use `contentTemplateEntityTypes` for entity type and bundle collection labels.
