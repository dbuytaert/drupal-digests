## Summary

On the `1.x-workspaces` feature branch, publishing a workspace through core (Workspaces UI, Drush, cron or `$workspace->publish()`) now handles Canvas drafts. Every pending Canvas item is validated and access checked first. If anything is invalid, the publish is refused with a message naming the items, and nothing goes live. If everything passes, config drafts (page variants, templates, code components and similar) are saved to Live together with the content revisions. Afterwards the workspace's Canvas draft storage is cleared. A published named workspace is deleted, and the Canvas default workspace is kept. There is no Canvas UI or API change.

## Impact

Affects module maintainers.

- **New API:** New `WorkspacePublishValidationException` (carries `getViolationSets()`) thrown on pre-publish when Canvas drafts are invalid, plus the `AutoSaveWorkspacePublishSubscriber` event subscriber.

## Technical details

The new `AutoSaveWorkspacePublishSubscriber` is registered with the `event_subscriber` tag in `canvas.services.yml`. It listens to `WorkspacePrePublishEvent` at priority -100, so it runs after other listeners such as content_moderation's. If an earlier listener already stopped the publish, it stages nothing. It listens to `WorkspacePostPublishEvent` at -600, after core's association cleanup.

Pre-publish runs inside `executeInWorkspaceUnchecked()` and walks `AutoSaveManager::getAllAutoSaveList()`. Each item gets an `update` access check. A Component generated from staged config is exempt, but only once `discoveryReadsStagedConfig` exists; that exemption is a todo for MR 4. Config items are validated through typed data. Content items get `$entity->validate()` plus the recorded form violations. A Page draft with an unresolved external-edit conflict is also refused, but only when `canvas_dev_cd` is installed. A content draft that storage rejected earlier (`getRejectedDraftError()`) blocks the publish until it is re-saved or discarded. Core has already captured the revisions to promote by then, so it can't be staged late.

Staged config translation overrides (`StagedLanguageConfigOverride`) are hidden from the item list. They get their own access and validation pass, and their base entity is validated from Live if it has no pending draft. If everything passes, `WorkspaceAutoSave::stageFallbackDrafts()` saves the fallback drafts to Live. Any draft that storage rejects is added as a violation. Failures throw the new `WorkspacePublishValidationException`, which core doesn't catch. Its message lists each item, because core's publish form and Drush only log `getMessage()`.

Core dispatches the pre-publish event before opening its transaction, so these Live saves are not atomic with core's revision promotion. Only a publish driven by `CanvasWorkspacePublisher`, which is not in this change, can roll them back. A todo for MR 11 covers this. Access is checked as the current user, so Drush or cron publishes without update access are refused while the workspace holds Canvas drafts. Post-publish calls `clearWorkspaceStores()` and then deletes any workspace other than `AutoSaveWorkspace::ID`. A todo for MR 13 questions that delete, since core keeps a published workspace and the delete bypasses access checks. The PHPStan ignore for the previously unused `stageFallbackDrafts()` is removed, and todos for MR 14 mark the exception classes to move.
