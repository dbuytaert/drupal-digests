## Summary

The Canvas editor no longer requests a new CSRF token from `/session/token` before every save. It fetches the token once while the editor loads and reuses it. The issue reports a 330–600 ms delay before each component PATCH on a dev site under load, and a first PATCH sent 21 ms after the edit with the change. If the session changes, for example after logging out and back in from another tab, a rejected save fetches a fresh token and is sent once more.

## Impact

No upgrade or configuration changes required.

## Technical details

`fetchCsrfToken()` in `ui/src/utils/csrf.ts` now keeps a per-base-URL `Map` of token promises. Concurrent callers share one in-flight request. A failed fetch removes its own entry, so failures are not cached. A new `forgetCsrfToken(baseUrl)` clears the entry so the next call fetches a new token.

`ui/src/main.tsx` calls `fetchCsrfToken()` at startup, so the first mutation reuses that request. In `rawBaseQuery` (`ui/src/services/baseQuery.ts`), a mutation that returns a 403 calls `forgetCsrfToken()` and is retried once. `fetchAssertion` in `useHeadlessDraftSession.ts` does the same drop-and-retry-once for its POST. The issue's reasoning for retrying is that Drupal rejects stale-token requests before handling them, so resending is safe. Vitest tests were added for the cache (`csrf.test.ts`) and for the assertion retry.
