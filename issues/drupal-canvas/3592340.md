## Summary

In the Canvas editor, moving, deleting or dropping a component from the library now updates the preview straight away instead of after the server has rendered a new page. Dragged components no longer appear to jump back before landing. When several edits happen quickly, an older server render that arrives late no longer briefly removes the newer edit. A component moved by dragging is now also selected, as already happened for components added from the library.

## Impact

No upgrade or configuration changes required.

## Technical details

A new RTK listener middleware, `optimisticPreviewListener` (registered in `makeStore`), reacts to `moveNode`, `shiftNode` and `deleteNode`, so every trigger (drag and drop, context menu, "Move into", hotkeys) gets the same behaviour. It edits the DOM of the active preview iframe (`getPreviewDocument()`) using the `canvas-start-…`/`canvas-end-…` comment markers found via `discoverCanvasBoundaries` from `@drupal-canvas/preview-geometry`. `optimisticPreview.ts` provides `movePreviewComponent`, `removePreviewComponent` and `insertPreviewComponent`. Insertion uses the component's `default_markup` and `css`; the markup is parsed through a `<template>` so scripts do not run, and CSS goes in the head before the `PREVIEW_HEAD_STYLES_ID` style. Empty slot and region placeholders are hidden when a component lands in them, but a container that becomes empty after a move is not given a placeholder until the server render arrives. If markers are missing (for example a headless, cross-origin preview), the functions return `false` and the drag handler falls back to the earlier 'pending move' state.

To stop stale renders undoing these edits, `previewEdits.ts` keeps a module-level counter (`notePreviewEdit`, `previewEditCount`, `isPreviewEditedSince`). `setHtml` now takes the edit count at request time, stored as `selectPreviewHtmlEditsAtRequest`. `IFrameSwapper` skips applying HTML (in place or by swap) when the shown preview has been edited since that HTML was requested, and also checks this again when a loaded document is about to be swapped in. Prop edits made while typing in code component forms (`createComponentFormStateHandler`) also count as preview edits. Renders superseded by other changes, such as typing, still show. The server-rendered document still replaces the preview afterwards, correcting what the immediate edit approximates. `useDropFromLayoutHandler` now calls `setSelectedComponent` on the moved component.
