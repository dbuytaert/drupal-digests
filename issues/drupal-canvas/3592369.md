## Summary

The Canvas CLI can now manage a site's registered headless frontends without the UI. `canvas headless:add <url>` registers a frontend (with `--default` to make it the default, including moving an existing one), `canvas headless:remove` removes frontends interactively or by URL with `--yes`, and `canvas headless:list` shows them. `canvas login` gains `--scope` to request an explicit space-separated list of OAuth scopes; list/add/remove need `canvas:headless:frontends`. Registering a URL does not synchronize its components; the Canvas editor still does that when the frontend selector loads or the user switches frontends. Using this needs the `canvas_oauth` module enabled and the update hook run.

## Impact

Affects module maintainers and site owners.

- **Database update:** `canvas_headless_post_update_0002_frontend_oauth_scopes()` creates the `canvas_headless_frontends` Simple OAuth scope on existing sites.
- **Config change:** New `simple_oauth.oauth2_scope.canvas_headless_frontends` config shipped in `canvas_headless` install config, tied to the `administer canvas headless frontends` permission.
- **Permission change:** OAuth tokens with the `canvas:headless:frontends` scope map to the existing `administer canvas headless frontends` permission.
- **API change:** `PATCH /canvas/api/v0/headless/frontends` now requires a `frontendUrlsHash` string (returned by `GET`) and rejects stale saves with 409; request items contain only `url`.
- **New API:** New `POST` and `DELETE` on `/canvas/api/v0/headless/frontends` (OAuth-capable via `canvas_oauth`), new `FrontendManager` service, new `canvas:headless:frontends` OAuth scope, and new `canvas headless:add|remove|list` CLI commands.

## Technical details

The CLI talks to `canvas_headless` through new routes. `canvas_headless.frontends.post` and `canvas_headless.frontends.delete` share the path `/canvas/api/v0/headless/frontends` with the existing GET and PATCH, require `administer canvas headless frontends` plus the CSRF header for cookie auth, and are flagged `canvas_external_api: true` (GET too) so `canvas_oauth` accepts bearer tokens on them. PATCH stays cookie-only. `POST` takes `{url, default?}` and returns `{url, changed}`; duplicates by canonical base URL succeed without change, and `default` moves an existing entry to the front while preserving its component associations and the others' relative order. `DELETE` takes only `{url}` and returns `{url, removed, newDefault?}`; a missing URL succeeds without change, and removal drops only the registration and associations, not components or content.

All list logic moved from `FrontendsController` into the new `FrontendManager` service (`get()`, `replace()`, `add()`, `remove()`, `replaceComponents()`). Writes take a short-lived lock (`canvas_headless_frontends`) and read from `config.storage.active` rather than a possibly stale config cache; lock contention returns 503, validation failures 422. `get()` returns a `frontendUrlsHash` of the ordered URLs; `replace()` (PATCH) now requires it and throws a 409 on mismatch, and association-only updates do not change the hash. `ExternalComponentSync` now calls `FrontendManager::replaceComponents()` instead of its own private method. The OpenAPI spec adds the `CanvasBearer` scheme and the new schemas.

## Upgrade

Run database updates so `canvas_headless_post_update_0002_frontend_oauth_scopes()` creates the `canvas_headless_frontends` scope (named `canvas:headless:frontends`). To use the CLI, enable `canvas_oauth` and log in with that scope:

```
canvas login --scope "canvas:headless:frontends"
canvas headless:add https://frontend.example --default
canvas headless:list
canvas headless:remove https://frontend.example --yes
```

Any client calling `PATCH /canvas/api/v0/headless/frontends` must now send the `frontendUrlsHash` from the preceding `GET` along with `frontends` (items with `url` only).
