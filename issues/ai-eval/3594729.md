# #3594729: Disabling a failure mode does nothing: it is still offered, saved, counted and exported

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3594729](https://git.drupalcode.org/project/ai_eval/-/work_items/3594729) · 1 contributor · 4 comments

## Summary

Disabling a failure mode in AI Eval now retires it. Before, the Status checkbox did nothing: a disabled mode was still offered to annotators, saved onto annotations, and exported. Now a disabled mode no longer appears in the annotation form or the trace review verdict bar, and a request that picks one is refused with a "not saved" message. Labels that already use the mode keep it and show "(disabled)". Failure rates still count them and mark the row "(disabled)". A taxonomy export leaves disabled modes out. The docs now recommend disabling over deleting, because deleting leaves labels pointing at a mode that no longer exists.

## Impact

Affects module maintainers.

- **API change:** `AnnotationStore::save()` and `LabelStore::saveGroup()` now throw `\InvalidArgumentException` for a disabled or unknown failure mode. Their constructors, and those of `EvalResultsController` and `TraceReviewController`, take a `ReferenceOptions` argument.
- **New API:** `ReferenceOptions::failureModes(?string $keep = NULL)` lists the failure modes a label may carry.

## Technical details

The fix adds `ReferenceOptions::failureModes(?string $keep = NULL)`. It returns enabled modes sorted by weight then label. If `$keep` names a disabled mode, the one the label already carries, it is also listed as "<label> (disabled)" so a re-save keeps it. `EvalResultsController::annotationFormBuild()` and `TraceReviewController` use it instead of an unfiltered `loadMultiple()`.

Enforcement is server-side as well as in the select. `AnnotationStore::save()` and `LabelStore::saveGroup()` now take `ReferenceOptions` as a constructor argument. They throw `\InvalidArgumentException` for a failure mode that is unknown, or disabled and not already on that record. The annotation endpoint checks the mode before saving. It returns HTTP 200 with a visible error and does not return a 4xx, because htmx does not swap 4xx responses. It also keeps a 400 for an invalid verdict. In the trace review verdict bar, typing a new mode name that matches a disabled mode is refused. The matching logic is split into `matchFailureMode()` and `createFailureMode()`.

`FailureModeTaxonomySerializer::export()` skips modes where `status()` is false. The schema carries no `status` key. Import never changes the status of an existing mode, and a new mode is created enabled. `FailureRateService` rows gain a `disabled` flag, and `FailureRateTable` renders "(disabled)". The same commit also changes rates to count one annotation per question, the earliest, through `AnnotationStore::joinCanonical()` ([#3594822](https://www.drupal.org/node/3594822)). The `FailureModeForm` Enabled checkbox gained a description.

## Upgrade

Code that constructs these services or the controllers directly must pass the new `@ai_eval.reference_options` argument. The commit adds it to the `AnnotationStore` and `LabelStore` definitions in `ai_eval.services.yml`, and to the `EvalResultsController` and `TraceReviewController` constructors. Existing disabled failure modes take effect on upgrade: they disappear from selects and exports, but stay on labels that already use them.
