## Summary

The `ai_eval_flowdrop` submodule previously told users the Drush command that makes a FlowDrop workflow synchronous would survive later saves in FlowDrop's editor. That was wrong for saves that change a node's settings, such as a system prompt. The editor removes `metadata.orchestrator_settings`, and ai_eval then refuses the next run. The README, the `ai-eval-flowdrop` skill and the "cannot run" reason shown on the target form now say to run the command again after such an edit. Model steps from `flowdrop_ai_provider` (Chat, Simple Chat and similar) are now recorded as AI steps instead of `other`. Entity Query and the session history step are recorded as deterministic.

## Impact

No upgrade or configuration changes required.

## Technical details

In `FlowDropRunReader`, the step kind is derived from the executor plugin id (`provider:base[:...]`). The provider is now checked before the `data_*` and `text_*` prefix rules, because some `text_*` executors from `flowdrop_ai_provider` also call a model. Any `flowdrop_ai_provider` executor maps to `WorkflowStep::KIND_AI`, except `session_history`, which reads memory and maps to `KIND_DETERMINISTIC`. `entity_query` was added to the `KINDS` map as deterministic. Unknown providers still fall through to `KIND_OTHER`.

`FlowDropWorkflowRunner::asynchronousReason()` appends a sentence saying the FlowDrop editor removes the orchestrator setting when node settings are edited and saved. The same text appears in the exception message for refused launches. Kernel tests cover the executor id to kind mapping (including `session_history` and an unknown provider), a real Entity Query run, and the new reason text. The docs also gain a troubleshooting row and a note on a FlowDrop 2.7.2 Prompt Template limit: printing a list variable fails with "Render context is empty", so loop over it and print a field instead. The issue says the root cause of the setting being dropped is in FlowDrop and would be reported there.

## Upgrade

After editing node settings of a FlowDrop workflow in the editor, run the command again:

```bash
drush config:set flowdrop_workflow.flowdrop_workflow.WORKFLOW_ID \
  metadata.orchestrator_settings.type flowdrop_runtime:synchronous -y
```

Use `flowdrop_stategraph:stategraph` instead for workflows that call tools.
