## Summary

When a dataset has `split` labels on only some questions and no `splits` block, unlabeled questions land in both train and validation. Previously the optimizer still reported the validation score as held out, with no warning. Now `eval:optimize` warns once per target, says how many validation questions were also used for training, and tells you to label every question or add a `splits` block. The baseline and final score lines also note the overlap.

## Impact

No upgrade or configuration changes required.

## Technical details

The check lives in `EvalOptimizeCommand::optimize()`, in the dual-phase path (when a split protocol is active). With no `splits` block, it counts questions lacking a `split` key, which is the `DatasetSplitter` rule for unlabeled questions, and the splitter rule itself is unchanged. It counts questions rather than ids because a question may have no id. If the count is above zero, a warning goes to both `$this->io()->warning()` and `$this->channelLogger->warning()`, once per target.

The same count builds an `$overlapNote` such as `(20 of 21 questions also in train)`. It is appended to the `Baseline:` line and to the `Final score:` line, which then reads `on validation (...)`. A docblock that said "held-out validation" was reworded, and the optimizer docs were updated to describe the partial-label case. A new kernel test, `testOverlappingValidationQuestions`, covers two targets and checks each gets one warning.
