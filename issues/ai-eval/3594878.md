## Summary

Workflow targets can now be created and edited in the AI Eval target form instead of only through YAML import. When at least one workflow runner is installed, the add form offers a Workflow mode. You pick the engine, then the workflow, then the input that receives the question. The lists refresh in place as you change the engine or workflow. You can also enter fixed inputs as YAML and set an output path. Chat provider and model settings now apply in workflow mode too, which AI Prompt needs. The form checks the engine, workflow, question port and fixed inputs on save, and shows a message if a runner fails to list its workflows or ports. Existing agent and chat targets cannot be switched to Workflow. Config YAML is still the export and import format.

## Impact

Affects module maintainers.

- **New API:** New optional `Drupal\ai_eval\Workflow\WorkflowRunnerDetailsInterface` (`label()`, `questionPorts()`, `validateTarget()`) and `WorkflowRunnerCollector::label()`. `WorkflowRunnerInterface` is unchanged.

## Technical details

`EvalTargetForm` gains engine, workflow and question port selects with htmx redraws. A workflow with no declared ports gets a text field for the port. Per the shipped docs, the redraws go through the form's own route and permission, so no separate fragment routes were added. On save the form writes the workflow keys, keeps the stored `workflow_snapshot` (the form has no field for it), and returns form errors before the entity throws. Those errors cover an uninstalled engine, an unlisted workflow (a new check), an undeclared or disallowed question port, fixed inputs that name an undeclared port, and fixed inputs that name the question port.

The new optional `WorkflowRunnerDetailsInterface` sits next to `WorkflowRunnerInterface`. `label()` gives the engine name. `questionPorts($workflowId)` returns the ports that can take the question, `NULL` for any declared port, or an empty list for none. `validateTarget()` takes the workflow id, question port, fixed inputs, output path, provider id and model id. It returns errors keyed by `workflow_input_port`, `workflow_inputs`, `workflow_output_path` or `provider_model`. A runner that implements only `WorkflowRunnerInterface` still works: `WorkflowRunnerCollector::label()` falls back to the engine id, and every declared port is allowed.

All four shipped runners implement the interface. AI Answers allows only `question`. Search API allows only `keys`. AI Automators allows every declared port except `text_format`. AI Prompt allows only declared variables that have a single-brace placeholder in the prompt. To keep save-time and run-time checks the same, each runner's `run()` checks were moved into shared private helpers (for example `validateInputs()` and `validateModel()`). `PromptRenderer::validateValues()` and `UnsavedEntityBuilder::validateTextFormat()` were extracted for the same reason. AI Automators now rejects a non-empty output path at save time. AI Prompt requires both a provider and a model. The docs in `docs/user/usage/targets.md` and `docs/user/developers/index.md` were updated.

## Upgrade

Optional for custom workflow runners. Implement `Drupal\ai_eval\Workflow\WorkflowRunnerDetailsInterface` alongside `WorkflowRunnerInterface` to get a label and question port filtering in the target form:

```php
final class MyRunner implements WorkflowRunnerInterface, WorkflowRunnerDetailsInterface {
  public function label(): \Stringable {
    return new TranslatableMarkup('My engine');
  }
  public function questionPorts(string $workflowId): ?array {
    return ['question'];
  }
  public function validateTarget(string $workflowId, string $questionPort, array $fixedInputs, ?string $outputPath, ?string $providerId, ?string $modelId): array {
    return [];
  }
}
```

Runners that do not implement it keep working: the form shows the engine id and allows any declared port.
