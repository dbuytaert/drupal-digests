## Summary

This covers the first part of the larger plan in the issue. Background queue and cron advancing, schedules, and the unique result key are not in these commits. Stepped runs started from the admin UI are now safer when several requests touch the same run. A run finished from two requests at once produces one result. A question that finishes after its run was cancelled can no longer change the cancelled run's scores. A run now keeps the list of question IDs it had at its start, so reordering or adding questions to the dataset mid-run no longer repeats or skips questions. If a selected question is removed, the run ends with an error that names it. A run also records who started it. It runs and grades its questions as that account, even when someone else has the run page open. The run page shows "Started by …". If the starter was deleted or blocked, the run stops with a message asking you to start it again. Run `drush updb` (or `/update.php`) after upgrading.

## Impact

Affects module maintainers and site owners.

- **Database update:** `ai_eval_update_10051()` adds nullable `selection_json` and `ai_eval_update_10052()` adds nullable `started_by` to `ai_eval_run`; existing rows keep NULL.
- **New API:** `EvalRunner` takes an optional trailing `AccountProxyInterface $currentUser` argument, and `runState()` and related run-state arrays gain a `started_by` key (`int|null`).

## Technical details

`EvalRunner::stepRun()` still takes the per-run step lock, but `doStepRun()` now takes only the run id and re-reads the row after the lock is acquired. A step returns early if the run is no longer `pending`/`running` or is already at full progress. The progress write is conditional on the `completed` value read and on an active status, so a step whose 60 second lock expired mid-question cannot overwrite a newer step or a terminal state. The method then returns the current stored state, which may be cancelled.

`finalizeRun()` now opens a transaction and claims the run by updating the status to `complete`, conditional on the status being `pending` or `running`. A caller that loses the claim returns the existing result id through the new `resultIdForRun()`. The winner re-reads the row, scores it, and inserts the result in the same transaction. A failure rolls back both writes, so `markRunError()` can still succeed. `EvalRunCompleteEvent` is dispatched only after commit. A cancel after the claim cannot replace completion. `RunController::progress()` now renders cancelled, error and complete states from the returned or stored state, even at full progress, and only calls `finalizeRun()` for an active run that reached its last question.

`startRun()` writes `selection_json` as `{"ids": [...]}` when every question has a unique, non-empty string `id`. Otherwise it stores NULL. At step time, valid stored IDs select the question by ID. A missing ID throws `RunDatasetException::questionNotFound()`. Rows with NULL or malformed selections keep the old dataset-index path and the `RunDatasetException::changed()` count check.

`startRun()` stores `started_by` from the injected `current_user`. A step with a non-NULL `started_by` and an available `account_switcher` loads the account through `callerAccount()` and switches to it around grader creation and `runQuestion()`, always switching back in a `finally`. A missing or blocked non-anonymous account throws the new `RunAccountException`, which `markRunError()` stores without a class prefix. A question's `caller_uid` still switches the account for the target call only. Rows with NULL `started_by`, or runners built without the optional dependencies, keep running as the requester.
