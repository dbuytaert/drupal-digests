## Summary

A workflow built in FlowDrop's editor used to be missing from the ai_eval target form, with only a generic "no available workflows" message. The cause is that the editor stores no orchestrator, so FlowDrop runs it in the background, and ai_eval can't wait for the answer. The target form now lists the workflows an engine can't run, with a reason. For FlowDrop the reason includes the Drush command that sets a synchronous orchestrator. The FlowDrop engine now has a proper label and checks the question port, fixed inputs, output path and an ignored provider or model when you save a target. Question port choices read "Title (name)", and a single allowed port is preselected. Steps on the results page show the canvas title with the node id. The README, the ai-eval skill and a new `ai-eval-flowdrop` skill document the extra FlowDrop modules a workflow needs and how to set the orchestrator.

## Impact

Affects module maintainers.

- **New API:** `WorkflowRunnerDetailsInterface::unavailableWorkflows()` returns hidden workflows keyed by id with a `label` and `reason`. `WorkflowStep` gets an optional `label` constructor argument.

## Technical details

`WorkflowRunnerDetailsInterface` (the optional interface, unreleased) gains `unavailableWorkflows()`. It returns `[id => ['label' => ..., 'reason' => ...]]` and must never include anything `listWorkflows()` returns. `EvalTargetForm` calls it when the runner implements the interface. With listed workflows present it renders a closed `details` element titled "Not listed (N)" below the Workflow select. With none, it adds the list to the notice ("No workflow from this engine can run yet."). Labels and reasons are cast to strings and passed through `@` placeholders, so engine text is escaped. If a saved target's workflow is hidden, the notice includes the reason.

Runners report what their lists already skip. AI Prompt reports a missing prompt type or a type with no variables. AI Automators reports automators whose `load()` throws a refusal. Search API reports disabled indexes or indexes without an enabled server. AI Answers returns `[]`.

`FlowDropWorkflowRunner` now implements `WorkflowRunnerDetailsInterface`. `label()` returns "FlowDrop". `unavailableWorkflows()` returns asynchronous workflows with the Drush `config:set ... metadata.orchestrator_settings.type flowdrop_runtime:synchronous` reason. `questionPorts()` goes through the new `FlowDropRunReader::questionPorts()`, which uses FlowDrop's `SchemaFragmentChecker::checkValue()` on the declared type, so FlowDrop's own rules apply. An enum is only checked per question at launch. `validateTarget()` and `run()` share `bindingErrors()`. It checks that the question port is declared (and typed for text at save time), that fixed inputs are declared and don't include the question port, that the output path starts with a declared output name, and that no provider or model is set (FlowDrop ignores them). `run()` now loads the workflow through `runnableWorkflow()`, which throws the same asynchronous reason text.

`WorkflowStep` has a new optional `label`. `FlowDropRunReader` sets it only when the canvas title differs from the node id. `WorkflowRecordMapper` stores it as a capped `label` key only when present. The workflow panel shows `Label (node_id)`.

In the form, question port options become "Title (name)" when they differ. A sole allowed port is used as the default and pinned after an AJAX reset.

## Upgrade

Custom workflow runners that implement `WorkflowRunnerDetailsInterface` must add the new method. Return `[]` if nothing is hidden:

```php
public function unavailableWorkflows(): array {
  return [];
}
```

To explain a hidden workflow, return `['workflow_id' => ['label' => $label, 'reason' => $reason]]`. The workflow must not also appear in `listWorkflows()`. To show a node label on the results page, pass `label:` when building a `WorkflowStep`.
