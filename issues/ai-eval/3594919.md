## Summary

A validated judge now goes stale when settings that change its scores are edited. For the decision rubric that means its question, rules, scoring points and pass score. For LLM judges it means `judge_response_char_limit` and `pin_judge_decoding`. Judge validation also gives the judge the criteria and expected facts a real run supplies, so a `fact_match` validation can now produce scores. A validation whose steps ran with different settings or prompt versions, including a prompt override deleted mid-run, can no longer count as trusted. Run database updates and re-validate judges whose trust shows as stale. Labeled items created before this change have no stored criteria or facts, and the validation report says so.

## Impact

Affects module maintainers and site owners.

- **Database update:** `ai_eval_update_10054()` adds a nullable `settings_fingerprint` varchar(64) column to `ai_eval_judge_validation`; old rows keep their state.
- **New API:** New `ValidationSettingsFingerprint` class and `ValidationSettingsReportingInterface`; `LabeledExample` gains `$criteria` and `$expectedFacts`; `JudgeValidationStoreInterface` gains `validatedSettingsMatch()` and `persist()` takes a `$settingsFingerprint` argument.

## Technical details

Each validation step now records a fingerprint from `ValidationSettingsFingerprint`: `llm()` hashes the response char limit and the pin-decoding flag, and `decision()` hashes `DecisionRubric::fingerprint()` plus `pointsPerError` and `passScore`. The two extra values are kept out of the rubric's own fingerprint, so calibration identity is unchanged. Graders expose it through the new `ValidationSettingsReportingInterface`, implemented by `LlmJudgeBase` and `DecisionRubricGrader`. `JudgeValidationRunner::finalizeValidation()` collapses the step fingerprints to one value, or `ValidationSettingsFingerprint::MIXED` when they differ, and stores it in the new `settings_fingerprint` column.

`JudgeValidationStore::validatedSettingsMatch()` compares the stored fingerprint with the current config (`ai_eval.decision_rubric` or `ai_eval.settings`). A mismatch makes the trust state `STATE_STALE`. It returns NULL for rows with no fingerprint, which keeps their state; fixture-file validations never run the judge, so they have none. `JudgeTrustReason` shows 'Validated with different judge settings' or 'Judge settings changed between validation steps'.

`JudgeValidationReport` gets `configurationConsistent` and `missingContext`. `trustBlocker()` returns the new `BLOCKER_CONFIGURATION` when steps recorded more than one config version (or `MIXED` settings). This covers versions like [1, 0], which the old `min() ?: NULL` collapsed to no version. The runner builds the report from the stored steps.

`LabeledExample`, `LabelFixture`, `HumanLabelSource` and the runner's stored labels now carry `criteria` and `expected_facts` (NULL when not recorded). The runner passes them to `grade()` instead of `criteria: ''`. `LabelFixture` rejects a non-string `criteria` or non-array `expected_facts`. The `ai-eval:sample-traces` command also exports both fields.

The same commit bundles fixes for [#3594906](https://www.drupal.org/node/3594906) through [#3594926](https://www.drupal.org/node/3594926), so unrelated changes appear in the diff.

## Upgrade

Run database updates (`drush updb`). `ai_eval_update_10054()` adds the column:

```php
$schema->addField($table, 'settings_fingerprint', $definitions[$table]['fields']['settings_fingerprint']);
```

Existing validation rows have no fingerprint and keep their current state. Re-validate a judge after changing the decision rubric or the judge settings. Label fixture files can now include optional `criteria` (string) and `expected_facts` (array) per row.
