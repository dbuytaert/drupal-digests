## Summary

Before this fix, anyone with only 'Administer AI Eval' could set a question's caller account to any user, including user 1. Anyone with 'operate ai eval' who ran that test then ran the agent with that account's access. A new restricted permission, 'Run AI Eval as another user', now controls this. 'Administer AI Eval' is also marked restricted. Runs now refuse a blocked caller account and record an error for that question. Site owners should give the new permission only to admins who need to set question callers.

## Impact

Affects site owners.

- **Security:** Any 'administer ai eval' user could make questions run as user 1 or a blocked account; this now needs the new restricted permission 'run ai eval as another user'.
- **Database update:** The same commit adds updates 10053, 10054, 10055 and 10057, which belong to sibling issues, not this one.
- **Permission change:** New restricted permission 'run ai eval as another user'; 'administer ai eval' is now marked 'restrict access: true'.

## Technical details

The check lives in `EvalQuestion::preSave()`, so every save path follows it: the question editor, Add to dataset, dataset copy, REST and JSON:API. A save throws `EntityStorageException` with `EvalQuestion::CALLER_PERMISSION_ERROR` when `data.caller_uid` is set, or was set before, and the user lacks the permission. Saves that change only `weight`, or that leave the decoded `data` equal, are not checked. Drush is detected with `Drush::hasContainer()`, not the PHP SAPI, because kernel tests also run under CLI. `DatasetQuestionController` shows the caller as read-only text to users without the permission and also checks it on submit (a forged form value is refused). The route `ai_eval.dataset.caller_accounts` now requires the new permission instead of `administer ai eval`.

In `EvalRunner::runQuestionBody()` a caller other than uid 0 must resolve to a `UserInterface` account that is not blocked, otherwise the question gets an error such as `caller uid %d is blocked`. The account switch no longer depends on the switcher being present for the refusal. `switchTo()`, `setEvalMode()`, `setCallerUid()` and `arm()` now run inside the `try` block. A `$switched` flag makes `switchBack()` run only when the switch happened, and it runs before `disarm()`, so a recorder exception cannot leave the request on the caller account. The `--as-user` option of `drush ai-eval:run` passes through the same runner path, so it also refuses blocked accounts. A question's own caller still takes priority.

## Upgrade

Grant the new permission to roles that edit question callers, in `ai_eval.permissions.yml` terms: `run ai eval as another user`. Existing questions with a `caller_uid` can only be edited or re-saved by users who have it.
