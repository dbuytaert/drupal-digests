# #3594747: Workflow target mode: a pipeline as the system under test (v0 slice)

- **Project:** Drupal AI
- **Type:** Normal feature request
- **Status:** Fixed
- **Discussion:** [#3594747](https://git.drupalcode.org/project/ai_eval/-/work_items/3594747) · 1 contributor · 3 comments

## Summary

ai_eval (1.1.x line) can now test a whole workflow, not only an AI agent or a chat model. A target set to `mode: workflow` runs a pipeline from a workflow engine such as FlowDrop. The pipeline can have deterministic steps, tool calls, model calls and nested sub-workflows. The response text is graded by the existing graders, and the steps taken are stored with each question's result. ai_eval depends on no engine: a bridge module supplies the engine. This first slice has no target form and no step tree view, so workflow targets are created as config YAML. With no engine runner installed, a workflow target is refused at run time with a message naming the missing engine.

## Impact

Affects module maintainers and site owners.

- **Config change:** `EvalTarget` gains optional `workflow_engine`, `workflow_id`, `workflow_input_port`, `workflow_inputs`, `workflow_output_path` and `workflow_snapshot` keys, exported only when `mode` is `workflow`.
- **New API:** New `Drupal\ai_eval\Workflow\WorkflowRunnerInterface` (`id()`, `listWorkflows()`, `inputPorts()`, `run()`), value objects `WorkflowRunResult`, `WorkflowStep`, `ModelCall`, `WorkflowRunOptions`, `WorkflowLaunchRefusedException`, and the `ai_eval.workflow_runners` collector for services tagged `ai_eval.workflow_runner`.

## Technical details

An engine implements `WorkflowRunnerInterface` and registers it as a service tagged `ai_eval.workflow_runner`. `WorkflowRunnerCollector` (service `ai_eval.workflow_runners`) indexes runners by `id()`. It throws a `LogicException` on a duplicate engine id or a tagged service that does not implement the interface. Because tagged services are lazy, this check happens on first read, not at container build. `run()` is synchronous and returns a `WorkflowRunResult`. Anything knowable before work starts (unknown workflow, malformed inputs) must be thrown as `WorkflowLaunchRefusedException`, so a record can tell "never ran" from "ran and failed". Runners must not retry on ai_eval's behalf.

In `EvalRunner`, mode dispatch is now an explicit `match`, with a `workflow` arm calling `invokeWorkflow()`. It builds inputs from the target's fixed `workflow_inputs`, merges the question's `metadata.inputs`, and sets the question text on `workflow_input_port`. A fixed input on the question port is refused. Each question's `scores_json` gets a bounded `workflow` block, written on graded rows and on failed or refused rows. The block holds steps, model calls, status and failure kind. A `WorkflowStep` has an engine-assigned `kind` from a closed set (`ai`, `tool`, `deterministic`, `subflow`, `other`). Steps form a tree by execution id, with an optional free-text `engineKind` and capped input and output previews. The handoff doc gives the v0 budgets as 200 steps, 500-character previews and a 64 KB block. I did not verify these in code. `token_usage` is the run total. The new `workflow_*` keys on `EvalTarget` are added to `config_export`, `toRunnerConfig()` and the config schema. Existing agent and chat targets export unchanged. A user guide section was added in `docs/user/usage/targets.md`.

## Upgrade

A bridge module registers its runner like this (the tag name is from `ai_eval.services.yml`; the service and class names are placeholders):

```yaml
services:
  my_bridge.workflow_runner:
    class: Drupal\my_bridge\MyWorkflowRunner
    tags:
      - { name: ai_eval.workflow_runner }
```

A target then references it by engine id:

```yaml
mode: workflow
workflow_engine: flowdrop
workflow_id: summarize_v2
workflow_input_port: url
```
