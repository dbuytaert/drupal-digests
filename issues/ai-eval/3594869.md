## Summary

The `ai_eval_droost` submodule now grades built Drupal state through Droost 2 and Tool API instead of the old MCP Server plugins. On a Droost 2 site the old code could not reach any tool. Droost 1 support is dropped. Two false passes are fixed: a Canvas read with no item list used to count as an empty tree, so `component_present` with `count: 0` passed. A failed View configuration read used to leave unfiltered assertions free to run and pass. Both now fail with a reason. View specs can only be graded from Drush (`drush aer`), because Droost 2 refuses build tools in a web request. Canvas and View row reads from the admin UI use the logged-in user's access. A site that updates ai_eval while still on Droost 1 keeps working, and the status page reports the missing requirement.

## Impact

Affects module maintainers and site owners.

- **Requirements:** `ai_eval_droost` now requires `drupal/droost` 2.0.0 or later and `drupal/tool` (1.0.0-beta12 or later); Droost 1 and MCP Server are no longer supported.
- **API change:** `DroostOracle` constructor now takes the gateway, entity type manager, logger and an optional SAPI string; new `DroostToolGatewayInterface`; `DroostOracleInterface::ALLOWED_TOOLS` shrunk to six tools.
- **New API:** New `ai_eval_droost.tool_gateway` service (`ToolApiGateway`, implementing `DroostToolGatewayInterface`) and a runtime requirements check on the status page.

## Technical details

Tools now run through a new `ToolApiGateway` (service `ai_eval_droost.tool_gateway`) behind `DroostToolGatewayInterface`, because Tool API's runner classes are final and tests need their own interface. The gateway takes `@?tool.runner`, so the container still compiles without Tool API. It calls `ToolRunner::run()` and returns a `{success, message, data, category}` envelope. The `data` value comes from the result's `data` context value, and messages are reduced to plain text. A missing tool, Tool API input and access failures, and exceptions all come back as envelopes rather than throwing.

`DroostOracle` keeps its fixed allowlist, now cut to `droost_views_get`, `droost_views_execute`, `droost_canvas_tree_get`, `droost_canvas_tree_validate` and `droost_entity_load`. Under the `cli` and `phpdbg` SAPIs it loads user 1 and passes it as the account, as `drush droost:tool` does. Otherwise it passes no account, so Tool API uses the current user. It rewrites failure messages: a missing tool names its providing module (`droost_build` or `droost_canvas`), access denials say which account was used, and a build-tool refusal gets "Grade this spec from Drush (drush aer)." appended. A `data` value that is not an array is a failure.

In `AssertionRunner`, a new `failTarget()` helper emits one failure per assertion, keeping each assertion's id and tier. It is used when `droost_views_get` fails and when `droost_canvas_tree_get` succeeds without an `items` array. Malformed-assertion failures are still reported. A new `DroostRequirements` hook (`runtime_requirements`) errors when Droost or Tool API is missing or Droost is older than 2.0.0, and warns when the Droost version cannot be determined, as in a dev checkout. Tests added: a rewritten unit test using `FakeGateway`, new false-pass tests, and a kernel `ToolApiGatewayTest` against real Droost 2. `verify_live.php` now resolves its expected node ids from the dataset UUIDs, and CI runs the `ai_eval_droost` group.

## Upgrade

Install the new dependencies before updating the submodule:

```
composer require drupal/droost:^2.0 drupal/tool:^1.0@beta
```

Enable `droost_build` for View specs and `droost_canvas` for Canvas specs. Run View specs from Drush (`drush aer`). Custom code that constructs `DroostOracle` directly must pass the new arguments: the gateway, `@entity_type.manager` and the logger.
