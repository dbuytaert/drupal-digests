## Summary

Re-importing an EEE envelope with the same `evaluation_id` but a different dataset name was reported as 'already imported' and skipped, leaving the stored row with the old test id. It is now refused as a conflict and nothing is written. An identical file is still skipped.

## Impact

No upgrade or configuration changes required.

## Technical details

The imported test id (`target_id`) is built from `source_name` and `source_data.dataset_name`, but the measurement fingerprint omits `source_data`, so the fingerprint alone could not detect the change. In `EnvelopeImporter`, the row is now mapped with `mapRow()` before the duplicate lookup, and the lookup also selects `target_id`. A stored import is skipped only when both the fingerprint and `target_id` match the freshly computed row. Otherwise it is reported as `conflict for evaluation_id ...: stored measurement or target differs`. The fingerprint itself is unchanged and `schema/*.schema.json` is untouched. Tests cover a changed dataset conflicting without modifying the stored row, and an identical re-import still being skipped without a conflict. The import documentation now says a different measurement or target under the same `evaluation_id` is a conflict.

The same commit also bundles fixes tracked in [#3594902](https://www.drupal.org/node/3594902), [#3594903](https://www.drupal.org/node/3594903) and [#3594905](https://www.drupal.org/node/3594905) (optimizer failure selection, `default_caller_uid` in run snapshots and comparability, interval handling in the importer), which are outside this issue.
