## Summary

Two requests for the same job arriving together (two tabs, a double click, a slow network) could previously start two runs for one test, write a judge validation twice, or generate the same question twice. These races are now closed. When a start is already being handled, the user sees "A start for this test is already in progress. Try again." instead of a duplicate run. Cancelling or finishing a job while a step is still running no longer lets that step write over the result.

## Impact

Affects module maintainers.

- **API change:** `EvalRunner::startRun()`, `GenerationRunner::startGeneration()` and `JudgeValidationRunner::startValidation()` throw `StartInProgressException` when the start lock is busy; `startValidation()` throws `ActiveValidationException` for a judge with an active validation; `finalizeValidation()` throws `JobBusyException` when the step lock is busy.

## Technical details

Start paths: `EvalRunner::startRun()` and `GenerationRunner::startGeneration()` used to fall back to an unguarded start when the lock could not be acquired and no active job existed. They now throw the new `StartInProgressException` (a `\RuntimeException` subclass). `RunController::start()` and `GenerationController::start()` catch it before the generic `\RuntimeException` branch that rejoins an active job. `JudgeValidationRunner::startValidation()` now takes an `ai_eval_validation_run_start:<grader>` lock and throws `ActiveValidationException` if the judge already has a pending or running validation with `total > 0`. `JudgeValidateController` was changed to show these refusals.

Validation: `finalizeValidation()` now takes the `ai_eval_validation_run_step:<id>` lock, rereads the run inside it, and throws `\RuntimeException` for a canceled run or one with unfinished steps. If the lock is busy it throws `JobBusyException`, so the caller can poll again. `doStep()` writes `completed` and `scores_json` with conditions on the `completed` value it read and on `status IN ('pending','running')`.

Generation: `stepGeneration()` rereads the job inside the lock and returns early unless it is still pending or running. Because a step appends questions before it records progress, the progress `UPDATE` (conditioned on the old `completed` and a running status) now runs first, in the same database transaction as `appendQuestions()`. A stale worker whose lock expired claims zero rows and appends nothing, and an append failure rolls the transaction back. The failure path of the step has the same conditions. `finalizeGeneration()` and `cancelGeneration()` take the same `ai_eval_generation_step:<id>` lock. Finalize only completes a job where `completed >= total`, and both leave the job unchanged if the lock is held. `GenerationController` rereads the job after finalize and cancel, and shows progress or a "still finishing, try Cancel again" notice when the job did not reach the expected state.

This commit also bundles fixes for [#3594906](https://www.drupal.org/node/3594906) to [#3594926](https://www.drupal.org/node/3594926); only the concurrency part ([#3594921](https://www.drupal.org/node/3594921)) is described here.

## Upgrade

Code that calls the runner services directly should handle the new exceptions. Catch `StartInProgressException` before the generic `\RuntimeException` that means "an active job exists":

```php
try {
  $runId = $runner->startRun($target, $source);
}
catch (StartInProgressException) {
  // Another request holds the start lock. Ask the user to try again.
}
catch (\RuntimeException) {
  // Rejoin the active run.
}
```

After `cancelGeneration()` or `finalizeGeneration()`, reread the job: both do nothing while another request holds the step lock.
