## Summary

AI Eval gets a fifth workflow-mode runner, in the new `ai_eval_flowdrop` submodule. With it, a target with `workflow_engine: flowdrop` runs a synchronous FlowDrop workflow once per question. The workflow's declared output is graded as the answer. Each FlowDrop job shows up as a step on the result page, and each individual tool invocation is available to tool-use checks and judges. Asynchronous workflows are not listed or run, because ai_eval waits for each answer. Paused, failed or cancelled runs supply no answer. The workflow really runs and its writes are saved, so use a test copy of the site for workflows that write.

## Impact

Affects module maintainers and site owners.

- **Requirements:** `ai_eval_flowdrop` needs `drupal/flowdrop` ^2.7.2 (added to `require-dev` and `suggest`) and its `flowdrop_workflow_executor` module.
- **New API:** New `ai_eval_flowdrop` submodule with an `ai_eval.workflow_runner` service (id `flowdrop`) and `ToolCallRecord::fromParts()` for engines whose tool calls are plain arrays.

## Technical details

`FlowDropWorkflowRunner` (id `flowdrop`) is tagged `ai_eval.workflow_runner`. It checks that the caller has `execute flowdrop_workflow` and a `view own` or `view any` `flowdrop_pipeline` permission. It refuses a missing or asynchronous workflow with `WorkflowLaunchRefusedException`, then launches through `flowdrop_workflow_executor.launcher` with `LaunchOptions(wait: TRUE)` and never relaunches. `listWorkflows()` only lists workflows whose resolved orchestrator is not asynchronous. Model calls are recorded through `ai_eval.model_call_recorder` while the workflow runs.

All reads of FlowDrop internals sit in one adapter, `FlowDropRunReader`, which reloads the pipeline through FlowDrop's storage registry. Declared outputs come from the last completed graph job of each node, passed to `WorkflowSchemaResolverInterface::extractOutputs()`. Without `workflow_output_path`, one declared output is used. With several, the single output marked `turn: reply` wins, otherwise the named-output map is encoded as JSON. A missing output is reported as an error, not as an empty answer. Booleans become `true` or `false`, and structures become JSON.

Steps are ordered by `execution_order` metadata, then start time and job id, with skipped jobs last. Kinds come from the node type's executor plugin: `reason` is `ai`, `tool_invoke` is `tool`, `flowdrop_workflow` and `workflow_executor` are `subflow`, a list of known logic nodes is `deterministic`, and anything else is `other`. The attempt is `retry_count + 1`. Previews are redacted and capped at 500 characters. Jobs marked `tool_invocation` become tool-call records and nest under the consumer job named in `invoked_by`. The batch `tool_invoke` job is a step but not a call record. Child pipelines are matched to subflow jobs by exact parent pipeline id, in order. If the counts differ, the children have no parent execution id and a note is added. Following child pipelines stops after eight levels.

To share the redaction and caps, `ToolCallRecord::fromFunctionCall()` now delegates to a new public `ToolCallRecord::fromParts()`, and `redactOutput()` became public. A unit test checks the two paths give identical records. The README says that with FlowDrop 2.7.2 a launched workflow's tools reach `tool_invoke` only on the stategraph orchestrator. It also says FlowDrop 3.0.0 moves the optional job lookup methods, so the supported range is stated as ^2.7.2.

## Upgrade

To use it, install FlowDrop and enable the submodule:

```bash
composer require 'drupal/flowdrop:^2.7.2'
drush en ai_eval_flowdrop
```

Then configure a workflow target in YAML, for example:

```yaml
mode: workflow
workflow_engine: flowdrop
workflow_id: answer_question
workflow_input_port: question
workflow_output_path: ''
```
