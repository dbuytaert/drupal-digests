## Summary

Users with only the `operate ai eval` permission can no longer write data that should need administrator rights. Creating, editing or deleting review labels now needs `administer ai eval`, as does starting, progressing or cancelling question generation and re-grading from an uploaded results file. Operators can still re-grade a stored run. Users with `operate ai eval` and `validate ai eval judges` now see their tests on the judge validation page instead of an empty list. Annotators and validators can still label through the UI. If operator roles relied on generation or results-file re-grade, give those users `administer ai eval`.

## Impact

Affects module maintainers and site owners.

- **Security:** Users with only `operate ai eval` could write any user's review labels through REST/JSON:API and could save a gate result from an uploaded results file.
- **Permission change:** Review label create/update/delete, `ai_eval.generate.start|progress|cancel` and `ai_eval.results.regrade_file` now need `administer ai eval` instead of `operate ai eval`.
- **API change:** `EvalTarget` now has an access handler, `EvalTargetAccessControlHandler`: `view` for `operate ai eval` or `administer ai eval`, `update` and `delete` for `administer ai eval`.

## Technical details

`ReviewLabelAccessControlHandler` now allows `view` for `operate ai eval`, `annotate ai eval results`, `validate ai eval judges` or `administer ai eval`. `update`, `delete` and `checkCreateAccess()` need `administer ai eval`. The admin UI writes labels through `LabelStore`, which checks the verdict and sets the owner and does not use entity access, so annotators and validators are unaffected. Direct entity API writes, such as REST or JSON:API, lose the unchecked operator path.

`ai_eval.routing.yml` changes `_permission` on `ai_eval.generate.start`, `ai_eval.generate.progress`, `ai_eval.generate.cancel` and `ai_eval.results.regrade_file` from `operate ai eval+administer ai eval` to `administer ai eval`. Generation saves questions into a dataset that only administrators can edit, so operators previously ended on an access denied page. `ai_eval.results.regrade` for stored runs is left as is.

New `src/Access/EvalTargetAccessControlHandler.php`, registered under `handlers.access` in `EvalTarget`, gives `view` to `operate ai eval` or `administer ai eval` and `update`/`delete` to `administer ai eval` only (`delete` on an unsaved entity is forbidden). `JudgeValidateController::thresholdContext()` filters tests by `$target->access('view')`, so it now lists tests for operators. A user with only `validate ai eval judges` still sees none. The commit adds `EvalTargetAccessTest`, `ReviewLabelAccessTest` and POST checks in `PermissionAccessTest`. The same commit bundles fixes for other issues ([#3594906](https://www.drupal.org/node/3594906) to [#3594926](https://www.drupal.org/node/3594926)).

## Upgrade

Roles that need to create or change review labels through the entity API, run question generation, or re-grade from an uploaded results file must now have `administer ai eval`. `operate ai eval` alone is no longer enough.
