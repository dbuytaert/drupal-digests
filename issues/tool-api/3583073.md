# #3583073: A map output whose keys are 0, 1, 2… is sent as a JSON array, so it fails its object schema

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3583073](https://git.drupalcode.org/project/tool/-/work_items/3583073) · 1 contributor · 5 comments

## Summary

The Tool module lets a plugin declare an output as a free-form "map", advertised in its schema as a JSON object. If the PHP array a tool returned for that output happened to have sequential integer keys starting at 0 (`['a', 'b']`, or `[0 => 'x']`), PHP's `json_encode()` wrote it as a JSON array instead of an object, because PHP cannot distinguish a list from a map by its contents alone. The result then failed validation against the tool's own advertised output schema. This affected MCP clients and other code that validates a tool's `structuredContent`, as well as Drush's `tool:run --json` output. The fix makes every non-multiple map serialize as a JSON object regardless of its keys, matching what the schema promises.

## Impact

No upgrade or configuration changes required.

## Technical details

The conversion happens in `OutputTypeCoercionSubscriber::onOutputTransform()`. Previously it only wrapped a map value in `\ArrayObject` when the value was exactly `[]`, relying on the fact that `json_encode(new \ArrayObject())` writes `{}`. The fix widens the check to `\is_array($value) && \array_is_list($value) && $definition->getDataType() === 'map' && !$definition->isMultiple()`, wrapping any list-keyed array (empty or not) in `new \ArrayObject($value)`. Since `json_encode()` always writes an `\ArrayObject` as an object, the wrapped value now matches the `object` schema type whatever its keys. A map with declared properties has string keys and is therefore never a list, so it still gets walked by `RecursiveToolValueTransformSubscriber` as before; only free-form, list-keyed maps take the new path.

Because the formatted value can now arrive as an `\ArrayObject` instead of a plain array even when non-empty, two call sites needed updating: `ToolOutputTrait::referenceEntities()` now unwraps an `\ArrayObject` via `getArrayCopy()`, replaces entities inside it, and re-wraps it, and `ToolRunCommand::serializeOutputs()` comments and handling were updated accordingly (it already passed `\ArrayObject` values through). Test coverage was added via a new `ListKeyedMapOutputTool` fixture exercising a top-level map, a map declared via the plain `OutputDefinition`, a map nested as a declared property of another map, and a list of maps, plus assertions in `AdvertisedOutputSchemaConformanceTest` and `ToolRunCommandTest`.
