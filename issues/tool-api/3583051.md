# #3583051: ListInputDefinition and MapInputDefinition accept output definitions

- **Project:** Drupal AI
- **Type:** Minor bug report
- **Status:** Fixed
- **Discussion:** [#3583051](https://git.drupalcode.org/project/tool/-/work_items/3583051) · 1 contributor · 7 comments

## Summary

List and map input definitions in the Tool module now reject output definitions. Before, passing an output definition as a list input's item or as a map input's property was accepted and then silently ignored. Now it throws an `\InvalidArgumentException`, matching what the output definitions already do for input definitions.

## Impact

No upgrade or configuration changes required.

## Technical details

Since [#3583019](https://www.drupal.org/node/3583019) the shared base methods `ListDefinitionBase::setItemDefinition()` and `MapDefinitionBase::setPropertyDefinitions()` accept any input or output definition. Only the output classes narrowed that. `ListInputDefinition::setItemDefinition()` and `MapInputDefinition::setPropertyDefinitions()` now override the base methods. They check for `InputDefinitionInterface` and throw `\InvalidArgumentException` otherwise, then delegate to the parent. Without the check, `ListInputDefinition::getItemDefinition()` fell back to an untyped `any` input item, so the declared output item was dropped. The issue says the map input walker skips output-definition properties. Unit tests mirroring the output-side boundary tests were added; this was not checked against a diff, since none was provided. The issue states there are no advertised schema changes.
