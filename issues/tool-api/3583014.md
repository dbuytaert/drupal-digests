# #3583014: Support example values in InputDefinitions (emit JSON Schema `examples`)

- **Project:** Drupal AI
- **Type:** Normal feature request
- **Status:** Fixed
- **Discussion:** [#3583014](https://git.drupalcode.org/project/tool/-/work_items/3583014) · 1 contributor · 8 comments

## Summary

Tool input definitions can now carry illustrative example values, which the module emits as the standard JSON Schema `examples` keyword when it normalizes a tool's inputs. This helps non-deterministic callers, such as LLM function calls or MCP clients, produce well-formed values for inputs whose correct shape is not obvious from the type and description alone (formatted strings, structured maps, IDs with a specific pattern). Tools that do not set examples are unaffected: the emitted schema is byte-for-byte unchanged.

## Impact

Affects module maintainers.

- **API change:** Any class implementing `InputDefinitionInterface` directly, rather than using `InputDefinitionTrait`, must now also implement `getExamples()` and `setExamples()`.
- **New API:** New `getExamples()`/`setExamples()` methods on `InputDefinitionInterface`, plus an `examples` constructor parameter on `InputDefinition` and `EntityInputDefinition`, to emit a JSON Schema `examples` keyword for an input.

## Technical details

`InputDefinitionTrait` gains a `protected array $examples` property with `getExamples(): array` and `setExamples(array $examples): static`, declared on `InputDefinitionInterface` alongside the existing lock methods. `InputDefinition` and `EntityInputDefinition` also accept a new trailing `examples` constructor argument so examples can be declared directly in a `#[Tool]` attribute, in addition to the fluent `setExamples()` call for imperatively built definitions.

`ContextDefinitionNormalizer::getNormalizationSchema()` emits `examples` next to `default`, guarded by an `InputDefinitionInterface` instance check so output definitions (which don't implement the interface) are skipped. Because examples describe a single value, the emit is placed after the multiple-value array wrapping: for a `multiple: TRUE` input, examples land on `items.examples` and the array-level schema stays clean, rather than being duplicated or wrapped incorrectly. The emit reads `getExamples()` off the post-transform definition (after `ToolInputDefinitionNormalizeEvent` subscribers run), the same exposure `default` already has: a subscriber that swaps in a whole replacement definition (as the entity-handle subscribers do) sheds stale examples automatically, since `examples` only lives on `InputDefinitionInterface`. Examples are treated purely as annotations: they are never validated or stripped at runtime. Instead, `InputExamplesEmissionTest` asserts every emitted `examples` entry validates against its own emitted schema, catching stale or mismatched examples for first-party tools at test time.

## Upgrade

Set example values on an input definition either through the attribute:

```php
'field_name' => new InputDefinition(
  data_type: 'string',
  label: new TranslatableMarkup('Field name'),
  description: new TranslatableMarkup('The machine name of the field.'),
  examples: ['field_tags', 'field_summary'],
),
```

or fluently on an already built definition:

```php
$definition->setExamples(['field_tags', 'field_summary']);
```

If you implement `InputDefinitionInterface` directly instead of using `InputDefinitionTrait`, add `getExamples()` and `setExamples()` to your class.
