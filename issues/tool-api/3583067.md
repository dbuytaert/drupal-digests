# #3583067: Decimal and string coercion of JSON numbers adds float noise to values with an integer part

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3583067](https://git.drupalcode.org/project/tool/-/work_items/3583067) · 1 contributor · 5 comments

## Summary

The Tool module's coercion layer, which converts JSON numbers coming from AI tool calls into Drupal field values (and back), was adding binary floating-point noise to any number with an integer part. For example, sending `1234.567` to a decimal or plain text field came back as `1234.56700000000001`, and `99999.99` came back as `99999.99000000000524`. Decimal fields usually hid this on save because core rounds to the field's configured scale, but plain string fields had nothing to round the noise away, so the corrupted value could be stored as-is. This fix makes the formatter emit the number exactly as given (up to the precision a double can represent), so values round-trip cleanly through tools that set, read, or preview field values before saving.

## Impact

No upgrade or configuration changes required.

## Technical details

The bug was in `DecimalStringTrait::formatDecimalString()`, used by both `InputTypeCoercionSubscriber` (for `string` and `decimal` inputs) and `OutputTypeCoercionSubscriber` (for `decimal` outputs holding a float). It formatted every float with a fixed 14 *decimal places* via `\number_format($value, 14, '.', '')`, under the mistaken assumption that this matched PHP's precision setting. PHP's precision counts *significant digits*, not decimal places, and a double only reliably holds about 15 to 17 significant digits, so once a value had an integer part, 14 decimal places reached past what the double actually stores and printed the binary rounding error.

The fix computes the decimal places needed to land on 15 significant digits: `$decimals = \max(0, 14 - (int) \floor(\log10(\abs($value))))`, then formats and trims trailing zeros as before. Zero is special-cased to return `'0'` directly. Below `1e15` this reproduces the value as written (`1234.567`, `99999.99`, `12345678.123`) while still collapsing genuine binary artifacts like `0.1 + 0.2` down to `0.3`. At `1e15` and above, every integer digit of the double is still spelled out without exponent notation, so artifacts past that point can still appear, consistent with the corrected docblock.

Matrix test cases were added to `InputCoercionMatrixTest` for `plain_decimal` and `plain_string` inputs, and a new `OutputCoercionMatrixTest` was added covering the equivalent `decimal` output cases, all asserting the exact strings callers should see. This bug was introduced alongside the decimal/string input coercion work in [#3582983](https://www.drupal.org/node/3582983) and the decimal output coercion work in [#3583030](https://www.drupal.org/node/3583030).
