# #3583028: Accept integer map keys and any entity as an entity input

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3583028](https://git.drupalcode.org/project/tool/-/work_items/3583028) · 1 contributor · 23 comments

## Summary

The Tool module (a contributed module providing a plugin type for defining typed, self-contained "tools" callable from Drush, controllers, ECA, AI agents, or MCP servers) had two gaps in how it validated the values passed into a tool's inputs. First, an input declared as `entity:user_role` (or any config entity type) rejected valid `Role` or `NodeType` objects, because the check only accepted content entities even though core derives an `entity:TYPE` data type for config entities too. Second, the entity type and bundle a tool author declared were not actually checked, so a `Node` passed where an `entity:user` was expected would pass validation and only fail later, deep inside the tool's own code, with a confusing error. Separately, a config mapping such as `system.site`'s `page.403`/`page.404` keys, which PHP stores as integers, crashed input-definition building entirely. All three cases are fixed: any entity type now satisfies its matching `entity:TYPE` input, mismatched types or bundles are reported as a proper validation violation naming the input, and integer-keyed mappings work.

## Impact

Affects module maintainers.

- **API change:** `TypedInputsTrait::validateInputValue()` now checks an entity input's declared entity type and bundle (and any author-declared constraints) instead of only checking that a value is a `ContentEntityInterface`; a mismatched entity now produces a validation violation naming the input instead of failing later inside the tool. `MapDefinitionBase::setPropertyDefinitions()` now accepts integer property names.

## Technical details

The entity branch of `TypedInputsTrait::validateInputValue()` (mirrored in `TypedOutputsTrait`) used to require `$typed_data->getValue() instanceof ContentEntityInterface`. It now accepts any `EntityInterface`, and when the value is an entity, builds a constraint set from the effective definition's dynamic `EntityType`/`Bundle` constraints merged with any constraints the input author declared, then runs only those against the entity via the typed data validator, explicitly excluding full entity/field validation and the entity type's own constraints (like `EntityChanged`). This required generalizing what was `validateListConstraints()` (list-only) into `validateDeclaredConstraints()`, used for both lists and maps, since a `Count` constraint on a map now binds the map's property count rather than being invalid on a scalar. That in turn made `Count` on a `MapInputDefinition` surface as `minProperties`/`maxProperties` in the generated JSON Schema, via a new `ContextDefinitionNormalizer::applyMapConstraintSchema()`.

`MapDefinitionBase::setPropertyDefinitions()` now accepts `is_int($name)` alongside `is_string($name)`, since PHP casts numeric array keys like `403` to integers. Several callers that pass property names into typed parameters (`RecursiveToolValueTransformSubscriber`, `ContextDefinitionNormalizer`, `MapDefinitionNormalizer`, `MapAdapter`) were updated to cast the key to `(string)` where a string-typed argument is expected.
