# #3582968: Tool Explorer execute form: masked exception on access denial, duplicate messages, no validation pass

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3582968](https://git.drupalcode.org/project/tool/-/work_items/3582968) · 1 contributor · 24 comments

## Summary

The Tool Explorer's execute form now reports each outcome once and correctly. Previously, a denied execution showed the real denial plus a confusing "Error executing tool: The action result cannot be retrieved…" message, and every failed run showed both a green status and a red error message. Invalid input is now caught during form validation and shown as inline field errors rather than as a generic failure after submit. The tool label and description header is also built from render elements instead of concatenated markup.

## Impact

No upgrade or configuration changes required.

## Technical details

`ExecuteToolPluginForm` now owns result reporting. `submitConfigurationForm()` checks the declared permission, extracts the values, checks `$this->plugin->access(NULL, TRUE)` (including the access result's reason when available), then executes and reports: `addStatus()` for success, `addError()` ("Tool execution failed: …") for failure. Denials go through a new `reportAccessDenied()`, which sets a failure result with `FailureCategory::Access` via `setFailureResult()` when the tool has no result yet, and adds an error message. Input extraction moved into a shared `extractInputValues()` used by both validation and submit.

The new `validateConfigurationForm()` returns early if the declared permission is not allowed. Otherwise it extracts the inputs and runs `validateInputValue()` for each input. Violations are joined into one message and set with `$form_state->setError()` on `$form[$name]['value']` if present, else on the wrapper element (for Entity and List adapters). A `ContextException` from `getExecutableValue()` is skipped, since an empty required input already fails `#required` validation.

In `ToolExecuteForm` (tool_explorer), `submitForm()` no longer reads `getResult()` and only delegates to the plugin form. A new `validateForm()` delegates the same way, and a `getPluginForm()` helper removes the duplicated class resolution. The header uses a `container` with `html_tag` `h2` and `p` elements. Tests were added (`ToolExecuteFormTest`, `ExecuteToolPluginFormTest`) plus two test tools, `MultiConstraintTool` and `RegexConstrainedTool`.
