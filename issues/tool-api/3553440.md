## Summary

The Tool module's `tool_system` submodule gets a new "Get Configuration" tool. It lets a caller, such as an AI agent over MCP, read a configuration object from Drupal, either in full or a single key like the site name from `system.site`. Access needs the new `use config_get tool` permission. That permission exposes any configuration, so grant it only to trusted roles. The merge request was marked as looking good but had not been committed when this summary was written.

## Impact

Affects module maintainers and site owners.

- **Permission change:** New `use config_get tool` permission in `tool_system`, which allows reading any configuration.
- **New API:** New `config_get` Tool plugin (`ConfigGet`) in `tool_system` for reading configuration objects or single keys.

## Technical details

The change adds `Drupal\tool_system\Plugin\tool\Tool\ConfigGet`, a `ToolOperation::Read` tool with id `config_get`. Inputs are `config_name` (required string) and `key` (optional string). The single output is `config_value` of type `any`. The issue text lists `key` without saying it is optional, but the MR makes it optional: an empty `key` returns all data for the object.

`doExecute()` loads the object through `config.factory`. It returns `ExecutableResult::failure()` if `isNew()` is true, meaning the object does not exist. Otherwise it returns `$config->get($key)` or `$config->get()`. A code comment says `get()` is used instead of `getRawData()` so that overrides are included. Any `\Exception` is caught and returned as a failure result. `checkAccess()` uses `AccessResult::allowedIfHasPermission($account, 'use config_get tool')`. The permission is defined in the `tool_system` permissions YAML with the description "Allows users to fetch any configuration from Drupal."
