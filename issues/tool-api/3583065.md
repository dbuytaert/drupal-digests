# #3583065: Report item and property positions in the violation path, not the message

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3583065](https://git.drupalcode.org/project/tool/-/work_items/3583065) · 1 contributor · 4 comments

## Summary

In the Tool module, a validation failure on a list item or map property now reports where it happened in the violation's property path (`code`, `codes.0`, `rows.0.sku`). Before, the position was embedded in the message text, e.g. `(item 0) ...`. Output validation failures now follow the same shape as input failures: the output name is on the path and the message states only the reason. The plain-text failure message still shows the path in front of each reason, so Drush-style text consumers still see where the failure is. Code that parsed `(item N)` or `(property x)` out of messages, or that matched the old output messages, needs updating.

## Impact

Affects module maintainers.

- **API change:** Violation property paths for list items and map properties now carry the position (`code`, `codes.0`, `rows.0.sku`); the `(item N)` and `(property x)` message prefixes are gone. Output violations carry the output name on the path with generic messages, and `getViolations()` is now populated on output failures.

## Technical details

`ValueViolationsTrait::addItemViolations()` no longer takes a `$kind` argument and no longer wraps the message. It rebuilds each violation with `static::joinPath($position, $violation->getPropertyPath())`, and now also passes the constraint through to the new violation. `validateInputValues()` now uses it for the input name too, replacing its own rebuild loop. `TypedOutputsTrait::validateOutputs()` uses it to put the output name on the path. `getItemDefinitionForViolations()` is removed, since messages no longer need the item's label, and callers use `$definition->getItemDefinition()`.

Messages that named the value by label became generic and name-free, because the name is now on the path: `This output is required but was not provided.`, `This property is required.`, `This output must be an entity.`, `This output is invalid: @type.`. The required-output violation now carries the output name as its path instead of an empty string.

`ToolBase` now builds the Runtime failure from `ToolMessages::violationList($violations)` and passes `$violations` to `ExecutableResult::failure()`. `ToolResultInterface::getViolations()` therefore covers output failures as well as input failures. Callers can use `getFailureCategory()` to tell an input they can correct from an output the tool got wrong. The `ToolResultInterface` docblock documents the path format: the name is the segment before the first dot, and a map property reads `product.sku`, a list item `codes.0`, both `rows.0.sku`.

## Upgrade

Read the position from the violation path instead of the message. Messages like `(item 0) This value should be of the correct primitive type.` are now path `codes.0` with the message `This value should be of the correct primitive type.`

```php
foreach ($result->getViolations() as $violation) {
  $path = $violation->getPropertyPath(); // e.g. "rows.0.sku"; first segment is the input or output name.
}
```
