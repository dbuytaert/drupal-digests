## Summary

Tools that refine their input definitions after dependency values arrive are now held to a narrowing contract: the unrefined definition is the upper bound, and a refined definition may only accept a subset of it. A refiner that changes an input's data type or flips its multiplicity now fails immediately with a `LogicException` naming the input, so the mistake shows up in the tool's own tests. Before this, such refiners were accepted silently, and the schema advertised to clients (such as the MCP `tools/list`) could disagree with what the tool accepted. Refiners that add constraints, declare properties on a free map, or supply list item definitions are unaffected.

## Impact

Affects module maintainers.

- **API change:** Refiners returning a definition with a different data type or flipped multiplicity now throw `\LogicException` from `TypedInputsTrait::setInputValue()`.

## Technical details

The check is `TypedInputsTrait::assertRefinementNarrows()`, called in `setInputValue()` right after `refineInputDefinition()` returns. It throws when the refined data type differs from the original, or when `isMultiple()` differs. Permitted exceptions: an original type of `any` may refine to any concrete type, and a type may refine to a sub-type with the original as prefix (`entity` to `entity:node`, matched via `str_starts_with($refined_type, $original_type . ':')`). The second commit adds one more allowance: an original with `multiple: TRUE` (for example a multiple map) may be replaced by a `ListInputDefinition`, since both advertise an array of items. The list's item data type must be `any`, the original type, or a sub-type of it. Otherwise a `LogicException` about the item data type is thrown. The contract is documented on `InputDefinitionRefinerInterface`. A new `tool_test` fixture, `refiner_contract_tool`, and `RefinerContractTest` cover each branch. The fixture is excluded in `AdvertisedSchemaAcceptanceTest` because it throws by design. The issue states that existing refiners in tool, tool_belt and the bridge fixtures were audited and comply. It also notes that the legacy-normalizer `any` schema fix landed under [#3583001](https://www.drupal.org/node/3583001), not in these commits.

## Upgrade

Custom tools implementing `InputDefinitionRefinerInterface` should check that `refineInputDefinition()` keeps the data type and multiplicity of the given `$definition`. Allowed changes are adding constraints, declaring map properties, supplying a list item definition, refining `any` to a concrete type, or narrowing `entity` to `entity:node`. A refiner that does anything else, such as returning `data_type: 'integer'` for a `string` input, now throws a `LogicException`. Make the declared definition stable and put any variation into constraints instead.
