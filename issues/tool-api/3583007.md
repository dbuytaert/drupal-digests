## Summary

Multiple-value tool inputs no longer advertise or accept NULL items. Previously a multiple string input advertised items as "string or null", so strict clients such as the MCP bridge let `[null]` through, and tools received `[NULL]`. For multiple map inputs, `[null]` was silently turned into `[[]]`. Now the advertised item schema contains only the real type, and a NULL item is rejected with a violation naming the input. Tools no longer need to handle NULL entries in list inputs.

## Impact

Affects module maintainers.

- **API change:** Item schemas for multiple inputs no longer include a `null` branch, and lists containing NULL items are rejected with "The @name input must not contain NULL items."

## Technical details

The cause was that the item schema was built from a clone of the input definition with `multiple` unset. The clone kept `required: FALSE`, which added a null branch to the item schema, and item validation skipped NULL because the clone was optional. The fix marks the item clone required in three places. `ContextDefinitionNormalizer` calls `setRequired(TRUE)` on the item definition in its multiple branch, so `items` no longer includes `null`. The item-level validation in `TypedInputsTrait` also uses a required clone, so NULL items are no longer skipped by the optional early-return. The input setter in `TypedInputsTrait` now throws an `InputException` ("The @name input must not contain NULL items.") when an array value for a multiple or `list` input contains a strict NULL. This check runs before typed-data storage can coerce the NULL, for example into an empty map array. The outer input stays nullable (`type: ['array', 'null']`) because required still describes whether the whole input may be omitted. Tests were updated: `InputSchemaMatrixTest` and `RicherSchemaEmissionTest` now expect non-nullable item schemas, and `InputCoercionMatrixTest` gained rejected-case rows for `[NULL]` on `multi_string` and `multi_map`.

## Upgrade

Tools that handled NULL entries in multiple inputs can drop that handling. Callers or clients that sent `[null]` or lists containing null items will now get an `InputException` (or a schema validation failure) instead of silent acceptance.
