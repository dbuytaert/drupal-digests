## Summary

Tools with Map or List inputs no longer fail validation with "Invalid values given. Values must be represented as an associative array." after an entity has been created earlier in the same request. Output validation now behaves like input validation: a missing required output, or an exception thrown during validation, is reported as a named violation instead of escaping or being skipped.

## Impact

No upgrade or configuration changes required.

## Technical details

Drupal core's `TypedDataManager::getPropertyInstance()` caches prototypes under a key that ignores the property's data type and constraints (core issue [#3616328](https://www.drupal.org/node/3616328)). Entity field items (for example a link field's `title`) cache `map::title` as `Map`, and a later `MapInputDefinition` defining `title` as `string` gets the wrong prototype. As a workaround, `TypedInputsTrait::validateInputValue()` now resets the protected `prototypes` property of the `typed_data_manager` service via `ReflectionProperty` before creating the `Context`, only when the definition is a `MapContextDefinition` or `ListContextDefinition`.

`TypedOutputsTrait::validateOutputs()` was rewritten to iterate `getOutputDefinitions()`, matching `validateInputs()`. A required output that was never set adds a `ConstraintViolation` ("The @name output is required but was not provided."). Each output's `validate()` runs inside try/catch, and an exception becomes a violation ("The @name output is invalid: @message"). The same prototype cache reset is applied for Map/List definitions. The `@return` and `@var` docblocks for `getOutputs()` and `$outputs` were corrected to `ContextInterface`. A new kernel test, `PrototypeCacheWorkaroundTest`, covers type collisions, dropped constraints, leaked constraints and list item constraints.

The reset clears the whole prototype cache for the request, not only the colliding keys. This is a workaround until core is fixed.
