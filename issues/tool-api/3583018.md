# #3583018: Store input and output values as typed data instead of Context objects

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3583018](https://git.drupalcode.org/project/tool/-/work_items/3583018) · 1 contributor · 9 comments

## Summary

The Tool API module (part of the AI tooling ecosystem) changes how it stores the values passed into and out of a tool. Previously every input and output value was wrapped in a core `Context` object; now values are stored as typed data directly. For developers this mostly matters through new accessor methods: `getInputData()` and `getOutputData()` return the value as typed data, while the existing `getInput()`, `getOutput()`, `getInputs()`, `getOutputs()` and `setInput()` methods are deprecated (they still work, minting a `Context` object on demand) and will be removed in `tool:1.0.0-rc1`. Sites and modules using only `getInputValue()`/`setInputValue()`/`getOutputValue()`/`setOutputValue()` are unaffected. The module's integration with the `ai` module's function-call contract, which still requires core context definitions, keeps working through a new adaptation layer in `tool_ai_connector`.

## Impact

Affects module maintainers.

- **API change:** `InputDefinitionInterface` and `OutputDefinitionInterface` now also extend `DataDefinitionInterface` (not just `ContextDefinitionInterface`), and both formally declare `isMultiple()`, `setMultiple()`, `setRequired()`, `getDefaultValue()` and `setDefaultValue()`; classes implementing these interfaces directly (rather than extending the provided base classes) must supply the typed-data contract too.
- **Deprecation:** `TypedInputsInterface::getInput()`/`getInputs()`/`setInput()` and `TypedOutputsInterface::getOutput()`/`getOutputs()` are deprecated in tool:1.0.0-beta10 and removed in tool:1.0.0-rc1 (#3583019); use `getInputValue()`/`setInputValue()`/`getInputData()` and the output equivalents instead.
- **New API:** New `getInputData()`/`getOutputData(): TypedDataInterface` methods on `TypedInputsInterface`/`TypedOutputsInterface` return typed data wrapping an input's or output's resolved value.

## Technical details

`TypedInputsTrait` and `TypedOutputsTrait` used to store every value inside a core `Context` object purely as a value holder, calling only `getContextValue()`, `getContextData()` and `validate()` on it. That wrapper is now gone from storage: values are held as typed data (`TypedDataManager::create()`) or, for an explicit `NULL`, a bare marker that resolves through the definition's default the way a value-less `Context` used to. A new internal helper, `Drupal\tool\TypedData\EffectiveDataDefinition::createFrom()`, rebuilds a fresh core data definition of the declared data type (merging the author's constraints with the type's own defaults) whenever a value needs to be created, validated, or turned into a JSON Schema; it replaces the ad hoc `new Context($definition, $value)` calls previously scattered through validation and normalization.

`getInput()`/`getOutput()`/`getInputs()`/`getOutputs()`/`setInput()` remain on the interfaces but are deprecated; internally they now mint a `Context` on demand via `mintInputContext()`/`mintOutputContext()` rather than reading it from storage. `ContextDefinitionNormalizer` (used to build the advertised JSON Schema) was retargeted to work directly against `InputDefinitionInterface`/`OutputDefinitionInterface` (through `getDataDefinition()`, backed by `EffectiveDataDefinition`) while still accepting plain core `ContextDefinitionInterface` objects, since the `ai` module's `setContextDefinitionOverride()` path and the [#3583015](https://www.drupal.org/node/3583015) acceptance shim still deliver those.

Because the `ai` module's function-call contract is still typed on core `ContextDefinitionInterface`, `tool_ai_connector` gained an adaptation layer at that boundary: `ToolContextDefinition`/`ToolEntityContextDefinition` (implementing a new `ToolContextDefinitionInterface`) wrap a Tool API definition inside a core context definition, and `ToolPluginBase::getContextDefinitions()`/`applyContextDefinitionOverridesToInputSchema()` convert back and forth so overrides made by the `ai` module (`setContextDefinitionOverride()`) still take effect. Output validation for entity values was also narrowed to only run the effective definition's `EntityType`/`Bundle` constraints (the declared-type checks), rather than the wrapped entity's own full constraint set (e.g. `EntityChanged`), matching the shape checking the rest of output validation already did. The core `TypedDataManager` prototype-cache workaround (`resetTypedDataPrototypes()`, worked around pending core [#3616328](https://www.drupal.org/node/3616328)) is retained rather than removed, and its kernel coverage was extended to cover output validation as well as inputs. Related work: [#3583016](https://www.drupal.org/node/3583016) is the parent plan issue, [#3583017](https://www.drupal.org/node/3583017) re-parented the definition families onto typed data, and [#3583019](https://www.drupal.org/node/3583019) will remove the deprecated context accessors and the remaining `ContextDefinitionInterface` parentage.

## Upgrade

Replace calls to the deprecated context accessors with the value or typed-data accessors:

```php
// Before
$value = $tool->getInput('name')->getContextValue();
$tool->setInput('name', new Context($definition, $value));

// After
$value = $tool->getInputValue('name');
// or, for typed data:
$data = $tool->getInputData('name');
$tool->setInputValue('name', $value);
```

The same applies to outputs: replace `getOutput()`/`setOutput()`-style usage with `getOutputValue()`/`setOutputValue()`/`getOutputData()`. `getInputs()`/`getOutputs()` (which returned all values as `Context` objects) should be replaced with `getInputValues()`/`getOutputValues()`, or `getInputData()`/`getOutputData()` per name if a typed-data wrapper is needed. All deprecated methods will be removed in `tool:1.0.0-rc1` ([#3583019](https://www.drupal.org/node/3583019)).

If you implement `InputDefinitionInterface` or `OutputDefinitionInterface` directly rather than extending the provided base classes (`InputDefinition`, `MapInputDefinition`, etc.), add implementations for `isMultiple()`, `setMultiple()`, `setRequired()`, `getDefaultValue()` and `setDefaultValue()`, since the interfaces now extend `DataDefinitionInterface` as well as `ContextDefinitionInterface`.
