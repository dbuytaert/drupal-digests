# #3583017: Re-parent the definition families onto typed data behind a temporary ContextDefinitionInterface bridge

- **Project:** Drupal AI
- **Type:** Normal task

## Summary

The tool module's input and output definition classes (`InputDefinition`, `OutputDefinition`, and their `Map`/`List`/`Entity` variants) now inherit from Drupal core's typed data system (`DataDefinition`, `MapDataDefinition`, `ListDataDefinition`, `EntityDataDefinition`) instead of from the Plugin Context system. This is an internal architectural step towards fully detaching tool definitions from Drupal's context API; it does not change constructor signatures, JSON Schema output, or any other observable behavior. `MapContextDefinition` and `ListContextDefinition` are now deprecated in favor of the corresponding `MapInputDefinition`/`MapOutputDefinition` and `ListInputDefinition`/`ListOutputDefinition` classes, and will be removed in a future release.

## Impact

Affects module maintainers.

- **API change:** Tool's input/output definition classes (`InputDefinition`, `OutputDefinition`, and `Map`/`List`/`Entity` variants) now extend Drupal core typed data classes instead of Plugin Context classes; `instanceof ContextDefinition`/`EntityContextDefinition` checks against them no longer match.
- **Deprecation:** `Drupal\tool\TypedData\MapContextDefinition` and `ListContextDefinition` are deprecated in tool:1.0.0-beta10 and removed in tool:1.0.0-rc1; use `MapInputDefinition`/`MapOutputDefinition` and `ListInputDefinition`/`ListOutputDefinition` instead.

## Technical details

This is step 1 of a 3-step plan (parent plan [#3583016](https://www.drupal.org/node/3583016)) to detach the tool module's definition classes from core's Plugin Context system. Each definition class now extends the matching typed data class rather than a context class, for example `InputDefinition extends DataDefinition` and `EntityInputDefinition`/`EntityDefinitionBase extends EntityDataDefinition`. To avoid breaking the three remaining context-coupled internals (`Context` storage in the input/output traits, `ContextDefinitionNormalizer` matching, and the ai module boundary), every class still `implements ContextDefinitionInterface`, with the missing methods supplied by a new `ContextDefinitionBridgeTrait`: `isMultiple()`/`setMultiple()`, `getDefaultValue()`/`setDefaultValue()`, a compatible `setRequired()`, `getDataDefinition()` (rebuilds a core definition via the typed data manager, needed because `Context::getContextData()` validates against its constraints), and a stub `isSatisfiedBy()` that builds a core `ContextDefinition` on demand since nothing in the tool stack calls it directly.

A key subtlety is `getConstraints()`: `DataDefinition::getConstraints()` would merge in `TypedDataManager::getDefaultConstraints()` (`PrimitiveType`, `NotNull` for required fields, data type constraints, `AllowedValues`), but `ContextDefinitionNormalizer` iterates `getConstraints()` to build the published JSON Schema, so the bridge trait overrides it to return only author-declared constraints, preserving the old `ContextDefinition`-style behavior. The base classes `MapDefinitionBase` and `ListDefinitionBase` now carry the property/item-definition handling that used to come from `MapContextDefinition`/`ListContextDefinition` by inheritance, and those two classes are thinned to deprecated subclasses that trigger `E_USER_DEPRECATED` on construction.

Because `instanceof ContextDefinition` and `instanceof EntityContextDefinition` no longer match these classes, this is flagged as an API change, though the issue notes no known usages outside the tool module itself. The bridge trait and the `ContextDefinitionInterface` parentage are marked `@internal` and will be removed in [#3583019](https://www.drupal.org/node/3583019) once [#3583018](https://www.drupal.org/node/3583018) detaches `Context` storage and the normalizer.</technical>
