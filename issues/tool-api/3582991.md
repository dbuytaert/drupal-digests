# #3582991: Drush tool:run should surface access denial reason and pre-flight validation

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3582991](https://git.drupalcode.org/project/tool/-/work_items/3582991) · 1 contributor · 14 comments

## Summary

The `tool:run` Drush command now tells you why it refused to run a tool instead of a generic "Access denied" message. It validates the tool's inputs first, so a bad or missing argument is reported as an input problem rather than a permission problem, and when access truly is denied, it surfaces the actual reason the tool gave (for example, which permission is missing). With `--json`, every pre-execution failure now also includes a machine-readable `error_type` field, useful for scripts, CI pipelines, or AI agents driving Drush programmatically.

## Impact

Affects module maintainers.

- **API change:** The `tool:run` Drush command's `--json` error output gains a new `error_type` field (backed by the `RunErrorType` enum), and now validates tool inputs before checking access rather than after.

## Technical details

`ToolRunCommand::run()` in the `tool` module now calls `$tool->validateInputs()` before checking access, since `access()` fails closed with a generic reason on invalid input; checking access first would misreport a bad argument as a permission problem. If violations exist, the command reports them and exits before ever calling `access()`.

The access check itself now calls `$tool->access(return_as_object: TRUE)` and, when the result implements `AccessResultReasonInterface`, appends `getReason()` to the error message instead of dropping it.

Every failure path in the command now passes a new `RunErrorType` backed enum (`src/Drush/RunErrorType.php`) to `writeError()`, which serializes it as `error_type` in the `--json` output: `tool_not_found`, `invalid_option`, `user_not_found`, `user_blocked`, `invalid_input`, `access_denied`, and `execution_failed`. A tool that runs and reports its own failure (a failed `ExecutableResult`) is not one of these: it has no `error_type`, since that's a result, not a command error. The docs at `docs/usage/drush.md` document the ordering, the JSON shape, and each error type. A new test fixture, `InvalidOutputTool`, exercises the one execution failure `ToolBase` doesn't absorb: a result whose output value doesn't fit its output definition, which makes `execute()` itself throw after `doExecute()` already succeeded.

## Upgrade

Scripts or CI pipelines invoking `drush tool:run --json` and inspecting failures should switch from string-matching the `error` message to reading the new `error_type` field:

```json
{
  "success": false,
  "error": "Access denied for tool 'send_email': The 'send emails' permission is required.",
  "error_type": "access_denied"
}
```

Possible `error_type` values: `tool_not_found`, `invalid_option`, `user_not_found`, `user_blocked`, `invalid_input`, `access_denied`, `execution_failed`. Note that a tool which runs and reports its own failure has no `error_type` at all, that document is a result (`success: false` plus the tool's own `message`), not a command error.
