# #3583091: Name the input when an entity handle fails, so getViolations() covers handle failures

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed

## Summary

When a tool call is given a malformed, missing or wrong-type entity handle, the failed result now says which input was at fault. Before, `getViolations()` was empty for these failures and the message was only a generic "Invalid input" text. A caller, such as an AI agent, can now see every bad input in one response and fix them together.

## Impact

No upgrade or configuration changes required.

## Technical details

`HandleExceptionInterface` is a bare marker with no input context, so `ToolRunner` could only produce `Invalid input: @message` with no violations. The issue weighed two options: a per-input catch in the runner, or an `InputAwareExceptionInterface` with `getInputNames()`. The merged code takes the per-input catch. It adds no new interface.

In `ToolRunner`, the loop that calls `$tool->setInputValue()` now catches `HandleExceptionInterface` for each input. It records a `ConstraintViolation` whose property path is the input name, built by the new private `handleViolation()`. A `HandleNotFoundException` gets an extra sentence saying a handle resolves only for the account that created it, until it expires. A refiner that throws is attributed to the input whose set triggered it.

The loop also catches `InputException` per input. Its named violations join the same list. A bare-reason exception keeps its own message as the whole result unless another input has already failed. The runner collects every input that cannot be stored before refusing the call. It then runs `validateInputs()` on the inputs that were stored and adds those violations, skipping the inputs that failed to store, so a bad value shows up beside a bad handle. The combined list is set with `setFailureResult()` using `FailureCategory::Input`. The private `inputNamed()` reads the first segment of a violation path to do that filtering. The outer `HandleExceptionInterface` catch remains only for handle exceptions thrown after the input loop, such as an output transform, which have no input to name.
