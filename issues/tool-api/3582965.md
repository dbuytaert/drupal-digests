## Summary

Tool plugins no longer claim to be cacheable. The cacheability methods always returned empty values, so anything caching tool results would have under-varied silently. Cacheability is now explicitly deferred: it may come back later as a designed feature.

## Impact

Affects module maintainers.

- **API change:** `ToolInterface` no longer extends `CacheableDependencyInterface`; `getCacheContexts()`, `getCacheTags()`, `getCacheMaxAge()` and `getCacheInputs()` removed from `ToolBase` and `TypedInputsTrait`.

## Technical details

The issue offered two options: implement `getCacheContexts()` by promoting the orphaned `TypedInputsTrait::getCacheInputs()`, or drop the interface. The commit took the second. `ToolInterface` no longer extends `CacheableDependencyInterface`, and the docblock now says tools are deliberately not cacheable because executions are per-request with per-call arguments and no consumer caches tool results. The stub `ToolBase::getCacheContexts()` is deleted. In `TypedInputsTrait`, `getCacheInputs()` (not on any interface and called by nothing), `getCacheTags()` and `getCacheMaxAge()` are deleted, along with the `Cache` and `CacheableDependencyInterface` imports. The kernel test from option (a) was not added.

## Upgrade

If custom tool plugins or consumers call `getCacheContexts()`, `getCacheTags()` or `getCacheMaxAge()` on a tool, or type-check a tool against `\Drupal\Core\Cache\CacheableDependencyInterface`, remove that usage. A tool class that needs these methods can implement `CacheableDependencyInterface` itself.
