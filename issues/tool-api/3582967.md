# #3582967: Harden the 'administer tool' permission

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3582967](https://git.drupalcode.org/project/tool/-/work_items/3582967) · 1 contributor · 7 comments

## Summary

The Tool Explorer's `administer tool` permission, which controls execution of arbitrary Tool plugins (including entity creation, modification, and deletion), previously had only a bare title with no warning that it was a sensitive, security-relevant permission. It is now flagged as restricted in Drupal's permissions UI, and its description explicitly warns that granting it allows executing tools that can change site data and configuration. A new `view tool information` permission lets roles browse the list of registered tools and view their input, output, and configuration schemas without being able to run them, so site builders no longer have to grant full execute access just to let someone audit what tools exist.

## Impact

Affects site owners.

- **Permission change:** The `administer tool` permission is now marked `restrict access: true` with a warning description; a new `view tool information` permission grants read-only browsing of Tool Explorer definitions without allowing execution.

## Technical details

The fix in `tool.permissions.yml` adds `restrict access: true` and a warning description to `administer tool`, and introduces a second permission, `view tool information` (also restricted), covering read-only browsing. `tool_explorer.routing.yml` changes the `tool_explorer.list` and `tool_explorer.view` routes' `_permission` requirement to `'view tool information+administer tool'` (either permission grants access), while `tool_explorer.execute` keeps requiring `administer tool` alone.

`ToolExplorerController::listTools()` now builds the row operations conditionally: the `view` link is always present, but the `execute` dropbutton link is only added when `$this->currentUser()->hasPermission('administer tool')` is true. Because the rendered operations now vary by permission, the list render array's `#cache` was given a `user.permissions` cache context to avoid serving a cached row with the Execute link to a user who lacks `administer tool`. A new kernel test, `ToolExplorerAccessTest`, asserts both permissions are marked restricted, checks route access for anonymous, no-permission, read-only, and administrator accounts, and verifies which operations links appear per role.

## Upgrade

Sites that grant `administer tool` to a role only so users can browse the Tool Explorer without executing tools should switch that role to the new `view tool information` permission instead:

```yaml
view tool information:
  title: 'View tool information'
  description: 'Browse tool definitions in Tool Explorer, including input, output, and configuration schemas.'
  restrict access: true
```

Custom code checking access to the Explorer's list or view routes should account for the new `_permission: 'view tool information+administer tool'` requirement (either permission suffices), while the execute route still requires `administer tool` alone.
