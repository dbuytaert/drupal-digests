## Summary

This adds a Tool module, `tool_sdc`, that lets Tool API callers such as AI agents build Single Directory Components (SDC) in a theme or module. The tools list existing components, read component files, write the `.component.yml` definition, the `.twig` template and css, js, scss or json files, and delete files. The tools write directly into theme or module directories on the filesystem. For that reason they sit behind two new permissions, and the write permission is marked as restricted. Only grant it on local or development environments. The issue is marked fixed, but no commits had landed when this was summarized. A late comment says the Tool project's tools are moving to the Tool Belt module (see [#3557721](https://www.drupal.org/node/3557721)), so the final home of this code may differ.

## Impact

Affects module maintainers and site owners.

- **Permission change:** New `read filesystem components` permission and a new restricted `write filesystem components` permission.
- **New API:** New `tool_sdc` submodule in the Tool project with seven tool plugins (`list_components`, `list_component_files`, `read_component_file`, `write_sdc_definition`, `write_sdc_twig`, `write_sdc_file`, `delete_component_file`) and an `SdcToolBase` base class.

## Technical details

This is based on the MR !57 diff, which is a proposal and not merged code. A new `tool_sdc` module depends on `tool:tool`. Its tools are `#[Tool]` plugins in `Drupal\tool_sdc\Plugin\tool\Tool`, all extending `SdcToolBase`. The base class injects `module_handler`, `theme_handler`, `file_system`, `plugin.manager.sdc` and `app.root`. It resolves the extension path and builds the path `<extension>/components/<component_name>`. Write tools call `ComponentPluginManager::clearCachedDefinitions()` after changing files.

Each tool takes `component_name` (regex-constrained), `extension_type` (`theme` or `module`) and `extension_name`. Path safety comes from `sanitizeFilePath()`, `sanitizeFileName()`, `getComponentDirectory()` and `validateFilePath()`. These reject `..` and null bytes and check that the resolved path stays inside the component directory. `write_sdc_definition` only checks that the YAML parses with `Yaml::parse()`. It does not check it against the SDC schema. `write_sdc_twig` checks syntax by tokenizing with the `twig` service.

File type allowlists: `write_sdc_file` accepts `css`, `js`, `scss` and `json`. `read_component_file` accepts those plus `twig`, `yml` and `yaml`. `delete_component_file` refuses `twig`, `yml` and `yaml`, so a component itself has to be removed by hand. Access is decided in `SdcToolBase::checkAccess()`. Tools whose operation is `ToolOperation::Read` need `read filesystem components`. All others need `write filesystem components`, which is declared with `restrict access: true`. The `copy_sdc_file` tool from the original proposal was dropped.
