# #3583033: Add ToolDefinitionSerializer::normalizeOutputSchema() as the twin of normalizeInputSchema()

- **Project:** Drupal AI
- **Type:** Normal feature request
- **Version:** 1.0.x-dev
- **Status:** Fixed
- **Discussion:** [#3583033](https://git.drupalcode.org/project/tool/-/work_items/3583033) · 1 contributor · 7 comments

## Summary

The Tool API module's `ToolDefinitionSerializer` already had `normalizeInputSchema()` to build a full JSON Schema object for a tool's inputs, but no equivalent for outputs, just a bare properties list. Consumers that needed a full output schema, such as the MCP server tool bridge and a hand-built OpenAPI generator, ended up reimplementing the wrapper themselves and getting details wrong, like omitting required outputs or mishandling the empty-properties case. This issue adds `normalizeOutputSchema()` as the output-side twin, so any module building on Tool API can get a correct, consistent output schema without re-solving the same problems.

## Impact

Affects module maintainers.

- **New API:** New `ToolDefinitionSerializer::normalizeOutputSchema()` method returns a complete JSON Schema object (`type`, `properties`, `required`) for a tool's declared outputs.

## Technical details

`normalizeOutputSchema(ToolInterface $tool, string $format = 'json_schema'): array` wraps `normalizeOutputDefinitions()` in `{type: object, properties: ...}` and adds a `required` array populated from each `OutputDefinition::isRequired()`, guarding the empty case with `new \ArrayObject()` so it serializes to `{}` rather than `[]`, mirroring `normalizeInputSchema()`.

The one deliberate asymmetry: `normalizeInputSchema()` sets `additionalProperties: FALSE` because a tool rejects unknown arguments, but `normalizeOutputSchema()` leaves it unset. The docblock explains why: `ToolBase::execute()` only copies declared outputs into the outputs bag, but `getFormattedResult()` deliberately passes undeclared result values through, so a serialized result can legitimately carry members beyond the declared properties, and closing the schema would make it lie. A kernel test (`OutputSchemaTest`) covers both the normal case, asserting `required` only lists outputs marked required, and the no-output case, asserting the empty properties bag encodes as `{}`.

The `required` list is currently advisory: nothing in `ToolBase::execute()` yet enforces that a tool actually returns its required outputs. That enforcement landed separately as commit `1ab3f3e` for the follow-up issue referenced in this one ([#3583029](https://www.drupal.org/node/3583029)).
