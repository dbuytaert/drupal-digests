## Summary

Tool plugins can now declare an icon, making it easier to build tool pickers, automation UIs, and agent surfaces that need a visual to scan through long lists of tools. Rather than inventing a tool-specific image system, the module hooks into Drupal core's Icon API (available in Drupal 11.1+), so any icon pack a module or theme already declares can be reused. The Tool Explorer module's listing page now shows each tool's icon, falling back to a generic icon based on the tool's operation type (read, transform, destructive, etc.) when a tool declares none.

## Impact

Affects module maintainers.

- **New API:** `#[Tool]` attribute and `ToolDefinition` gain an optional `icon` argument/`getIcon(): ?string` method for referencing a core Icon API icon (`pack_id:icon_id`).

## Technical details

The `#[Tool]` attribute gains an optional `icon` argument: a string in the form `pack_id:icon_id` referencing an icon declared in any module or theme's `*.icons.yml` file. Because it's a plain string, it's a valid constant expression for use in attributes, and because it's stored as a regular definition property, a `deriver` can set a different `icon` per derivative, which was the original motivation for supporting MCP/derived tools with distinct icons.

`ToolDefinition::getIcon(): ?string` simply returns the stored reference verbatim. Nothing is resolved or validated at plugin discovery time; the module still supports core `^10.5`, and the Icon API only exists from 11.1 onward, so validating early would break on older cores. Resolution is left entirely to consumers, who go through `Drupal\Core\Theme\Icon\IconDefinition` (or `plugin.manager.icon_pack`) and are expected to treat a missing pack, missing icon, or pre-11.1 core the same way: as "no icon".

`ToolExplorerController::buildIcon()` demonstrates this pattern: it feature-detects `IconDefinition::class` before doing anything, and for a tool that declares no icon it falls back to `tool:operation-<operation value>`, a small icon pack shipped in `tool.icons.yml` with one SVG per `ToolOperation` case. This fallback is presentation-only and never touches the definition itself, so other consumers such as the MCP bridge still see `NULL` and can apply their own defaults.

## Upgrade

To declare an icon for a tool plugin, add the `icon` argument to the `#[Tool]` attribute, referencing an icon pack declared in a `*.icons.yml` file:

```php
#[Tool(
  id: 'my_tool',
  label: new TranslatableMarkup('My Tool'),
  description: new TranslatableMarkup('Does something.'),
  operation: ToolOperation::Transform,
  icon: 'my_module:my_icon',
)]
```

This is additive; existing tool plugins without an `icon` argument continue to work, and `ToolDefinition::getIcon()` returns `NULL` for them.
