# #3583038: Allow output definitions to declare examples

- **Project:** Drupal AI
- **Type:** Normal feature request
- **Version:** 1.0.x-dev
- **Status:** Fixed

- **Followers:** 1

## Summary

Tool API input definitions could already carry illustrative "examples" values (e.g. a status field's example values `draft`, `completed`), but output definitions could not. This mattered for anyone generating an OpenAPI document or an MCP `outputSchema` from Tool API definitions: every request property could carry an example, but no response property could. This issue extends the same `examples` capability to outputs, so a tool's output schema can now show a client what a value looks like after it is published.

## Impact

Affects module maintainers.

- **API change:** Any class implementing `OutputDefinitionInterface` directly (without extending one of the module's four output classes) must now also implement `getExamples()` and `setExamples()`, e.g. by using the new `ExamplesTrait`.
- **New API:** `OutputDefinitionInterface` gains `getExamples()`/`setExamples()`, and `OutputDefinition`/`EntityOutputDefinition` gain an `examples` constructor argument, so tool outputs (not just inputs) can declare illustrative example values, emitted as the `examples` keyword in generated JSON Schema/OpenAPI output.

## Technical details

The `examples` property and its accessors, previously hard-coded into `InputDefinitionTrait`, were extracted into a new standalone `ExamplesTrait`. `InputDefinitionTrait` now composes `ExamplesTrait` so input behavior is unchanged, and `OutputDefinitionInterface` declares `getExamples()`/`setExamples()`, implemented via the same `ExamplesTrait` in all four output classes (`OutputDefinition`, `EntityOutputDefinition`, `MapOutputDefinition`, `ListOutputDefinition`). `OutputDefinition` and `EntityOutputDefinition` (the scalar/entity leaf classes) also gained an `examples` constructor argument, mirroring `InputDefinition` and `EntityInputDefinition`, so a `#[Tool]` attribute can declare output examples inline; the map and list output classes don't take the argument directly since their examples live on their child definitions.

`ContextDefinitionNormalizer::getSchemaProperty()` (or its equivalent private schema-building method) now checks for `OutputDefinitionInterface` alongside `InputDefinitionInterface` when deciding whether to emit the `examples` keyword: `if (!$object->isMultiple() && ($object instanceof InputDefinitionInterface || $object instanceof OutputDefinitionInterface) && ($examples = $object->getExamples())) { $schema['examples'] = array_values($examples); }`. Examples are read off the post-transform definition, so an output example shows the value as it is actually published to a client, and a definition swapped out by a `ToolOutputDefinitionNormalizeEvent` subscriber loses its examples unless the subscriber re-sets them. As with inputs, a multiple output's examples land on the `items` sub-schema rather than the array level.

A follow-up, referenced in the issue body, is tracked to let `#[ToolProperty]` and `#[ToolOutput]` attributes take an `example` argument the way `#[ToolInput]` already does.

## Upgrade

Any class that implements `OutputDefinitionInterface` directly, rather than extending `OutputDefinition`, `EntityOutputDefinition`, `MapOutputDefinition`, or `ListOutputDefinition`, must add `getExamples()`/`setExamples()`, most simply by adding `use ExamplesTrait;`:

```php
use Drupal\tool\TypedData\ExamplesTrait;

class MyOutputDefinition implements OutputDefinitionInterface {
  use ExamplesTrait;
  // ...
}
```

To declare example values on an output:

```php
$output = new OutputDefinition(
  data_type: 'string',
  label: new TranslatableMarkup('Status'),
  description: new TranslatableMarkup('The order status.'),
  examples: ['draft', 'completed'],
);
```
