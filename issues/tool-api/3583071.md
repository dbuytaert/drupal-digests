# #3583071: Inputs and outputs declared with data type "map" are advertised as strings on Drupal 10 and 11.0

- **Project:** Drupal AI
- **Type:** Major bug report
- **Status:** Fixed
- **Discussion:** [#3583071](https://git.drupalcode.org/project/tool/-/work_items/3583071) · 1 contributor · 5 comments

## Summary

On Drupal 10 and 11.0, Tool API's JSON Schema generator incorrectly advertised any tool input or output declared with the plain `map` data type (as opposed to the dedicated map classes) as a string instead of an object. This mismatch broke tools in practice: a server or client that validates arguments or results against the advertised schema, such as mcp_server, would reject the object the tool actually needs or returns. The `tool_belt` module alone declares 28 such plain map inputs and outputs, so this affected a substantial share of real tools. The fix makes plain map definitions advertise as objects consistently on every supported core version, matching the behavior already present on Drupal 11.1+.

## Impact

No upgrade or configuration changes required.

## Technical details

The root cause was in `ContextDefinitionNormalizer::getNormalizationSchema()`. A `data_type: 'map'` declared on the dedicated `MapInputDefinition`/`MapOutputDefinition` classes (subclasses of `MapDataDefinition`) was already handled correctly, taking the map branch that builds `{"type": "object", ...}`. But the same `map` data type declared on a plain `InputDefinition` or `OutputDefinition` is just a `DataDefinition`, so it fell through to the typed-data branch, which asks the serializer for the `json_schema` of a `Map` typed-data object. On cores before 11.1, that request is handled by `LegacyTypedDataNormalizer` (registered at a higher priority than `MapDefinitionNormalizer` in `tool.services.yml`), which has no arm for `Map` and returns an empty array, which then falls back to advertising `{"type": "string"}`.

The fix extends the existing map branch's condition from `$object instanceof MapDataDefinition` to also match `$object->getDataType() === 'map'`, mirroring how the `list` data type is already special-cased a few lines above it. When the object isn't a `MapDataDefinition`, there are no property definitions to iterate, so `applyMapConstraintSchema()` and the empty-properties object logic now apply uniformly to plain maps too. A new test, `PlainMapSchemaTest`, asserts that a plain map definition and its `MapInputDefinition`/`MapOutputDefinition` equivalent normalize to identical schemas, including under a `Count` constraint that bounds `minProperties`/`maxProperties`.

The issue notes other data types (`binary`, `language_reference`) may hit the same legacy-path string fallback on Drupal 10.6 but leaves deciding whether they need their own arm as a remaining task, not addressed by this change.
