## Summary

A connector that needs content entities to cross its boundary as handle strings (an LLM function call, an MCP tool call) no longer has to ship its own event subscriber and service. It passes an `Invoker` that carries the `EntitiesAsHandles` capability when it creates the tool, and Tool API's own subscriber does the rest. Plain string invoker IDs still work. Code that reads the invoker from a tool or an event now gets an `Invoker` object instead of a string, so identity checks need updating. The change is marked breaking, which the issue says is acceptable in beta.

## Impact

Affects module maintainers.

- **API change:** `getInvoker()` on `ToolInterface` and the four transform/normalize events now returns `?Invoker` instead of `?string`. Event constructors take `?Invoker $invoker`. `EntityHandleTransformSubscriberBase` is removed.
- **Deprecation:** Removed without deprecation: `EntityHandleTransformSubscriberBase`, `ToolAiConnectorEntityHandleTransformSubscriber` and the `tool_test` entity handle subscriber, along with their service definitions.
- **New API:** New `Drupal\tool\Tool\Invoker` value object and `InvokerCapability` enum (case `EntitiesAsHandles`). `ToolManager::createInstance()` and `ToolInterface::setInvoker()` accept `string|Invoker`.

## Technical details

`Drupal\tool\Tool\Invoker` is a `final`, `\Stringable` class with a `readonly string $id` and variadic `\UnitEnum ...$capabilities`. It has `has(\UnitEnum)`, which does a strict `in_array`, and `from(string|self)`, which wraps a legacy string into an `Invoker` with no capabilities. `ToolBase::setInvoker()` calls `Invoker::from()`, so a string passed to `createInstance()` or `setInvoker()` still works. Capabilities are typed as any `\UnitEnum`, so a module can define its own enum and check it with `$event->getInvoker()?->has(MyCapability::Case)`. Cases from different enums do not match each other.

The former abstract base class is now the concrete `final` `EntityHandleTransformSubscriber`, registered as `tool.entity_handle_transform_subscriber` in `tool.services.yml`. Its four handlers return early unless `$event->getInvoker()?->has(InvokerCapability::EntitiesAsHandles)`. Handler bodies are unchanged. The event classes (`ToolInputTransformEvent`, `ToolOutputTransformEvent`, and the two definition-normalize events), `ToolInterface`, `ToolBase`, `ToolManager` and `RecursiveToolValueTransformSubscriber` are retyped from `?string` to `?Invoker`.

In `tool_ai_connector`, `ToolAiConnectorInvoker::create()` returns `new Invoker(self::ID, InvokerCapability::EntitiesAsHandles)`. `ToolPluginBase::getPluginInstance()` passes it, and the connector's own subscriber and service are deleted. `tool_test` gains `TestInvokerCapability::UppercaseOutputs` and `TestCapabilitySubscriber`, with `InvokerCapabilityTest` showing that a capability from another module's enum is honored. `tool.api.php` and `docs/developers/events.md` now describe the call-site opt-in. `tool.api.php` also adds a short group of guidelines on when a behavior should be a capability and when it should be the subscriber's default.

## Upgrade

Subscribers that gate on invoker identity must compare the `id` property:

```php
if ($event->getInvoker()?->id !== 'ai_agents') {
  return;
}
```

A connector that extended `EntityHandleTransformSubscriberBase` should delete the subclass and its `event_subscriber` service. It should pass the capability when creating the tool instead:

```php
$tool = $this->toolManager->createInstance(
  $plugin_id,
  [],
  new Invoker('mcp_server', InvokerCapability::EntitiesAsHandles),
);
```

The issue says `mcp_server_tool_bridge` follows separately, in its own issue (3613896 in that project).
