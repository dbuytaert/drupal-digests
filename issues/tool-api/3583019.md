# #3583019: Remove ContextDefinitionInterface from the definition interfaces

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3583019](https://git.drupalcode.org/project/tool/-/work_items/3583019) · 1 contributor · 7 comments

## Summary

The tool module's `InputDefinitionInterface` and `OutputDefinitionInterface` no longer extend Drupal core's `ContextDefinitionInterface`. This completes a three-step plan (after [#3583016](https://www.drupal.org/node/3583016) and [#3583017](https://www.drupal.org/node/3583017)) to detach the module's input and output definitions from core's Plugin Context system now that they are built on typed data instead. Code that relied on tool definitions also behaving like core context definitions (type hints, `instanceof` checks against `ContextDefinitionInterface`, or event subscribers written against it) will stop matching. The module also removes the deprecated `getInput()`/`getOutput()` (and `getInputs()`/`getOutputs()`) accessors that minted `Context` objects on demand, and the deprecated `MapContextDefinition`/`ListContextDefinition` classes. None of this affects how tools are declared, the value APIs, or the JSON Schema the module publishes; the `ai` module integration is unaffected because `tool_ai_connector` already converts between tool definitions and core context definitions at that boundary.

## Impact

Affects module maintainers.

- **API change:** `InputDefinitionInterface` and `OutputDefinitionInterface` no longer extend `ContextDefinitionInterface`; `getDataDefinition()` and `isSatisfiedBy()` are removed from those definitions, `TypedInputsInterface::getInput()`/`getInputs()` and `TypedOutputsInterface::getOutput()`/`getOutputs()` are removed, and `MapContextDefinition`/`ListContextDefinition` are deleted.

## Technical details

The bridge trait that let tool definitions answer as `ContextDefinitionInterface` (`ContextDefinitionBridgeTrait`, added in [#3583017](https://www.drupal.org/node/3583017)) is deleted and replaced by a smaller `ToolDataDefinitionTrait` that only carries the value semantics the definitions still need: `isMultiple()`/`setMultiple()` and `getDefaultValue()`/`setDefaultValue()`, now declared directly on `InputDefinitionInterface` and `OutputDefinitionInterface` rather than inherited from core's context interface. The bridge methods that existed purely to satisfy `ContextDefinitionInterface`, `getDataDefinition()` and `isSatisfiedBy()`, are gone; callers that previously called `$definition->getDataDefinition()` to get a typed data definition (for example `ConfigureToolPluginForm` and `ExecuteToolPluginForm`) now call `EffectiveDataDefinition::createFrom($definition)` instead.

`TypedInputsInterface::getInput()`/`getInputs()` and `TypedOutputsInterface::getOutput()`/`getOutputs()`, deprecated since `tool:1.0.0-beta10`, are removed along with their on-demand `Context` minting; `TypedInputsTrait` and `TypedOutputsTrait` are deleted entirely. The deprecated `MapContextDefinition` and `ListContextDefinition` classes, thin wrappers around `MapDefinitionBase`/`ListDefinitionBase` for constructing core-style context definitions, are also deleted. The acceptance shim that still lets a plugin *declare* an output using a core `ContextDefinition`/`EntityContextDefinition` remains for now; its removal is tracked separately in [#3583050](https://www.drupal.org/node/3583050).

## Upgrade

Replace any use of the removed context accessors with the typed-data equivalents:
```php
// Before:
$context = $plugin->getInput('name');
$plugin->setInput('name', $context);
$output_context = $plugin->getOutput('name');

// After:
$value = $plugin->getInputValue('name');
// or, for the typed data object:
$data = $plugin->getInputData('name');
$plugin->setInputValue('name', $value);
```

Replace calls to the removed `getDataDefinition()` bridge method on input/output definitions with `EffectiveDataDefinition::createFrom()`:
```php
// Before:
$typed_data = $this->getTypedDataManager()->create($definition->getDataDefinition(), $value, $name);

// After:
$typed_data = $this->getTypedDataManager()->create(\Drupal\tool\TypedData\EffectiveDataDefinition::createFrom($definition), $value, $name);
```

Remove any type hints, `instanceof` checks, or `use` statements against `\Drupal\Core\Plugin\Context\ContextDefinitionInterface` for tool input/output definitions; they no longer implement it. Replace `MapContextDefinition`/`ListContextDefinition` with `MapInputDefinition`/`MapOutputDefinition` or `ListInputDefinition`/`ListOutputDefinition`.
