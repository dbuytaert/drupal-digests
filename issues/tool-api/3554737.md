## Summary

The Tool project gets a "Format Date/Time" tool that converts a timestamp, a date string or a relative expression such as "+1 day" into a formatted string. You can choose the output format, timezone and language. It can also return a relative time difference instead of an absolute date. It ships in a new `tool_utilities` submodule for generic utility tools and needs no access check, so anyone can run it. The merge request was marked RTBC after testing, but the diff was still unmerged when this was written.

## Technical details

The tool is a `ToolBase` plugin with id `date_time_formatter` and the `Read` operation. Its inputs are `input_value` (required), `input_format`, `output_format` (default `Y-m-d H:i:s`), `timezone`, `locale` and `relative` (default FALSE). It has one output, `formatted_date`.

Input parsing happens in `parseInput()`. A numeric value is treated as a Unix timestamp. Otherwise `\DateTime::createFromFormat()` is used when `input_format` is given, and `new \DateTime()` is used when it is not. The `timezone` value is applied when parsing the string as well as when formatting the output. Any parse failure, including an invalid timezone, returns `ExecutableResult::failure()`.

When `relative` is set, the tool calls `DateFormatterInterface::formatTimeDiffSince()`, passing `locale` as `langcode`. Otherwise it calls `DateFormatterInterface::format()`. If `output_format` matches the ID of a `date_format` config entity such as `short` or `medium`, that entity is used. If not, the string is used as a custom PHP date format. `checkAccess()` always returns allowed.

The MR also adds a `tool_utilities.info.yml`. It requires Drupal `^10.3 || ^11` and depends on `tool:tool`. A unit test, `DateTimeFormatterTest`, covers timestamp, string, timezone, relative and date format entity inputs. It uses a mocked `date.formatter` service, so it does not check real timezone or locale output.
