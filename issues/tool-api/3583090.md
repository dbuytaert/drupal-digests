## Summary

Tool input validation no longer passes the message of any exception to the caller as if it were a problem with the input. Previously an unexpected error during validation, such as an unknown constraint listing every constraint plugin ID, or a database error carrying SQL, could reach an LLM over MCP, the AI connector, the CLI or a form. Now only genuine "this value can't be held by this type" rejections are reported as input violations. Other errors are logged. The caller sees a generic failure naming only the exception type, or a generic access denial.

## Impact

Affects module maintainers.

- **API change:** `validateInputs()` can now throw unexpected exceptions (e.g. `PluginNotFoundException` for an unknown constraint) instead of converting every `\Exception` into a violation; direct callers must handle them.

## Technical details

In `TypedInputsTrait::validateInputValue()` the typed-data branch's `catch (\Exception $e)` is narrowed to `\InvalidArgumentException | UnexpectedTypeException`. These are the structural rejects, such as an array given for a string, and their messages are still turned into a `ConstraintViolation`. Anything else now propagates out of `validateInputs()`.

Propagated exceptions are handled by the existing paths. `ToolBase::execute()` catches `\Throwable`, logs it, and returns a Runtime failure with the message `Tool execution failed: <ExceptionClass>. The full error has been logged.` (the Runtime-failure message comes from [#3583121](https://www.drupal.org/node/3583121), referenced in the test docblocks). In `ToolBase::access()` a new `catch (\Throwable $e)` logs via `Error::logException()` and returns `AccessResult::forbidden('Tool input validation failed.')` with max-age 0, so access fails closed without exposing the detail.

Tests cover an unknown constraint (`NoSuchConstraint`, throwing `PluginNotFoundException`) in `TypedInputsValidationTest` (exception propagates, Runtime failure, access forbidden and logged once) and in `ToolRunnerTest`, where `ToolRunner::run()` returns a Runtime failure and logs once.

## Upgrade

Code calling `validateInputs()` directly, outside `ToolBase::execute()` or `ToolRunner`, should expect exceptions other than `\InvalidArgumentException` and `UnexpectedTypeException` to propagate rather than appear as violations.
