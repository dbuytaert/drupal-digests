# #3583079: A denied Explorer execute submission reports an internal exception message and still offers the Execute button

- **Project:** Drupal AI
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3583079](https://git.drupalcode.org/project/tool/-/work_items/3583079) · 1 contributor · 2 comments

## Summary

When a user without the right permission tried to execute a tool from the Tool Explorer, the denial page still showed an Execute button, and pressing it produced a second, confusing error exposing an internal developer-facing exception message rather than just the plain access-denied notice. This fix ensures that a denied execution page no longer offers an Execute button, and that submitting a denied (or otherwise un-run) tool reports only the original denial message instead of layering a cryptic internal error on top of it.

## Impact

No upgrade or configuration changes required.

## Technical details

The root cause was that `ToolExecuteForm::buildForm()` unconditionally appended the Execute submit button after the plugin form ran, even when the plugin form's `access()` check had denied execution and returned only denial markup (`access_denied`). Separately, `ToolExecuteForm::submitForm()` unconditionally called `$tool->getResult()` after submission, but `ToolBase::getResult()` throws a `BadMethodCallException` if the tool's `execute()` method never ran, which is exactly the case on a denied submission.

The fix adds two guards in `modules/tool_explorer/src/Form/ToolExecuteForm.php`: `buildForm()` now only adds the `actions.submit` Execute button when `$form['access_denied']` is not set, and `submitForm()` now checks `$tool->hasResult()` before calling `getResult()`, returning early (leaving the plugin form's own denial message as the only reported error) when there is no result to retrieve. Kernel test coverage was added in `ExecuteToolPluginFormTest` (`testDeniedPageOffersNoExecuteButton` and `testDeniedSubmitReportsOnce`) to assert the denial page has no `submit` action and that a denied submission produces exactly one error message with no `::execute()` exception text. The issue notes this flaw predates [#3583077](https://www.drupal.org/node/3583077) (declared-permission pre-checks) but that change made the denial path routine to reach rather than a rare edge case.
