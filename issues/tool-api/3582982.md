## Summary

Items inside list inputs (`ListInputDefinition`) are now validated. Previously a list such as `['not an int', 5]` for an integer list reported no violations, and the tool ran with the bad value. Invalid items now fail validation, so the invoker's correction loop gets a usable error. Messages name the failing position, for example `(item 0)`, so a caller fixing a long list knows which element to change. Tools that relied on lenient list handling, such as a JSON-object string wrapped into an integer list, will now be rejected.

## Impact

No upgrade or configuration changes required.

## Technical details

`TypedInputsTrait::validateInputValue()` branched on `isMultiple()`, but a list definition has `isMultiple()` FALSE and data type `list`. It fell through to `Context::validate()`, which does not surface `ItemList` item violations. The fix adds a branch for `ListContextDefinition` values that validates each item against `getItemDefinition()`. A second branch handles `MapContextDefinition` values: for properties that are multiple or list-typed, it recurses into `validateInputValue()`. Scalar map properties are skipped because `Context::validate()` already covers them, which avoids duplicate violations.

A new `addItemViolations()` helper rewraps each item violation with a message prefix: `(item N)` for list and multiple inputs, `(property name)` for map properties. Nested cases combine both prefixes. The multiple-input branch from [#3582960](https://www.drupal.org/node/3582960) now uses the same helper. Kernel tests were added in `TypedInputsValidationTest` for list items and for lists nested in maps. `InputTypeCoercionTest::testJsonShapeMismatchForList` now expects failure with an "invalid input" message naming `numbers`, instead of success.
