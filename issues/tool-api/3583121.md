## Summary

If an input transform subscriber or a refiner throws before a tool runs, `ToolRunner::run()` no longer lets the exception escape. An `\Error` such as a `TypeError` used to become a fatal at the Drush CLI and abort the whole AI connector batch. A plain `\Exception` used to reach the user with its raw message. Now the run returns a failed invocation that did not execute, with a Runtime failure message naming only the exception class ("Tool execution failed: TypeError. The full error has been logged."). The detail goes to the site log. `drush tool:run` reports these failures as `execution_failed` with that message.

## Impact

Affects module maintainers.

- **API change:** `ToolRunner` constructor takes a fourth argument, the `logger.channel.tool` logger; `tool.runner` service definition updated. `ToolRunCommand` constructor gains the same logger.
- **New API:** `ToolMessages::unexpectedFailure(\Throwable $e)` builds the type-only failure message.

## Technical details

`ToolRunner::run()` gets a final `catch (\Throwable $e)` after the `HandleExceptionInterface` and `InputException` catches. It logs through `Error::logException()` and records a `FailureCategory::Runtime` failure. If a tool was already resolved it uses `setFailureResult()` and returns `ToolInvocation::forTool($tool)`. If not, it returns `ToolInvocation::forFailure()`. If the tool `hasExecuted()`, the throwable is rethrown, so failures after execute() (output transforms) are left to [#3583104](https://www.drupal.org/node/3583104). The message comes from the new `ToolMessages::unexpectedFailure()`, and `ToolBase::execute()` now uses the same helper.

The two in-tree invokers widen their last-resort catch from `\Exception` to `\Throwable`. Both log the exception and surface only the type. In `ToolRunCommand`, a Runtime failure category in the result now maps to `RunErrorType::ExecutionFailed`. Previously everything that was not Access mapped to `InvalidInput`. In the Drush output, the earlier "Error running tool '<id>': <message>" form is replaced by the type-only message. The Drush README and `RunErrorType` docs now describe `execution_failed` as "a bug in the tool or the site", no longer limited to `execute()` throwing.

## Upgrade

Code that constructs `ToolRunner` or `ToolRunCommand` directly must pass the tool logger. The `tool.runner` service definition already does:

```yaml
tool.runner:
  class: Drupal\tool\Tool\ToolRunner
  arguments: ['@plugin.manager.tool', '@account_switcher', '@current_user', '@logger.channel.tool']
```

Scripts that parse `drush tool:run --json` output may now see `error_type: execution_failed` for failures in input transforms or refiners, where this used to be a crash or a raw exception message.
