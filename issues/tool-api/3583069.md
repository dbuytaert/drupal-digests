# #3583069: Align map validation with JSON Schema: a required map may be empty

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3583069](https://git.drupalcode.org/project/tool/-/work_items/3583069) · 1 contributor · 13 comments

## Summary

Tool API publishes a JSON Schema for every tool input and output, but until now its own validation disagreed with that schema for maps: a required map was documented as accepting `{}` but validation rejected it as if it were NULL. This broke real tools, for example `canvas_get_component_schema` in canvas_tools failed for every component without slots or props because that output is a legitimately empty map. This issue aligns map validation with the schema, the same way a companion issue ([#3583040](https://www.drupal.org/node/3583040)) previously did for lists: a required map may now be empty, and only an explicit `NULL` is rejected. Tools that had to declare such maps as optional as a workaround can go back to declaring them required.

## Impact

Affects module maintainers.

- **API change:** A required map input or output now accepts an empty value (`{}`/`[]`); only `NULL` is rejected. Declare `NotBlank` or `Count` on the map to require at least one property, which now publishes as `minProperties` in the JSON Schema (mirroring `minItems` for lists).

## Technical details

The fix mirrors the list treatment from [#3583040](https://www.drupal.org/node/3583040): `EffectiveDataDefinition::createFrom()` no longer marks a `MapDataDefinition` as required (alongside lists), so core typed data adds no `NotNull` constraint to it and an empty map passes. Required is still enforced for `NULL`: `TypedInputsTrait` and `TypedOutputsTrait` explicitly reject a `NULL` value for a required list or map via `ValueViolationsTrait::validateListNotNull()`. Required properties of a map stay protected on a different path: `TypedInputsTrait::validateInputValue()` and `TypedOutputsTrait::validateOutputValue()` walk a map's declared properties directly and report a missing required property before typed-data validation runs, which is what keeps core's known gap (an empty map's properties are never validated, drupal.org [#3256536](https://www.drupal.org/node/3256536)) from reopening.

A related bug in the "multiple" to list conversion was fixed alongside this: `ListDefinitionBase::splitMultipleConstraints()` previously promoted a `NotNull` or non-nullable `NotBlank` found among a multiple's item-level constraints up to the converted list itself, implicitly making the list not empty. Since a multiple's constraints only ever bind its items, that promotion was wrong and is removed; only `Count` still moves to the list.

To let an author still require a genuinely non-empty list or map, `NotBlank` (or `Count`) declared directly on the list or map now normalizes through `ContextDefinitionNormalizer::applyListConstraintSchema()` and `applyMapConstraintSchema()` into `minItems: 1` or `minProperties: 1` in the published schema, and is enforced the same way at validation time.</technical>
<parameter name="upgrade">If a tool declared a map input or output as optional purely to work around the old empty-map rejection, it can be declared required again:

```php
'settings' => new MapOutputDefinition(
  label: new TranslatableMarkup('Settings'),
  description: new TranslatableMarkup('The settings.'),
  required: TRUE,
),
```

If a map or list must never be empty, declare that explicitly instead of relying on `required`:

```php
'nodes' => new ListInputDefinition(
  label: new TranslatableMarkup('Nodes'),
  description: new TranslatableMarkup('The nodes to export.'),
  constraints: ['NotBlank' => []],
  item_definition: new EntityInputDefinition('entity:node', ...),
),
```

`NotBlank` publishes as `minItems: 1` for a list or `minProperties: 1` for a map; `Count` can set an explicit minimum/maximum instead.
