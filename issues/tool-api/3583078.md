## Summary

The Tool module now has one place that runs a tool call: the `tool.runner` service. It checks the declared permission, sets inputs, validates, checks access and executes, in that order, so each caller no longer repeats the sequence. The `tool:run` Drush command and the AI connector now use it. Failure messages changed as a result: for example `Access denied for tool send_email. The 'send emails' permission is required.` and `Invalid input:` followed by the violations. Anyone parsing the old wording needs to adjust. The runner also gives a place to attach future features such as destructive-tool confirmation, at-most-once execution and auditing, but none of those are implemented here. This landed as a first phase: the plugin is still stateful and the invocation object is only a view over the tool instance. The issue's comments, which hold the agreed plan, could not be retrieved, so the summary is based on the merged commit.

## Impact

Affects module maintainers.

- **New API:** New `tool.runner` service (`Drupal\tool\Tool\ToolRunner::run()`) returning a `Drupal\tool\Tool\ToolInvocation`; `drupal:user` added as a dependency of the Tool module.

## Technical details

`ToolRunner::run($tool_id, $values, $configuration, $invoker, $account)` first runs `ToolManager::checkPermission()` against the definition, before any plugin instance exists. It then switches to an explicit `$account` with the account switcher and restores it in a `finally` block. A blocked non-anonymous `UserInterface` account is refused with an Access failure. Inside the switch it creates the instance, calls `setInputValue()` for each value, then `validateInputs()`, `access()` and `execute()`, and finally materializes `getFormattedResult()` so output transforms (handle downcasting) run at execute time. `InputException` and `HandleExceptionInterface` are caught and recorded as `FailureCategory::Input`. Validation and access denials are written to the tool with `setFailureResult()`. Comments in the code mark where an at-most-once claim, destructive confirmation and auditing would attach.\n\n`run()` always returns a `ToolInvocation`, whether the call was denied or completed. It exposes `getResult()`, `getFormattedResult()`, `getInputValue()`, `getInputDefinitions()`, `getTool()` and `hasExecuted()`. `getTool()` is NULL when the call was denied before the tool was instantiated. The class docblock says the per-call state is intended to move into the invocation later.\n\n`ToolRunCommand` no longer switches accounts itself. It passes `account:` to the runner and maps the invocation to output: refusals before execute become `RunErrorType::AccessDenied` or `InvalidInput`, and an exception escaping the runner becomes `ExecutionFailed`. In `tool_ai_connector`, `ToolPluginBase` collects the declared inputs, calls the runner with `ToolAiConnectorInvoker::create()`, adopts the executed instance as its `toolPluginInstance`, and mirrors the transformed inputs into its contexts. The Explorer execute form is not changed in this commit. The developer docs now recommend `tool.runner` and describe the manual sequence for invokers such as the Explorer form that drive the stages themselves.

## Upgrade

Invokers can replace the hand-written sequence with the runner:

```php
$invocation = \Drupal::service('tool.runner')
  ->run('my_tool', values: ['name' => 'value']);
$result = $invocation->getResult();
```

Pass `account:` to run as a specific account. Code or tests matching the old messages (`Tool plugin access denied`, `Tool plugin execution failed`, `Input validation failed for tool ...`) should match `Access denied for tool <id>.` and `Invalid input` instead.
