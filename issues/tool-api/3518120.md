## Summary

The Tool API module can now turn a public method of an existing service into a tool by adding PHP attributes, with no plugin class. The method's parameters become the tool's inputs, its return value becomes the output, and the docblock supplies the descriptions. Access is never inferred. Each tool must declare a permission, an access method, or an entity operation on each entity parameter. Existing `#[Tool]` plugins can also declare a typed `__invoke()` and get the same inference, so they can be converted one definition at a time. This landed in the `1.0.x-dev` release.

## Impact

Affects module maintainers.

- **API change:** `ToolBase::doExecute()` is no longer abstract: a `#[Tool]` plugin may declare a typed `__invoke()` instead. Other changes to existing behavior are listed in the MR.
- **New API:** New attributes `ToolMethod`, `ToolInput`, `ToolEntityInput`, `ToolOutput` and `ToolProperty` in `Drupal\tool\Attribute`, plus `Drupal\tool\Tool\Method\MethodTool` as the plugin class for method tools.

## Technical details

`#[ToolMethod]` goes on a public service method, or on the class of an invokable service, where it applies to `__invoke()`. It requires an explicit `id`, because agent, ECA and MCP configuration refer to tools by ID. `operation` defaults to `ToolOperation::Write`. Access options are `permission` (same syntax as `#[Tool]`) and `access` (a service method returning an `AccessResultInterface`). Every entity parameter must use `#[ToolEntityInput(op: ...)]`, which is checked through the entity's access handler. A method with no declared check fails discovery. An entity operation only counts if it sits on a required, single entity parameter.\n\n`#[ToolInput]` refines a parameter. `#[ToolOutput]` names or refines the output, and two or more declare several outputs. An `array{...}` shape in `@return` also declares several outputs. `#[ToolProperty]` marks the public properties or zero-argument methods of a plain PHP value object to publish. Outputs can narrow to a subset with `members:`.\n\nInference reads native and docblock types: scalars, entities, backed enums, DateTime, lists, and `array{}` shapes. Unsupported parameter types fail discovery.\n\nDiscovery runs in a compiler pass that scans service class sources for the attribute name before autoloading them. It records the results in the `tool.method_tools` container parameter, which the tool manager merges with plugin discovery. A definition that cannot be built is logged to the `tool` channel and skipped. The other tools still load. Definitions are cached, so a new attribute needs a cache rebuild.\n\nA method may return an `ExecutableResult` to set its own message, failure category, or outputs on failure. Throwing `Drupal\\tool\\Exception\\InputException` reports a caller error. Other exceptions are logged and the caller only learns that the run failed. For `#[Tool]` plugins, a typed `__invoke()` is used when `doExecute()` is not overridden, and a plugin that declares `#[ToolEntityInput]` parameters but overrides `access()` is skipped at discovery. The change also adds a docs page, `docs/developers/tool-methods.md`, and a Typed tools section in the creating-a-tool docs.

## Upgrade

To convert an existing `#[Tool]` plugin, replace `doExecute()` and the `input_definitions`/`output_definitions` arrays with a typed `__invoke()`:\n\n```php\n#[ToolOutput(name: 'message')]\npublic function __invoke(string $name, ?string $greeting = NULL): string {\n  return ($greeting ?? 'Hello') . \", $name!\";\n}\n```\n\nThe required `op` on `#[ToolEntityInput]` adds an access check on every entity passed in, so a converted tool can deny calls the old plugin allowed. Throw `InputException` instead of `\\InvalidArgumentException` for messages meant for the caller.
