## Summary

When a tool returns `ExecutableResult::failure()` with values, those values can now be read through `$tool->getOutputValue()` and `getOutputValues()`. Before, only a success published outputs. A caller using the documented accessor after a failure got a `ContextException`, and the values were reachable only through `getResult()->getContextValues()`. A failure can still be partial: a required output it does not carry stays unset, and `getOutputValue()` still throws for that one. `drush tool:run` now prints the outputs a failed tool carried.

## Impact

Affects module maintainers.

- **New API:** After `execute()`, a failed result's declared values are published as outputs, readable via `getOutputValue()`; `getOutputValues()` skips unset outputs on a failed result instead of throwing.

## Technical details

`ToolBase::execute()` no longer returns early from its catch blocks. After any path, it resets `$this->outputs` and copies result context values whose keys are declared in `output_definitions`, for failures as well as successes. On a success, a `setOutputValue()` exception still propagates. On a failure, a value its output cannot store (for example a string for a list output) is logged with `Error::logException()` and left out, so the tool's own failure message is not hidden by an exception. A `@todo` notes that the formatted result still carries such a value (work item 3583124). `failOnOutputViolations()` still runs only on success. When it converts a success into a Runtime failure, it now also clears the outputs, so rejected values are not readable.

`TypedOutputsTrait::getOutputValues()` checks whether the tool is a `ToolInterface` with a result whose status is false. If so, it catches the `ContextException` for an unset required output and omits that key. In every other case it still throws. The `TypedOutputsInterface` docblocks now say that a failure's outputs may be partial. `ToolRunCommand` drops its comment saying a failed tool carries no output values. It already reads `getFormattedResult()->getContextValues()`, so a failure's values now appear in its output. The agent docs and the drush docs were updated to match. Kernel and drush tests were added, using a new `partial_failure_tool` test plugin.

## Upgrade

Callers that guarded output reads with `if ($tool->getResultStatus())` because a failure would throw can now read a failure's outputs. They should expect a required output to be missing on a failure. Use `getOutputValues()`, which skips unset outputs on a failure, or catch `ContextException` around `getOutputValue()`.
