# #3583023: Emit the JSON Schema from tool:info and pass a Drush invoker

- **Project:** Drupal AI
- **Type:** Normal feature request
- **Status:** Fixed
- **Discussion:** [#3583023](https://git.drupalcode.org/project/tool/-/work_items/3583023) · 1 contributor · 14 comments

## Summary

The Tool module's `drush tool:info <id> --format=json` command previously reduced every input and output to a bare data type (`string`, `map`, etc.), with no way to see that a field only accepts a fixed set of values, or what keys a map input expects. Now the JSON output also includes `input_schema` and `output_schema` keys with the full JSON Schema for the tool, so a script or AI agent reading this command's output can discover enum choices, numeric ranges, formats, and nested map properties before invoking the tool. The human-readable table and markdown output formats gained a matching `Constraints` column, and now show map inputs' individual properties as indented sub-rows, so all three output formats stay in sync.

## Impact

Affects module maintainers.

- **New API:** `tool:info --format=json` gains `input_schema` and `output_schema` keys carrying the full JSON Schema (enums, min/max, map properties) for a tool's inputs and outputs, alongside the unchanged flat `inputs`/`outputs` keys.

## Technical details

The fix routes `tool:info` through the same `tool.definition_serializer` (`ToolDefinitionSerializer`) that already powers the MCP bridge and AI connector, instead of hand-building arrays. Because that serializer normalizes a tool instance rather than a bare definition (`ToolDefinitionNormalizeEvent` subscribers key off the invoker), `ToolInfoCommand` now instantiates the tool via a new `Drupal\tool\Drush\DrushInvoker` (`@internal`, ID `drush`, no capabilities) and calls `$serializer->normalizeInputSchema($tool, include_locked: TRUE)` and `normalizeOutputDefinitions($tool)` in a new `buildSchemas()` helper. `ToolRunCommand::executeTool()` was also switched from a bare `createInstance($tool_id)` to passing `DrushInvoker::create()`, so both commands now identify themselves consistently to invoker-aware subscribers. A one-shot Drush invoker declares no capabilities (in particular no `EntitiesAsHandles`), unlike the MCP/AI connector invokers, since a CLI process has no session to hold entity handles.

The table and markdown renderers were reworked around the same schema data via new private helpers (`buildInputRows()`, `buildPropertyRows()`, `summarizeConstraints()`, `schemaType()`) so the three output formats can't drift: `summarizeConstraints()` reads `enum`, `const`, `format`, `pattern`, `minimum`/`maximum`, `min/maxLength`, `min/maxItems` off a schema node, and `buildPropertyRows()` recurses into a map input's `properties` (or a multiple map's `items.properties`) to emit indented `└ property` rows. The `tool.definition_serializer` service is wired with the optional `@?serializer` argument, since Tool doesn't hard-depend on core's `serialization` module; note that in this landed version, if that service is unavailable `ToolDefinitionSerializer` throws `LogicException` and `tool:info` does not catch it (the issue's proposal to degrade gracefully by omitting the schema keys and printing a stderr notice is not present in the merged code). Tests in `ToolInfoCommandTest` were extended against `schema_matrix_tool`, asserting `enum`, `properties`, `required`, and `minimum`/`maximum` show up correctly in `input_schema` while the flat `inputs`/`outputs` keys stay unchanged.
