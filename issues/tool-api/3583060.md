# #3583060: Structure-reading constraints on a map input throw instead of validating

- **Project:** Drupal AI
- **Type:** Minor bug report
- **Status:** Fixed
- **Discussion:** [#3583060](https://git.drupalcode.org/project/tool/-/work_items/3583060) · 1 contributor · 6 comments

## Summary

The Tool module (a contributed module that lets developers define typed, self-contained "tools" callable from Drush, controllers, ECA, AI agents, or MCP servers) had a bug in input validation: a map input (`MapInputDefinition`) whose author declared a structure-reading constraint, such as Symfony's `ComplexData` naming one of the map's own declared properties, would crash with an uncaught `InvalidArgumentException: Property X is unknown.` instead of reporting a normal validation violation. This is now fixed so such constraints validate correctly and report per-property violations as expected. No in-tree or known consumer tool currently declares this kind of constraint, so the practical exposure before this fix was limited to third-party tool authors who did.

## Impact

No upgrade or configuration changes required.

## Technical details

This was the second regression in the same code path. [#3583004](https://www.drupal.org/node/3583004) split map validation out of core's `Context::validate()` into a per-property walk, which silently skipped map-level declared constraints (the map counterpart of the list regression fixed in [#3583048](https://www.drupal.org/node/3583048)). [#3583028](https://www.drupal.org/node/3583028) then restored enforcement of declared constraints, but rebuilt the typed data from a bare `createDataDefinition($definition->getDataType())`, a map with no properties, so any constraint that reads the map's structure (like `ComplexData` naming `sku`) found the property "unknown" and threw outside any catch.

The fix, in `TypedInputsTrait::validateDeclaredConstraints()`, builds the typed data for a `MapDataDefinition` from `EffectiveDataDefinition::createFrom($definition)` instead, which carries the map's declared properties, while a bare data type is still used for lists (no list-level constraint reads items). Each declared constraint is now run individually through `RecursiveValidator::startContext()` as a non-root call rather than delegating to a single recursive `validate()`, so a constraint only visits the members it actually names instead of re-validating every property or descending into entity fields. A new `$members_rejected` flag lets exceptions from a constraint reading a property whose value already failed its own type check be swallowed (the value is already rejected), while exceptions from genuinely misdeclared constraints, such as `ComplexData` naming a property the map does not declare, still throw loudly, consistent with the authoring-mistake ruling from [#3583048](https://www.drupal.org/node/3583048). The regression lineage and the interaction with the earlier required-empty-collection fix ([#3583040](https://www.drupal.org/node/3583040)) and the entity-input change ([#3583028](https://www.drupal.org/node/3583028)) are documented in the updated method docblock.
