## Summary

Five signature and semantic mistakes in the Tool module were corrected before the RC1 freeze, while they could still change without BC handling. `InputDefinition::create()` and its entity, list and map variants now work. `ExecutableResult` no longer throws a `TypeError` when given NULL context values. `ToolOperation::Transform` is now reported as idempotent. `getInputDefinition()` no longer claims to return an exception. `prepareExecutableValue()` is no longer part of the public interface.

## Impact

Affects module maintainers.

- **API change:** `TypedInputsInterface::getInputDefinition()` returns only `InputDefinitionInterface`. `prepareExecutableValue()` is removed from the interface and is now protected in `TypedInputsTrait`. `getExecutableValue()` in the trait types `$skip_validation` as `bool`.
- **New API:** `create()` overrides on `InputDefinition`, `EntityInputDefinition`, `ListInputDefinition` and `MapInputDefinition` now return working input definitions.

## Technical details

`TypedInputsInterface::getInputDefinition()` and the trait implementation now return `InputDefinitionInterface` and document `@throws \Drupal\tool\Exception\InputException`. The union with the exception type was never returned in practice.

`ExecutableResult` is `final readonly`. The constructor still accepts `?array $contextValues`, but now normalizes NULL to `[]` into a separate private `contextValues` property. So `getContextValues()` always returns an array, and `success()`/`failure()` accept NULL safely. The original issue proposed making the parameter non-nullable. What landed is more lenient: NULL is still accepted.

The inherited `ContextDefinition::create()` failed because the constructors require a label and description. It also returned a core `EntityContextDefinition` for `entity:*` types, and that class does not implement `InputDefinitionInterface`. Each class now overrides `create()` with generated default labels and descriptions:
- `InputDefinition::create()` delegates `entity:*` types to `EntityInputDefinition::create()` and otherwise returns `new static`.
- `EntityInputDefinition::create()` accepts both `entity:node` and bare `node`.
- `ListInputDefinition::create()` and `MapInputDefinition::create()` ignore `$data_type`, because their constructors fix the type to `list` and `map`.

`prepareExecutableValue()` is removed from `TypedInputsInterface`. In `TypedInputsTrait` it is now `protected`, and the docblock replaces `{@inheritdoc}`. `getExecutableValue()` in the trait now types `$skip_validation` as `bool`, matching the interface. In `ToolOperation::isIdempotent()`, `Transform` moves to the TRUE arm, so every non-modifying operation is idempotent. Unit tests cover `ExecutableResult`, the `ToolOperation` matrix and the `create()` factories.

## Upgrade

Classes implementing `TypedInputsInterface` without using `TypedInputsTrait` should drop `prepareExecutableValue()` from the interface contract, or keep it as a protected helper. Classes overriding it should change its visibility:

```php
protected function prepareExecutableValue(string $name, InputDefinitionInterface $definition, mixed $value, string $source): mixed
```

Custom `getInputDefinition()` implementations should declare the return type as `: InputDefinitionInterface`. Code that branched on `ToolOperation::Transform->isIdempotent() === FALSE` will now see TRUE.
