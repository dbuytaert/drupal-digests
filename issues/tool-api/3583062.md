# #3583062: Required means present for lists and maps; an explicit NotBlank carries non-empty

- **Project:** Drupal AI
- **Type:** Normal task
- **Status:** Fixed
- **Discussion:** [#3583062](https://git.drupalcode.org/project/tool/-/work_items/3583062) · 1 contributor · 4 comments

## Summary

The Tool module's rule for whether an empty list (`[]`) or map (`{}`) satisfies a `required` input or output has been made consistent. Before this, behavior disagreed depending on how the definition was declared: a required list converted from the older "multiple" style rejected an empty array while a hand-declared required list accepted it, and different schema consumers (the tool-native schema, the MCP bridge, and the ai module's context bridge) disagreed about whether an empty array was even allowed. The rule now applied everywhere, for both lists and maps, and for both inputs and outputs, is that `required` means the value must be present and not `NULL`; an empty array or object still counts as present. A tool author who needs to guarantee a non-empty list or map has to say so explicitly, with a `NotBlank` or `Count` constraint.

## Impact

Affects module maintainers.

- **API change:** A required list or map input or output no longer rejects, or advertises as non-empty, an empty array or object by itself; add `NotBlank` or `Count` to require a non-empty value, which is what is now advertised as `minItems`/`minProperties`.

## Technical details

`ListDefinitionBase::splitMultipleConstraints()` (`src/TypedData/ListDefinitionBase.php`) no longer infers a list-level `NotNull` from a converted multiple's `NotNull` or `NotBlank`; it moves only `Count` to the list, leaving every other constraint, `NotBlank` included, bound to the item. `EffectiveDataDefinition::createFrom()`, which builds the typed-data definition `TypedInputsTrait`/`TypedOutputsTrait` actually validate against, now withholds the `required` flag from maps the same way it already did for lists, so typed data's automatic `NotNull` default constraint never reaches a list or map's effective definition. `TypedInputsTrait::validateInputValue()` rejects an explicit `NULL` for a required list or map itself (via `validateListNotNull()`) while letting an empty array or object through.

On the schema side, `ContextDefinitionNormalizer::applyListConstraintSchema()` and the new `applyMapConstraintSchema()` (`src/Normalizer/ContextDefinitionNormalizer.php`) only emit `minItems`/`minProperties: 1` when the definition carries an explicit `NotBlank`, not merely because it is `required`, removing the tool-side inference that a required multiple implies a non-empty array. `tool_ai_connector`'s `ToolContextDefinitionTrait::toListDefinition()` was updated the same way: a list-level `NotBlank` is treated as author-declared only, never something the ai-context adapter infers.

This settles the "open question" the issue raised about maps by extending the existing list/output rule (`required` means present, not empty, per the earlier [#3583040](https://www.drupal.org/node/3583040)) uniformly to maps and to the input direction, rather than adopting the input-specific "reject empty" rule this issue's body had proposed.

## Upgrade

To require a non-empty list or map input (or output), declare `NotBlank` (or `Count` for bounds) explicitly; `required` by itself no longer implies it:

```php
'nodes' => new ListInputDefinition(
  label: new TranslatableMarkup('Nodes'),
  description: new TranslatableMarkup('The nodes to export.'),
  constraints: ['NotBlank' => []],
  item_definition: new EntityInputDefinition('entity:node', ...),
),
```

This is advertised in the generated JSON Schema as `minItems: 1` (or `minProperties: 1` for a map), rather than being inferred from `required`.
