# #3583040: A required list rejects the empty array its JSON Schema allows

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Version:** 1.0.x-dev
- **Status:** Fixed
- **Discussion:** [#3583040](https://git.drupalcode.org/project/tool/-/work_items/3583040) · 1 contributor · 9 comments

## Summary

Tool API's validation for required list inputs and outputs previously disagreed with the JSON Schema it publishes. A required list (for example, search results, validation problems, or changed IDs) is advertised in the schema as accepting an empty array, but validation rejected `[]` with "This value should not be null." This meant a tool could return a valid empty result and still fail its own output validation, or a client following the published schema could send a value the tool would reject anyway. Validation now matches the schema: a required list accepts `[]`, and only `NULL` (a genuinely missing value) is rejected. Required maps are unaffected: an empty object still fails validation as before.

## Impact

Affects module maintainers.

- **API change:** A required list input or output (`OutputDefinition`/`InputDefinition` with `multiple: TRUE`, or `ListInputDefinition`/`ListOutputDefinition`) now validates successfully when set to an empty array `[]`; only `NULL` is rejected. Required maps are unchanged and still reject an empty value.

## Technical details

The root cause is core's `NotNullConstraintValidator`, which Tool API inherits as a default constraint whenever a definition is marked required. That validator treats any empty `ListInterface` or `ComplexDataInterface` as `NULL` before checking for nullness, so an empty list tripped the same rejection as a genuinely missing value, even though typed data's "not empty" reading of required diverges from JSON Schema's "key is present" reading.

The fix is in `EffectiveDataDefinition`: when building the effective typed data definition for validation, a list definition (anything implementing `ListDataDefinitionInterface`) is no longer marked required, which keeps core's `NotNull` off of it entirely. `TypedInputsTrait::validateInputValue()` and `TypedOutputsTrait::validateOutputValue()` each detect the case that `NotNull` would otherwise have caught (a `NULL` value against a required list definition) and explicitly run a `NotNull` check via the new `ValueViolationsTrait::validateListNotNull()`, so a `NULL` list is still rejected with the same message as before. Maps keep their required flag unchanged: they're objects with named properties rather than sequences, and core already skips validating the properties of an empty map (drupal/drupal[#3256536](https://www.drupal.org/node/3256536)), so an empty required map still fails.

A tool that needs at least one item still declares that explicitly with a `Count` constraint, which the normalizer publishes as `minItems` in the JSON Schema, for example `constraints: ['Count' => ['min' => 1]]`.</technical>
<parameter name="upgrade">If a tool relies on a required list rejecting an empty value, add an explicit `Count` constraint rather than depending on the removed implicit behavior:

```php
new InputDefinition('entity:node', 'Nodes', 'The nodes to export.', required: TRUE, multiple: TRUE, constraints: ['Count' => ['min' => 1]]);
// {"type": "array", "minItems": 1, ...}
```

No changes are needed for tools that already treat an empty required list as valid, or for required maps, whose validation is unchanged.
