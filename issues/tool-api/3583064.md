# #3583064: Declare permissions on a tool definition for static access checks

- **Project:** Drupal AI
- **Type:** Normal feature request
- **Status:** Fixed
- **Discussion:** [#3583064](https://git.drupalcode.org/project/tool/-/work_items/3583064) · 1 contributor · 4 comments

## Summary

The Tool module (an API for defining executable "tools", used for things like AI agent/MCP integrations) lets a tool plugin declare the permission an account needs to run it, directly on the `#[Tool]` attribute, instead of writing that check by hand inside `checkAccess()`. A new static check on the tool manager can test that declared permission against an account straight from the tool's definition, without creating an instance of the tool. This means a picker or a listing that advertises many tools to a user can filter out the ones they cannot run cheaply and with a cacheable result, rather than having to instantiate every tool and supply input values just to find out. Tools that declare no permission behave exactly as before.

## Impact

Affects module maintainers.

- **API change:** `ToolBase::checkAccess()` is no longer abstract: it now has a default implementation that allows access when the tool declares a permission, and `ToolBase::access()` composes the new permission check with `checkAccess()` via `andIf()` instead of calling `checkAccess()` alone.
- **New API:** `#[Tool(permission: ...)]` attribute parameter and `ToolManager::checkPermission(ToolDefinition $definition, AccountInterface $account)` let code check a tool's required permission from its definition alone, without instantiating the plugin.

## Technical details

The attribute gains a `permission` string parameter, exposed on `ToolDefinition::getPermission()`/`setPermission()` (derivers can set it per derivative). It follows the syntax of a route's `_permission` requirement: names joined with `,` are all required, names joined with `+` are OR'd, and mixing both operators in one string is rejected. The actual implementation differs from the issue's original proposal of a `permissions` array plus a `checkPermissionAccess()` method: what landed is a single route-style string and a static `ToolManager::checkPermission(ToolDefinition $definition, AccountInterface $account): AccessResultInterface`, which parses the string and delegates to `AccessResult::allowedIfHasPermissions()`, carrying `user.permissions` cacheability.

`ToolBase::access()` now runs this permission check first, short-circuiting before input resolution/validation, then `andIf`s it with the result of `checkAccess()`. `checkAccess()` is no longer `abstract`: its default implementation just allows when the definition declares a permission, so a purely permission-gated tool needs no override at all; an override still runs and its result is combined with the permission check, so it can only add restrictions, not bypass the declared permission. A bare `bool` returned from `checkAccess()` is wrapped with `setCacheMaxAge(0)` before being combined, since a bool carries no cacheability metadata of its own.

`ToolManager::processDefinition()` adds two discovery-time guards, thrown as `InvalidPluginDefinitionException` when the plugin cache rebuilds: a permission string mixing `,` and `+` fails immediately, and a tool that declares no permission and overrides neither `checkAccess()` nor `access()` (i.e. has no access rule at all) is rejected, replacing what used to be a hard PHP fatal from the removed abstract method. `drush tool:info` and the Tool Explorer UI both print the declared permission and flag names that match no defined permission.

## Upgrade

A tool whose access rule is only a permission check can drop its `checkAccess()` override and declare it on the attribute instead:

```php
#[Tool(
  id: 'my_tool',
  // ...
  permission: 'administer users',
)]
final class MyTool extends ToolBase {
  // No checkAccess() override needed.
}
```

Multiple required permissions: `permission: 'administer users,access administration pages'`. Any-of: `permission: 'operate test tools+audit test tools'`. An override of `checkAccess()` no longer needs to re-check the declared permission itself: `access()` already requires it before `checkAccess()` runs, and the override's result is combined with `andIf()`.
