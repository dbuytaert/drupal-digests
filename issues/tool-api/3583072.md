# #3583072: The schema of an optional enum input allows null in its type but not in its enum, so null is rejected

- **Project:** Drupal AI
- **Type:** Major bug report
- **Status:** Fixed
- **Discussion:** [#3583072](https://git.drupalcode.org/project/tool/-/work_items/3583072) · 1 contributor · 5 comments

## Summary

Optional tool inputs that are restricted to a fixed set of values (via Symfony's `Choice`/`AllowedValues` constraints, a derived `PluginExists` enum, or an `IdenticalTo` constant) advertised a JSON Schema that contradicted itself: the schema's type allowed `null`, but its `enum` or `const` keyword did not, so any JSON Schema validator rejected a `null` value even though Tool API itself accepted it for an optional input. In practice, MCP clients validate `tools/call` arguments against the published schema before the call ever reaches the tool, so a model sending `null` for an optional enum input it didn't want to set (ordinary, expected behavior) got its call rejected with a JSON-RPC error. This is now fixed: an optional input's schema lists `null` as an allowed enum value (or widens a `const` to an enum of the constant and `null`), so the published schema matches what the tool actually accepts.

## Impact

Affects module maintainers.

- **API change:** Optional inputs with a `Choice`/`AllowedValues`/`PluginExists` constraint now advertise `null` as a listed `enum` value, and an optional `IdenticalTo`-constrained input's `const` is widened to `enum: [<const>, null]`, so the published JSON Schema matches what Tool API already accepted for those inputs.

## Technical details

The fix lives in `ContextDefinitionNormalizer::allowNullValue()`, called from the optional-input branch that already appends the null type (or `oneOf` null branch on Drupal 11.1+). When the input is optional and not excluded by `NotNull`/non-nullable `NotBlank`, the new method widens the value keywords to agree with the type: if `const` is set it becomes `enum: [<const>, null]`; if `enum` is set and lacks `null`, `null` is appended. This covers both the legacy `type: [string, null]` array and the newer `oneOf` composition without per-core branching, and applies uniformly to `Choice`/`AllowedValues`-derived enums, `PluginExists`-derived enums, and `IdenticalTo`-derived `const` values.

A separate but related gap was closed in `SchemaToolsPropertyConverter::prepareAiPropertySchema()`, used when rendering schemas for AI providers that require a flattened (non-union) `type`: since that flattening drops the `null` type member, any `null` left in `enum` would then mismatch the flattened type and be rejected by strict providers, so it now strips `null` from `enum` (and drops `enum` entirely if that empties it) after flattening.

Test coverage was updated accordingly: `InputSchemaMatrixTest`'s `enum_string`/`enum_integer` expectations now include `null`, `RicherSchemaEmissionTest` checks that an optional `IdenticalTo` widens `const` to an `enum` with `null` (while a required one keeps a plain `const`), and a new `AdvertisedSchemaAcceptanceTest::testNullIsAcceptedWhereTheSchemaOffersIt()` iterates every discovered tool's optional inputs whose schema allows the null type and asserts both that a JSON Schema validator accepts a `null` value and that Tool API's own `validateInputValue()` raises no violation for it, closing the gap that the prior sampled round-trip test never exercised the null branch.
