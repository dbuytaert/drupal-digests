## Summary

`InputDefinition::fromDataDefinition()` in the Tool module now accepts plain typed-data definitions that have no label, and plain list definitions. Previously an unlabeled definition crashed with a `TypeError`. A plain `ListDataDefinition` produced an item input definition whose data type was NULL. Tools and code that build inputs from typed-data definitions now get a working `InputDefinition`, with an item type such as `string` for lists. The config-schema path was not affected.

## Impact

No upgrade or configuration changes required.

## Technical details

The factory passed `$definition->getLabel()` (NULL when unset) to constructors that require `string|TranslatableMarkup`. It also read `$definition->toArray()['type']`, which is missing on list item definitions. The fix computes `$data_type` as `$definition_array['type'] ?? $definition->getDataType()`. When there is no label, it generates `new TranslatableMarkup('@type input', ['@type' => $data_type])`. That label is used for the map, list and scalar branches. The default description now interpolates this resolved label instead of the raw, possibly NULL one. Two kernel tests were added to `InputDefinitionFactoryTest`: `testFromDataDefinitionList` and `testFromDataDefinitionWithoutLabel`. The second asserts the generated label is `integer input`.
