# #3583025: Show requirement status in tool:info, tool:list, and tool:search

- **Project:** Drupal AI
- **Type:** Normal feature request
- **Status:** Fixed
- **Discussion:** [#3583025](https://git.drupalcode.org/project/tool/-/work_items/3583025) · 1 contributor · 14 comments

## Summary

The Tool module's Drush commands now show whether each tool is actually ready to run. `drush tool:list` and `drush tool:search` gain a `Requirements` column showing `Met` or the reason it is not (for example, a missing API key), plus a new `--unmet` option (`show`, the default; `hide`; or `only`) to filter the listing. `drush tool:info` gains a `Requirements:` line in its table and markdown output, and a `requirements` key (`{"met": ..., "message": ...}`) in its JSON output. Previously a builder had no way to see a tool would fail until they actually ran it with `tool:run`; now the listing and info commands surface that up front. None of the commands change their exit code based on requirement status: `tool:list` and `tool:search` still exit `0` for an empty or fully-filtered result, and `tool:info` still exits `0` for a tool whose requirements are unmet, since these commands answer "what exists" and "what is this", not "can it run".

## Impact

Affects module maintainers.

- **New API:** `tool:list`, `tool:search`, and `tool:info` Drush commands report each tool's `checkRequirements()` status; `tool:list`/`tool:search` gain a `--unmet=show|hide|only` filter option and `tool:info --format=json` gains a `requirements` key.

## Technical details

The three commands share one probe: the new `@internal` `Drupal\tool\Drush\RequirementStatus` value object. Its static `forTool()` instantiates the plugin via `ToolManager::createInstance()` (passing a `DrushInvoker`) and calls `checkRequirements()`. A caught `RequirementsException` produces an unmet status carrying the exception message; any other `\Throwable` (for example a broken `create()`) is also caught and reported as unmet with a `Could not instantiate tool: ...` message, so one plugin with a broken service dependency cannot take down the entire listing. `label()` renders `Met` or the message for table/markdown output, and `toArray()` produces the JSON shape.

`ToolOutputTrait` gained `requirementStatuses()` (probes every listed definition) and `filterByRequirementStatus()`, driven by the new `@internal` `UnmetFilter` enum (`Show`, `Hide`, `Only`), whose `keeps()` method encodes the filtering logic and whose `tryFrom()` validates the raw `--unmet` option value, exiting `1` with the same message shape as an invalid `--operation` on failure. `ToolInfoCommand::buildSchemas()` now returns `NULL` instead of throwing when `createInstance()` fails, so `tool:info` on a tool whose `create()` throws still reports its status and omits `input_schema`/`output_schema` rather than erroring out.

The test module `tool_test` gained `broken_constructor_tool`, a plugin whose `create()` unconditionally throws, used to exercise the instantiation-failure path in the new `RequirementStatusTest` and in the command kernel tests. This work builds on the `DrushInvoker` machinery introduced in [#3583023](https://www.drupal.org/node/3583023).

## Upgrade

No upgrade steps are needed for module users; this only adds output and an option to existing Drush commands. Scripts parsing `tool:info --format=json` can now read the new `requirements` key:

```json
"requirements": {"met": false, "message": "Test API key is not configured."}
```

Scripts parsing `tool:list`/`tool:search` table or markdown output should account for the new `Requirements` column inserted after `Operation`.
