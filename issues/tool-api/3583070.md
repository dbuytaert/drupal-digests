## Summary

Tool definitions can now describe an object keyed by names that are not known in advance, such as an entity reference's `target_bundles` (bundle ID to bundle ID) or an image style's `effects` (keyed by UUID). Before, these config sequences were always derived as lists and published as a JSON array. Strict clients then rejected the object the setting needs, or sent a list that lost the names. A map-shaped value sent anyway was wrapped into a one-item list. Such maps are now published as a JSON object, each value is validated against the item type, and an empty map is sent as `{}`. Existing list derivations are unchanged unless a sequence is marked or named as keyed.

## Impact

Affects module maintainers.

- **API change:** `InputDefinition::fromConfigSchema()` and `fromDataDefinition()` take a new optional `$keyed_sequences` argument; a sequence with `orderby: key` is now derived as a `MapInputDefinition` instead of a `ListInputDefinition`.
- **New API:** `MapInputDefinition` and `MapOutputDefinition` accept an `item_definition` (with `getItemDefinition()`, `setItemDefinition()`, `getItemValues()` on `MapDefinitionBase`), published as `additionalProperties`.

## Technical details

`MapDefinitionBase` gains an optional item definition, which describes every key the map does not declare. `MapInputDefinition` and `MapOutputDefinition` take it as a new last constructor argument, `item_definition`, and each enforces its own input or output interface. A map can declare properties and an item definition together: declared keys use their own definitions and all other keys use the item definition. The JSON schema normalizer (`InputOutputDefinitionNormalizer`) emits `additionalProperties` with the item schema. `TypedInputsTrait` and `TypedOutputsTrait` validate the undeclared keys against the item definition. `RecursiveToolValueTransformSubscriber` transforms each item. For outputs, a null in an optional item is dropped. A map whose keys run 0, 1, 2 is returned as an `ArrayObject`, so it is encoded as an object rather than a JSON array ([#3583073](https://www.drupal.org/node/3583073)).

In `InputDefinition::fromDataDefinition()`, a config `sequence` becomes a `MapInputDefinition` when it has `orderby: key`, or when the caller names its property path in the new `$keyed_sequences` argument. Otherwise it stays a `ListInputDefinition`. Paths use dots between property names, `*` for the items of a sequence, and an empty string for the definition itself. `fromConfigSchema()` takes the same argument. Config schema does not mark keyed sequences in general, so the caller has to name them.

Other changes: `InputTypeCoercionSubscriber` now treats a JSON string starting with an opening brace as a map even when its keys decode to a sequential array (object keys 0 and 1). `OutputTypeCoercionSubscriber` leaves a list-keyed map with an item definition to the recursive walk. `OutputDefinition::fromContextDefinition()` carries the item over. The refiner check in `TypedInputsTrait` applies the item-type narrowing rule to keyed maps. `ToolInfoCommand` prints an `example_key` example for such a map. The docs gain a "Maps keyed by name" section.

## Upgrade

To declare a map keyed by name:

```php
'target_bundles' => new MapInputDefinition(
  label: new TranslatableMarkup('Target bundles'),
  description: new TranslatableMarkup('The bundles to reference, keyed by bundle ID.'),
  item_definition: new InputDefinition(
    data_type: 'string',
    label: new TranslatableMarkup('Bundle'),
    description: new TranslatableMarkup('A bundle ID.'),
  ),
),
```

To derive keyed sequences from config schema, name them in the second argument:

```php
$settings = InputDefinition::fromConfigSchema(
  ['type' => 'entity_reference_selection.default'],
  ['target_bundles'],
);
```

A refiner must not change the item data type of a list or keyed map (for example string to integer), or it throws a `LogicException`.
