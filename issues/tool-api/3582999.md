## Summary

Tools with a multi-value map input, such as `tool_belt:field_set_value` on a multi-value field, now accept a single item given as its property map, for example `{"target_id": 1}`. Before, this threw an `InputException` saying values must be an associative array. Callers had to know to send `[{...}]`. A single map is now treated as one item and wrapped automatically. Lists of maps and empty arrays behave as before.

## Impact

No upgrade or configuration changes required.

## Technical details

The list-wrapping guard in `InputTypeCoercionSubscriber` only wrapped values that were not arrays. A property map is a PHP array, so it passed through unwrapped and typed data rejected it. The condition is now `$is_list && (!\is_array($value) || !\array_is_list($value))`. Scalars and non-list arrays are wrapped in a single-item array. `array_is_list([])` is TRUE, so an empty array is left as an empty list. The wrap happens before child dispatch, so nested properties are still coerced (`'7'` becomes `7`).

One side effect: an array with non-sequential integer keys, such as `[1 => [...]]` (what a JSON object like `{"1": {...}}` decodes to), is now wrapped. It then fails validation with a clear message. Before, it was silently read as a delta-keyed list.

The issue notes that `decodeJsonStructure()` has a matching gap. A JSON string holding a single object is still rejected, and it is left for a follow-up. The test tool `CoercionTestTool` gained a multiple `variants` map input and output. Three new `InputTypeCoercionTest` cases cover a single map, a list of maps, and an empty array. The issue says the fix was verified only through this synthetic tool, not end to end against a real multi-value field.
