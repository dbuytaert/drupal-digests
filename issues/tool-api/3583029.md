# #3583029: Enforce required outputs in ToolBase::execute() so a success cannot omit a declared output

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3583029](https://git.drupalcode.org/project/tool/-/work_items/3583029) · 1 contributor · 18 comments

## Summary

The Tool API's `OutputDefinition` has always defaulted `required` to `TRUE`, but nothing enforced it: a tool could return `ExecutableResult::success()` without setting one of its own required outputs and `execute()` would report success anyway. A caller would only discover the problem later, either from an exception when reading the missing value or, worse, not at all if it just read the raw context values off the formatted result. Now `execute()` validates the outputs right after a successful `doExecute()` and, if a required output is missing or a set value doesn't match its declared shape, replaces the result with a failure categorized as `Runtime` and logs the violation against the tool. This closes the gap that had forced the MCP Server Tool Bridge module to omit `required` from the JSON Schema it advertises for tool outputs, since it could not promise something the Tool API itself did not guarantee.

## Impact

Affects module maintainers.

- **API change:** `ToolBase::execute()` now fails a tool (with `FailureCategory::Runtime`) instead of silently succeeding when a `doExecute()` implementation omits a declared required output, sets it to `NULL`, or sets a value that violates its output definition.

## Technical details

The check lives in a new private `ToolBase::failOnOutputViolations()`, called from `execute()` immediately after the loop that copies matching context values into `$this->outputs`. It calls the existing `validateOutputs()` and, if the returned `ConstraintViolationList` is non-empty, logs the violation against the tool's plugin ID and overwrites `$this->result` with `ExecutableResult::failure(..., FailureCategory::Runtime)`, since a missing or malformed output is a bug in the tool, not something the caller can fix by changing its arguments.

`TypedOutputsTrait::validateOutputs()` was rewritten to check shape as well as presence: an output whose `Context::hasContextValue()` is false now counts as unset (previously only a wholly-absent key did, so a required output explicitly set to `NULL` slipped through), and each set value is run through a new private `validateOutputValue()` that mirrors `TypedInputsTrait::validateInputValue()`. Multiple-value and `ListOutputDefinition` outputs are checked item by item with the failing index named in the message; `MapOutputDefinition` properties are checked individually, with missing required properties reported by name; and entity-typed outputs (data type `entity` or `entity:*`) are only checked for being an `EntityInterface` instance, not run through full entity field validation, so a tool that merely returns an entity it loaded is not failed for that entity's own data problems. The item/property-naming helper and the core `TypedDataManager` prototype-cache workaround (for the upstream bug in drupal/drupal[#3616328](https://www.drupal.org/node/3616328)) were extracted from `TypedInputsTrait` into a new shared `ValueViolationsTrait`, used by both input and output validation.

Test coverage was added via two new fixture plugins, `RequiredOutputTool` and `EntityOutputTool`, plus `tests/src/Kernel/Tool/OutputValidationTest.php` and additions to `ToolBaseTest`, covering a missing or `NULL` required output failing with the output named, an omitted optional output still succeeding, an invalid output value failing the same way, and entity outputs being validated by shape rather than by full field validation.

## Upgrade

Any tool plugin whose `doExecute()` can return a success without setting a value for one of its declared `output_definitions` will now fail instead. For each such output, either always set it:

```php
protected function doExecute(array $values): ExecutableResult {
  // Make sure every required output is set on every success path.
  return ExecutableResult::success($message, ['answer' => $computed_value]);
}
```

or mark it optional in the plugin's `output_definitions` if it legitimately may not always have a value:

```php
output_definitions: [
  'link' => new OutputDefinition(
    data_type: 'uri',
    label: new TranslatableMarkup('Link'),
    description: new TranslatableMarkup('An optional uri output.'),
    required: FALSE,
  ),
],
```
