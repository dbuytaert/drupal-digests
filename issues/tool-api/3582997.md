## Summary

Tool inputs of type `datetime_iso8601` can now declare whether they hold a date only or a full datetime. Before, every value was rewritten to a full ISO 8601 timestamp, so a bare date like `2026-08-12` became `2026-08-12T00:00:00-06:00`. Date-only fields then rejected it. The JSON Schema shown to MCP clients and LLMs also always said `date-time`, which encouraged clients to send full timestamps. Bare dates now pass through unchanged. Date-only inputs coerce other formats to `Y-m-d`. The schema reports `date` or `date-time` according to the declared flavor.

## Impact

Affects module maintainers.

- **API change:** `datetime_iso8601` inputs with no marker constraint no longer get `format: "date-time"` in the generated JSON Schema, and bare `Y-m-d` values are no longer coerced.
- **New API:** New `DateOnly` and `DateTime` validation constraint plugins in the Tool module, used as markers on `datetime_iso8601` input definitions.

## Technical details

Both date-only and datetime fields share the `datetime_iso8601` typed data type, so the property definition had no way to tell them apart. The commit adds two constraint plugins, `DateOnly` (`DateOnlyConstraint`) and `DateTime` (`DateTimeConstraint`), under `Drupal\tool\Plugin\Validation\Constraint`. They are attached through the `constraints` key of an `InputDefinition`.

`InputTypeCoercionSubscriber` now returns early for strings matching `/^\d{4}-\d{2}-\d{2}$/`. Other parseable strings are formatted as `Y-m-d` when the definition has a `DateOnly` constraint. Otherwise they are formatted as `c`, as before. `ContextDefinitionNormalizer` emits `format: "date"` for `DateOnly` and `format: "date-time"` for `DateTime`. With neither constraint it emits no `format`. That last case is a behavior change for existing `datetime_iso8601` definitions.

The issue describes the constraints as no-op markers. The shipped code also includes validators. `DateOnlyConstraintValidator` requires a string in `Y-m-d` form that passes `checkdate()`. `DateTimeConstraintValidator` requires a string that `DateTimeImmutable` can parse, and bare `Y-m-d` is accepted. Empty values pass both. The diff also adds `constraints: ['DateTime' => []]` to a datetime input in an existing tool plugin. The diff does not show which file that is. Per the issue, `tool_belt`'s `FieldSetValue` is meant to choose the constraint from `$field_definition->getSetting('datetime_type')`. That change is not in this commit.

## Upgrade

To get correct coercion and schema format, add a marker constraint to your `datetime_iso8601` input definitions. This is the form the diff uses:

```php
new InputDefinition(
  data_type: 'datetime_iso8601',
  label: new TranslatableMarkup('Published at'),
  required: FALSE,
  constraints: ['DateTime' => []],
),
```

Use `'DateOnly' => []` for date-only values. Inputs with neither constraint now get no `format` in their schema.
