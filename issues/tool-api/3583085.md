# #3583085: Tell callers which input a failed tool call is about

- **Project:** Drupal AI
- **Type:** Normal unknown (0)
- **Status:** Fixed
- **Discussion:** [#3583085](https://git.drupalcode.org/project/tool/-/work_items/3583085) · 1 contributor · 5 comments

## Summary

When a tool call fails on bad input, the failed result now says which input was at fault, as data rather than only inside the message text. A client such as an MCP agent can read the input name and pass it back to the model for a retry. A tool that checks several inputs together, such as an end date that must follow a start date, can now name the input it is complaining about. Failure messages are reworded to show each problem as `input_name: reason`, with the duplicate naming removed.

## Impact

Affects module maintainers.

- **API change:** `InputException` now extends `\InvalidArgumentException`, and `getExecutableValues()`/`getExecutableValue()`/`setConfigurationValue()` throw it (with violations) instead of a bare `\InvalidArgumentException`. `ToolResultInterface` gains a method, and `ToolInterface::setFailureResult()` gains an optional third `$violations` parameter. Failure message text changed: the `Input @name:` and `The @label input is invalid:` wrappers are gone, replaced by a `name: reason` line prefix, and `Tool execution failed due to invalid input:` became `Invalid input:`.
- **New API:** `ToolResultInterface::getViolations()` on results, `InputException::getViolations()`, `getInputNames()`, `fromViolations()`, and an `inputNames` constructor argument; `ToolMessages::invalidInput()` added.

## Technical details

`validateInputValues()` in `TypedInputsTrait` now keeps each violation's message as the reason alone and sets its property path to the input's machine name, joined to any inner path via the new `ValueViolationsTrait::joinPath()` (for example `product.sku`). The per-violation wrappers `Input @name:` and `The @label input is invalid:` are removed, and several other messages dropped their label (`This input is locked...`, `This property is required.`, `This input must be an entity.`). `ToolMessages::violationList()` now prefixes each line with its path, so text output reads `recipient: This value should not be null.`. A new `ToolMessages::invalidInput()` supplies the single `Invalid input:` message template used by `ToolRunner`, and `ToolBase::execute()`.

`InputException` now takes a named `inputNames` argument (`new InputException($message, inputNames: ['end_date'])`; the issue text called it `inputs`, but the merged code uses `inputNames`). Each name becomes a violation with the reason as message and the name as path. `InputException::fromViolations()` wraps validation violations, and `getViolations()` and `getInputNames()` read them back. `MarkupInterface` messages are converted to plain text once in the constructor. `ExecutableResult::failure()` and the constructor accept an optional violation list, exposed by the new `getViolations()` on `ToolResultInterface` (also forwarded by `FormattedExecutableResult`). It is empty for a success or a failure without violations. `ToolBase::execute()` catches `InputException` separately and fills the result's violations from it. A bare `\InvalidArgumentException` thrown by tool code still fails as input, with message `Invalid input: @message` and no violations. List item and map property positions still appear in the message text rather than on the path; that is left to [#3583065](https://www.drupal.org/node/3583065).

## Upgrade

Tools that validate across inputs should name the input when throwing:

```php
throw new InputException(new TranslatableMarkup('The end date must be after the start date.'), inputNames: ['end_date']);
```

Pass `TranslatableMarkup` objects directly, not cast to string. Code or tests that match on the old text (`Input recipient: ...`, `The X input is invalid: ...`, `Tool execution failed due to invalid input: ...`) should read the input from `$result->getViolations()` (`getPropertyPath()`) or expect the new `name: reason` lines under `Invalid input:`. Any custom `ToolResultInterface` implementation must add `getViolations()`, and any `ToolInterface::setFailureResult()` override must accept the new optional `?ConstraintViolationListInterface $violations = NULL` parameter.
