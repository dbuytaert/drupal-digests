## Summary

Violations returned by a tool's `validateInputs()` now keep their constraint. A required input with no value reports a `NotNull` constraint, so callers can tell it apart from a `Choice` or other failure by calling `getConstraint()`. A kernel test now covers this for top-level inputs, list items and map properties.

## Impact

No upgrade or configuration changes required.

## Technical details

The issue described a bug in the code that rebuilds violations to put the input name on the property path. It passed `getCause()` where `ConstraintViolation::__construct()` expects the constraint, so `getConstraint()` returned NULL. The commit message and the new test's docblock say the constructor argument fix for `validateInputValues()` and the list item and map walkers landed with [#3583065](https://www.drupal.org/node/3583065). The diff for this commit therefore contains only the remaining gap in `TypedInputsTrait::validateInputValues()`. The special-case violation for a required input with a NULL value, which replaces the typed-data detail with an instruction, now passes `new NotNull()` as the constraint argument. It still carries the entity type check code from [#3583083](https://www.drupal.org/node/3583083) for single entity inputs.

The commit adds `RebuiltViolationConstraintTest`, a kernel test that goes through `validateInputs()`. It checks the constraint class and the property path (for example `subject.1`, `subject.status`, `subject.rows.1.status`) for `NotNull` and `Choice` failures. It also checks that two failures on one tool report different constraint classes.
