## Summary

In the `tool_ai_connector` submodule, reading a tool function call's readable output before the tool had run could throw a `BadMethodCallException`. This happened, for example, when a function call was restored from serialized state with its earlier output re-applied. The readable output now returns the stored string in that case, and no exception is thrown.

## Impact

No upgrade or configuration changes required.

## Technical details

`Drupal\tool_ai_connector\Plugin\AiFunctionCall\ToolPluginBase` overrides `getReadableOutput()` and ignored the `$stringOutput` that `FunctionCallBase::setOutput()` populates, so it always recomputed from the underlying tool instance. That instance is created lazily and un-executed, and `ToolBase::getResult()` throws when called before `execute()`. The fix makes `getReadableOutput()` return `$this->stringOutput` first when it is non-empty, which matches the `FunctionCallBase` contract. Otherwise it still delegates to `getStructuredOutput()`. `execute()` now resets `$this->stringOutput = ''` at its start, so a fresh run does not return stale restored output. `getStructuredOutput()` is unchanged and still reports 'Tool has not executed yet.' for an un-executed tool. A kernel test, `testSetOutputStringIsHonoredByReadableOutput()`, covers the restore-then-execute sequence.
