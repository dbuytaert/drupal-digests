## Summary

Tool inputs of type `decimal` now accept bare JSON numbers such as `19.99` or `5`, which are converted to strings (`"19.99"`, `"5"`) before validation. Decimals are carried as strings to preserve precision, but their schema looks numeric, so models often send plain numbers. Those values used to fail validation and force a retry. Non-numeric values such as arrays still fail validation.

## Impact

No upgrade or configuration changes required.

## Technical details

The change is in `InputTypeCoercionSubscriber`, in the input transform handler, and runs before the existing numeric-string coercion. For `decimal` data types, `int` values are cast directly with `(string)`. `float` values go through a new private `formatDecimalString()`, because a plain cast can give exponent notation such as `1.0E-7`, which decimal validation rejects. The helper uses `number_format()` with 14 decimal places, trims trailing zeros and any trailing dot, and returns `0` for an empty or `-` result. So `0.1 + 0.2` becomes `0.3` and `0.0000001` becomes `0.0000001`. Floats with more than 14 significant decimal places are rounded. Kernel coverage is in `InputTypeCoercionTest::testNumberCoercedToStringForDecimal()`, using a new `price` decimal input on `CoercionTestTool`. It covers `19.99`, `5`, `0.0000001` and an array that stays invalid. This continues the coercion work in [#3582973](https://www.drupal.org/node/3582973), which handled other input types, and relates to [#3582972](https://www.drupal.org/node/3582972), which emits `type: string` plus a pattern for decimals.
