## Summary

Tools can now know who is calling them (an AI agent, an MCP server, or plain code), and other modules can change a tool's inputs, outputs and published schemas depending on that caller. A module can accept an email address where a tool expects a user entity, or return a short token where the tool produced a full entity. Calls that don't set an invoker behave as before. The tool module ships only the mechanism. Connector modules supply the actual transformations.

## Impact

Affects module maintainers.

- **API change:** `ToolInterface` gained four methods, and `ToolBase::__construct()` takes a new `EventDispatcherInterface $eventDispatcher` argument. `ContextDefinitionNormalizer` now requires the event dispatcher in its constructor.
- **New API:** New `setInvoker()`, `getInvoker()`, `hasInvoker()` and `getFormattedResult()` on `ToolInterface`; optional `$invoker` argument on `ToolManager::createInstance()`; four new events in `Drupal\tool\Event`; new `tool.definition_serializer` service.

## Technical details

The invoker is a string stored on `ToolBase`. You can pass it as the third argument of `ToolManager::createInstance($plugin_id, $configuration, $invoker)` or call `$tool->setInvoker()` afterwards. Four events carry it.

- `ToolInputTransformEvent` is dispatched from `ToolBase::setInputValue()` before the value is stored. Subscribers call `setValue()`.
- `ToolOutputTransformEvent` is dispatched once per output value from the new `ToolBase::getFormattedResult()`. Subscribers can call `setValue()` and `addMessage()`.
- `ToolInputDefinitionNormalizeEvent` and `ToolOutputDefinitionNormalizeEvent` are dispatched by `ContextDefinitionNormalizer` for each definition node while the schema is built. A subscriber can swap in a different `ContextDefinitionInterface`, for example `entity:user` replaced by a string definition. The normalizer only dispatches them when the context contains `tool_invoker`, `tool_id`, `tool_definition_name` and `tool_direction`, so no events fire without an invoker. Child properties of a map definition get their own `tool_definition_name`.

The new `ToolDefinitionSerializer` service (`tool.definition_serializer`) builds that context bag. Its `normalizeInputDefinitions()` and `normalizeOutputDefinitions()` methods take a tool and return normalized definitions. It throws a `LogicException` if the serialization module is not installed.

`getFormattedResult()` returns a `FormattedExecutableResult`. It wraps the original `ExecutableResult`, the transformed `getContextValues()`, and `getHints()`, which are the messages subscribers added. `getResult()` still returns the raw, untransformed result.

A second commit added `RecursiveToolValueTransformSubscriber`, registered at priority -100 on the two value transform events. It walks nested values using the tool's definitions: `multiple` values, `ListContextDefinition` items, and `MapContextDefinition` properties. It dispatches a separate transform event for each child, named by the property name (or the parent name for list items). Subscribers therefore only need to handle scalar leaf values. Messages added on child output events are merged into the parent event's messages.

## Upgrade

Code that instantiates `ToolBase` subclasses directly, or overrides `create()` and calls the constructor, must pass the event dispatcher as the fifth argument:

```php
$container->get('current_user'),
$container->get('event_dispatcher'),
```

Classes that implement `ToolInterface` without extending `ToolBase` must add `setInvoker()`, `getInvoker()`, `hasInvoker()` and `getFormattedResult()`. A custom subclass or replacement of `ContextDefinitionNormalizer` must accept the `EventDispatcherInterface` constructor argument.

Invoker-aware subscribers look like this (the third argument to `createInstance()` is optional):

```php
$tool = $toolManager->createInstance('tool:my_tool', [], $invoker_id);
$formatted = $tool->getFormattedResult();
```
