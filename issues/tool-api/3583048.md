# #3583048: Constraints declared on a ListInputDefinition are never validated

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Status:** Fixed
- **Discussion:** [#3583048](https://git.drupalcode.org/project/tool/-/work_items/3583048) · 1 contributor · 6 comments

## Summary

In the Tool module, constraints declared directly on a `ListInputDefinition` (such as a minimum or maximum item count via `Count`) were silently ignored during validation. Only constraints on the list's item definition were checked, so a list required to have at least two elements would happily accept one, or even zero. This was a regression introduced by an earlier refactor ([#3583004](https://www.drupal.org/node/3583004)) that moved the call validating a value's own constraints into an `else` branch meant for maps, which accidentally excluded lists from ever reaching it. The fix restores enforcement of list-level constraints so validation matches what the module's generated JSON Schema already advertised (`minItems`, `maxItems`, etc.).

## Impact

No upgrade or configuration changes required.

## Technical details

The regression lived in `TypedInputsTrait::validateInputValue()`: the list branch iterated items and validated each one, but never validated the list value itself against its own declared constraints, because the fall-through to typed-data validation had been moved into the map-only `else` branch.

Simply restoring the fall-through was rejected because it would also run typed-data's implicit `NotNull` default constraint, which treats an empty list as "missing" and rejects it with "This value should not be null", a false positive not implied by the advertised schema (see [#3583040](https://www.drupal.org/node/3583040)). Instead, the fix adds a new `validateListConstraints()` method that reads only the constraints the author explicitly declared via `getConstraints()`, builds them through the validation constraint manager, and validates the list's typed-data representation against just that constraint set, bypassing the implicit typed-data defaults entirely. It also calls the existing `resetTypedDataPrototypes()` helper before building the list, to avoid an unrelated prototype-poisoning issue with lists of `any`-typed items ([#3616328](https://www.drupal.org/node/3616328)). Item-level violations continue to be collected separately via `addItemViolations()`, so failures are not double-reported. Output validation (`validateOutputs()`) was already unaffected since it uses full typed-data validation directly.
