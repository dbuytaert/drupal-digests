# #3583077: Invokers must check the declared permission before processing caller input

- **Project:** Drupal AI
- **Type:** Major task
- **Status:** Fixed
- **Discussion:** [#3583077](https://git.drupalcode.org/project/tool/-/work_items/3583077) · 1 contributor · 2 comments

## Summary

The Tool module's built-in ways of running a tool (the `tool:run` Drush command, the Explorer's execute form, and the AI connector used by `tool_ai_connector`) previously processed the caller's input, resolving entity handles, running coercions and refiners, before checking whether the caller was even allowed to run the tool. For a tool that declares a `permission` (added in [#3583064](https://www.drupal.org/node/3583064)), that meant an unauthorized caller's attacker-controlled values were still touched before being denied. These invokers now check the declared permission first and deny immediately, before touching any input, falling back to the existing `access()` check afterward as before.

## Impact

Affects site owners.

- **Security:** `tool:run`, the Explorer's execute form, and the AI connector now call `ToolManager::checkPermission()` to deny a caller lacking the tool's declared `permission` before any of the caller's input is parsed, transformed, or validated, instead of only after resolving handles and running refiners on it.

## Technical details

Each in-tree invoker now calls the static `ToolManager::checkPermission($definition, $account)` before setting any caller-supplied value. `ToolRunCommand::executeTool()` checks it right after fetching the plugin definition, before `createInstance()` or `setInputValue()` runs; `ExecuteToolPluginForm::buildConfigurationForm()` checks it before building any widgets from refined definitions, and `submitConfigurationForm()` checks it again before extracting submitted values; `tool_ai_connector`'s `ToolPluginBase::execute()` checks it before forwarding any LLM-provided context value. All three still call `access()` afterward as the real execution gate, since `checkPermission()` is definition-only and cheap, while `access()` also runs the tool's own values-dependent `checkAccess()`.

Denial reporting was consolidated so a caller cannot tell which stage denied: `ToolRunCommand` gained a private `accessDeniedMessage()` helper and `ToolPluginBase` gained `recordAccessDenial()`, both now shared between the permission pre-check and the `access()` check.

The invoker contract is now documented in `docs/developers/index.md` under "Invoking a tool": check the declared permission, set inputs, validate, call `access()`, then `execute()`. It also specifies what each stage may reveal: nothing before the permission check passes (no transform events, no violation text, no schema echo), and only shape feedback (schema-based violations, correctable-failure schema echo) after it, since the schema is already advertised at that gate. `docs/developers/creating-a-tool.md` now explains that a value-independent access rule belongs in `permission`, not `checkAccess()`, precisely because only the former denies before input processing. Kernel tests (`DeclaredPermissionDenialTest`, additions to `ToolRunCommandTest` and `ExecuteToolPluginFormTest`) assert the denial happens before any input transform event fires.</technical>
<parameter name="upgrade">Custom invokers (the MCP bridge, other external callers) should follow the documented ordering to get the same early-denial behavior:

```php
$definition = $tool_manager->getDefinition($tool_id);
$permission_access = ToolManager::checkPermission($definition, $account);
if (!$permission_access->isAllowed()) {
  // Report the denial the same way an access() denial is reported.
  return;
}

// Now safe to process caller input:
$tool = $tool_manager->createInstance($tool_id, [], $invoker);
$tool->setInputValue($name, $value);
// ... validate, then:
$access = $tool->access(NULL, TRUE);
```

Keep a value-independent access rule in a tool's `permission` rather than its `checkAccess()` override, since only `permission` is checked before input processing.
