## Summary

When a tool is run from its execute form, a field left empty now means "not set". The tool's configured value applies, and if there is none, the input's default applies. Before this fix, an empty field was passed as an explicit empty input and skipped the configured value. The fix ships with kernel tests that check the values the tool actually receives, not the raw form values.

## Impact

No upgrade or configuration changes required.

## Technical details

In `ExecuteToolPluginForm`, the shared extraction step for validation and submission now reads the typed value after `extractFormValues()`. It calls `$this->plugin->setInputValue()` only when that value is not `NULL`. An explicit `NULL` input would resolve straight to the default and bypass configuration. An input set before the form keeps its value.

The configure form is unaffected. Clearing a stored field there still resets it to the default, which a test covers. An unchecked checkbox still reaches the tool as `FALSE`, so a configured `TRUE` does not win.

The commit adds a `form_values_tool` test plugin in `tool_test` and a kernel test, `ToolPluginFormValuesTest`. The test covers numeric strings becoming `int` or `float`, checkbox handling, empty execute fields falling back to configuration, and the configure form clearing a stored value. The type casting described in the issue title comes from the existing typed data extraction. This diff only changes the NULL handling.
