# #3583043: Output definitions cannot say "always present, may be null"

- **Project:** Drupal AI
- **Type:** Normal bug report
- **Version:** 1.0.x-dev
- **Status:** Fixed
- **Discussion:** [#3583043](https://git.drupalcode.org/project/tool/-/work_items/3583043) · 1 contributor · 13 comments

## Summary

Output definitions can now say a value is always sent but may be null, such as a photo's EXIF date or a timestamp that has not happened yet. Before, one `required` flag meant both "key must be present" and "never null", so such outputs were published as optional and possibly missing. This also changes existing behavior: an optional output that holds NULL is now left out of the result, and its published schema no longer advertises `null`. The change landed before rc1 because it alters the published schema of every optional output.

## Impact

Affects module maintainers.

- **API change:** Custom classes implementing `OutputDefinitionInterface` must implement `isNullable()` and `setNullable()`. Optional outputs set to NULL are now omitted from the result, and their schema no longer includes `null`.
- **New API:** `nullable` constructor parameter and `isNullable()` / `setNullable()` on output definitions (`OutputDefinitionInterface`, `NullableOutputTrait`), default `FALSE`.

## Technical details

`required` now means key presence only. A new `nullable` flag, default `FALSE`, means null is a value the output carries. This is provided by `NullableOutputTrait` (`isNullable()` / `setNullable()`), added to `OutputDefinitionInterface` and to the `OutputDefinition`, `ListOutputDefinition`, `MapOutputDefinition` and `EntityOutputDefinition` constructors as a trailing `bool $nullable = FALSE` argument.

The four combinations behave as follows:
- `required: TRUE, nullable: FALSE`: the key is always present and never null.
- `required: TRUE, nullable: TRUE`: the key is always present, may be null, and is listed in the parent's `required` with `[T, "null"]` as its type.
- `required: FALSE, nullable: FALSE`: an output holding NULL is left out of the result.
- `required: FALSE, nullable: TRUE`: the output may be missing or null, and its type is `[T, "null"]`.

`InputOutputDefinitionNormalizer` reads `isNullable()` for outputs and strips the null branch (`removeNullBranch()`) from non-nullable outputs. Inputs keep the old rule, where an optional input is nullable. `EffectiveDataDefinition` does not mark a nullable output required, so core's `NotNull` is not added.

Runtime handling is in several places. `setOutputValue()` and `ToolBase` drop an optional non-nullable output set to NULL. `validateOutputs()` uses `array_key_exists()` to tell "set to NULL" from "never set", so a required nullable output set to NULL passes. The same rule applies inside maps through `RecursiveToolValueTransformSubscriber`: a null in an optional, non-nullable property is removed. A null list item is not removed, because that would shift the positions after it. It fails validation unless the item definition is nullable. `ListOutputDefinition::createFrom()` carries the flag on the list itself and sets it `FALSE` on the item.

`TypedMethodDescriber` now maps nullable method-tool return types and members to `required` plus `nullable`. `omit_when_null` maps to optional and non-nullable. `memberIsRequired()` and its `@todo` were replaced by `memberAllowsNull()`. Input-side `nullable` is left to a follow-up issue.

## Upgrade

For an output that is always sent and may hold null, declare both flags:

```php
new OutputDefinition('timestamp', 'Date', 'When the photo was taken.', required: TRUE, nullable: TRUE);
```

Optional outputs that relied on sending an explicit null now need `nullable: TRUE`. Without it, a NULL value is dropped from the result and the schema no longer lists `null`.
