## Summary

The merge request adds a tool that runs a View and returns its rendered output, so tool consumers such as AI agents can call a View by machine name, display ID and arguments. It ships as a new `Tool - Views` module. Access follows the chosen View display's own access rules. The MR was still a draft proposal when summarized, and a comment suggested moving the work to the Tool Belt project.

## Impact

Affects module maintainers.

- **New API:** New `tool_views` module with a `views_execute` Tool plugin (`Drupal\tool_views\Plugin\tool\Tool\ViewsExecute`) taking `view_name`, `display_id` and `arguments`.

## Technical details

The MR adds a `tool_views` module (it depends on `tool:tool`) containing the `ViewsExecute` plugin, declared with `#[Tool(id: 'views_execute', operation: ToolOperation::Trigger)]`. Inputs are `view_name` (string), `display_id` (string, default `default`) and `arguments` (map, optional). `doExecute()` loads the View with `Views::getView()` and calls `setDisplay()`. It fails with an `ExecutableResult::failure()` if either the View or the display is missing. Otherwise it calls `setArguments()`, `execute()` and `render()`. A render array result is turned into a string with the `renderer` service's `renderRoot()`. An empty result becomes the placeholder `[No output returned by view]`. The output is a `results` map with a single `output` string.

`checkAccess()` returns forbidden when the View or display does not exist. Otherwise it delegates to `$view->display_handler->access($account)` and wraps a non-`AccessResultInterface` result as allowed or forbidden. The `.info.yml` description mentions tools for creating, modifying and removing views, but only execution is implemented in this diff.
